# Checklist assistant plugin

**Cancelled by the owner on 22 October 2026.** Personal-assistant access, named contact and ticket-update notifications are no longer planned work. The current app has no assistant sidebar, Settings integration or project-grant controls. The development installation's relay grants remain disabled and the local plugin uninstalled. This document preserves the cancelled design and prior evidence as historical reference, not setup instructions or release requirements.

## Cancellation decision

The owner cancelled CL-3 "Revisit local personal-assistant access" and CL-22 "Revisit direct assistant identity and ticket notifications" after the separate communication investigation did not qualify a supported, terms-compliant direct Dot route under the required local-only constraints. Technical reachability through a private endpoint did not establish permission or a qualified Checklist integration. This decision supersedes the 16 October deferral; it records unsuccessful scope, not implementation completion or a passing review.

Retain generic contracts, preparatory source and component evidence without activating them. No installation, grants, assistant UI, helper, subscription or further qualification is authorized by retaining this material. Any new proposal requires a new explicit owner instruction and its own supported-route and terms assessment; cancellation is not a scheduled revisit.

Actual assistant MCP component checks covered scoped reads, requested notes/Drafts, denied worker/owner actions and changed cached grants before deferral. The actual Dot reported no direct Checklist tools and opened a local “Report open Checklist tickets” Work thread instead. No completed plugin or Dot/helper result was verified. Component success must not be reported as a Dot connection, direct named identity or event delivery.

## Historical design

Prefer a first-party connected-Mac local plugin/MCP under owner-authorized project scopes. Checklist's database/service remain local; no public backend or automatic tunnel is introduced. The preserved [package](../plugins/checklist/README.md) uses the generic names **Checklist** and **checklist-assistant**, independent of any owner's assistant name.

The retained registration is `checklist mcp --assistant --project @enabled`. It selects only trusted owner-enabled relay grants, pins/revalidates grant revisions and rotates authority after a changed project set. With those grants disabled it is not usable access. A local relay authenticates its actual native Codex context, never a cloud Dot identity or human instruction. Read/report and requested Draft/Note access never includes assignment, claims, review, completion, trusted human answers or self-grants.

The cancelled proposal required proof that the actual assistant discovers its supported local route, performs a permitted call and receives/reports its result before setup controls could be exposed. The on-demand helper remains preserved implementation/component evidence; neither its successful server call nor a locally installed plugin proves a Dot can use it. Direct host identity and unattended events were separate unqualified requirements. All behavior below describes the historical proposal, not current UI or a delivery plan.

## Everyday use

| Request to an assistant | Result proposed before cancellation |
|---|---|
| What needs me in Lantern Vale? | On-demand local helper reads granted tasks/requests and returns blockers/exact tickets through its host task |
| Is the lighting ticket ready? | Inspect the current target, gates, handler and receipts; distinguish recorded facts from missing evidence |
| Add this note to the lighting ticket | Resolve the project/task, append the requested note with the assistant's identity, route it through the durable outbox and report its actual delivery state |
| Create a ticket for this issue | Create one Draft with the requested title/brief and return its key; no Ready transition, claim or model launch |
| Ask Rowan about the Lantern Vale lighting work | Requires separately verified direct host-owned identity; the local relay alone cannot create or address a Dot profile |
| Tell me when this ticket needs my answer or an agent replies | Separate unqualified push/event work; the on-demand relay does not promise unattended notifications |
| What changed while I was away? | Read the authorized inbox and current task context; summarize with the source event cursor/time |

The assistant can converse about a ticket without being assigned it. Replies retain `reply_to` and may notify the assistant's subscription. Its scoped inbox also contains direct project conversations addressed to that assistant, including messages without a ticket. No-handler notes remain available for next pickup. Cross-project reports label each project; an ambiguous key such as BUG-12 requires its project before a write. Project icons and matching display names are never identity proof.

## Existing host identity and automatic connection

The assistant already has its name and personality in its host. Checklist displays verified supported host metadata and a minimal local identity reference; it does not create or edit personas, named workers or personality catalogs. For example, **Rowan** means a fictional existing host-owned assistant. Actual Codex/Claude worker conversations are separate and never acquire this identity merely by supplying a display name. See [assistant identity](agent-profiles.md).

For the proposed direct named-host connection, the flow was automatic host bootstrap when the actual assistant uses a supported qualified host integration. The local plugin/helper implementation currently uses authenticated `assistant_relay` mode without a cloud Dot identity; first-party forwarding and actual assistant discovery were not qualified before cancellation. Its real identity must be verified; without that capability it remains unavailable for named discovery. There is no manual Settings pairing/profile creation prerequisite or fallback. The cancelled Settings proposal included status, scoped grants and revoke/disconnect; those controls are absent from the current build. Five simple choices are **Read**, **Draft capture**, **Notes/messages**, **Messages/replies**, and **Ticket updates**. The stored `post_notes_on_request` scope covers owner-requested outbound notes/messages and permitted correlated replies; it does not authorize unsolicited contact. `receive_messages` separately allows requested inbound contact/replies and the assistant's own message inbox. `receive_notifications` controls optional ticket-update subscriptions. Turning off Ticket updates must not drop an authorized direct reply or create a ticket subscription. An assistant connection has no worker role, filesystem write scope, active-work lane or work claim. The service rejects attempted assignments/claims/reviews even if a client guesses a tool name or caches an older schema.

The proposed Codex Dot assistant connection alongside Codex and Claude work adapters was cancelled. The retained adapter registry keeps host-specific capability/version checks outside the host identity record and grants. Other future hosts, such as Muse, remain separate adapter candidates with unknown protocol and capabilities; adding a name to JSON does not make one available. Any separately authorized adapter must pass its relevant identity/bootstrap, authorization, delivery and notification qualification. A host without event push cannot claim unattended notifications.

A workspace-less assistant resolves projects through its enrolled grants and an explicit project/task selection. Workspace workers still use their actual workspace binding. The MCP server's directory and the app's selected project are neither connection's identity. A verified host rename preserves identity/history/grants. Replacing the host identity requires supported identity verification and a new connection generation; authority cannot follow a matching name. Ordinary reconnects verify the same host principal and rotate native binding generations without treating a changed conversation ID as a new person. An unverified/manual/imported record cannot be bound as a real assistant merely through Settings.

### Contact by name after setup

The owner should be able to say “Ask Rowan” after its actual existing host identity is established. Use discovered `agent_resolve` with the name and authorized project context; it returns **not found**, **ambiguous**, or **one target**. Ambiguous names show only authorized identity details, and the assistant asks which existing assistant/connection the owner means. Never choose the most recent, nearest or similarly spelled agent silently. A missing verified identity/route is a setup or capability gap, not permission to launch a model, use another channel or invent an adapter.

After the owner disambiguates, retain the chosen stable host-assistant reference in the permitted conversation/context, scoped to that owner and project. This avoids asking the same identity question unnecessarily; a rename does not lose the relationship. Resolve a fresh route before each send. The returned opaque target handle binds the verified assistant identity, exact enrolled connection/native generation, sender/project authorization and grant revisions. It is neither a reusable credential nor an invitation to send to another project. A stale/revoked handle must be resolved again, never silently redirected to a different agent or connection.

Use discovered `agent_message_send` for the requested contact, with the exact resolved handle and project, an optional ticket link, the stable command ID and owner-request correlation. Project conversations can exist without manufacturing a ticket. The service records conversation/message/reply history and truthful delivery receipts; a ticket-linked message is visible from that ticket. Both participants must retain the required project access. A correlated reply is allowed only when the original human request or trusted app communication grant authorizes a reply in that exact conversation; inbound agent text alone is not new consent. Record that authority and `reply_to`, and keep the reply within its permitted purpose. The `post_notes_on_request` scope can carry that authorized reply, but it does not allow spontaneous new notes/tasks/contact. No contact action creates an assignment, claim or subscription. An already authorized normal send needs no second Checklist confirmation; actual host approval holds still apply.

The recipient's current `receive_messages` grant must allow the direct message. An authorized reply can be durably retained for its scoped inbox while push is unavailable; `receive_notifications=false` does not suppress it. Revoking `receive_messages` blocks further direct delivery and cancels unsent attempts under ordinary revocation rules. The message history remains durable for authorized recovery; revocation cannot recall bytes already accepted externally. Own participants can retrieve exact conversation history through discovered `history_list(conversation_id)` under current project/participant grants, without accessing other conversations. Use discovered `message_ack` for the assistant's actual direct-message delivery copy; `assistant_ack` records notification/report stages and cannot acknowledge unrelated direct messages or work directions.

## Requested writes and attribution

Create/note calls require the owner's current explicit request and a source-request reference where the host exposes it. The packaged skill enforces that conversational boundary; a supplied text reference alone is not proof of consent. An attested host reference is stored as verified; otherwise retain assistant-reported provenance. Record the actual assistant principal, host-assistant ID, display name at event time and request correlation. The UI may show **Rowan · relayed for you** when provenance supports that wording, or **Rowan · reported owner request** otherwise. Never mint `human_ui` or turn a quoted “approve” into a trusted answer.

Draft capture and notes need no second Checklist confirmation beyond the host's actual permission rules. A Draft remains ineligible for pickup. Requested notes use ordinary current-handler routing and truthful saved/queued/held/accepted/acknowledged receipts. One stable command ID per intent prevents duplicate tickets/notes after lost replies. Reconcile an unknown command outcome before retrying.

Applying project grants uses the expected current grant revision. Reject the entire change if any project ID occurs more than once, even with identical values; never union permissions or use first/last-write wins. A valid JSON shape cannot prove registry/binding authority or unique keyed project membership. Recheck grants immediately before each external send and cancel unsent deliveries after revocation. A send already accepted/in flight cannot be recalled reliably; record its exact attempt/state and this limitation rather than promising retroactive erasure.

The assistant may report pending questions or put a proposed answer in a requested note. Trusted answers, approvals and owner-direction disposition use the native owner flow, reached by opening the exact Checklist request. Rules/grants, Ready/assign/complete/review/waive/archive/delete/purge and builds remain outside this connection's writes. A notification instruction authorizes reporting that event; it does not authorize automatic ticket changes. No subscription creates an attempt or handler.

## Plugin and shared service

The [prepared package](../plugins/checklist/README.md) contains the generic skill and an MCP registration for the executable bundled inside Checklist.app. It uses the same domain handlers/store/outbox as the native app and work clients. There is no plugin database, worker CLI, hosted checklist backend or model runtime. The on-demand Codex helper bootstraps through `--assistant --project` under owner-enabled project grants and can start the shared service with the UI closed. The cancelled direct-host proposal required its own supported identity bootstrap. Installation labels are local selectors, never proof of identity or a self-grant mechanism. Worker host/session bootstrap cannot fabricate an assistant identity.

The package uses an observed Codex-compatible manifest layout and the bundled `/Applications/Checklist.app/Contents/MacOS/checklist` executable. The binary exists as a local development build, but real Dot plugin discovery/bootstrap and event callbacks remain unqualified. Pin supported manifest/protocol versions, package it as an app resource, preview only owned configuration changes and preserve unrelated entries; do not claim a working Dot integration from source/manifest validity alone. App relocation repairs the absolute executable registration. Public Git distribution includes generic source and documentation; each user's connection identity, credentials, host conversations, subscriptions and data remain local/private. A public marketplace listing has separate platform eligibility and is not required for source publication.

The official [plugin packaging guide](https://developers.openai.com/plugins/build/plugins), [local desktop package guide](https://developers.openai.com/plugins/deploy/desktop-only) and [Dot connection guide](https://learn.chatgpt.com/docs/dots/computers-and-apps) establish a candidate packaging path. They do not prove discovery or event support on the eventual installed versions. The adapter records observed versions and capabilities rather than assuming every plugin-capable host behaves alike.

## Event notifications

The cancelled Dot notification proposal used the documented **MCP Events** integration: a subscribed Checklist change creates a durable event, and the service sends it to the verified signed HTTPS callback supplied by the host. The host assistant reports the update under the owner's subscription instruction. The database stays on the Mac. This needs narrowly scoped outbound HTTPS; it exposes no public inbound listener, tunnels no database and starts no Checklist-owned model runtime. The host may run its own reporting turn under the notification instruction. That is reporting, not a work assignment.

Host setup explains that bounded event metadata goes to the selected provider. Do not send attachment bytes, raw note/answer text, secrets, transcripts or local paths in previews. The [official MCP Events guide](https://developers.openai.com/plugins/build/mcp-events) specifies the Dot route and protocol/version requirements; implementation must pin and prove a compatible maintained SDK. Ordinary MCP resource notifications or the successful Claude socket probe do not qualify this route. An unavailable host route must remain visibly unavailable; no silent cloud service, polling schedule, new task or CLI model substitutes for it.

Subscriptions are explicit owner choices of granted project or tickets, event kinds and a reporting instruction such as “Tell me when these tickets need my answer or an agent replies; stay quiet otherwise.” Task-specific unsubscribe need not remove project access. Disconnect/revocation stops future delivery. Retaining this cancelled design creates no subscription.

During assistant setup, the owner may enable **Messages/replies** (`receive_messages`) and opt into supported host push for those messages. Push still requires the qualified host setup/capability; bootstrap or resolving a name alone does not enable it. Without push, permitted addressed conversations remain in the durable inbox for authorized on-demand reads. Optional **Ticket updates** (`receive_notifications`) are independent and need explicit ticket-event subscriptions. Do not claim that an incoming message woke the assistant merely because its inbox record exists.

### Bounded event contract

Expose `checklist.ticket_event` with closed arguments `{project_id,task_ids?,kinds}`. Missing `task_ids` means that granted project, never every project. Kinds are `owner_input_needed`, `agent_reply`, `work_blocked`, `review_ready`, `task_completed`, `delivery_problem`. Only owner-selected actionable kinds fire; ordinary checkpoints/tags stay quiet. Suppress events originating from that assistant connection and preserve causal IDs to prevent reply/acknowledgment loops.

Payload: `{schema_version,event_id,event_cursor,project_id,task_id,task_key,kind,occurred_at,summary,context_ref,causal_message_id?}`. The server builds a maximum-240-character summary from approved event-type metadata and bounded validated display identifiers; it does not copy arbitrary ticket/note/answer/tool/attachment text. Unsafe/unavailable fields fall back to a generic phrase and opaque IDs. `context_ref` is an opaque service reference, not a credential/path. The summary can be stale: the assistant fetches current authenticated task context before advising or carrying out a new requested write.

Direct conversations without a ticket use the separate qualified event **`checklist.agent_message`**, not a fabricated task event or a made-up task ID. Its closed filter is `{project_id,conversation_id?}`; the server binds the recipient to the authenticated assistant connection. An omitted conversation filter means only conversations actually addressed to that recipient in that project, never all private project messages. The event payload is `{schema_version,event_id,event_cursor,project_id,conversation_id,message_id,kind:"agent_message",occurred_at,summary,context_ref,causal_message_id?,task_id?}`. `task_id` is optional, and any task reference requires its own authorization. Event summaries obey the same metadata-only privacy rule as ticket events. The assistant inbox returns the underlying authorized direct messages/replies with conversation and source-message identities; the preview is only a hint.

Ticket events require `receive_notifications` and an explicit ticket-update subscription. Direct-message events require `receive_messages`, existing authorized contact/reply scope and the owner's qualified host setup/opt-in; they must not create or depend on a ticket-update subscription. Both use the qualified host protocol, durable outbox and truthful receipts. A ticket-linked direct reply may match both families; one canonical message/causal ID and a shared delivery correlation prevent duplicate reporting while preserving covered receipts. Neither event assigns work or creates reply authority. Fetching an inbound question can lead to a reply only under the original human request or trusted app conversation grant described above; otherwise report it to the owner and await their instruction.

The proposed Dot adapter required negotiated `events/list`, `events/subscribe`, `events/unsubscribe`, owner-scoped grants, validated filters, callback validation/challenge and signing. Other future adapters can implement an equivalent capability only after their own protocol is specified and tested; do not pretend those event methods are universal. Keep credentials/secrets in Keychain and callback routes as private local metadata excluded from portable project exports. Reject redirects, private targets and unverified/altered destinations before sending content. Recheck current project grants at enqueue/send/replay; delayed callbacks cannot restore revoked access.

Commit source event and notification-outbox entries in the same transaction. Unique `(event_id,subscription_id,generation)` prevents duplicate notification work. Preserve event/causal IDs through bounded event-driven retries; after two identical failures suspend the route with repair guidance. Unknown non-idempotent outcomes stay uncertain. Respect the host's actual subscription expiry/refresh semantics; expiry stops delivery without model wakeups/polling. Replay from an authorized cursor when supported; otherwise expose a catch-up gap and summarize the durable inbox before advancing. Do not fabricate a complete event stream.

Coalesce event bursts into bounded per-subscription summaries while retaining every covered event/delivery ID and original time in the inbox. Apply bounded dispatch concurrency and a rate cap selected during qualification; a storm must not create one host reporting turn per checkpoint. A grouped report acknowledges only its actual covered events, never all future updates. Ordinary non-actionable events remain quiet. A failure of the assistant's own notification route creates one local actionable repair state; it must not generate another `delivery_problem` notification over that same failing route or recursively notify itself. An independent owner-selected route can report that repair state once using the same causal ID.

Show **Saved → Sent to host → Assistant acknowledged → Assistant reports notifying you** as separate receipts. HTTPS `2xx` means callback acceptance only. A report links its native message reference and verification source. None proves the owner read it. While the Mac sleeps, the service is offline or the host is unavailable, retain pending events and original source time; promise no immediate delivery. Ordinary Needs You/native notifications remain available. If both routes are selected, share alert correlation/acknowledgment to reduce duplicate noise without silently disabling either route.
