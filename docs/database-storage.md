# Database and local storage

Group display keys are additive JSON fields on existing `group` records. Projects retain `next_triage_number` and `next_epic_number`, separate from ticket `next_number`. Creation allocates the key and advances its counter in the same transaction. Under the existing startup object gate, after protocol bootstrap and before admission, one SQL transaction fills missing keys in `created_at`, then byte-exact ID order for each project/kind. It preserves assigned keys, starts above both the retained counter and every assigned numeric suffix, and advances changed record revisions. A repeated start changes no group/counter records. This runs again if a compatible older writer created an unnumbered group.

This enrichment does not change the SQL schema, `user_version=2`, storage identity or checksummed protocol ledger. It is an ordinary additive startup transaction, separate from the protected schema-1-to-2 upgrade/rehearsal path: no original field or managed file is replaced and existing protocol-2 binaries accept the extra JSON. A failed transaction rolls back every label and counter together. The protected backup requirement for a protocol upgrade remains unchanged. Qualify complete startup and older-binary reads on an owned existing-store copy; a backup still requires every retained managed authority and cannot be qualified from a copy missing those files.

The current storage protocol opens an existing SQLite file without CREATE, verifies its exact container, ordered migration checksums and external initialization identity, and refuses unknown versions or malformed originals. Protocol 2 uses a checked, length-aware raw UTF-8 collation with SQLite BINARY semantics. Older released code lacks that collation and must refuse startup. This persistent fence supplements the native service's lifetime `service.lock`; it does not stop filesystem work already running in an old process. A pre-upgrade path first obtains that same exclusive service lease, so the supported prior service must have exited through all of its SQL and filesystem continuations. New router operations acquire admission and the same root object gate before entering the writer; drain waiting runs outside queues needed by admitted work.

For an installer-driven upgrade (CL-305), the staged `ChecklistService --prepare-upgrade` first captures and verifies a protected SQLite-and-managed-object generation and rehearses the exact migration while the old service continues serving. It uses the existing online snapshot retention barrier; it does not open a router, acquire the service lifetime lease, change the source schema, enroll a session or dispatch work. Preparation publishes a durable, instance-bound `preupgrade-ready.json` receipt only after verification and rehearsal. This receipt binds the logical store, incarnation, source fingerprint, target migration checksum, exact staged service executable hash, backup manifest hash and the device/inode/type/size/mtime/ctime identities of every required source and backup file (including captured links). Source file bytes are checked against the snapshot during preparation; the final identity check reads no workspace or original-store fallback paths.

After the old service exits and the new service holds its lifetime lease and object gate, startup compares the full source database fingerprint and all bound file identities. An unchanged preparation skips durable copying and rehearsal and runs the fingerprint-checked upgrade transaction. Schema 3→4 does not compute an unused managed-path relocation plan. A write, changed/missing file, incompatible target, invalid receipt or absent preparation requires a fresh protected snapshot and rehearsal of the stopped store; it never silently uses the earlier backup. The backup pointer committed by the migration therefore represents the store at the swap. A current-schema restart requires no upgrade preparation. Unenrolled installer preparation is a local executable operation, not a new MCP method or agent grant.

Only offline startup publishes the advisory `upgrade-progress.json` marker, with its live PID, stage, estimate and fallback reason. CLI/app clients show **upgrading** for preparation validation, protected snapshot, rehearsal and final migration; they preserve ambiguous command IDs and never turn a transport timeout into a rejected write. A normal completion or handled failure removes the marker; clients reject a dead/stale publisher. Estimates are advisory (90 seconds for reusable preparation, about 15 minutes for fallback), not a deadline or a measured result. Install/promote prints the estimate before stopping the old service and measures through the first healthy answer. The qualification gate must measure launch-to-first-answer separately.

Qualification must use the exact staged code on an owned consistent copy of the existing store, including retained record families and required managed files. Exercise the complete online preparation, durable protected publication and verification, exact target rehearsal, stopped-store revalidation and first answered call; verify the protected generation matches the source at the swap. Exercise a post-preparation write and changed/missing source or backup object, crash before/after migration commit, invalid preparation and the visible upgrading/fallback estimates. Record load, preparation time, unavailable window, launch-to-answer and the final backup manifest/fingerprint; a SQL-only rehearsal or synthetic fixture does not replace this gate.

A known migration is rehearsed on a separate copy and preceded by a self-contained SQLite-and-managed-object generation. The final transaction compares the exact source fingerprint, preserves record rowids/event sequence and commits the schema identity, checksummed ledger and protected-generation pointer together. An interrupted external identity publication is repaired forward from the committed database. No startup path restores an older database over later writes, creates an empty replacement for a missing initialized database, or attempts an unknown upgrade. The owner-only disposable-root restore and its new-incarnation authority quarantine are described below.

After the semantic command receipt commits, cleanup is best effort. A cleanup failure cannot turn a committed registration or mutation into an apparent failure. The response retains its result and current human-answer observations, with a content-free `_checklist.storage_maintenance` warning when applicable. Two repeated failures pause cleanup for that router lifetime; service restart supplies a fresh recovery opportunity. Source-process restart fences commit before maintenance or normal admission. Archive cleanup uses its durable jobs and exact current reference/hold validation under the root permit; the legacy direct-unlink engine is removed.

Managed imports reserve the authenticated principal plus original command UUID before filesystem work. A matching retry can use retained, verified finalized bytes even after the original chooser/workspace source disappears. Finalization flushes immutable bytes and parent entries before attachment availability, event and command result commit together. A failed original read is attributed only to that exact current representation after the failed transaction rolls back. Optional preview failure leaves a verified original usable. Unreferenced or uncertain staging is retained conservatively; no general orphan sweep gains deletion authority from an error. The only removals are the two bounded rules below, each tied to a record of the files' own command.

**Bounded folder access (CL-206).** Managed imports and snapshots acquire selected source/destination roots through one reusable native descriptor helper. Each complete no-follow root walk has a five-second parent deadline covering request transfer and reply; a stalled privacy or sync-provider open kills and retires that helper generation. The service never enters that root `openat`. Serial worker admission waits at most five seconds (initial SIGCHLD registration at most two); capacity admission is immediate and caps active/retired generations at 16. Retired PIDs are reaped without a blocking wait. A fresh helper closes inherited service, SQLite, retention and object-gate descriptors before serving. Anonymous datagrams transfer only the selected path and descriptors; lifetime pipes report either endpoint’s death. A request alarm bounds an interruptible active orphan to at most six seconds; a 60-second total generation lifetime (at most 61 seconds with alarm rounding) bounds forked heap-snapshot retention and covers inherited lifetime-pipe writers in unrelated forked children. Generation expiry reconnects once under the original request deadline. The helper cannot create files or commit metadata. The error names the folder, privacy/sync possibilities and the original-command reconciliation step. After root acquisition, relative `openat`/`fstatat` operations run in process with no-follow checks, regular-file/type/size limits and nonblocking FIFO refusal. There is no child per descendant or file, and repeated root acquisitions reuse the same helper without forking. This uses the selected-folder privacy/sync boundary; it does not hard-cancel later metadata, regular-file reads, writes, fsync or SQLite work. Publication flushes, command ownership and receipt transactions remain required. Backup destination existence checks use the bounded root path instead of a preceding Foundation folder probe. Selected managed source paths are normalized lexically before the helper; preflight does not resolve source symlinks through Foundation. Managed owner-answer selections use folder descriptors for metadata-only identity checks, preserving the rule that a prepared answer does not reread source bytes at commit. The router retains its already-open store root and at most 64 pinned ancestor descriptors for its object gates. Short-lived managed readers can duplicate that same root only after validating every retained ancestor’s no-follow device/inode identity. A weak registry retains no store authority beyond the router’s lifetime and does not reuse external source or backup-destination roots. Backup root acquisition count is independent of file count; the shared snapshot budget still applies to the complete backup.

An opener timeout cannot commit an attachment: the child has no metadata/publication code. The pending parent stays reserved/staged/finalized under its original principal and UUID. Explicit same-intent retry first returns a committed receipt if present, otherwise verifies retained finalized bytes or reads/stages the source under that same attachment ID. Never infer failure from the old client timeout, use a new UUID to “retry,” or remove an uncertain original. Missing-root checks use structured errno from the opener error rather than an errno value altered during unwinding. Unreadable or symlinked managed source files retain the plain `FILE_ACCESS_REQUIRED` classification; a folder timeout retains its folder error. No storage schema or migration changes. Exact staged startup and protected pre-upgrade backup still need the owned-existing-store qualification, including open-process overhead and the complete durable-copy/verification budget.

Stopped-store revalidation (CL-305) uses a versioned single-pass SHA-256 over every table's ordered rowids, column names, SQLite storage types and complete length-delimited bytes. Text is read as bytes, including embedded NULs and distinct Unicode encodings; it is never hex-expanded or normalized. The final migration transaction repeats this exact digest. Managed source and verified backup identities still include device, inode, kind/mode, length, mtime and ctime; changed or missing entries force a fresh full protected snapshot and rehearsal. A bounded no-follow descriptor walk reuses only the current path's ancestors, checking each pinned directory's named identity and change times before release. Paths beyond the cache depth use ordinary no-follow traversal. During online identity capture, source and backup bytes are hashed between metadata observations, including the backup database, and validates the intent’s exact identity fields, so edits since the earlier snapshot verification cannot be blessed by a later identity. Preparation format 2 rejects earlier fingerprints. The protected copy's complete hashes and rehearsal remain online work; stopped validation never trusts a database timestamp alone. The exact staged real-store qualification must cover both unchanged reuse and SQL plus managed-file writes after preparation, then verify the fresh backup matches the pre-swap store.

**Read snapshots (CL-254).** Pure service reads retain one bounded canonical-record cache per router. Each snapshot frame drains its own autorelease pool after restoring the previous thread context. This releases temporary decoded objects and retired generations even when the calling queue inherits a pool spanning many commands. A key includes the exact project/query bytes and the complete caller role, installation, session, workspace, project grants, assistant permission map, execution domain and locale. The cache belongs to one specific read-only connection and its `PRAGMA data_version`, observed inside the pinned read transaction. Every committed SQLite write from another connection invalidates that generation, including ticket, Triage, Epic, status, note, settings, archive, purge, event-only and maintenance changes with no domain event. A request begun after a commit sees the new generation; a request overlapping a commit retains SQLite's consistent earlier snapshot. Writer transactions never use this cache, so uncommitted or rolled-back values cannot enter it. Connection replacement, caller/grant changes and router/store replacement also discard reuse.


**Triage list field selection (CL-254).** Validated `triage_list.fields` selects projection work before constructing optional active-attention, warning, orchestration-connection, membership-history and batch-lifecycle fields. A summary does not read those unrequested record families. Requested fields use the same builders as a full row, and omitted/empty fields retain the full legacy response. Project/caller authorization, rowid order, field validation, mandatory identity fields and canonical-record cache invalidation are unchanged; no projected result is cached. The generated 250-Triage fixture with members, retained intervals/exits, findings and batches measures five reads in the isolated timing group; default parallel cases compare results without timing budgets.

**Window content reuse (CL-254 P9-r1).** Each window keeps the last accepted Tickets page for at most 12 exact queries and workspace/Overview pages for at most 32 exact queries. Project identity, filters, ordering, focused limits and digest timestamps stay part of those queries; one window never borrows another window's pages. The service's opaque `read_version` supplies the caller/grant and pinned data-generation boundary. Navigation installs matching content synchronously, then refreshes it in the background. The Tickets native scroll/list subtree is scoped to the selected project, so a cached switch retires the preceding project’s rows and accessibility tree. Header/filter controls stay mounted; project-local selection, dialogs and expansion overrides reset on a project change. The toolbar project picker uses direct buttons in a popover, starting navigation before dismissal rather than waiting for native menu tracking to dispatch the selection. Tickets and project-switch ScreenTiming probes belong to the prepared ticket content, never the independently drawn project tabs; a loading branch cannot finish those clocks. Every display probe captures the token with its content builder; it cannot observe and consume a later navigation from a retained old frame. The digest's new visit timestamp is initialized before the combined loader, so the later native appearance callback cannot replace it with ten single reads. A new digest scope cannot reuse the preceding digest page. On native leave, one cancellable read prepares the next visit's exact digest timestamp/project; its epoch fences installation into the bounded workspace cache. No preceding digest page is relabeled. Project-settings record pages share that same versioned workspace cache, and the cleanup receipt cache retains its separate project/store/change-epoch scope plus the settings reply's exact data/grant version (or a non-reusable-across-reads generation when that version is absent). Cached settings display never replaces the fresh background read: navigation installs the retained receipts of the restored scope before the first display pass, the section then reads receipts in the background and replaces the rows only when their facts differ, and a failed background read keeps the retained rows of that exact scope. A closing panel, or one whose settings record is not installed, reads no receipts and never takes over the receipt observation (CL-260). App presentation sorting parses each row timestamp once before comparisons and retains at most 1,024 immutable timestamp-to-Date entries with keys no longer than 128 UTF-8 bytes; formatter access is locked. No relative ages, records or authority are retained in this cache.

Every known mutation and live coverage update clears reusable query entries. Affected reusable content is retired before refreshing; Overview retains its valid same-query displayed rows/counts with an explicit refresh-needed generation until each replacement arrives. Reset/unknown coverage, changed query/project/digest and changed data/grant identity still retire visible content. Other affected surfaces retain their existing retirement rules; unrelated visible content remains valid under the existing scoped coverage rules. Learning another data/grant version from a read clears visible pages and retained entries before accepting the new response. During one pending live coverage interval, reads dispatched after that interval's epoch fence may pin different snapshots under concurrent writes. A differing equality token clears reusable entries without retiring those sibling replies or their accepted display. A later coverage interval still retires earlier reads before dispatch, and project/query/selection/store checks still apply. Tokens establish equality, never temporal ordering. An epoch fences earlier in-flight responses, including a selected read learning a commit before live coverage; partial reads trigger a visible-page rebase. Cancellation, window close and service recovery retire reusable entries; close retains the last accepted display. Missing-version responses cannot populate reusable caches, and losing a token or installing a compatibility snapshot clears the namespace. Epoch fences also apply to unversioned replies. A newer list version retires older selected authority and requests fresh selected context; the fresh selected UI read discovering its own version retains its shared recovery. Cached rows are display content and never supply current work/review authority. In-process read/model timings are distinct from installed AX content timing and authenticated IPC cost.

**Committed status display (CL-254 L254c/L254d).** Owner-only schema-2 change coverage may add `store_incarnation` and at most 100 `status_updates`, each `{task:{id,project_id,revision,status_id,status_name,status_category,archived,trashed},surfaces:[...]}`. Optional `triages:[{id,revision,member_count}]` on each update supplies current membership identities only; more than 100 membership links omits that metadata while retaining task statuses. They come from the same read transaction as the coverage; membership uses the ordinary need-surface SQL predicates, not an app approximation. Reset/incomplete coverage and catch-up beyond 100 affected task identities omit this optional fast path. No task text, history, credentials or global sequence is added. The app can overlay a strictly newer committed status on already displayed Tickets ordinary/member rows and selected detail, and move that retained row between loaded first Overview need pages in the same main-actor turn. It checks store incarnation, project/catalog scope, task identity and the maximum displayed task revision, and rejects later lower-revision page/context replies. Equal revisions do not authorize an overlay; read-version equality tokens still cannot order snapshots. Complete coverage retains the Tickets page and its mounted filter controls during refresh, avoiding repeated worker-session reads from remounting. Unknown/reset coverage and task/group changes without the optional status projection still clear it. A Triage header derives status only from complete current membership coverage with matching project, the same or a newer group revision, no older known member revisions and at least one strictly newer displayed member revision. Partial member coverage, a changed membership count or a header-only page without a revision anchor waits for the full page. Page overlays never insert unseen tasks or certify membership/action authority. Full page/context replies replace the provisional display. Counts and page cursors remain provisional until those replies arrive; the patch neither advances the change cursor nor supplies current detail/action authority. A new interval resets its read-age clock, accepted Overview pages renew progress, and message-only coverage does not fan out Overview reads. The combined-loader watchdog deferral and sequential timeout fallback remain unchanged. This is read/display logic, with no schema, migration, validation, backup or startup change; installed status latency remains a separate measurement.

Only canonically validated raw records are retained, capped at 2,048 records, 256 query entries and 4 MiB of encoded payload; oversized queries bypass retention. Projections, authorization checks, time-sensitive health, current notices and newly sealed cursors run on every request. The per-connection timestamp parser separately retains at most 1,024 short strings: those immutable string-to-time values need no data invalidation. Ticket display-key lookup selects at most two matching canonical rows (including ambiguity detection), rather than decoding every ticket. Triage history/batch and Epic membership queries select their group's records before decoding, using the existing project/type scope index; no persistent schema/index or storage-protocol change is introduced. The Overview latest-review selection ranks each authorized project once with a SQL window, avoiding a count of the entire review history for every candidate. The small global project catalog and global owner request/task counts enumerate row identities through the existing covering scope index before loading payloads, preserving raw identity and row order without scanning retained history bodies. Workspace task pages aggregate cleaned-original counts only for selected page identities in the same pinned transaction, and health reuses that request’s status/prerequisite projection. Compact task context reuses its already-read attempt window and derives exact counts from a window only when it is shorter than its SQL limit; windows at the limit keep their full count queries. A newly saved claim supplies its exact attempt for direction-cursor construction within that same transaction, without another caller-attempt search. These values are discarded with the request; health and cursors still recompute and the canonical cache limits above remain unchanged. Native screens continue using their bounded list/detail pages. These source rules do not establish installed screen latency.

Pure-read service identity includes an opaque `read_version` for the pinned WAL snapshot and exact caller/grant namespace, independent of the single retained canonical-record cache. A per-router keyed digest covers SQLite's complete opaque snapshot handle and that namespace; no snapshot bytes, SQLite counter or event position leave Core. Interleaved callers and pooled readers of unchanged data keep the same scoped token even when they evict each other's decoded-record cache. An eventless commit changes it; a rollback does not. A checkpoint that resets the WAL may advance SQLite's observed data version and rotate the token even with unchanged committed rows; this conservatively invalidates display reuse. A precommit read finishing after a newer commit keeps its earlier token. No per-caller map or snapshot history is retained, and the temporary native handle is freed in its producing read frame. When SQLite cannot supply a WAL snapshot (including a non-WAL database or empty WAL), the service omits reusable display identity. Writer responses issue no token. The app may reuse loaded screen content only while its project, caller/grant identity and this generation remain current, and retires it when a committed mutation or newer coverage becomes known. Tokens support equality, never age ordering.

Combined Overview replies carry project metadata, compact authenticated service identity, global owner count and content cursor once at the parent; each group retains its exact rows, total and pagination cursors. Single-surface replies remain self-contained. Full provider/capability/route catalogs stay in `service_info`. Quiet attention builds its authorized actionable-Triage member set once, then looks each sibling up through the existing record primary key instead of scanning every task in that project for every candidate. These read/payload changes add no persisted schema or indexes.

CL-254 N254c changes only window navigation and display qualification. A project/surface change cancels its preceding live-reader lane and starts a fresh visible recovery interval, preserving the versioned content-cache and committed-change fences above. The optional Overview-return digest prefetch waits for the destination read and retains its scope/epoch/ready-content fences. Ticket navigation has no slide transition. Tickets/project-switch and ticket-detail notices require their captured destination accessibility text at the native draw; only fixed surface/cache/duration fields are logged. An unavailable AX tree leaves the text-qualified navigation unmeasured and stops its probe redraws. Detail accessibility is grouped ahead of the background workspace without hiding its navigation. No storage validation, migration, backup or startup path changes. CL-254/CL-260 M35 uses one optional AX-content requirement: expected text, static-text-only matching when requested, and an optional identified section whose subtree must contain every expected fact. Each content/token may request at most two additional draws, without a timer; later natural draws can finish a pending probe, and missing AX never certifies content. Settings and ticket opens both omit the slide. Cleanup rows retain accepted facts only within the same panel/project/store presentation during refresh; exact scoped cache reuse and late-reply fences remain. Native receipt labels preserve every displayed fact. Exact composed-build native latency remains runner qualification.

**File work, failed commands, reads and retention (20 October 2026).**

- *Indexed identity reads (CL-152).* Record ID, project-scope and command principal/command-ID predicates use the columns’ `checklist_storage_v2` collation, including the type component of `records_scope(project_id,type)`, the cleanup-cursor identity join and export receipt lookup. Query-plan coverage exercises these production lookups; a source guard rejects new explicit binary overrides on stored identity predicates. Do not add `COLLATE BINARY` to these predicates: it prevents SQLite from searching their indexes. The storage collation still compares complete raw UTF-8 bytes and lengths, including embedded NUL and malformed bytes; canonical decoding continues to refuse malformed text. This is a query change, with no schema or store-format migration.
- *File work outside the writer (CL-71).* A source submission copies, hashes and re-inventories its capture before the object gate and the SQL writer; a managed import reads, hashes and copies between short locked steps; a reference-mode import reads and hashes its file before the writer. A command that checks managed objects or a captured target (submission artifacts, review claims, verdicts and evidence, human-request targets) hashes and validates them before the writer; inside it, an unchanged content identity (device, inode, size, modification time) stands for the bytes. A prevalidated source capture keeps a content observation of every captured entry (kind, inode, size, modification time, executable bit, symlink target, membership). Inside the writer, a prepared object or capture is decided without a read: the same identity or observation is accepted, a changed one fails with `SOURCE_CHANGED` or `EVIDENCE_STALE`, and an item whose preparation failed (a read error, a missing file, a change during the check, a wrong hash or a failed live inventory) fails at once with the recorded result; a retry prepares the files again outside the writer. A change of permissions or ownership alone keeps the identity. Only an object or capture that the command did not prepare is read inside the writer. The check proves that the bytes matched during this command; the file owner can change bytes and reset the modification time, as at any time after the check. A stage file appears only complete, through an exclusive rename under the object gate, and the object link also takes the gate. The transaction checks the prepared capture or object (presence, size, recorded hashes) and commits metadata only. Writes that check a submitted source target take the live inventory just before the writer. Each git call has a 60-second limit and reads stdout and stderr at the same time. Source capture chooses the first trusted executable from `/opt/homebrew/bin/git`, `/usr/local/bin/git`, then `/usr/bin/git`, never from `PATH`. The executable, every parent folder and every symlink destination must be owned by root or the local owner and must not be writable by group or others (symlink permissions themselves are ignored). Unsafe candidates are skipped; if no trusted Git remains, `SOURCE_GIT_UNAVAILABLE` explains the refusal. Each Git call checks the selected executable again; if it has become unsafe, `SOURCE_GIT_UNTRUSTED` names the path and reason. Captures record the resolved `git_path` and `git_version`; these provenance fields do not change the source-content hash. An Xcode license refusal returns `SOURCE_GIT_LICENSE_REQUIRED` and asks the owner to run `sudo xcodebuild -license accept` in Terminal, then retry. The service runs these commands, and pure reads, off its serial queue.
- *Files of a failed command (CL-70).* A source capture writes a pending marker in `staging/source-captures/` before its first file; commit removes the marker. After a failed command, its own capture is removed when no `source_capture` record names it, and startup does the same for every marker that a crash left. A managed import job without a receipt for 7 days is abandoned: startup removes only its own unreferenced stage, partial-stage and final files and marks the job `settled` (`settled_reason=abandoned_without_receipt`). A retry of that command then returns `MANAGED_IMPORT_RECOVERY_REQUIRED`. A committed, referenced or held object is never removed. An export is assembled in a private sibling folder and renamed exclusively to its destination when complete; a failure removes the partial folder. The published folder keeps an owner marker (principal, command ID, digest) until the command's receipt commits; when the receipt or transaction rolls back, the export is removed, and a retry of the same command replaces only an uncommitted export with its own marker, so a retry can use the same destination. Before the partial folder exists, a durable pending record in `staging/pending-exports/` names the destination, partial folder, authenticated principal, original command UUID and intent digest. While that record remains, the principal/UUID reserves that digest across command methods: changed intents fail with `IDEMPOTENCY_CONFLICT` before file preparation or publication. A same-intent retry may replace only its own uncommitted export. Startup and post-command reconciliation accept a receipt only when its principal, command UUID and digest all match the journal. Without a receipt, cleanup renames the folder carrying that exact command/intent marker back to the recorded partial name and removes it; with a matching receipt it removes only the marker. A conflicting receipt leaves the journal and files untouched for recovery. An unreadable or malformed pending journal refuses command intent admission rather than freeing its unknown reservation. A record stays until its cleanup is complete, so a removal that failed (for example while the export parent was not writable) is retried at a later startup. A folder or marker that exists but cannot be read also keeps the record, and nothing is removed until the marker can be read.
- *Reads (CL-72).* Every read method starts on read-only connections, without the object gate or the writer. A read that turns out to write runs again on the writer path: an owner's `attachment_read` of an original (it issues a reader hold), an availability repair, a first cleanup preview, or a failed managed-original read, whose observation the writer path records. Metadata, preview and agent original reads of available files stay on the read-only connections.
- *Cursors (CL-72).* Event, page, history and direction cursors are sealed tokens (ChaCha20-Poly1305 with a per-store key in `metadata`, bound to principal, scope and incarnation, valid for 24 hours). No method adds a `cursors` row; rows issued by earlier builds stay valid until they expire.
- *Retention (CL-72).* Maintenance after a write (at most every ten minutes) and startup each prune a bounded batch: `cursors` rows older than 24 hours; command results older than 30 days, measured with hourly `(time, rowid)` marks in `metadata`, become a tombstone that keeps principal, command ID and digest, so a late retry returns `COMMAND_RESULT_EXPIRED` and never runs twice (policy-bearing project results, pairing receipts and commands that a storage job names are kept); cleanup previews of an older ticket revision, and current ones after one day. A repeated preview of the same ticket revision, settings and plan reuses its record.

`backup_create` enters its own storage boundary outside a semantic SQL transaction. It takes a distinct read-only SQLite backup source under a writer lease and root object permit, derives the closed object list from that copy, verifies required originals/previews/icons/captures and retained import bytes, flushes the complete generation, and publishes it atomically. Cancellation/deadline checks include SQLite's completed callback and the final publication boundary; they are cooperative limits, not hard filesystem-IO deadlines. A publication-uncertain retry re-verifies the generation and retries the containing-directory flush before issuing its completion receipt. A partial stage is retained before a deliberate same-command rebuild. A retained published or staged generation must match the current logical store, incarnation and source root before publication/completion; the physical operation namespace also includes that identity while command ownership remains authenticated principal plus original UUID. Historical backup-retention descriptors are bound to the verified manifest and committed with the command receipt; they do not assert current external presence or physical allocation.

Disk-full/commit errors return an explicit unknown outcome with the original command ID for reconciliation. Existing database/WAL/objects are preserved; content-free recovery metadata is best effort because a failed volume can refuse that write too. If authoritative startup refuses, the existing local service route answers a content-free recovery state and rejects data access; it does not enroll connections, dispatch messages, run cleanup or open a replacement store. Process-kill checks qualify their actual boundaries, not abrupt power-loss durability. Installed target evidence and independent review remain separate from source implementation.

**Full storage target, 16 October 2026.** The local development service already uses SQLite and managed files; [implementation status](implementation-status.md) identifies remaining restore/failure qualification. Checklist keeps the owner's game and app projects in one local store on this Mac. Tickets, notes, answers, review history and delivery receipts remain available together; images and larger files live beside the database. A project does not need its own database, cloud account or storage setup.

## Store ownership and layout

Ship SQLite inside the native app's storage layer, using the pinned Swift wrapper selected during the packaging spike. Only `ChecklistService` opens the authoritative database for mutation. UI windows, MCP shims, the diagnostic executable and retained assistant components use authenticated service commands. They never coordinate by editing a shared JSON or Markdown file.

```text
~/Library/Application Support/Checklist/
  store/
    checklist.sqlite              authoritative records and metadata
    checklist.sqlite-wal          SQLite-managed committed journal
    checklist.sqlite-shm          SQLite-managed shared-memory coordination
  objects/
    originals/<digest-prefix>/…   immutable managed bytes; private internal names
```

## Transactions and durable delivery

Enable foreign keys on every connection, WAL, a bounded busy handler and short write transactions. Start with durable `synchronous=FULL` for authoritative writes; measure it on the release Mac rather than weakening crash durability to meet a speculative benchmark. Pin connection configuration in the store layer and test actual filesystem/SQLite behavior. The service serializes mutation commands and uses a bounded reader pool; a singleton lock plus signed service identity prevents a second writer process. No long-running provider call, preview generation or file copy holds a SQLite write transaction.

Each mutating command has an idempotency ID bound to the authenticated principal/project and a canonical request digest. In one transaction:

1. Resolve binding/grants and verify expected revisions, current policy, fencing incarnation and domain invariants.
2. Update projections, reserve/release authority and append immutable records/events.
3. Insert the semantic command result and any exact-recipient outbox work.
4. Commit; only then publish live-change hints or call a native provider.

The same command ID with the same payload returns its original semantic outcome and current authority state; a different payload is a conflict. Retain compact command identity/digest/outcome references for the lifetime of the relevant history, even after a larger diagnostic response is compacted. Do not expire deduplication after a short transport timeout and permit an old command to execute twice. Import source identities and build fingerprints have their additional domain-specific deduplication keys.

### Durable long-command acceptance (CL-353)

Long-command admission durably records an operation identity, original UUID/intent digest, method, caller/project/incarnation/authorization generation, `queued` state and creation time before acknowledging acceptance. Ordinary admission uses one SQLite transaction under atomic backup writer admission. During capture or FIFO draining, acceptance instead atomically publishes and flushes `backup-write-queue/operation-<operation-id>.intent` through the existing no-follow queue-file protocol. The root/incarnation-bound, size-bounded sidecar contains only operation metadata and an optional prior-canonical hash; it contains no original input or reply bytes and is never a legacy FIFO semantic intent. Read operations execute against its pooled metadata during capture, retaining their terminal outcome in memory until write admission opens. The terminal transaction imports canonical state before retiring the sidecar. Startup validates and imports accepted metadata before the existing interruption reconciliation, then retires the sidecar before FIFO recovery; a canonical record that advanced beyond the captured prior hash always wins over stale staged metadata. As with ordinary backup-write intents, these post-snapshot queue files are not managed-object inventory or input to the captured snapshot. The service's concurrent command-operation queue, separate from the storage-maintenance queue, executes the accepted work outside the request path, so a backup or cleanup scan never delays another operation; start/finish transitions are durable. Short semantic commands remain synchronous. The command retains its original writer admission/lease, object and retention gates, prepared scan fence, expected revisions, grant checks and filesystem publication protocol. A narrow journal exception lets acceptance, operation-state and final-reply transactions use `StorageOperationLease` and the sole `dbQueue` writer without `ArchiveStorageGate`, because those transactions create no file names or references. Domain handlers still acquire all their existing gates. Ordinary durable acceptance can wait for that writer; the real-size about-one-second target therefore also requires the combined CL-345 writer-occupancy gate. Capture-time acceptance does not enter SQLite's unavailable writer.

`operation_get` and original-UUID `command_status` expose the operation's `queued|running|succeeded|failed` state. Final successful results come from the canonical semantic command journal, including exactly the former synchronous reply envelope. Operation metadata keeps no duplicate private result/error snapshots and respects existing command pruning/purge. Actual failure details are stored in a separate canonical `commands` error receipt under a derived UUID; metadata retains only `error_result_command_id`. The original command slot remains available for unknown-outcome reconciliation. Error reads honor command-result purge/expiry; generic startup interruption errors may remain in metadata. Stored successful replies retain relative managed descriptors, with owner URLs projected when read. Claim tokens are removed before result persistence and refreshed through the normal replay checks when read; operation history never stores usable claim credentials. Purge uses SQL without decoding large known operation result/error snapshots and may conservatively expire those snapshots when any ticket is purged. The generic purge generation also expires a result whose execution overlaps purge, so completion cannot resurrect scrubbed content. Reader-hold results retain the original hold expiry; historical operation reads never renew the lease. Failed operations retain their error-receipt reference and timestamps; `OUTCOME_UNKNOWN` keeps its original command UUID and publication/commit uncertainty, not a fabricated rejection.

Startup reconciles an accepted operation against its semantic receipt. A matching committed command is succeeded even if the process stopped before recording the operation finish. Without that receipt the interrupted operation is failed with `OPERATION_INTERRUPTED` and an explicit reason: running retains unknown outcome, while queued unstarted work is rejected only without prior semantic uncertainty. The internal `outcome_unknown` marker preserves earlier uncertainty across exact-original replay and another crash before the queued retry starts. Explicit exact-original replay may resume only interrupted/uncertain work under that same operation ID and current authority. Restore fences/quarantines old operation execution; copied history grants no authority in the new incarnation. This changes backup/restore command execution and startup reconciliation: installation qualification must exercise the exact staged startup and protected pre-upgrade backup path on an owned consistent existing-store copy, retained operation/command families and required managed files, interrupted backup/restore publication reconciliation, and command-result purge. SQL-only or synthetic migration tests do not establish that compatibility.

Outbox jobs retain the exact message, causal ID, recipient principal/native generation and route used. Sending and recording a provider response are separate commits with attempt receipts. If acceptance is uncertain after a crash, reconcile by the provider's supported message ID or show **Delivery uncertain**; never silently send a duplicate. Held/refused routes retain their native receipt and permission provenance, without changing settings or pretending delivery. Each recipient acknowledges its own delivery. Immediately before each external send, compare current grant/route generation. Revocation cancels unsent jobs and attempts in-flight cancellation; already transmitted bytes cannot be recalled. Preserve actual submission/revocation/result ordering and deny subsequent reads/replay. Apply the existing limit of two identical failures/unchanged results before suspending a route. Store scheduling for a bounded I/O retry is not permission to poll or launch a model.

Stable named assistant identities and their project grants belong in this store when that optional integration is enrolled. An assistant can read/check/report, exchange ticket messages, and receive subscribed notifications for the owner; it is never a work assignee, worker, claimant or reviewer. When the owner asks, assistant may create a Draft ticket or add a note through the ordinary domain handler. Record `actor=assistant` with the assistant's stable principal and the source owner-request reference when available. This cannot create a `human_ui` note, human answer or approval. Notes use the ordinary exact-recipient task outbox, and Draft creation remains ineligible for pickup until normal readiness validation.

Persist granted project memberships, ticket subscriptions/event filters, subscription expiration, causal/reply IDs, inbox cursors, exact host-session binding and delivery receipts independently of work attempts. The preferred MCP Events notification route uses host-supplied authenticated subscriptions and outbound signed HTTPS webhooks; it creates no inbound public listener. Store callback destinations as private routing metadata excluded from exports/diagnostics, and signing secrets in Keychain. Commit event-to-subscription deliveries atomically with the relevant event/outbox work so a reconnect can deduplicate using delivery/event IDs. A webhook `2xx` is only transport acceptance, not proof that assistant read it or the owner saw it. Expired/revoked subscriptions stop future dispatch and retain receipt history; resume requires a currently valid subscription and cursor reconciliation. No polling, streaming or model runtime substitutes for an unavailable host event route. Keep source receipts but coalesce obsolete same-ticket/cause notifications into one bounded reconnect/catch-up report, retaining unresolved owner requests. Do not emit a failure event through its own failing route; report connection health locally or through another explicitly selected route with causal deduplication.

The storage layer grants no authority because of a display name, personality or imported assistant reference. Route availability, host capabilities and consent are defined in the integration contract and would require real local-Dot qualification under a new separately authorized proposal; a saved subscription does not prove the host can wake an agent or route a subagent.

### Uncertain-command recovery on this Mac (CL-196)

The native app saves an uncertain command in its window's private recovery file before sending it (CL-373). The folder is `OwnerPrivate/` under the instance's owner data root (live `~/Library/Application Support/Checklist/OwnerPrivate/`, slot N its `data/OwnerPrivate/`), mode 0700. Each key has one file, mode 0600, named from the kind and the key's SHA-256 (`pending_command-<sha256>.json`; the key is `pending-command-v2` or `pending-command-v2-window-<uuid>`). Every save uses no-follow descriptor calls, an atomic rename, a flush of the file and folder, and a read-back. The record retains the original method, parameters and command UUID, plus the connected store's `store_incarnation` and the native transport's bundle-derived Mach service name (`org.checklist.coordination` for live, `org.checklist.testN.coordination` for a test slot). A new command cannot be saved without a known store incarnation. A save failure stops the send and reports the real cause, its errno and the next step. These local recovery records are separate from draft journals and are not portable commands or part of backups/exports; the store inventory does not list `OwnerPrivate/`, and a slot seed does not copy it.

The record never holds a claim token in plain form. For a command with `claim_token`, it holds `claim_token_ref`: the command's `attempt_id` and the token's SHA-256. Recovery reads the token from the attempt's claim file (`claim-<sha256>.json` in the same folder) and sends it only when its SHA-256 matches, so a replay has the original bytes. A missing or changed credential makes the record unreadable: it is ignored and not sent. The claim file holds the token itself, protected by the file modes and not by encryption. A claim whose credential exists only in Keychain has no claim file, so the app shows its existing unavailable-credential message and recovery route, with no prompt.

At launch the saved command remains unavailable until an accepted service read identifies the connected store. Only an exact byte match of both incarnation and service name offers **Check the last change**; nothing is sent automatically. The owner's retry reads `service_info` again before sending the original command with its original UUID. A failed identity read preserves the command for a later check. An observed store change withdraws the offer. A restored incarnation, another installation or test service, malformed/unbound older records and unreadable or untrusted files (wrong owner, group or other access, a link, or bytes of another key) are ignored without sending them.

An ignored file remains in the folder. The app shows one plain-language warning per item and window key, remembering only its SHA-256 notice marker in local preferences, not its parameters. An unreadable file has no accessible fingerprint: its warning is suppressed until a later launch observes a readable or absent file, or the window saves a new command. Clearing preferences also clears this notice memory. A successful newer save replaces the ignored file. Removing a recovery file only removes the retry offer; it neither rolls back nor proves the outcome of the original change.

Leftover Keychain items are ignored and can stay. The native app makes no Keychain call for recovery or claims: it never reads, writes or deletes the old `Checklist.HumanClaim` / `Checklist.TestN.HumanClaim` items, and it offers no retry for a command that only such an item holds. Removing a leftover item is optional and changes nothing in the app.

## Immutable files and crash consistency

Use an internal content digest for deduplication and integrity, with separate attachment UUIDs/project links and attribution for each import. A digest is not an access token. Do not provide an agent-facing digest-exists query, other-project reference counts, global blob paths or deduplication receipts that reveal another project's files. Import validates and reads the caller's authorized source even if identical bytes already exist elsewhere. Access checks resolve a permitted project attachment first, then the internal blob. A caller's cleanup preview reports its own logical bytes and a neutral shared/retained reason; only the owner storage view may explain other projects. Shared physical bytes count once in global disk usage; project totals are logical attachment bytes and must be labeled accordingly.

Treat original and preview bytes as immutable. A replacement creates a new ID/hash; a filename cannot replace a review target. Authoritative manifests live in SQLite or as immutable checksummed objects referenced by it. Avoid mutable sidecar manifests whose update must race a database commit. External references store approved scoped bookmark/grant information and an optional observed fingerprint; do not copy a directory recursively or back up its contents merely because its path was selected.

An import uses this recoverable sequence:

1. Allocate a job/command receipt and staging path. Safely open the authorized source, reject escaping aliases/symlinks, copy within limits, compare source observations before/after, and hash/validate the copied bytes. No task attachment is available yet.
2. Flush the staged file and finalize its immutable name inside the managed object directory with a same-volume atomic operation. If another import already finalized the same digest, verify/reuse the known object. Flush the affected directory using supported platform durability primitives; the packaging spike must prove that boundary rather than assume rename alone survives power loss.
3. In a short transaction, create/link the blob descriptor, attachment, project/task references and event/command result. Mark availability only after finalized bytes exist. Commit and publish.
4. Generate bounded previews outside that transaction, then attach their immutable descriptors in a separate idempotent commit. Preview failure leaves the original usable.

A crash before commit can leave an orphaned finalized object or staging file, never a committed **Available** record pointing to an incompletely written file. Recovery identifies orphans through recorded jobs plus a guarded inventory and grace period; it does not delete active staging. A crash after commit retries the command receipt and returns the existing attachment. Startup verifies descriptors relevant to interrupted jobs; a missing/damaged original is marked unavailable and recoverable, not silently accepted because its database row exists. An abrupt power loss still needs an actual release test on the target filesystem.

## Archive cleanup and retention

The implemented bounded job/hold/Undo behavior and honest logical-versus-physical accounting are described in [Archive cleanup](archive-cleanup.md). Current cleanup uses the single shared writer/object permit and durable intent/outcome path; it never runs the removed legacy unlink loop. Completed backup copies remain separate and are not purged by archive cleanup.

Keep the [attachment policy](attachments.md) defaults unchanged: an archived managed original of **20 MiB or larger** is eligible, and retained unpinned originals have a **50 MiB per archived ticket** budget. Aggregate overflow can prune smaller files largest-first. **Keep originals** is the alternative preset; the owner can customize project thresholds, and an individual **Keep original** hold wins. These are shipped project defaults; an explicit saved project override remains authoritative.

The database records link retention, active review/build/reader holds, backup capture holds, cleanup preview revisions and the durable job. Shared originals remain while any live attachment/settings reference outside the same cleanup scope or applicable hold needs the bytes. Removing one task's original must not make another task, project icon, pending approval or captured build unavailable. Evidence hashes and metadata remain after original pruning, with explicit cleaned availability.

Cleanup is a three-step state machine: transactionally revalidate eligibility and mark a deletion candidate; under the storage helper's per-object gate, recheck all references/holds and unlink only an app-owned object; then commit the actual result and bytes reclaimed. A new reader/link/hold must obtain the same gate and cancel deletion or wait/retry; it cannot acquire a valid handle after final eligibility checking but before unlink. A crash between unlink and result commit is reconciled as already absent. A crash before unlink can safely retry. Do not derive the result from a previously displayed preview alone.

Undo cancels a pending cleanup while bytes still exist. Unarchive restores task visibility/history, not deleted originals. Restore from a retained copy or source requires checksum verification and a new availability event. Show logical bytes selected, active-store bytes removed and actual retained/estimated physical savings separately. APFS clones, hard links and older backups can retain physical allocation; do not claim the sum of file lengths as disk space reclaimed. No cleanup operation deletes external Finder targets, source project files, user exports or unrelated backups.

## Consistent backup

Provide **Back up now** and automatic local backups. Proposed default: create the first backup after the first saved project; thereafter, when changes exist and the last successful backup is at least 24 hours old, request one bounded backup while the service is available. Evaluate after commits and at ordinary service startup; if it was closed, overdue work waits for that next startup. Coalesce concurrent requests; do not wake a model or install a recurring task. Retain **seven daily and four weekly successful generations**, plus a protected pre-upgrade/pre-restore rollback generation until its operation is verified. These are product defaults to validate, not existing automation. The owner can choose off, daily-on-change or a longer interval, change retention and choose an export destination. Local backups protect recovery from app mistakes; an owner-selected external copy protects against losing this Mac.

Each completed backup directory is self-contained: consistent SQLite backup, versioned manifest/checksums, all managed originals/previews/icons recorded as available in that snapshot, and a non-secret settings/schema/build summary. Do not rely on the live store's future paths to make a backup restorable. External references remain references and are listed as requiring relink/access; secrets are excluded. A successful metadata-only export is not labeled a full backup.

Use SQLite's documented [Online Backup API](https://sqlite.org/backup.html) and [WAL behavior](https://sqlite.org/wal.html) as the implementation basis. The completed database copy includes committed data; SQLite consistency alone is insufficient for the separate managed files. The following filesystem barrier is Checklist's additional design requirement, not a SQLite guarantee. Use the following storage barrier:

1. Enter the backup job gate and pause physical object deletion; wait for any in-flight unlink to finish. New task writes/imports may continue. Staging and cleanup plans are not authority to delete during this barrier.
2. Produce a bounded consistent SQLite backup through the backup API, with progress/cancellation. The SQLite `IMMEDIATE` writer lease covers only the consistent database copy, including its page-count budget checks. Release the writer lease and ordinary object gate before journal normalization, database validation, required-object inventory or object verification. Those checks run on the backup worker outside the service's ordinary write lane.
3. Keep the root-wide capture retention barrier after releasing the ordinary object gate and SQLite writer lease. Normalize and open the copied database read-only and derive its exact required-object manifest from that snapshot, not from a second query of the changing live database. Retention begins before the database copy and protects the complete namespace before the inventory is known. The implemented barrier is a private no-follow, single-link `.snapshot-retention.lock` kernel lease; it conservatively protects the complete immutable managed namespace, including inventoried pending ordinary-import stages and finalized recovery files. Missing required bytes fail capture. Notes, ticket edits and new immutable imports proceed without holding the backup's file-copy or verification work in the database writer or service coordinator queue. Existing publications never overwrite an immutable name. Cleanup previews report a backup-capture hold, final managed unlink paths refuse `BACKUP_CAPTURE_ACTIVE`, and routine import/archive/purge maintenance waits without incrementing failure/suspension counters. A fresh UUID review-report file can still be removed by its creating transaction's rollback: its `O_EXCL` creation and inode-bound rollback callback remain under the object gate, so no capture could have inventoried it. No general retention bypass is exposed.
4. Materialize immutable objects inside the staging backup. Same-volume hard links may be used only for immutable bytes; otherwise verified copies are valid. An APFS clone/copy optimization must retain checksum checks. Never hard-link a mutable live SQLite database. Finish the manifest and verify database integrity, object sizes/hashes and completeness. A link/copy failure or cancellation keeps the generation incomplete.
5. Flush and atomically publish the completed backup directory; prepare the large receipt index outside the writer and record its successful receipt in a short gated transaction, then release capture retention. Concurrent owner backup requests refuse `BACKUP_IN_PROGRESS` and retain their original command identity. An incomplete generation cannot count toward retention or displace the last working backup. The kernel releases retention if its process dies: retry verifies a complete independent stage, or quarantines an incomplete stage and captures a fresh database/inventory under a new hold. It never resumes copying from an unprotected old source inventory. Cleanup's one-shot wake defers to a 60-second capture-lease recheck while capture is active and is rearmed after backup success or failure. Receipt reads expose the retention reason, unknown release time and dated next check even before a first pass exists. Protected pre-upgrade copying retains its exclusive-service drain and gate throughout; it does not admit production writes before migration.

### Backup write admission (CL-320)

Fresh CLI/MCP transports can bootstrap an existing committed automatic connection without writer admission. Bootstrap still verifies the native caller, workspace, credential, current session registration and authorization generation; it returns the current `write_admission` observation. The subsequent reads and ordinary writes therefore reach the same read/queue paths as an already connected client during capture. Initial enrollment, interrupted-registration repair, host resumption and changed grants still require immediate writer admission and defer the complete bootstrap until it opens. Prepared or queued registration is never treated as committed authority.

During online database capture, ordinary writes return a durable `command_outcome: queued` acknowledgment instead of waiting for the SQLite writer. A private `backup-write-queue` directory stores atomically published, flushed intents bound to this root, store incarnation, authenticated principal, original command UUID and input digest. The service applies them in arrival order after the database copy; new writes join that order until it drains. Current session authorization and ordinary domain/revision checks still apply. A retry keeps the same UUID and intent. The `command_status` read reports pending, applied or failed; successful results come from the canonical command journal and obey its expiration/redaction rules. The acknowledgment itself is never proof that a change committed. Accepted intents participate in storage drain, survive service restart and retain unknown outcomes for original-command reconciliation.

Every ordinary router reply carries `write_admission`: whether writes are locked/queued, the reason, backup activity and an optional estimated remaining duration. The estimate is `null` when unknown; the service does not invent a countdown. Reads such as `service_info`, `task_get`, Overview, import previews/receipts, native media metadata/projections and the enrolled-worker media reads (`media_type_list`, `media_type_get`, `media_round_get`, `media_intake_get`, `media_decision_list`) use read-only connections during capture; worker reads check the current project grant, worker session and own-intake rule in that snapshot. Import authorization is checked on that pool before source preparation and again in the result snapshot; committed pairing-receipt authentication also reads current authority there. Writer-dependent read/check fallbacks (managed-original reader holds, failure observations, availability repair and first cleanup previews) return `data.state: locked`, `queued: false` and `retry_required: true` immediately when capture or queued work closes writer admission. Native media original reads and example lease/release use the same admission fence because they change reader holds. If the read-only pool is unavailable, import/media reads retain writer admission rather than waiting behind capture. The reply retains the observed `write_admission` lock state and reason. It grants no hold, lease, availability change or cleanup preview, and creates no queued intent: retry the read after admission opens. An admitted writer-dependent read finishes before a new database capture can begin. Native registration and native-send commit fences defer without inventing a successful registration or external-send receipt. The app and Quick Capture retain original commands, drafts and staged images until the applied semantic result, and show the write-lock reason separately from service reachability. Inventory, file copying and verification continue on the backup worker after the short capture lock ends; unrelated writes then run normally under the retention barrier.

The 28 October 2026 in-process Core qualification on a complete real-store copy (schema 4, about 1.69 GB of SQLite data, seeded with 252,809 managed entries) measured a **2.677-second writer lease**. A note and ticket edit issued during that lease returned queued acknowledgments in **5.6 ms and 6.0 ms**, then applied. During the lock, maximum service-info, ticket and Overview read times were 5.6 ms, 8.4 ms and 62.1 ms (baselines 2.1 ms, 8.3 ms and 59.5 ms). Recorded 1/5/15-minute host load was 8.04/13.72/15.74 on ten cores; other package work was concurrent. These are Core observations, separate from signed-app/XPC timing and complete staged startup/protected-upgrade qualification.

Hard-linked backup bytes survive removal of the active-store link, and backup retention protects those remaining links/copies. Report this as backup-held storage; deleting one active copy may reclaim no physical blocks. Retention removes only whole unprotected completed generations after a newer verified generation exists; it does not mutate their SQLite snapshot or manifest. Never delete the sole good backup in an attempt to make a new backup fit. Manual exports and owner-pinned backups are not swept by automatic retention. A project archive preset does not override global backup retention; Settings explains when backup copies delay final space reclamation.

If a backup cannot finish within its bounded work budget or required free space, retain the last successful one, release/resume barriers safely and show the precise failed job. A read snapshot must not hold the WAL indefinitely. Startup/self-update uses the same tested backup path, not a direct `cp` of a live `.sqlite` file.

### Snapshot capacity (CL-163)

Owner backups and protected pre-upgrade generations use the same explicit product policy in `StorageSnapshotBudget`: **no fixed logical byte ceiling** (CL-340; the earlier 8 GiB ceiling stopped every backup once the live store reached 8.6 GB), with the logical published bytes (database, managed objects, intent and manifest) bounded by the free space on the backup volume less a safety margin, **500,000 managed objects**, **128 MiB per manifest**, **500 MiB per managed file**, **100,000 canonical records**, and a **1,800-second cooperative deadline** for the complete snapshot build, including both full verification passes and publication. Every owner receipt/reconciliation manifest read uses the same manifest cap. These limits replace the earlier 1 GiB / 30,000-object / 8 MiB manifest caps and the 60-second owner / 300-second pre-upgrade deadlines. They are product bounds, not editable project retention rules. Existing generations remain readable under the larger bounds.

The sizing basis is an owned retained-store copy needing roughly 1.7 GiB, 49,406–56,132 objects and a 35.3 MB manifest; earlier durable copying alone took 525–564 seconds on a heavily loaded Mac. The new byte/object/manifest bounds provide several times that observed capacity; the deadline must also cover exact inventory and digest verification. A fixed bounded deadline avoids treating an estimated throughput as a guarantee. Qualification measures actual copying, flushing, publication and reconciliation; inventory or SQL rehearsal alone does not qualify an installation. No APFS clone optimization or retention deletion is introduced: ordinary independent copies, `fsync`/`F_FULLFSYNC`, descriptor-relative `O_NOFOLLOW` access, the existing object permit/SQLite lease and exact database/inventory/object digests remain in force. No additional file work moves into a semantic command transaction. CL-320 releases the owner backup's object gate and SQLite lease after database copy, before normalization, validation and inventory; the root-wide retention lease protects managed copies through publication and receipt. Settings shows an indeterminate copying/verifying indicator and guidance that large stores can take about ten minutes, with the thirty-minute cooperative limit; it disables a duplicate backup click for that request. This is duration guidance, not measured percentage progress or a cancellation control.

Before copying managed objects, the builder measures their full descriptor-relative lengths against the copied database inventory. Capacity failures return `BACKUP_CAPACITY_EXCEEDED` with logical byte/object counts, explicit limits and a next step; deadline failures return `BACKUP_DEADLINE_EXCEEDED`. An inventory stopped by its object/record safety bound reports an explicitly labeled lower bound, as does a pre-copy byte measurement that excludes the not-yet-encoded manifest. A completed manifest measurement includes all published bytes. These are logical lengths, not physical-allocation estimates. Before the database copy the builder measures the free space on the backup volume once (`statfs` available blocks) and refuses when less than the 1 GiB minimum margin is free; after the inventory measurement and before any managed object is copied it refuses when the measured bytes plus a safety margin (10% of the measured bytes, at least 1 GiB) exceed that free space. The refusal returns `BACKUP_CAPACITY_EXCEEDED` with reason `snapshot_free_space`, the needed bytes (`required_free_bytes`), the margin and the free bytes (`available_bytes`); during copying the running byte limit is the free space less the minimum margin. Only an exhausted byte-space budget reports `snapshot_free_space`; a free-space sample never reclassifies another bound. A configured fixed byte ceiling and the canonical-record limit report `snapshot_capacity` (including `maximum_records`); the object, manifest and per-file limits report `snapshot_object_capacity`, `snapshot_manifest_capacity` and `snapshot_object_bytes`, and the deadline reports `snapshot_deadline`. These refusals retain their measured counts and configured maxima. Restore applies the same free-space refusal to the restored copy. Preserve the store and existing backups; retry a time-limited attempt on an idle Mac, or use a build with sufficient supported capacity. Never delete retained captures or attachments merely to fit a snapshot. Partial/uncertain staging and previous completed generations retain the existing restart-safe behavior. Cooperative checks cannot interrupt a blocked filesystem call, SQLite integrity query or JSON encode/decode; a longer budget does not promise completion under arbitrary load or power-loss durability.

## WAL, upgrades and recovery

Checkpoint WAL passively at safe boundaries and inspect its size. Proposed starting cadence is **1,000 WAL pages**, with a **64 MiB** retained-WAL diagnostic threshold and bounded attempts; tune against measured page size/workload. Do not force a blocking truncate while a long reader is active. Identify/cancel the service's own stale read job or show diagnostics and retry at the next safe boundary. A closing UI window does not delete WAL. A clean service stop can attempt a bounded checkpoint after writes finish; failure leaves valid SQLite files intact. Never repair space usage by deleting `-wal` or `-shm` beside an open database.

Schema migrations have ordered versions/checksums, a declared compatible reader range and a durable receipt. First validate on a disposable copy; take a full pre-migration backup. Stop new mutations/dispatch and safely drain storage jobs before a production migration. Use one transactional migration where SQLite supports it; resumable filesystem work uses explicit phases and immutable objects, never a half-published schema. Keep service/MCP/UI version negotiation read-only until compatible. A failure returns to the intact pre-migration store before new production writes, or enters repair-forward mode if reverting would lose later writes. See the [self-build rollback rules](self-hosting.md).

Restore runs in staging. Validate store/export format, schema compatibility, integrity, project identities, complete object manifest and reference availability; show what will replace the current store and any unavailable originals. Pause mutations/dispatch, settle helper jobs and save/reconcile UI drafts. Keep a consistent rollback generation, then switch validated store/object state using a durable restore receipt and directory/file replacement protocol. A crash at any step can identify which generation is authoritative. Do not merge a partly restored database with the old object manifest.

Every restore creates a new store incarnation and revokes old connection/claim authority, including tokens whose records reappear in the backup. Revalidate installation/project grants through supported current host bootstrap/identity revalidation; mark restored active attempts recovery-required. Preserve historical delivery/answer receipts, but quarantine unresolved restored outbox work for reconciliation rather than automatically resending messages that may already have been delivered after the backup. Resume dispatch only after the explicit restore reconciliation; restoring data is not evidence that an external writer stopped. Local drafts and plugin inbox cursors reconcile against the new incarnation, with a full authorized snapshot when their cursor is no longer valid.

Handle `SQLITE_FULL`, quota and write-I/O failure as failed commands unless the persisted receipt proves commit. Do not publish live changes, acknowledge saved notes or delete rollback data on a failed commit. Preserve unsaved text in the draft journal if its write succeeds; otherwise show **Not saved** and retain the editor text for copying. Stop imports/build capture/automatic backup creation and offer measured cleanup, without deleting originals/last backups opportunistically. Existing read-only task context should remain available where safe.

On corruption, stop mutations and delivery, preserve the database/WAL/objects unchanged, and offer a verified backup restore. Run bounded integrity/foreign-key checks on diagnostic copies, with cancellation for larger stores. Search-index corruption can rebuild from intact canonical data. Any salvage of damaged canonical records is an explicit separate recovery export with provenance and missing-record report; it is never silently promoted to a fully verified store. File checksum failure marks that representation damaged and offers a verified copy. Repeated identical failure suspends the job after two attempts with actionable repair details.

## Export, removal and privacy

Canonical project export contains that project's permitted records, event/message history, revisions, settings/icon, source identities and immutable artifact/attachment availability manifest; managed copies are optional and clearly labeled. Include checksums, schema version and all required shared identity descriptors without other-project grants or associations. A full-store backup preserves all projects; a project export does not disclose another project's blob references or assistant subscriptions. Never export secrets, claim tokens, reusable routes/socket endpoints or a usable live session binding. Imported/restored records retain provenance without inheriting live authority, as specified in [migration](migration.md).

The owner can export drafts explicitly; ordinary canonical task exports exclude unfinished drafts and personal UI preferences unless selected. Project icon and native file bookmark data are local data; exports can carry the bounded icon copy and descriptive external reference, while access is re-granted on restore. Diagnostics use a closed, content-free report rather than exporting or redacting raw records. Settings → General → Save diagnostics opens a native Save panel and writes one owner-readable JSON file at the chosen destination, with no upload. It includes numeric app/bundle/macOS versions, the build ID, architecture, current service responsiveness/version, aggregate counts under fixed record-type labels, and at most 20 error codes with times from this owner app run. Error messages, note/answer text, file contents, source, home and destination paths, actor/session identities, tokens, routes and connection secrets are excluded. Unknown record types count only as `other`; unrecognized errors become `OTHER_ERROR`. If the service cannot answer, the report says unavailable and omits counts. Canceling Save creates no file. No analytics upload or cloud sync is required.

Removing the app bundle or unregistering its service does not delete the store. Offer a separate owner-only **Remove Checklist data** action that previews local store/backups/cache removal, resolves active claims/jobs, optionally exports first and explains irreversibility. External project files, Finder references, user-created exports and separately selected backup destinations are not included automatically. Removing a project follows its archive/trash/explicit-purge rules and removes only its references; globally shared bytes remain while another project or protected backup needs them. Secure erasure of APFS snapshots/backups is not promised by deleting local files.

### Ticket purge (CL-24, 20 October 2026)

The owner-facing Trash/purge view is removed (CL-226); existing trusted-owner purge commands and maintenance behavior retain their current impact-preview and Trash guards. `task_purge` requires the current ticket revision and the current preview digest. Active implementation, review or child work, an owner check, source execution and pending owner requests block it. One validated transaction replaces the ticket with an immutable minimal "Purged ticket" reference (same ID, project and key, purge time and actor), removes the records and grouping entries that only this ticket owned, keeps incoming relations and shared records, clears the data of the ticket's history events without removing their sequence rows, and expires earlier cached command results that refer to removed content. The purge has its own idempotent receipt. Other tickets and their quoted copies are outside granular redaction.

The record transaction saves a durable `storage_job(kind=ticket_object_delete,cause=task_purge)` intent with exact object descriptors before deleting their owners. After commit, the archive cleanup pump removes exclusive managed originals, previews, captured-source files and captured manifest sidecars through its existing object permit and verified unlink. Captured links are checked as link text and removed before any link or file in their target chains. Every retained link keeps its whole target chain and final file, whatever caused retention. Before each unlink, the pump recomputes this closure, including after partial failure or restart. It never sweeps directories. External originals and workspace files are never deleted.

Each continuation takes the object gate before the SQL writer and checks the current record graph, typed media references and reader holds before unlink. The remaining-record check counts only owners outside the same cleanup scope; a record removed by this purge, or an unchanged historical Done-evidence owner whose bytes are being retired, cannot retain its own file. Shared records, Keep original, active reader/media/backup-capture holds, workspace overlap and uncertain identity or authority retain the bytes with a receipt reason. Ticket-byte cleanup also retains live-only bytes with `backup_required`: a completed backup must independently hold the exact path, kind, digest and length. Its verified independent copy or backup-owned hard link permits unlink of the live pathname without changing the backup or its exact restore. Historical backup-generation descriptors alone do not prove current backup bytes. Preparation pins and hashes the recorded manifest when its generation enters the bounded root/manifest cache and verifies candidate payloads outside the writer. An evicted generation is verified again if later needed. The final unlink checks that both named manifest and payload still have those verified identities; missing, changed or unverified entries retain the live copy. Invalid historical backup authority conservatively retains bytes and does not block record purge. Backups and exports made before the purge can contain the ticket; Checklist does not change them.

Each continuation verifies at most 256 candidates or one second of work outside the writer, further reduced by the available descriptor budget, then unlinks at most 128 objects or 25 ms of writer work. Time budgets are cooperative and do not interrupt an individual filesystem call. Startup resumes pending intents. The durable descriptor survives a crash after record commit or unlink; an absent object is reported as already missing, not newly deleted. Two failed attempts report retained bytes and a bounded failure code. A completed purge job retained solely for backup or remaining-record reasons can be rearmed once under `cleanup_policy_version=2`, and subsequently when a newer completed backup generation exists. Explicit transient backup-copy errors and the one-time recovery of old `backup_copy_unavailable` holds also permit a generation-independent retry, as detailed in the CL-321 rules below. Each recheck rebuilds current authority and verifies no-follow identity and digest before deletion. Keep original, reader/media holds, identity failures and other permanent reasons are not blindly reset. Releasing a hold alone creates no retry or retained-file polling timer. Pending and retained descriptors remain backup inventory authority while their bytes exist. No schema migration or second unlink path is introduced.

Done-job accounting uses one project-scoped `records_scope` stream per selection. Every bounded storage-job envelope receives canonical JSON/UTF-8 validation once; only the selected tickets' pending flags and distinct retained `(stored_path, sha256, ordered reasons)` signatures survive. Ticket and project matching uses exact UTF-8 identity; descriptor comparisons preserve the existing optional-String and ordered-reason semantics. The observation admits at most 32 tickets, 100,000 streamed jobs, 4 MiB per job, 4,096 matching jobs and 100,000 distinct signatures/16 MiB per ticket, and 200,000 signatures/64 MiB in aggregate. Duplicate signatures share admission within a ticket. A ticket exceeding a retained-state bound is kept for retry and releases its observation budget; an unassignable oversized row or exhausted stream bound defers the affected scope. An incomplete observation never means that prior jobs are absent. The observation is discarded after this snapshot; action fences and final deletion proofs are unchanged.

Selected lifecycle plans share one snapshot-local backup-descriptor observation, one project event observation and one command-result stream for aged purges. Complete backup entry shapes are validated even when unrelated; the observation is the wanted keys intersected with the per-receipt backup index below (CL-355). The observation records exact generation manifest digests; the final deletion fence guards generation metadata, and the byte continuation pins/verifies the independent manifest and payload again before unlink. Rows are tokenized once for matching and admission; existing owned-row tokens are reused. Reference preparation reuses its already validated full payload from one bounded blob read through 4 MiB, rather than rereading/copying the SQLite value per 64 KiB slice. Larger rows retain the canonical header, exact SQL matcher and bounded UTF-8 stream. A token traversal-limit fallback uses exact SQL relevance to refuse only affected inventories; an unrelated deeply nested row cannot stop the cohort. Backup candidates/descriptors and shared history each have a 64 MiB retention bound; history keeps the existing 4 MiB row, 16 MiB per-ticket and 100,000-row scan limits. Backup observation is capped at 1,024 generations, 10,000,000 descriptors and 2 GiB of generation JSON. Exceeding a bound retains the bytes. Lifecycle observations never cross a preparation snapshot or pass. Existing pending Done-evidence jobs continue their durable byte intents without replanning them.

The preview reports pending, retained and already-missing object counts and logical sizes, plus retained reason totals. The command returns a byte receipt ID; a same-command retry observes the current durable byte receipt alongside its original semantic result. The byte receipt reports removed, retained, pending and already-missing objects and reasons. These logical pathname sizes do not measure physical disk savings or secure erasure. Manual purge has no timer; the optional project lifecycle policy below can purge aged closed tickets.

Byte deletion observes a bounded cohort of at most 32 receipts for one project, 16 MiB of receipt JSON and 100,000 object descriptors per maintenance call. Its receipts share one complete corpus stream, one media-authority validation and one exact backup-generation/manifest descriptor observation; their references and ticket/receipt fences stay independent. Reference inventories and reverse-index charges each cap at 64 MiB. Candidate admission prepares at most 256 objects or one second of verification, further reduced by its available descriptor budget; each writer chunk attempts at most 128 objects or 25 ms of unlink work. Unconsumed candidates and their verification pins are reused only inside this call, which admits at most 2,048 writer chunks or 30 seconds of continuation work (cooperative; a single verification retains its 60-second ceiling). Candidate pins are released before budgeting the next admission. At most two root/manifest pairs remain in the shared cache; active candidates keep their exact pairs through final validation. The original bounded TEMP change journal stays active between chunks, and each receipt validates its original fence immediately before its next chunk. Only this executor's receipt state, attachment availability and cleanup-outcome accounting bypass that journal while it exclusively holds the writer; they add no byte authority. Every intervening command and external writer remains fenced. A stale receipt defers independently while valid siblings continue. Every later maintenance call freshly prepares its cohort; no unchecked observation or verification is cached across calls. The normal four-times-elapsed production rest includes the whole cohort call.

## Storage failure replies (CL-362)

A `StorageSnapshotFailure` never reaches a caller as an enum number. `StorageFailureReport` (`Sources/ChecklistCore/StorageFailureReport.swift`) gives it a stable code, a plain reason and the next step in the message, and the same values in `details` (`reason`, `next_step`, `retryable`, `command_outcome`). | --- | --- | --- |
| `STORAGE_OPEN_FILES_EXHAUSTED` | `EMFILE` or `ENFILE` | Same command ID |
| `STORAGE_TEMPORARILY_UNAVAILABLE` | `EINTR`, `EAGAIN`, `EBUSY`, `ETIMEDOUT` | Same command ID |
| `STORAGE_DISK_FULL`, `STORAGE_FREE_SPACE` | No free space | After space is free |
| `STORAGE_ACCESS_DENIED` | `EACCES`, `EPERM`, `EROFS` | After access is restored |

Source hashing/regular-file reads precede the writer; content-addressed immutable objects are flushed before atomic metadata/receipt publication. A pre-commit identity check fences changed source files. Interrupted/unreferenced object copies are retained, and rollback never unlinks potentially shared/backup-retained bytes. Missing/pruned files stay explicitly unavailable. Destination digests include all project record payloads and its event boundary; rollback therefore refuses even a later note which does not revise its task. See [transfer](migration.md) and [commands](mcp-contract.md#one-way-project-transfer-cl-21).

### Verified-copy status and retained usage (CL-6 rework)

Settings → Storage shows the last verified backup and rehearsal, source/capture/verification times and copy paths. The restore confirmation shows source installation/store, backup folder, capture time (explicitly unknown for older manifests), project/record contents and unavailable-content reasons. Capture time is checksummed manifest metadata recorded while source writes are fenced; verification time is a separate observation. The current installation remains available throughout preview and candidate preparation.

Backup completion and disposable-restore completion atomically retain small status/usage receipts with their command result. Allocation is observed outside the writer through the verified root's no-follow descriptors: logical pathname lengths and allocated file blocks (`st_blocks * 512`), with hard-linked inode allocation counted once within a copy. The totals sum recorded copies at their verification times, exclude directories/staging/unrecorded copies, and do not recheck later moves/deletions. Hard links across copies and APFS shared extents can count the same blocks again. Exclusive physical storage and reclaimable space are **unmeasured**, never invented from logical lengths or allocated-block sums. Legacy receipts preserve known verification time but leave absent capture/path/allocation information unknown. A pre-upgrade rehearsal is identified separately; preparing a fenced restore copy does not establish native startup/reconnection.

Portable project exports recursively exclude structured credentials, session/grant authority and native endpoint bindings across records, profiles and events. Historical attribution and user file/prose content remain; the projection is not a secret scanner for user-authored content. Canonical store backups are unaffected by that projection.

### Compact capture backups (CL-270)

New snapshots use **manifest format 2**; the manifest change leaves the SQLite protocol
(3 when CL-270 shipped, schema 4 since CL-125), canonical records and managed paths unchanged. Format-1 snapshots remain readable, fully
verifiable and restorable. Older binaries and seed tools that only understand
format 1 cannot read new generations; preserve the older working bundle and its
backup until qualification finishes. There is no live-store format migration.

The top-level manifest metadata is unchanged. `objects` is a compact table with
`strings`, `contents` and `entries`. Each string is `[commonUTF8PrefixBytes, suffix]`
relative to the preceding string; the prefix ends at a UTF-8 scalar boundary.
A content row is `[shaStringIndex, size]`. An entry is `[pathStringIndex,
kindStringIndex, expectedSHAStringIndexOrMinusOne, expectedSizeOrMinusOne,
executableZeroOrOne, linkTargetStringIndexOrMinusOne, contentIndex,
authorityStringIndices...]`. Decoding reconstructs every original descriptor,
including nil expectations and exact authority strings. Unused contents, invalid
indices/UTF-8, over 500,000 entries and over 512 MiB of expanded strings refuse.
Intent `format` matches the manifest version. The seed harness understands both
versions and retains its full hash, membership and database checks.

Within a new backup, repeated regular-file content with a declared expected hash shares a hard-linked inode
with an already durably copied file in that same unpublished generation. Every
source pathname is read, hashed and checked for size/identity changes; declaring
an expected hash cannot substitute for reading it. No backup inode is shared
with the source store or another generation. Only newly created unpublished snapshot/restore stages batch durability: each
regular file is fsynced, then every touched directory is fsynced bottom-up, with
a same-device check, before creating the commit manifest/identity receipt. That
file's F_FULLFSYNC persists all prior fsynced data on the device (macOS fcntl(2)).
The commit file never precedes its payload/directory barriers. Same-command stage
resume repeats the root-directory and full-device commit barrier before publishing.
Ordinary live managed writes retain immediate ancestor/file flushes. Unsupported
or saturated hard links fall back to verified independent copies. Both complete
verification passes still compare the captured database inventory, every path,
hash, size, confined symlink and exact file membership. Restore copies every
path to independent candidate bytes and preserves executable mode and authority
fencing. A malformed table or corrupted shared inode cannot pass verification.

The object ceiling rises from 200,000 to **500,000 logical managed paths**, allowing
capture growth after the observed 170,344-path store. Other bounds stay unchanged:
logical published bytes bounded by free space since CL-340 (8 GiB before; duplicates still count), 128 MiB manifest,
524,288,000 bytes per managed file, 100,000 records and a shared 1,800-second
cooperative deadline covering capture, durable copying, both verification passes
and publication. Deduplication saves allocated storage and full-device flushes;
it does not disguise logical-byte accounting or claim exclusive APFS savings.

Storage gate: qualify the exact composed code on an owned consistent real-store
copy with all retained families/files, complete startup, the protected pre-upgrade
copy and migration rehearsal, agent backup with synthetic growth beyond 200,000
paths, both full verifications, durable publication, legacy/new-format restore
and startup of the fenced candidate. Record wall times, logical/allocated sizes,
manifest bytes and all ceilings; synthetic unit templates alone do not qualify
the installation. After installation the orchestrator must also observe a fresh
agent backup of the live store.

Known coverage still retires a selected detail restored from cache; only an already live-loaded detail can retain its display while its status/context refreshes (CL-254 L254c).

While a complete live interval waits for its page/context reads, a temporary window-local status read-ahead lane can consume newer complete coverage using its own observation cursor. It patches only newer known ticket statuses and retires older in-flight content epochs, including empty pages, before publishing. It never advances the applied cursor or certifies full context; the primary subscription still replays from its last applied cursor after failed/retired reads. The lane ends with its pending interval, query/window retirement, cancellation, reset or an error. This prevents a status commit made midway through slow reads from waiting for the entire page batch (CL-254 L254c).

CL-254 D254 defers the ticket Epic-choice page until the selected-ticket context is current. Its replies are fenced by the mounted picker, store incarnation and current selection before they can affect cache versions. Reopening a cached detail therefore does not start an auxiliary snapshot that can retire its display ahead of its authoritative refresh. Known changes still retire cached content; cached display never grants work or edit authority. Hosted fake-service coverage checks the read ordering without a wall-clock assertion; native detail budgets require exact-stage slot observations.

CL-353 import-preview replies/errors are conservatively expired on ticket purge regardless of size: their source identities need not match the imported ticket UUIDs. This retires the canonical cache without changing external import sources, backups or exports.

Any ticket purge conservatively expires all canonical operation error snapshots, including historical errors retained after a successful retry: private diagnostic text need not carry a matching ticket UUID. Operation identities and intent digests remain reserved.

UUIDs already accepted by the pre-existing backup FIFO keep that journal’s original intent, authorization generation and direct execution/replay route; they are not reaccepted as generic operations. A per-principal/UUID admission lock serializes the routing decision and durable acceptance across both journals, then releases before semantic/file execution. Different command IDs and ordinary reads do not share that lock.

Whole-project policy_preview/policy_propose/policy_apply, status_retire and relation_import also return operations. Uncapped media_publication_preview, media_type_adopt/media_type_retire, media_context_approve and media_round_finish/media_round_successor do likewise. project_edit/project_settings_save become operations when brief or pinned_decisions can trigger project-wide context propagation; settings saves with policy/policy_proposal_id are also operations. Cosmetic project edits and short no-copy media leases remain synchronous. Media publication-preview results retain the original read envelope without an added command_id; their canonical journal stores one semantic payload, not a nested envelope.

CL-321 backup lookup evaluates requested keys in bounded one-key chunks against an immutable observation of the shared per-receipt index. It does not allocate a wanted set or a URL for every key/copy pair; large selections therefore keep the same lookup working-set bound as small selections. Backup alternatives are visited lazily until an exact manifest and payload verify, including fallback from missing or corrupt older copies. Candidate payload pins survive their bounded admission, including its writer chunks; the 256-candidate ceiling is reduced by the available file-descriptor budget described below. The existing receipt-count, receipt-byte and entry-count limits remain. The 64 MiB cleanup observation budget covers additional generation descriptors and candidate lookup state, not the separately shared receipt cache or total process RSS. A cache update may copy shared Swift collection storage while an older observation is pinned.

Every backup-index build failure retains bytes with `backup_index_error:<error-code>[:<reason>]` in the durable object reasons and aggregated receipt summary, and emits that same reason in the TicketCleanup diagnostic log. It cannot become a silent `backup_authority_unavailable` hold. These reasons preserve the existing completed-purge retry on a later completed generation; they do not grant unlink authority or start polling. The active capture barrier, same-cleanup reference rules, manifest/payload identity pins and final no-follow unlink fences remain required. No storage schema, backup format or migration changes. Service startup attempts to raise its process's `RLIMIT_NOFILE` soft limit toward the hard limit, capped by `kern.maxfilesperproc`; this is extra headroom, while admission remains safe at the inherited soft limit.

Each verified regular-file candidate retains one open live-file descriptor and one verified backup-payload descriptor; a captured link retains its no-follow identity and recorded link text instead of a payload descriptor. A backup generation shares one manifest descriptor and one snapshot-root descriptor with its pinned ancestor chain across candidates. The cohort caches at most two root/manifest pairs; an admitted candidate retains its exact pair through final validation even if that pair leaves the cache. Root traversal and payload-parent descriptors are temporary and close when their operation ends. If root-ancestry pinning fails, both the already-open root and every descriptor in the partial ancestor walk close before the error returns. These pins remain through final writer checks of the open file's device, inode, length, modification time and change time against its current no-follow pathname, and the named backup root, manifest and payload. Candidate pins are released at the admission boundary after its candidates are decided (or when the preparation is discarded), before budgeting the next admission; shared cached root/manifest pairs survive only until eviction or the end of this cohort call. No verification pins survive into a later maintenance call.

Each admission computes its reserve once from the generation-root paths already present in the immutable manifest observation, without enumerating candidate-copy alternatives. The reserve covers 32 descriptors for ordinary service work, the maximum observed root depth capped at 64 (64 if no root is observed), and 12 temporary verification descriptors. Before admitting another candidate, cleanup counts free descriptor slots below `min(RLIMIT_NOFILE.soft, 4096)` against that reserve. A depleted budget ends admission with remaining objects pending, rather than treating descriptor exhaustion as missing backup bytes. The count and one-second verification limits, 128-object/25-ms writer chunks and ordinary cooperative yields still apply; hashing remains on the read lane.

Backup-copy verification failures retain their cause as `backup_copy_unverified:<error-code>`, including `POSIX_<errno>` for system errors, rather than collapsing every failure to `backup_copy_unavailable`. `EMFILE` (`POSIX_24`), `ENFILE` (`POSIX_23`), `EINTR` (`POSIX_4`) and the verification deadline are retryable on the next ordinary byte turn without a new completed backup. Other failures remain explicit holds and retain the completed-purge generation retry rule. Existing policy-v2 Done-evidence and purge receipts, pending or completed, receive one generation-independent retry of old `backup_copy_unavailable` holds, tracked by the internal `ticket-cleanup-copy-retry-seen:<receipt-id>` marker. That retry rebuilds current authority and verifies bytes again; an object with a permanent mixed hold is never reset merely because it also has an old unavailable or transient reason. This adds no per-file polling timer or deletion authority.
