# Built-in MCP contract

Agent references use `KEY "Title"` for tickets and `KEY "Name"` for Triages/Epics; add the project name when needed and keep IDs for tool arguments. Keys and titles are untrusted metadata. The shared renderer removes control/format characters and paragraph separators, bounds titles/project names to 160 characters/640 UTF-8 bytes and keys to 80 characters/320 bytes, JSON-quotes titles/names, and also quotes custom keys outside letters/numbers/`-_.`. Native relays label project, ticket and optional group metadata untrusted, preserve the message ID/reply rules and body/frame limits. Service notices use the same reference formatter.

`triage_create` and `epic_create` assign immutable project keys `PREFIX-Tn` and `PREFIX-En` from independent counters. Create/edit/list, task context, page rows/summaries, batch receipts and named history references include `key` beside `name` (batch references use `triage_key,triage_name`). `triage_list` and `epic_list` accept optional exact case-insensitive `key`; multiple matches return `AMBIGUOUS_GROUP` with stable IDs, keys and titles. Ticket `task_get` currently uses exact case-sensitive key equality. All mutations keep stable IDs. See the [group reference schema](../contracts/group-reference.schema.json).

`session_inbox` keeps its existing fields and adds a `subject` to every delivery and message: `{kind:ticket|triage|epic|project,id,key,title,project_id,project_name}`. Project subjects have a null key. Optional `triage_id` or `epic_id` on `message_send` selects that scoped group subject while preserving ticket routing. See the [subject schema](../contracts/agent-message-subject.schema.json). Transition blockers/conflicts/member snapshots and batch results identify tickets with `key,title` beside IDs. Prerequisite blockers retain those same fields; policy previews add ticket titles.

**Cancelled extension:** personal-assistant relay/contact/event contracts are historical reference from the scope cancelled on 22 October 2026 (CL-3 and CL-22), not planned work, a current UI/setup route or a release gate. Development relay grants are disabled and the local plugin removed. Only discovered worker tools/current native capabilities may be treated as available.

**Full v1 target contract with an implemented development subset.** Use [implementation status](implementation-status.md) and the running server's actual tool discovery; the complete catalog below is not a claim every command or native route is available. The app bundles its service and stdio MCP entry point. UI, MCP and diagnostic commands share authoritative domain handlers. MCP supplies durable task data/control; qualified provider adapters supply native session delivery. [Domain semantics](domain.md) are normative.


### Native communication advertisement

`service_info` retains `native_push=false` and adds `native_routes`, the build-level [route table](integrations.md#native-communication-route-qualification). Each row has stable `id`, `provider`, `direction`, `title`, `status`, `qualified`, `reason`, `qualified_versions` and `qualification_receipts` and `qualification_scope`. Unavailable rows have `status=unavailable`, `qualified=false`, empty version objects and empty receipt arrays. Only `claude_idle_wake` carries CL-5's independently reviewed pass: `status=qualified`, `qualified=true`, pinned recorded versions/receipt aliases and `qualification_scope=recorded_versions_and_configuration_only`. That row does not check a current recipient, qualify a new build or qualify any child/relay route. `native_push_status` explains MCP pickup and the qualification limit. Enrollment, an individual transport/parent receipt and simulated acknowledgments cannot promote these rows. The ticket communication disclosure uses the same catalog. Per-message queued/held/transport/acknowledged states remain separate observations, not route qualification.

### Native resumption recovery

`service_info` and `session_inbox` include `data.native_recovery`, an array scoped to the caller's own verified worker session and current project grants (empty for other callers). Each project's latest verified resumption has a stable `summary_id`, `project_id`, `session_id`, `native_closure_ref`, `closed_at`, `resumed_at`, `released_claims`, `recovery_required_orchestrations`, `fenced_notices`, `claims_restored:false` and `reading_is_acknowledgment:false`. It is available on the first read, persists across repeated reads, and supports conversations that resumed before this build without a write or acknowledgment.

Released claims identify `attempt_id,task_id,key,title,released_at,reason,recovery_step`. Orchestrations identify `triage_id,key,title,orchestration_id,expected_revision,orchestration_connection:recovery_required,recovery_required_at,recovery_step`; fetch the current revision before a later mutation. Fenced notices include the old `delivery_id,message_id,created_at,subject,body,state:fenced`. The summary is informational; current ticket eligibility and revisions still control ordinary claims. Other conversations cannot read these recovery facts or receive the notices.

Verified native resumption creates distinct current-generation receipts for unacknowledged notices on the same message, linked by `resumed_from_delivery_id` and `resumed_native_closure_ref`. The original deliveries stay fenced; owner-disconnected, restore-quarantined, acknowledged and addressed deliveries are not revived. Reading the summary or a new inbox receipt is neither acknowledgment nor work authority. An explicit `message_ack` must name the new current-generation delivery. See [closure and resumption](work-authority.md#confirmed-native-conversation-closure).

### Bounded Tickets pages

`task_list` applies the authorized project predicate and SQL limit before decoding canonical task rows. Default worker/assistant calls keep `tasks,total` and add `has_more,next_cursor,previous_cursor`; they require one exact granted project. Continuations bind caller, current grant/session generation, store incarnation, locale, complete query/order/limit and relevant project event coverage; changes refuse with `CURSOR_RESET`, rather than silently skipping or repeating rows. Tokens reveal neither offsets nor global sequences.

`task_list` filters by current `triage_id` members, primary `epic_id` and exact case-insensitive ticket `keys` (at most 200). These filters combine with AND and with `text`, `status_ids` and `archived`, before pagination. An empty `keys` array selects no tickets. Foreign-project group IDs are refused. `triage_list` accepts an exact `triage_id` alongside its existing exact case-insensitive `key` filter. Both lists accept `fields`: each row contains only those top-level full-row fields plus mandatory `id`, `key` and `revision`. An omitted or empty `fields` array returns all fields. Unknown field names return `INVALID_INPUT` with valid names sorted in the message and `details.valid_fields`. Page metadata stays outside rows. Owner `task_list view` behavior and unprojected app reads retain their defaults.

The trusted owner may supply a closed `view` object (required `surface` (`tickets|overview|archived|trash`), `status_filter,tag_filter,group_by,order_by`; optional `tag_ids,tag_mode,planned_assignee,actual_assignee,epic_id,triage_id`) for a separate bounded Tickets page, and explicitly omit project_id for All Projects. Workers/assistants cannot supply that field, including a false or malformed value. The owner page contains ordered task rows, ordinary IDs, bounded Triage summaries/page-member IDs, truthful scoped/matching counts, continuation/coverage tokens, taxonomy/sidebar metadata and a maximum-three Overview request preview with its separate total count. Page omission never means deletion from the full snapshot index. Pagination counts visible list units, including Triage headers and member appearances; a task may appear in multiple Triages without inflating the distinct matching-task count. A header-only group-name/purpose search is preserved even when current facets match no member.

### Saved list filters and bulk changes

Owner Tickets views accept tag IDs with `tag_mode=any|all|none` (empty IDs mean no tag restriction), planned assignee (`all`, `unassigned`, `human`, `agent` or an actual worker session ID), actual assignee (the current active attempt's session ID, `human`, `agent`, `unassigned` or `all`), and Epic/Triage IDs (`none` or `all` included). They combine with status and search. Inactive or missing attempts count as unassigned. Filter Triage choices use separate slim `filter_triages` metadata, so pagination never hides a filter option. IDs stay project-scoped; identical names are disambiguated in All projects. Personal saved views are local preferences, not project settings; see [view precedence](interface.md#capture-and-lists) and the [view schema](../contracts/ticket-view.schema.json).

`task_bulk_edit(project_id,command_id,tasks,changes,preview=true)` selects 1–200 distinct `{task_id,expected_revision}` rows and exactly one change kind: `status` with `action=queue|defer|block|cancel|reopen` and optional `changes.reason` (at most 4,000 UTF-8 bytes, required and nonblank for Cancel/Reopen); `tags` with `add`/`remove` ID arrays; `assignee` with `planned_assignee` and an optional assignment reason; `epic` with a required nonblank Epic ID; `triage` with an ID and `action=add|remove`; or `archive` with `action=archive|unarchive|trash|restore`. Agent assignment requires an eligible worker/provider; personal assistants cannot be selected. Whole-ticket human assignment follows Needs You → Your tickets. Tags are independent of providers. Bulk status reasons are validated once before row checks; a missing Cancel/Reopen reason returns plain `INVALID_INPUT` without changing any ticket. The reason reaches each row’s transition history. An explicit `changes.assignment_reason` reaches every changed row and its history. First assignment from an unassigned ticket needs no reason unless the agent policy override rule requires one; changing an existing different planned assignee (including clearing it) requires a nonblank reason. No assignment reason is synthesized; preview reports each ineligible row and apply remains atomic. Bulk archive never requests file cleanup. See the [edit schema](../contracts/ticket-bulk-edit.schema.json) and [synthetic example](../examples/ticket-bulk-edit.json).

Preview runs the actual guards in rollback-only savepoints and returns `affected_count` plus every `rows[{task_id,key,current_revision,eligible,code?,reason?}]`. `preview=false` rechecks every row and applies atomically; `BULK_CONFLICT` contains all blocked rows and changes nothing. The app may explicitly submit the eligible subset with a new command ID. Active claims block bulk edits. Ordinary status actions keep Triage membership under the [Triage orchestrator contract](triage-orchestrators.md); they cannot enter protected work/review/Done states. Existing agent-edit/project/owner limits remain authoritative. Each changed ticket gets normal history plus a bulk event. The durable command result includes row before/after values/revisions, membership snapshots and ownership/review progress fences; no new unregistered storage family is added.

`task_bulk_undo(project_id,command_id,original_command_id,tasks,preview=true,reason?)` uses an applied bulk-edit receipt from the same caller principal/project and supplied current revisions. It is a new compensating command, with the same atomic preview/apply behavior. A claim or intervening ownership/review/request progress leaves the row unchanged. Changed fields still equal to the receipt's after value can return to their before value; newer values are retained. Tag compensation preserves unrelated tag edits. Triage compensation checks this ticket's current membership snapshot, uses the ordinary [Triage membership rules](triage-orchestrators.md#product-rules) (one Triage per ticket; only the orchestrator or the owner adds to an orchestrated Triage) and records a new membership interval rather than restoring a historical claim. Status compensation records “Undo of bulk change <original command id>”, appending optional caller `reason` after a colon (the combined reason is limited to 4,000 UTF-8 bytes). It still follows ordinary status guards and membership rules: the ticket keeps its current Triage unless the restored status is Done or canceled, and the compensation cannot restore a protected status or reattach an earlier Triage. Assignment compensation revalidates current eligibility and records new provenance. Notes and history are retained. Archive compensation never recreates cleaned file bytes; its result says so. The command journal's ordinary retention also bounds Undo: a missing/pruned receipt returns `UNDO_UNAVAILABLE`. `UNDO_CONFLICT`, `CLAIM_CONFLICT`, ordinary permission/policy errors and per-row `REVISION_CONFLICT` appear in previews; apply wraps blockers in `BULK_CONFLICT`. See the [Undo schema](../contracts/ticket-bulk-undo.schema.json) and [example](../examples/ticket-bulk-undo.json).

## Pending human-answer observations on ordinary results

A successful authenticated Codex worker command can add `data._checklist.pending_human_answers` with `schema_version=1`, `status=pending_pickup`, `channel=authenticated_tool_result`, `native_codex_wake_qualified=false`, up to eight `items`, and `has_more`. Each item names the authorized project/task/request/response/form/message and this exact recipient generation's delivery ID/state, and includes `project_name,task_key,task_title`. The bounded text notice names the ticket before the UUID tool selectors and retains UUID validation. No answer text, question title, answer file path or reusable routing authority is included. The current form revision/state is separate from the answered form revision so an old response never silently answers a replacement form.

This is a **live observation**, added after durable command receipt persistence and refreshed on replay. It is not part of the semantic command result stored under `command_id`; retries do not create an answer or continuation again. A notice-query failure returns a bounded unavailable notice without hiding a successfully committed command. Reading a result never acknowledges a delivery. An explicit recipient `message_ack` after actual consumption remains necessary; ended/revoked/rotated sessions cannot consume another generation's copy.

The metadata is inside standard `data` so clients that unwrap the service envelope retain it. The MCP adapter also emits a fixed, bounded text pickup notice alongside the complete JSON/structured result. Clients must preserve the reserved `_checklist` metadata when adapting command results. Workers read the named exact request/form, acknowledge their own delivery after reading it, and reconcile current authority and waiting tickets before continuing. No hidden polling, schedule, model invocation or native Codex wake is introduced. An idle client still requires an ordinary authenticated call or explicit inbox pickup; route qualification remains CL-37/CL-83 work rather than a fabricated event capability.

## Current ticket status reason

Ticket projections in `task_get`, `task_context.task`, `task_list` and owner ticket/group lists include optional `status_reason: {text, actor, actor_display, at}`. `actor` is the authenticated event principal; `at` is the event timestamp. It comes from the latest status action, including `task_transition`, `work_release`/`batch_release` and `work_recover`, and is omitted when that action has no nonblank reason. Notes, edits and other history do not replace it. A later status action without a reason clears it; history retains every earlier reason. Legacy events without a captured display name use the current scoped session label when available, otherwise You for owner actions or Agent, while preserving the exact actor. The projection reads at most one decoded status event per ticket through the existing project/entity index; it never loads a project event corpus. `task_list.fields` can explicitly select `status_reason`, including on empty results. No new write field, schema version or migration is introduced.

The per-ticket status event inventory is `task_transitioned`, legacy `status_changed`, `status_remapped`, `work_claimed`, `work_released`, `work_submitted`, `claim_revoked`, `work_released_native_closure`, `review_requested`, `review_reject`, `human_approval_reject` and `task_completed`. Every kind uses the same nonblank-reason rule, rather than a separate allowlist of reason-producing events. `work_recover` writes its mandatory reason on `claim_revoked`; `status_retire` writes a reasonless `status_remapped` for each moved ticket, which also clears old-format releases without a target status ID. Batch operations and Triage transitions use these same per-ticket events. Agent/human passes that change the ticket to Done and release-set completion emit `task_completed`; a reject returns the ticket to Queued. Every verdict ends the review claim: `evidence_missing`, `not_run` and `blocked` with `blocked_on:"implementation"` return the ticket to its implementing holder as Active (Queued for any eligible implementer if that holder is unavailable); `blocked` waiting only for reviewer-side input keeps Review and returns the request to any eligible reviewer. Archive/unarchive, trash/restore and takeover do not change its status ID and do not replace its status reason.


## Scope, authority and retry

- Workspace agents use `project_resolve(workspace_path)` with the caller's actual open workspace. Never use the server directory or selected app project. Return `registered`, `unregistered`, `ambiguous` or `root_mismatch`, with no writes. Enrollment/relocation rejects canonical overlapping writable project roots in v1.
- Bundled CLI/MCP bootstrap connects the actual observed native host/session/workspace automatically under current project grants. Service authentication pins signed native host PID/kernel start time, execution domain and actual kernel cwd. Codex thread IDs are host-exported observations, not signed exact-thread identity. Review claims exclude recorded contributor principals/installations/sessions, including prior/delegated contributors, while allowing a genuine separate non-contributor subagent on the same host. Changing a contributor’s label or parameters is not independence. Claude registry PID/session/workspace/socket are independently cross-checked where used. `session_register` updates only the already bound session where discovered; caller fields never create a verified assistant or a push capability. Worker identity/status/current-prior attempts and recovery are ticket-attached; an internal session registry is not a user-facing catalog. No assistant settings/sidebar/grant UI is active and no worker Settings pairing is required.
- A native conversation whose actual folder is not an active registered project gets a limited start from `checklist mcp` and `checklist tools`, because a user-scope registration starts in every folder. The same native verification as ordinary bootstrap is required: Codex host-exported `CODEX_THREAD_ID` or the independently checked Claude session registry, with the actual host/process/workspace binding. Before creation there is no project enrollment, selected project or stored credential. Discovery lists `service_info` and `project_create`; `service_info.data.connection` remains `{connected:false,state:"project_setup_required",message}` until setup succeeds. `project_create` creates only that verified workspace and atomically enrolls/grants its calling worker as described below. The same MCP connection then completes bootstrap and sends `notifications/tools/list_changed` once, exposing the full granted tool set without restart (`tools.listChanged: true`; resources stay false). `checklist call project_create` from the same native conversation/folder uses this flow too; later calls resolve the new binding. Other `call` methods and `connect` still require a registered project. Workspace-less assistants cannot create projects. Permanent bootstrap errors, for example `CONNECTION_REVOKED`, `BINDING_CHANGED`, `WORKSPACE_MISMATCH` or `NATIVE_ROUTE_MISMATCH`, still stop `checklist tools`, `call` and `connect`; `checklist mcp` instead starts with `service_info` only and returns the same error from every other tool, without a retry (CL-346). The separate [Claude spare-process registry race](integrations.md#claude-desktop-spare-processes) has a 10 s window for new attempts at intervals of at most 250 ms, with whole-bootstrap retry budgets that end the retry path by 20 s; only `mcp` can then start unconnected with `service_info` and one lazy bootstrap attempt per tool/resource request. Successful recovery sends the same one-time catalog-change notice.
- Service availability (CL-346): `checklist mcp` never exits because the service does not answer at startup (`OUTCOME_UNKNOWN`, `SERVICE_UNAVAILABLE`, a store upgrade in progress or a restart). Its startup connection attempt has a reply budget of 2 s for each bootstrap attempt and for the session check, so initialize answers in about 2 s even while the service stalls (Codex's default MCP startup limit is 10 s); in the Claude registry race the same cap ends the `mcp` startup path by about 12 s. A startup reply timeout counts as a service that does not answer. It finishes initialize and lists `service_info` only, and its instructions and `service_info.data.connection` (`state:"service_not_answering"`) say that it is not connected yet. Catalog lists answer at once; each `tools/call` or `resources/read` then waits for the service with backoff (0.25 s doubled to at most 2 s, up to 60 s plus the last attempt), repeats the complete native bootstrap and session check, and sends `notifications/tools/list_changed` once when it connects. When no listener answered and launchd reports this installation's own job (label = its Mach service name) not running, the wait starts it once through the same on-demand XPC start as the CLI; launchd keeps one service, and a test slot is never started this way. After the bound the call returns `SERVICE_NOT_READY` with `details.retryable:true` and `command_outcome:"not_sent"`; the next request waits again by itself. No manual reconnect is needed.
- Concurrent tool calls (CL-352): one `checklist mcp` process runs the tool calls of its conversation at the same time. A call that waits for the service (a socket reply or a delegated installed-CLI child) does not hold later calls; for example a fast `service_info` answers while a slow command of the same conversation still runs, and each call gets only its own reply. The shim reads its connection state (bound client, identity, workspace and native context, catalog, update and setup notices) one call at a time and then sends each request on its own connection. It passes arguments and `command_id` unchanged, so idempotency and every identity, workspace and native-context check stay the same. Calls that arrive while the service does not answer share one wait and one connect attempt at a time. Limited, setup and not-connected states keep the earlier serial path. The service still orders writes on its own writer queue.
- A Claude conversation that its host resumed in a new process (same native session ID) reconnects through the same bootstrap after the verified closure of its earlier process. The service verifies the new process and gives the session a new credential and authorization generation; it never carries over the old claims, attempt tokens or queued deliveries. Errors: `NATIVE_SESSION_MISMATCH` while the earlier process has no verified closure, `NATIVE_CLOSURE_PENDING` while its work still stops, and `CONNECTION_REVOKED` after an owner disconnect.
- The native owner app exposes ticket-scoped `connection_revoke` and `connection_allow` with `project_id`, `session_id`, exact `installation`, `expected_revision` and `command_id`; the app also supplies `task_id` for ticket history. Neither is an agent tool. Disconnect fences authorization and returns eligible claims to Queued with history, retaining source/writable-child reservations for explicit recovery. Allow again refuses while retained claims remain, then permits a verified native bootstrap with fresh credentials; old claims and deliveries stay fenced. Both actions are revision-checked and replay their durable command receipt. No verdict, completion, acknowledgment or model launch follows.

- Project tools other than `project_create` require `project_id` and check every referenced object against its authenticated project grant. A foreign ID returns no foreign content. Workspace agents use their actual workspace/session binding; an assistant uses a separately enrolled assistant connection and explicit selection from its granted projects, never an invented workspace. Owner aggregate queries use their separately authenticated app channel.
- Writes require UUID `command_id`, deduplicated by durable installation principal and canonical payload. Same intent returns the original semantic outcome/current authority; different intent returns `IDEMPOTENCY_CONFLICT`. An unknown transport outcome is reconciled with that ID, never retried as a new mutation. Replayed/released claims never resurrect credentials; valid authenticated reattachment rotates still-live authority.
- A direct `checklist call service_info '{}'` skips the redundant tool-catalog preflight because `service_info` is a known read in both limited and full catalogs. Native bootstrap, optional expected-session verification, service caller/revocation/schema checks and stale-client refusal remain active; all supplied parameters reach the service. No catalog, grant or response is cached. Other direct methods and MCP discovery keep their existing catalog checks.
- Optional call timing: `CHECKLIST_TIMING=1 checklist call …` or `CHECKLIST_TIMING=1 checklist mcp` requests diagnostic timing outside tool parameters. Each service reply carries top-level `_checklist_timing` with `request_id`, `queue_wait_ms`, `bootstrap_verification_ms`, `execution_ms`, `encoding_ms` and `total_ms`. These monotonic milliseconds are live observations, never durable command receipts or authorization. Queue wait includes coordinator and off-queue dispatch admission; verification includes bootstrap/coordinator routing and current caller checks; optional `route_lifecycle_ms`, `route_native_identity_ms`, `route_current_session_ms` and `route_registration_receipt_ms` identify measured subphases of that verification, so they must not be added to it again; execution covers the routed Core handler. Encoding measures the semantic JSON once; total ends before the small timing trailer and XPC delivery. Deferred change-wait time appears in total. Client stderr has `ChecklistTiming` JSON lines for preparation, IPC round trip (including the service timing), CLI setup/total and MCP setup. IPC separates `connection_setup_ms` (local connection/proxy preparation) from `send_to_reply_ms` (which includes the lazy XPC connection/admission); neither is a pure wire-connect measurement. CLI `cli_call` separates argument decoding, bootstrap/session binding and the command. CLI `cli_setup` reports `main_entered_uptime_s` and the separate `instance_ms`, `arguments_ms`, `shim_capture_ms` and `bridge_ms` phases. Only `mcp` captures replacement/signing state, before native discovery; one-shot commands do not initialize that discarded monitor. The main-entry timestamp lets an external launcher using the same monotonic uptime clock measure spawn-to-main separately from application work; that interval includes loader/runtime initialization and host scheduling, not just dyld CPU time. Direct CLI calls retain bootstrap/session verification and let the service validate the requested command against current grants/schema, without a redundant full-catalog preflight; MCP advertised-tool and unregistered-workspace restrictions remain. Service stderr correlates post-reply `service_hooks` time by request ID and method. Its `service_hook_phases` observation separates change-wait callbacks, native dispatch, storage wake planning and work-health work; monotonic start times identify which serial interval admitted later requests. Storage deadline discovery runs on a coalesced background read lane; `storage_wake_ms` measures enqueue/apply work and `storage_wake_plan` reports its separate read duration. Timing is absent by default; stdout remains JSON or MCP frames. Refused XPC peers cannot receive service-side diagnostics; the client still reports its transport duration. Startup/loader time and complete MCP initialize latency require an external runner. See [the measured source costs and installed-check limit](implementation-status.md#per-call-agent-overhead-cl-262-source).
- New-process latency qualification (CL-361): while disk work is active, 20 new `checklist call service_info '{}'` processes must reach a p95 under 1 s with at most one reply above 1 s (the strict maximum of 1 s moved to CL-375), including process creation, loader/runtime startup, native bootstrap, connection/admission, command execution, reply and output. Record each monotonic spawn-to-exit wall time, exit status, start/end `sysctl -n vm.loadavg`, p95 (nearest rank, the 19th sorted sample of 20) and maximum; do not subtract startup or scheduling time to turn a failure into a pass. Run from the actual session/workspace environment, retain timing stderr separately from JSON stdout, and use at most 20 new probes per measurement. Measure the same probes while 10 concurrent `cleanup_job_list` requests run, including a fresh connection and scoped `task_get`. Busy-disk operations (cleanup preview, live-size archive with cleanup, executor or slot creation) need their own observed start/end receipts. A local `checklist service status` diagnostic issues unenrolled `service_info` without bootstrap or credentials and can isolate transport, but it does not qualify the authenticated call target. Record process/loader, signing/setup, connect/admission, service queue, verification, execution and reply costs separately where observable; the IPC residual includes lazy connection admission, delivery and client scheduling and must not be labeled pure wire time. Missing phases remain unmeasured. Source tests and a warm connection never establish this per-call installed gate.
- Accepted long commands return a durable operation acknowledgment promptly, targeting about one second, before their file work or scans run on the service's concurrent command-operation queue, separate from the storage-maintenance queue, so a cleanup scan never delays another operation. Read operations take no backup write admission: a backup capture never waits for them, and they run during a capture. Write operations wait while a capture locks writes, like synchronous writes. Short commands retain their synchronous replies. Callers with a bounded lifetime may set `ChecklistClient.call(..., replyTimeout:)`; expiry returns `OUTCOME_UNKNOWN` with the original command ID and does not cancel service execution. Connection interruption/invalidation also ends the wait with an unknown outcome. Bootstrap and service-start probes keep separate bounded waits. Preserve the original method/input/UUID and explicitly read `operation_get` or `command_status`; no model polling, schedule or new execution runtime is started. See [long command operations](#long-command-operations-cl-353).
- During offline store upgrade, the bundled transport can return `STORAGE_UPGRADING` with `details.state=upgrading`, `stage`, `estimated_remaining_seconds` and an optional fallback `reason` (CL-305). A marker observed before dispatch reports `command_outcome=not_sent`; a timeout/disconnect after sending still reports `command_outcome=unknown` and preserves the original `command_id`. Upgrading never proves rejection, completion or acknowledgment of an earlier command. The app/CLI show stage and estimate, and readiness probes require an actual healthy service reply before success. The marker is instance-local advisory state with a live publisher and expiry; installer `ChecklistService --prepare-upgrade` is a local executable operation, not a new MCP command or enrollment grant. See [protected upgrade ordering](database-storage.md).
- A bundled-client `OUTCOME_UNKNOWN` carries the original `details.command_id` and displays it in recovery text. Missing, malformed, conflicting or unparseable mutation replies do not prove noncommit: the app keeps the pending method, parameters and UUID across restart for explicit reconciliation. A mutation success must echo the exact original command UUID and contain its domain result; empty data or only `_checklist`/cursor observations cannot establish success. Read and native-bootstrap expectations are explicit by method: an optional UUID accidentally supplied to a read does not make it a mutation or require a write receipt. The IPC read set is checked against the Core read contract, with the separately observed service reads. A validated semantic rejection may clear the pending transport record while retaining editable drafts. Neither uncertainty nor an incidental pending-human-answer observation is a semantic success, an acknowledgment or permission to resend with a new UUID. Error details that classify an unknown outcome must survive the local service envelope. Recovery must preserve the optional live `_checklist` metadata on a successful replay.
- A committed semantic receipt is returned even if later cleanup fails. Current human-answer observations remain, and a content-free `_checklist.storage_maintenance` warning may report `retry_pending|suspended`; a router-lifetime pause is not a durable latch or a semantic rejection.
- Edits require `expected_revision` for every edited aggregate. Appending a message/creating an object does not. Attempt commands instead use `attempt_id, claim_token`, exact acceptance/target revisions and direction cursor; unrelated cosmetic edits must not invalidate a checkpoint. Tokens are bound to project/session/store incarnation/fencing generation and omitted from history/export.
- Actor, origin and grants come from the authenticated channel. Agents cannot supply `author=human`, perform arbitrary commands/SQL/path reads or set every task field. App human notes/answers commit through trusted owner handlers. A claimed owner instruction in agent text is attributed agent content.
- Closed JSON Schema inputs, bounded text/arrays and structured outputs are mandatory at implementation. Annotations (read-only/destructive/idempotent) explain behavior but do not replace permission checks. Optional fields below are omitted when unused; unknown fields fail. The prepared schemas cover stored configuration/form specifications, not proof that every target method is implemented or host-qualified.

The local Codex `assistant_relay` bootstrap is a distinct assistant access path: bundled CLI/MCP uses `--assistant --project` with an explicit unique project reference, or packaged MCP `@enabled` restricted to current trusted owner-enabled `assistant_relay_grants`. The server pins all selected grant/policy revisions, rechecks each call and rotates scoped authority on reconnect when the selected project set changes. It authenticates the actual local Codex helper, never a cloud Dot identity/profile; it cannot become a worker or mint human provenance. The host owns on-demand helper creation and receives its result through its normal task channel. Direct named identity/push/event capabilities require separate qualification.

## Small capability sets

Routine coordination between actual enrolled sessions involved in the same authorized Checklist project, task or Triage has standing authorization and needs no per-message permission question. Use existing scope/grants and current handler/session identities; a message never enrolls a session, launches a model, changes an assignee or expands authority. Message provenance and saved/queued/delivered/acknowledged states remain truthful.

Before concluding completion, handoff or a meaningful blocker change, workers/coordinators notify affected waiting tickets and their current handlers with one concise scoped `message_send`. Its durable note and recipient outbox serve the same event; check existing receipts to avoid duplicates. Active tickets can be waiting, and a source status change or final source-chat reply is not a cross-ticket notice. This is a [shared handling rule](policies.md#involved-session-coordination), not automatic resumption, reassignment, a new subscription or proof of acknowledgment.

For an explicit session notice use `recipient={"kind":"session","session_id":"<verified scoped session>"}`. Inspect returned `deliveries` and confirm an entry has that exact `recipient_session_id` before claiming a recipient notification was queued. `saved_for_pickup` with no delivery means history was saved; `queued` means an actual recipient delivery awaits pickup/transport. Only that recipient’s explicit `message_ack` after reading establishes acknowledgment. No receipt alone proves native push or model resumption.

The coordinating host owns resuming an authorized existing idle subagent through its supported host operation; a Checklist queue receipt does not do that. Preserve the original note/delivery for pickup and avoid duplicate sends. Work-health assessment uses current-attempt and accepted-child progress, separately from liveness and known waits, rather than the ticket edit timestamp alone. Silence grants no recovery or reassignment authority. The local service now provides configurable advisory health checks and correlated late-reply reconciliation; system requests have an honest exact-session MCP-pickup fallback and native wake is unavailable. See [work health](work-health.md); no model runtime or assistant integration is added. See the [coordination procedure](../skills/checklist/references/coordinate.md).

The shared workflow composes compatible changes from one orchestrator's Triage into one application target and qualifies selected cases together using the normal build graph, followed by independent per-ticket Review targets. Existing active claims can remain in the handling group without release/reclaim; they are not retroactively frozen batch claims. Shared evidence does not transfer verdicts or bypass exact-target gates. Routine harness corrections within the authorized scope need no renewed coordinator approval, and compiler release is not work release. See the [implementation and qualification path](../skills/checklist/references/coordinate.md#implementation-and-qualification); this guidance does not introduce a shared-target MCP command.

Discovery exposes tools appropriate to the caller's role and project feature use; a caller cannot gain permission by manually guessing a hidden tool name. `service_info` returns its supported tool names/limits and unsupported native-delivery capabilities. Refresh discovery on grant changes where supported; otherwise denied calls explain how to reconnect.

Do not replace this with one unbounded “manage everything” tool.

## Result and common types

Read-method classification is authoritative in `ChecklistContracts.CommandMethods`, consumed by Core catalog/dispatch and IPC reply validation. The [shared module boundary](shared-modules.md) preserves the existing wire values, principal-scoped retries and service-only read distinction; it does not create a remote API.

`connection_bootstrap` for a fresh CLI/MCP transport revalidates an existing committed automatic connection without taking writer admission, including its native identity, workspace, credential and current registration generation. Its reply includes current `write_admission`; ordinary calls then use the read and queued-write protocol below. Bootstrap that must create, repair or rotate registration or grants still defers until immediate writer admission is available. A prepared enrollment or queued registration never grants authority.

Success has `data`, opaque `event_cursor`, `command_id` for writes, `revision` for an aggregate, `pending_message_ids`, `policy_changes`, and `next_cursor` for paginated reads. Lists default to 50, max 200. All external event/history/inbox/page cursors are opaque handles bound to the authenticated principal, project set/filter, grant generation and store incarnation; never expose or merely base64-encode the internal global sequence. A changed/revoked scope, restore or expired cursor returns `CURSOR_RESET` with a fresh authorized snapshot/catch-up plan before replay. Current cursors are sealed tokens that need no stored row; they stay valid for 24 hours and across a service restart, and a change of store key also returns `CURSOR_RESET`. Direction cursors are opaque task/work-round tokens, not global event numbers. Context names source revisions/truncation and older-history cursors. Large stored text is never silently discarded.

During a backup's consistent database copy, ordinary read-only paths return their normal data with top-level `write_admission={backup_active,locked,queued,reason,message,estimated_remaining_seconds,generation,revision}`. This is a current service observation, not part of a durable domain result. `locked=true` identifies temporary write admission, not an offline service. `reason=backup_in_progress` covers the database copy or an accepted operation waiting for the backup's retention barrier; `backup_queue_draining` means accepted writes are applying in order. `estimated_remaining_seconds` is null when there is no measured estimate. Backup admission transitions wake an existing `changes_wait` even when no domain event has committed. A read that needs the writer (for example an original-reader hold, availability observation or first cleanup preview) may instead return `data: {state: "locked", queued: false, retry_required: true}` with the observed `write_admission` state and reason. Native media original reads and example lease/release use this response too; metadata and projection reads, including the enrolled-worker media reads, use the read-only pool. No semantic result, hold or queued command is created; retry that read after admission opens. See [backup write admission](database-storage.md#backup-write-admission-cl-320).

An ordinary routed write arriving while admission is locked returns promptly after its complete original intent is durably queued: `command_outcome:"queued"`, the exact original `command_id`, the observation above, and `data={state:"queued",queued:true,status_method:"command_status",command_id}`. This acknowledges acceptance only. The caller keeps its draft and original method/parameters/UUID until application or a real rejection is observed. Accepted writes apply in arrival order after the copy releases its writer lease; a backup retention conflict keeps the original queued rather than failing it. Current project/session authorization, authorization generation and ordinary domain guards are checked again when applying. Accepted intents survive a service restart. A storage uncertainty retains the original intent with `reason=backup_queue_recovery_required`; it is not discarded or reported as failed because of the backup.

`command_status(project_id,command_id)` is a read for the same authenticated principal and authorized project. For backup write admission it returns `data.state=queued|applied|failed|unknown`; applied includes the original journal `result`, and failed includes the actual domain `error`. For a long command it returns the operation and its `queued|running|succeeded|failed` state described below. Success is read from the canonical command journal and honors its expiry/purge (`COMMAND_RESULT_EXPIRED`); the queue and operation metadata store no second copy of private successful results or actual failure details. Claim-producing methods return `retry_original:true`: replay the exact original command to refresh still-current credentials through its normal authority checks. Status never grants work authority or reveals another principal's command. The native app reconciles its accepted command through bounded status reads while preserving that original UUID; an MCP caller may explicitly read status. This adds no model runtime or schedule.

### Long command operations (CL-353)

An accepted long command commits its operation identity, original `command_id`, method, authenticated caller, project/incarnation and authorization generation, intent digest, `state=queued` and creation timestamp in the transaction that accepts it. Its immediate envelope is `{command_id,command_outcome:"accepted",data:{operation_id,command_id,method,state,status_method:"operation_get",created_at}}`. Acceptance is separate from the semantic command result. The CLI and MCP return this operation envelope; keep the UUID and wait for the outcome as described under [waiting for the final reply](#waiting-for-the-final-reply-cl-364), or read the indicated method.

`operation_get(operation_id,project_id?)` returns `{data:{operation_id,command_id,method,state,created_at,started_at?,finished_at?,result?,error?}}`. Supply the original project for a scoped operation. A succeeded operation includes `result`, the complete former synchronous reply envelope, including its original `data` and `command_id` where applicable. A failed operation includes its retained structured `error`, subject to command-result expiry/purge. Queued/running replies contain neither a fabricated final result nor a completion claim. These reads recheck the same principal, current project grant/session generation and store incarnation. An operation ID confers no access by itself. For a succeeded `work_claim`, `batch_claim` or `work_takeover` operation, each read issues a fresh claim token through the normal replay checks and invalidates the token from any earlier read or replay of that claim, exactly like a replay of the original command. Use the token from the latest read. The service stores only token hashes, so it cannot return an earlier token again. A failed or canceled status observation does not reject an already accepted original command: preserve its method, input and UUID for recovery. Only a terminal operation or command receipt supplies the original semantic rejection; transport or read-authorization failures leave that original outcome unknown.

The service always uses this route for `backup_create`, `restore_create`, `restore_preview`, `backup_prune_preview`, `backup_prune`, `attachment_cleanup_preview`, `import_preview`, `import_commit`, `import_rollback`, `export_project`, `media_intake_preview`, `media_intake_capture`, `media_intake_confirm`, `media_round_publish`, `media_context_reconcile`, `project_icon_import`, `task_purge_preview`, `task_purge`, `epic_delete`, `policy_preview`, `policy_propose`, `policy_apply`, `status_retire`, `relation_import`, `media_publication_preview`, `media_type_adopt`, `media_type_retire`, `media_context_approve`, `media_round_finish` and `media_round_successor`. `project_edit` and `project_settings_save` use it when the request changes `brief` or `pinned_decisions`; `project_settings_save` also uses it with `policy` or `policy_proposal_id`. Archive (`task_archive`) uses it when `action=archive` (including the omitted default action) requests `cleanup=true`; ordinary visibility changes remain synchronous. `attachment_add` uses it when a local `path` is supplied directly or inside `source`. `work_submit` and `batch_submit` use it when the request names artifact/attachment IDs or a submitted evidence manifest contains source capture, artifact references or a Playtest bundle. Metadata-only short paths remain synchronous.

Evidence preparation uses operation admission for the source-target methods (`work_claim`, `review_request`, `review_record`, `batch_review_record`, `batch_claim`, `batch_prepare`, `task_complete`, `batch_complete_passing`, `review_evidence_add`, `human_request_answer`, `triage_transition`, `review_draft_save`, `review_draft_submit` and `release_set_complete`) and for `review_context`, `review_prepare`, `review_batch_inputs`, `work_takeover`, `human_request_create`, `human_request_revise` and `task_get` when the request names an artifact, attachment or source capture, or the selected current manifest needs source/artifact/Playtest evidence verification. The planner follows the ordinary task/attempt/review/batch/Triage selection using record reads; it reads no file bytes. `task_get` enters this route only with `include_completion_eligibility=true` and file/source-backed evidence. `attachment_read` enters it only for nonmetadata representations; its default metadata read stays synchronous. `release_set_complete` also uses this route because it enumerates member targets. Human Request create/revise/answer paths enter it only for target/file or evidence preparation; ordinary text paths remain synchronous. `review_assessment` is review data, not a standalone command. `source_review_execute` remains the synchronous disabled capability; this change enables no review execution.

Read operations run exactly as their synchronous reads: on the read-only pool, without backup write admission. These are `restore_preview`, `backup_prune_preview`, `attachment_cleanup_preview`, `import_preview`, `policy_preview`, `media_publication_preview`, `attachment_read`, `task_get`, `review_context`, `review_prepare` and `review_batch_inputs`. A backup capture does not wait for a running read operation, and a read operation starts and runs during a capture. A writer continuation inside such a read (for example a first cleanup preview) keeps the synchronous rule: during a capture it returns the retryable `state=locked` reply. After acceptance, only the operation's own `running` marker and terminal-state write take write admission; a read that starts during a capture keeps `state=queued` durably, `operation_get` reports it as `running`, and its finished reply waits in service memory until admission opens. Every other operation is a write and, like a synchronous write, waits while a capture locks writes. `CommandOperationTests` checks these lists against the code.

The installed catalog describes operation-bearing command results. Converted preview reads accept an optional original `command_id`; when omitted, retain the UUID returned with the operation to correlate later reads and retries. An about-one-second acceptance observation on a live-size copy also requires the combined CL-345 bounded writer-occupancy gate: ordinary operation acceptance uses the sole SQLite writer with atomic backup admission. While capture or FIFO draining closes that admission, acceptance is atomically flushed as metadata in the existing private backup-write-queue directory; status reads and same-intent replay see that record immediately. Read operations run during capture and defer only their terminal write. On restart these accepted records enter the existing canonical interruption reconciliation before queue recovery.

Replaying the identical method/input/`command_id` returns the same operation; different input under that UUID returns `IDEMPOTENCY_CONFLICT`. Service restart reconciles accepted operations with canonical semantic receipts: a committed result becomes succeeded, while an interrupted operation without a result becomes failed with `OPERATION_INTERRUPTED` and a reason. A running interruption retains an unknown semantic outcome; an unstarted queued interruption is rejected only when it carries no prior unknown outcome. Once an earlier attempt became uncertain, that uncertainty survives exact-original replay and another restart while queued. Explicit exact-original replay can resume the same interrupted/uncertain operation through its ordinary command reconciliation path. Never replace its UUID merely because it is slow or interrupted. Ordinary definite failures remain final.

Operation scheduling preserves each command's existing preparation, authority, expected revisions, writer lease, object/retention gates, scan fences, publication checks and idempotency. Operation journal state and final-reply transactions, and ordinary acceptance, use `StorageOperationLease` plus the sole `dbQueue` writer without `ArchiveStorageGate`: they create no managed-object names or references. Capture-time acceptance uses the existing queue directory's no-follow atomic publication and flush protocol, stores only accepted metadata (no input/result bytes), and never becomes a legacy FIFO semantic command. A prior-canonical hash fences replay staging: an advanced canonical running/final record wins over a stale sidecar. Terminal commit or startup reconciliation retires the sidecar. Every domain handler retains its existing gates. Stored successful replies keep relative managed descriptors; owner URLs are projected at read time. Claim credentials are rehydrated through the normal current-authority replay path and are never persisted in operation result snapshots. Acceptance supplies no claim, delivery acknowledgment, archive change or backup/restore completion. Unknown publication/commit outcomes retain their original `OUTCOME_UNKNOWN` detail for reconciliation. Successful results and actual failure details share normal command-result expiry/purge. Failure details live in a separate canonical command receipt under a derived UUID, with only an error-receipt reference in operation metadata; this leaves the original command slot available for unknown-outcome reconciliation. Generic startup interruption errors may remain in metadata. Large known operation results/errors may conservatively expire on ticket purge without decoding their snapshots. A generic purge generation also expires an in-flight result if purge crosses its execution, preventing finalization from restoring scrubbed content. A historical result containing a reader hold retains that hold's original expiry; reading the operation never renews the lease. [Synthetic examples](../examples/agent-project-commands.json) show acceptance and an explicit result read.

Failure is MCP `isError=true` plus `{code,message,retryable,details,correlation_id}`. Protocol errors use JSON-RPC. Validation/authorization failure makes no changes. `details` includes relevant safe IDs/current revisions/changed fields and the blocking reason, never another project's contents or tokens. Error text never contains SQL: a storage-engine failure returns `STORAGE_ERROR` with only `details.sqlite_code` (or `OUTCOME_UNKNOWN` for a write with its command ID), and the service log keeps the full description. A replay of a command ID whose stored result passed its 30-day retention returns `COMMAND_RESULT_EXPIRED`; the command does not run again.

The service admits commands only from the exact bundled `ChecklistApp` and `checklist` cdhashes. XPC checks their code-signing requirement against each message's audit token. An earlier Checklist signing identity can connect only to a fixed `CLIENT_OUTDATED` reply object, which has no command capability. Its `details.recovery_action` is `restart_mcp_server`; if automatic delegation cannot recover, the text directs the Codex or Claude host to restart/reconnect its checklist MCP server and retry the original request. Other identities are refused. A process-ID race on the error-only path cannot run a command. Running fixed MCP shims switch to the signed CLI at their saved launch path and keep the SDK transport. Parent preflight checks the resolved bundle root and instance against startup. A delegate starts suspended; the parent obtains its dynamic `SecCode` by PID and requires `SecCodeCheckValidity` to pass the exact pinned CLI cdhash requirement before resume. It also checks the kernel executable path against the captured bundle root. Static signing information is diagnostic only and cannot admit the child. A failed check kills and reaps that child before it executes an instruction. After resume, the CLI checks its resolved instance and bundle root against the delegate's environment expectation before Checklist IPC, a credential read or bootstrap. An instance mismatch is not sent and retains the original command ID. CLI `call METHOD -` reads at most 1 MiB of JSON from a separate child stdin pipe; MCP stdin is never passed to the child. A delegated result needs exit zero with JSON stdout, or exit one with a final CLI error line. Other child results retain the original command ID in `OUTCOME_UNKNOWN` with reason `delegate_ended`; see [install recovery](integrations.md#installs-and-running-mcp-shims). A non-owner call that names a session with no registered record in the project fails with `FORBIDDEN`. Agent reads of reference files open the final component with `O_NOFOLLOW` and check the descriptor's own path against the workspace again after the open.

Connection admission reads no disk for a repeat client (CL-357). The listener keys each peer's executable by kernel facts only: `proc_pidpath`, the file's device, inode, modification and change times and size, and the kernel's cdhash for the running process. The first connection from a key reads the signing identity (`SecCodeCopyGuestWithAttributes` and signing information) on a concurrent admission queue, not on the listener's serial queue; the connection stays unresumed until that check classifies it, and a refused peer is invalidated. A successful read is cached for that key, so a later client of the same unchanged executable is classified at once. A changed path, inode, time, size or kernel cdhash causes a new full read; a failed read is never cached. Classification is unchanged: same user, exact current cdhash with the per-message XPC requirement, the error-only outdated peer, and refusal of every other identity. The owner-channel check is unchanged.

Reusable shapes:

- `TaskRef`: exactly one of `task_id` (UUID) or `key` (project-local string). Mutations use task UUID after resolution.

A note with `triage_id` and no `task_id` goes to that Triage's orchestrator or an exact recipient (a plan without a recipient saves it); a note with neither needs an exact recipient. An explicit route is exactly `{kind:"session",session_id:"<verified scoped session>"}` with both fields required and no additional keys. Missing/unsupported kind, blank or invalid session ID, null/non-object values and unknown fields return `INVALID_INPUT` atomically; they never select current handlers as a fallback. A new trusted owner `requires_action=true` message must omit recipient for mandatory handler direction fanout. Combining it with an explicit session returns `INVALID_INPUT` before writes or reply allowance changes. Previously committed valid-shape command receipts still replay their original result without being rerouted or rewritten. A reply to an owner note retains its original human route and must omit recipient; an explicit route is rejected before consuming that reply allowance. Ordinary agent-to-agent ticket replies retain their valid explicit route. Valid original-command UUID retries preserve the committed message, delivery IDs and actual recipient if the handler later changes, without new writes. Tightened explicit-shape validation runs before cached receipt replay: retrying a malformed intent committed by an older version can now return `INVALID_INPUT` while leaving its existing note, deliveries and durable receipt intact. That error does not prove the original intent never committed; retain its IDs and inspect existing receipt/history before treating it as unsent. Current authorization still applies.

Git captures also record resolved `git_path` and `git_version` from the fixed trusted executable list described in [storage](database-storage.md); `SOURCE_GIT_UNAVAILABLE` explains missing/unsafe candidates, `SOURCE_GIT_UNTRUSTED` refuses a selected executable that becomes unsafe, and `SOURCE_GIT_LICENSE_REQUIRED` names the Xcode license step. Artifact refs are immutable `{artifact_id,sha256}`. Each check names `{label,command_text?,target_ref,execution_mode,result,started_at,ended_at,before_hashes?,after_hashes?,not_run_reason?}`. Mode is `immutable_artifact|captured_source|serialized_checkout`; result is `passed|failed|not_run`. Source modes require reservation/capture receipts and before/after validation, not self-declared empty hashes. Service returns manifest ID/digest; relevant limits must be policy-acceptable.

#### Waiting for the final reply (CL-364)

Use the wait form. A caller then needs no `operation_get` loop and no second code path for a command that returns an operation.

```bash
checklist call --wait attachment_add '{"project_id":"…","task_id":"…","command_id":"…","path":"/absolute/file"}'
checklist call --wait=600 backup_create '{"project_id":"…","command_id":"…","qualification_name":"round"}'
```

`checklist call --wait[=SECONDS]` (default 120, maximum 3600, in any position after `checklist`) sends the command once. A reply that is not `command_outcome=accepted` or `queued` is already final and prints unchanged. Otherwise the CLI reads `operation_get` (or `command_status` for a queued write) with the same project, and each read has a reply budget inside the wait.

| Result | Standard output | Standard error | Exit |
|---|---|---|---|
| Succeeded or applied | The `result` envelope, in the shape of the former synchronous reply | | 0 |
| Failed | | `Checklist: CODE: message`, as for a synchronous failure | 1 |
| Not final after the wait, or a lasting read failure | The last known envelope (the receipt or the operation with its `state`) and `wait` | | 124 |

`wait` is `{finished:false,reason,state,limit_seconds,waited_ms,next,read_error?}`. `reason` is `timed_out`, `read_failed` (the status read failed for a lasting reason, with `read_error`), `result_unavailable` (the command finished and its result expired, or `retry_original` applies) or `state_unknown`. Exit 124 is never a rejection: the command can still be running. Read the status again with the same ID and do not send a new command. `OUTCOME_UNKNOWN` and `SERVICE_UNAVAILABLE` during a read, for example a service restart, do not end the wait. Exit 124 is the same code as timeout(1); a usage error before the send exits 1.

MCP callers use the `operation_wait` tool: `operation_wait(operation_id,project_id,wait_seconds?)`. The shim adds it to the catalog of every caller that can read `operation_get`, so it is not a service command. It returns the same final reply, or a tool error with the operation's own code when the operation failed. `wait_seconds` has the default and the maximum 45; a larger value waits 45 and `wait.limit_seconds` says so. After that it returns the operation and `wait.finished=false` as an ordinary result: call it again with the same ID. The whole tool call, including a wait for a service that does not answer, ends by 55 s, below Codex's default 60 s MCP tool limit, with a retryable `SERVICE_NOT_READY`. The wait sleeps without a thread and reads on a dispatch worker, so other calls of the same shim continue (CL-352). A bad ID or a read refusal on the first read is a tool error at once. The description of each command in the catalog that can return an operation says so and names this tool. Queued backup-admission writes have no MCP wait; read `command_status`.

A wait ending never cancels, rejects or repeats the command. Each read of a succeeded `work_claim`, `batch_claim` or `work_takeover` operation issues a fresh claim token, so the token in the final reply is the current one. Reads back off from 0.1 s to 2 s (27 reads in a 45 s wait).

## Provider-plugin and planned conversation contracts (CL-124, CL-128)

`service_info` adds `provider_plugins`, an array of `{schema_version,interface_version,plugin_id,version,provider_id,display_name,enabled,availability,capabilities,qualified_capabilities,models}`. Model entries are `{id,name,selectable}`. Disabled/unqualified entries expose metadata only; enabled capabilities still require verified current native identity, project grants and route receipts. Existing unsupported/native-push fields retain their meaning. See [provider plugins](provider-plugins.md) for registration, model-selection refusal, update/recovery and exact native evidence limits. No new provider command or arbitrary loader is introduced.

[Triage orchestrators](triage-orchestrators.md) is the CL-269 contract that CL-125, CL-248 and CL-126 implement: a Triage is the work list of one orchestrator conversation, a Triage with no orchestrator is a plan, one conversation orchestrates at most one Triage per project, and a ticket is in at most one Triage. Command changes (CL-125, CL-248): `triage_orchestrate start` with no `triage_id` creates the caller's Triage and `start` on a plan makes the caller its orchestrator (CL-125); the orchestrator's own claim, batch claim, review claim, takeover or handoff acceptance moves the ticket into its Triage; group, Triage and batch commands drop the Triage phase checks while a batch keeps its own phase; CL-248: `message_send` has `audience=all|holder|orchestrator` (default `all`), which cannot be combined with the exact `recipient` field, and accepts `triage_id` with no `task_id` for a Triage note; the project policy `coordinator_session_id` routes nothing and new policy saves refuse a new or changed value. See [message routing](triage-orchestrators.md#message-routing) for the routes and their limits. The CL-124 `orchestrator_*` registry commands are superseded history and will not be built. Existing ticket sessions, the exact `recipient` shape and Human Requests keep their authority. [Optional conversation content](conversation-content.md) defines future version-1 companion envelopes while `body` and other current string fields remain valid and unchanged; no current tool accepts a rich envelope solely because this proposal describes it.

The owner snapshot omits per-ticket `completion_eligibility`: it does not run completion guards for every offscreen ticket. The selected ticket detail explicitly reads `task_get` with `include_completion_eligibility: true`. Field presence requires the trusted owner channel, including `false`; workers and assistants cannot supply it, and their task_get schemas and default result remain unchanged. The flag accepts a JSON boolean, never a string, number or null. The preview runs the existing completion guards in a rolled-back savepoint and returns `eligible`, exact blockers, `task_revision` and `manifest_id`; it creates no completion, verdict, Triage departure or durable direction acknowledgment.

The app keeps this selected-read receipt separate from raw snapshot records. Selection/project navigation, close/Back, successful snapshot installation and observed event invalidation discard the prior receipt, including policy, prerequisite, relation, direction, finding, human-answer and project-context changes which leave the selected task revision and manifest unchanged. Concurrent refresh requests coalesce into another fetch.

`work_handoff` is a closed union: `offer` requires claim, target session, summary and direction cursor; `accept` requires offer ID, expected offer revision and target-session binding; `withdraw` requires offer ID/revision and reason from offerer. `work_submit.acceptance_evidence` is an array with exactly one entry per acceptance item at the submitted `acceptance_revision`. `batch_submit.members` accepts the same field for every member; an uncovered item refuses the complete batch before any source copy or member submission. Reference kinds are `{kind:"attachment",attachment_id,sha256}`, `{kind:"check",name}`, `{kind:"carried",producer,target,sha256}` and `{kind:"check_runner_report",attachment_id,sha256,build_id}`. Attachment references name an available same-ticket managed original with the exact lowercase SHA-256. Check names match one `evidence_manifest.checks` entry (`name` or `label`) with a recorded `passed`, `failed` or `not_run` result. Carried results retain nonblank original producer and target plus a 64-character lowercase hexadecimal hash; they are attributed carried evidence, not new execution.

An `installed` or `native` observation requires a valid check-runner report; a limitation alone does not cover it. `evidence_manifest.installed_build_id` is required for either observation or any check-runner reference. The report's `build_id` equals that ID, its attachment description contains the ID, and its author is a non-contributor session. Current, prior and delegated implementation contributor principals, installations and sessions use the same exclusion as review independence. An owner-authored attachment does not impersonate a check-runner session.

Missing coverage returns `ACCEPTANCE_EVIDENCE_MISSING` with a message and `details.uncovered_items`, each containing 1-based `item`, the first 80 characters of `text` and a `reason`. Validation precedes source capture and state changes. Invalid references are refused rather than retained as verified evidence. The normalized map records each index, acceptance text snapshot, references, limitation, observation and coverage result in the immutable manifest evidence/digest. Source targets with file scopes use scoped freshness: every read/write scope and additional path plus every AGENTS.md or CLAUDE.md at any depth. `review_context.source_relevance` returns the mode/scopes. Unrelated live edits and Git HEAD/index-only changes preserve scoped targets. Relevant additions, deletions, byte/kind/executable/link changes stale them. Legacy captures and unscoped attempts retain whole-inventory checks. See [source evidence](source-evidence.md).

Declared scope aliases use physical parent-directory coordinates and keep their final component unresolved. Claims, batches, scope adjustments, checkpoint scope changes and relevance reads normalize them consistently, including equivalent `/tmp` and `/private/tmp` or `/var` and `/private/var` roots. Canonical reservations keep their existing identity and conflict rules.

Passing `review_record` requires `review_assessment:{contract_sha256,target_manifest_id,acceptance,project_requirements,evidence_refs,instruction_coverage,all_applicable_project_requirements_assessed,additional_requirements}` from fresh `review_context`. The actual reviewer chooses inspection/checks and its own managed hash-verified evidence. No Swift test or validate-plan receipt is forced. `source_review_execute` is disabled without a qualified sandbox and queues no new process; old execution history and explicit stop-recovery fences remain. See [source evidence and agent review](source-evidence.md).

Review contract version 2 contains `review_requirements` (separate applied snapshot) and `review_requirements_state`. Classes are `reviewer_report`, `source_capture`, `image`, and `text_record`; they do not establish test success, native observation or approval. See [review requirements](policies.md#revisioned-review-requirements) for limits, inheritance and legacy review handling. Rubric-changing `checkpoint_active` application is explicitly unavailable in this slice; use `future_attempts`.


`instruction_coverage` copies complete `project_instruction_refs` from the current contract: `{source_capture_id,source_sha256,path,sha256}` for regular AGENTS.md files, plus `resolved_path` and `link_chain:[{path,target,sha256}]` for captured internal symlinks. The top-level instruction `sha256` hashes resolved regular file content; link hashes cover exact target text. Resolution is bounded to 32 captured internal hops and every coverage field must match, including nested instruction aliases.

[Ticket fields](ticket-fields.md) defines the task field/readiness matrix and canonical prerequisite arrays; prose names become stable task IDs through explicit resolution.

New findings are `{client_ref,severity,description,evidence_refs}` with optional `same_cause_as`; service returns stable finding UUIDs, scoped to request/gate/target. Severity is `blocking` (default) or `advice`; older values (`critical`, `high`, `normal`, `low`, `info`, `blocker`, `major`, `minor`) count as blocking. Advice findings stay open and visible in every later round but never block completion, and a pass may add advice findings only (CL-42). `same_cause_as` names an earlier finding of the same ticket, also a resolved one (a reopen); each finding stores `cause_id`. `task_context.review_summary` has `rounds` per gate (`failed_rounds` counts reject verdicts; `passes`, `blocked`, `evidence_missing`, `not_run`) and `warnings`: a cause with three or more findings (it returned for the second time) produces a `repeated_finding` warning that suggests a split or a new brief; `triage_list` shows each member's warnings as `member_warnings`. Warnings never change a status, claim or verdict (CL-43). A resolution is `{finding_id,disposition:"resolved"|"rejected",reason,evidence_refs}`; only an independent qualified reviewer can finalize it. `finding_waive` requires a reason and trusted owner authority or enrolled-worker authority while `agent_rule_changes=allowed`; the disposition retains `human_ui/owner_waiver` or `agent/agent_waiver` provenance. Later verdict explicitly supersedes the previous gate verdict and accounts for every applicable open finding; silent pass does not clear them. `satisfies_gate_ids` can include only pinned required gates whose evidence this captured verdict actually covers.

## Human requests, groups and attachments

Status changes keep Triage membership. A ticket leaves its one Triage only when it is Done or canceled, when another orchestrator handles it, or when it is removed; the [Triage orchestrator contract](triage-orchestrators.md) lists every move. Individual status actions (claim, release, submission, review request/verdict, completion, recovery and gate-bearing human approval) keep membership too, except the moves the contract lists (CL-125).

## Trusted native actions

These handlers share domain validation but are not agent tools:

- `diagnostics_summary` is a read. The owner receives installation aggregates without input fields; an enrolled worker supplies `project_id` and requires `agent_rule_changes=allowed`, receives only project record/event counts and no global command-receipt count. It returns schema version, observation time, service version/responsiveness and aggregate counts under fixed record-type labels; it never returns record contents, dynamic labels, paths, session identifiers or secrets. Settings combines it with strictly validated version/build metadata and bounded owner-app error codes for a native Save-panel JSON export. It is absent from assistant catalogs; worker aggregates stay project scoped and unavailable service counts stay omitted. This is separate from project export and full backup.

- Project create/update/relocate/enroll/archive, expected-revision project settings save/icon import and project context save; root changes use fresh Finder/verified workspace grants and overlap validation. Project brief/decision edits require expected revision/provenance.
- Policy apply from unchanged proposal ID/digest plus expected revision and `future_attempts|checkpoint_active` mode. Status/tag edits use the simple Name/behaves-like/color editor; the service generates protected transitions/defaults and supplies impact mappings for structural changes.
- Human request forms use flat fields. `title` defaults to “Needs your input”; `blocking` defaults true. `questions` and `file_requests` default empty, with at least one entry across both and at most 30 each. Each has a unique nonblank `id` (100 bytes) and required `prompt` (4,000 bytes). Question `type=text|choice|approval|check` defaults to `text`; `required` defaults true; `multiple` and `allow_custom` default false. A choice requires `options=[{id,label}]` (unique IDs, at most 100; labels 4,000 bytes), with at least one option unless custom answers are allowed. File `kind=file|directory|either` defaults to `either`; `selection` is an alias, with `kind` taking precedence when both are supplied. File `multiple` and `optional_explanation` default false. Extra nested entry fields are currently ignored; they cannot replace required fields or change accepted enums. `label` cannot replace `prompt`, and `single_choice|multiple_choice|short_text|long_text|file_or_directory` are unsupported types/selections. Unknown top-level fields, including `request_spec,purpose,blocking_scope,target`, are rejected on agent calls.
- Form `command` (also allowed on a question) is instructions only: `{text,working_directory,expected_result,reason?}`; text is at most 16,000 bytes, other fields 4,000. The service never executes it. Title is at most 4,000 UTF-8 bytes; agent create `explanation` is at most 4,000 bytes (revision patches allow 16,000). Optional booleans must be actual booleans. Service-derived authorship, revision, state, continuation and target hash are not form inputs. A `check` alone does not bind a review gate; human gate binding requires exactly one `approval` question and the exact managed target. Explicit `review_request_id` selects the queued gate; without it, exactly one matching queued human gate can be selected automatically when an approval question and attachment are present. Merely naming `target_manifest_id` does not create a gate.
- `human_request_answer` takes request ID/revision, target ID/hash where applicable, complete typed answers/file grants and optional explanation. `clarify|cannot_do` appends response but keeps pending/blocking; personal snooze changes only presentation. Clarify/cannot-do (including Not checked) retain a gate-bearing request’s verification slot; cancellation frees it with gate unsatisfied, and eligible replacement transfers it atomically. `send` validates all required fields, commits answer and deduplicated outbox deliveries to original requester/current handlers/configured coordinator atomically and applies only the eligible continuation. Ended requesters remain historical recipients; next pickup gets the answer through context. Gate approval records its exact trusted pass/reject verdict and releases verification slot; explicit No (`declined`) rejects the gate. Not checked with an owner explanation may also use Send answer; it keeps the request pending without a verdict or slot release. A complete gate-bearing answer additionally requires the caller-observed `expected_task_revision` and `direction_cursor`; the service revalidates current owner directions and approved project context before file import, answer/verdict writes or releasing the verification slot. Missing/stale context or unresolved directions reject the transaction with the draft and slot retained. Ordinary answers, clarification/cannot-do and Not checked remain available without recording a gate verdict. Forms start unanswered; no implicit selected default.

- Multi-select typed changes (tags, planned assignment, epic/triage, guarded status, archive) take all expected revisions and a preview. - File/Finder grants, integration registration/bootstrap diagnostics, export, later authorized transfer/restore and trash purge. No migration now. Runtime/endpoint enrollment is explicit; proposed task text cannot authorize it.

## Ordinary comment mention preparation

`message_mentions_prepare(command_id, project_id, task_id, body, reply_to?, selections?)` is an idempotent preparation command that sends nothing. Assistant-only connections cannot discover or invoke it. `body` is the exact intended comment. Each optional selection has exactly `{start, end, target}`: nonnegative integer UTF-8 byte offsets naming a complete parsed token, and a returned exact target. Target is exactly `{kind:"ticket", task_id}` or `{kind:"session", session_id, authorization_generation}`. IDs/generations use exact bytes; labels confer no authority.

Recognized syntax: bare `@CL-12`, `@worker`, or `@<actual-session-id>` (the angle brackets here denote a placeholder, not literal syntax). Exact labels with spaces/punctuation use `@{Target worker}`. Bare tokens contain Unicode letters/digits/combining marks, `_`, and `-`; markers start at the beginning of a comment or after whitespace or `([{"'`. Email/interior-word markers are literal. Odd preceding backslashes escape a marker. Inline backtick code and line-start backtick/tilde fences are literal; unfinished code remains literal through the end of the comment. This small rule is not a complete Markdown renderer. Preserve the original body bytes; parsing does not remove escapes, rewrite code or normalize Unicode. Empty/unclosed brace tags and more than fifty tags are refused.

Each raw query collects all currently eligible same-project ticket-key, worker-label and exact-session-ID matches. Do not prefer a ticket based on its spelling or choose the first duplicate label. A duplicate key/worker label/cross-namespace match returns all exact candidate descriptors. A supplied selection must still be one of that token's current scoped matches. Otherwise refuse `RECIPIENT_CHANGED`; it cannot grant enrollment or route outside scope.

Responses include `body_sha256`, parser version, tokens with exact `{start,end,query,state,candidates,target?}`, and truthful pickup-only capability. State is `untagged`, `needs_selection`, or `prepared`. `needs_selection` can contain resolved, ambiguous and not_found tokens, but has no route token and creates no partial plan. Choose exact candidates for ambiguous tokens and prepare the entire unchanged body again. Unknown tokens must be corrected/escaped; they do not silently become untagged notes. `prepared` includes the opaque `mention_target`, expiry and references from the existing atomic preparation path. It binds the caller/project/task/reply/store, exact body hash, references and current recipient generations.

For ordinary `message_send`, pass that `mention_target` with the **same body** and normal project/task/reply/destination fields. A recognized tag without preparation refuses `MENTION_PREPARATION_REQUIRED`; changed public-token body refuses `RECIPIENT_CHANGED`. Current recipients/generations are revalidated atomically before delivery. A failed preparation/send preserves the draft and has no partial message/delivery. Use the original command ID to reconcile an unknown outcome; do not make a replacement intent. Prepared/saved/queued/acknowledged remain different receipts.

Writes admitted during the copy use the durable FIFO queue described above; backup-sensitive queued operations wait for retention release. Cleanup reports a backup-capture hold or `BACKUP_CAPTURE_ACTIVE`; a concurrent owner backup returns `BACKUP_IN_PROGRESS`. A failed/canceled attempt releases retention but preserves its recovery stage and earlier generations. `restore_supported: true` denotes the separate owner-only disposable-root restore below; it grants no agent restore authority. Retries retain the original principal/UUID and durable receipt; an uncertain final receipt preserves reconciliation rather than reporting an empty success. See [database storage](database-storage.md).

### Applying the owner's retention answer (CL-360)

An enrolled worker (not an assistant) calls `backup_retention_apply_answer {project_id, command_id, request_id, response_id}` after the owner answers a retention request in the app. The agent supplies no numbers; the schema has no such fields, so a call with `newest_count` or `daily_days` fails with `INVALID_INPUT`. The service checks that the request is in this project, the response belongs to it, has `origin: human_ui`, is complete, is the latest complete response and answers the current form. Exactly one selected option label or custom text in the response must state `Newest N, plus one per day for D days` (N 1–1000, D 1–366), optionally followed by one parenthetical note. Otherwise the call fails with `BACKUP_RETENTION_ANSWER_REFUSED`, a plain message with the next step, and `details.reason`: `request_not_in_project`, `response_not_on_request`, `response_not_from_owner`, `answer_not_complete`, `answer_for_old_form`, `answer_superseded`, `no_rule_in_answer`, `more_than_one_rule`, `answer_time_unknown`, `answer_from_other_installation` or `newer_rule_exists`.

On success the installation rule is confirmed with `owner_confirmation.source: owner_answer` and the request and response IDs, and the reply returns `status: rule_confirmed_from_answer`, the numbers, the IDs and `already_applied`. The call moves no files; the rule applies after the next completed backup with the protections below. Replay of the same command returns its receipt. A new command naming the answer already in force returns `already_applied: true` with no new event. An answer older than the current rule refuses, so an agent cannot undo a later owner save. A later owner save with `backup_retention_set` replaces the rule. The event `backup_retention_answer_applied` is in the ticket's project history and in `automatic_prune_history`. `backup_retention_set`, `backup_pin` and `backup_prune` stay owner-only.

### Owner backup retention (CL-360)

The trusted owner channel discovers `backup_retention_get`, `backup_retention_set`,
`backup_pin`, `backup_prune_preview` and `backup_prune`; workers and assistants
cannot call them. Get and preview are reads; preview and prune return long-command operations,
which the native app reconciles through the existing receipt path. Set takes a command UUID and
`newest_count` (1–1000), `daily_days` (0–366), confirms the installation rule and
preserves pins. The initial proposal is five newest completed snapshots plus one
newest per UTC day for seven days; it removes nothing until the trusted owner confirms. Saving the rule records the authenticated owner confirmation bound to this store root and incarnation and enables automatic retention after each completed backup. Legacy rules saved as manual-only need this new confirmation. The values remain configurable; no installation-specific owner answer is a product default. Pin takes a
command UUID, `path` and boolean `pinned`; unpin works when the snapshot is
absent. After copy/restore/seed, a strict `snapshot-<UUID>` folder name also carries
its old pin or historical protection into this instance’s local backups folder;
this is keep-only authority and never permits reading the old path. An explicit
owner unpin/history-retire on the local path removes the corresponding copied
binding in this store. Optional `retire_upgrade_protection:true` requires `pinned:false` and
retires historical upgrade protection only. Current upgrade protection and current
installer preparation remain protected separately.

Preview returns every observed snapshot's state, exact keep reasons, candidate
flag and `preview_sha256`. Failed/incomplete/unrecorded folders count in the
inventory and never become complete merely because a manifest exists. They stay
unless the owner explicitly supplies `include_unrecorded:true`. Apply takes a
command UUID, the exact preview digest and the same `include_unrecorded` value.
An unconfirmed rule or changed preview refuses. In-use restore/cleanup/upgrade
snapshots stay. Apply returns `moved_to_trash`, `retained_in_use`, `moved_count`
and `physical_space_freed:null`; moving to Trash does not free disk blocks.
Automatic retention uses the same protections, durable intent and same-volume Trash move as explicit prune, retains incomplete/unrecorded folders, reports `origin: automatic_backup_retention` in history and exposes `last_automatic_prune` and a bounded `automatic_prune_history` in get and native Storage controls. Relocated/restored stores do not inherit automatic consent; the owner must confirm their rule in that installation. That new trusted confirmation fences any inherited foreign automatic marker as an inert record without completing or deleting its original prune journal. It runs after capture releases. A bound durable due trigger is committed atomically with each successful backup receipt or protected-upgrade ready record, so termination before the post-commit hook cannot lose automatic retention. Startup resolves that trigger and resumes an interrupted automatic intent with its original UUID; deferred outcomes keep the due trigger, and completing an older trigger cannot consume a newer one. A deferred prune never changes a completed backup into a failure. A durable intent reconciles interrupted renames and accounting retirement when
the original command is retried; replay never prunes again. See [retention and
crash behavior](database-storage.md#owner-backup-retention-and-trash-pruning-cl-360).

### Agent backup and owner restore (CL-258 / CL-6)

Enrolled workers can call `backup_create` with `project_id`, a new `command_id`, optional `reason` and optional `qualification_name` (1–64 ASCII letters, numbers, `_` or `-`). The project must allow `agent_rule_changes`; scope, session and policy are rechecked before reserving and completing the operation. Assistants cannot discover or call this command. Agent input never accepts `path`: the service publishes `backups/snapshot-<command UUID>` or `backups/qualification-<name>/snapshot-<command UUID>` below its own no-follow storage root. The full-store artifact stays inside that storage boundary. The trusted app retains its owner-selected `path` route. Both routes use the same complete snapshot, bounds, verification, retention and original-intent replay.

Read receipts through discovered `history_list` with `project_id` and `entity:"backup"`, plus optional `cursor,limit` (maximum 200). It returns ordered `backup_created` events with `actor` (the actual caller), `occurred_at`, and `data` containing `origin` (`agent` or trusted-owner `human_ui`), `session_id` (empty for an owner without a session), `command_id`, `operation_id`, `manifest_sha256`, `captured_at`, `verified_at` and the reason. This is historical completion evidence, not a check of current backup bytes or permission to read the full-store artifact. Current project read grant, worker workspace/session checks and caller/grant-bound cursors apply on every page, including while archived. Assistants cannot discover the backup selector or use it, even with project read permission. Agent events belong only to their selected project; unscoped owner events are readable only in projects present in that exact captured database. Neither other project IDs nor store/destination paths are returned. Earlier agent events with no entity are included; missing command/time fields are recovered only from retained command/generation receipts, otherwise omitted (a recorded unknown capture time remains null). Earlier unscoped owner events lack captured-project evidence and remain excluded rather than guessing their scope. `entity:"project"` continues to select only the project entity itself.

`restore_preview {path,command_id?}` and `restore_create {command_id,path,manifest_sha256}` are trusted native-app commands, absent from worker/assistant MCP catalogs. Both return operations; read the final result before continuing. Preview verifies the entire generation and returns unavailable-original/external-reference summaries and the exact manifest digest. Create rechecks that digest and prepares a separate data root under `restore/restored-<opaque operation>`, publishing only after complete file verification, canonical/schema validation, an authority-fencing transaction, integrity check and durable identity/restore receipts. It preserves the working installation and source backup. A current protocol-3 backup is required; older/future schemas refuse without replacement. The disposable-root implementation does not switch the running service's root.

A successful preview opens the confirmation and keeps **Review verified backup…** in Settings > Storage until a restore starts or another preview runs; a failed or retired preview names why (CL-370). A blank store identity in the window is not a store change; only a different known identity ends a preview and names that. `operation_get` is bound to the calling principal, so an agent cannot read an owner operation. Settings > Storage therefore lists this window's last 10 long operations with operation ID, service state (`Queued`, `Running`, `Succeeded`, `Failed` and the error code) and the time from sending the command to the reply that named the operation. `State not known` means the app stopped reading it; the operation may still run. Checks read this text from the app and use no owner identity. The list is not saved and excludes Quick Capture commands.

Preview also returns the verified manifest's `source_root`, `store_id`, optional `captured_at`, current `verified_at` and record-family counts. New format-2 manifests bind `capturedAt` to the consistent source capture under the SQLite lease. Older manifests remain readable and return null capture time; filesystem dates are not substituted. The native confirmation shows source, both times, contents and unavailable-content reasons before Create.

The owner-only `storage_status` reply includes `last_verified_backup`, `last_verified_rehearsal` and `retained_usage`. Successful backup/restore receipts save small, durable verification summaries outside the large object index. Rehearsal means a verified restore copy with integrity/authority checks (`native_startup_verified:false`), or an explicitly identified historical pre-upgrade database rehearsal. It does not certify native startup/reconnection. Available-original `managed_bytes` remains a logical attachment-record total. Retained-copy measurements record file lengths and `st_blocks * 512`, deduplicating hard-linked inodes within each copy, with measurement/verification times. Shared blocks across copies/APFS extents are not deduplicated; exclusive physical/reclaimable bytes remain null. Totals exclude staging, directories and unrecorded copies; external presence is not rechecked. Missing/legacy measurements stay null with an unmeasured-backup count. Settings exposes these scopes and limitations alongside the last receipts, and refreshes after successful backup/restore.

Portable `export_project` metadata recursively removes exact credential, grant/generation and native endpoint/binding fields from project records, profiles and event data, retaining historical IDs, actors, display information and user-authored prose. This is a structured metadata projection, not content redaction of user notes or captured files. Full recovery snapshots retain canonical history and use restore's separate incarnation/authority fence.

The restored database preserves historical records, IDs, actors and immutable evidence. A new incarnation and cursor key invalidate old tokens/cursors; sessions are revoked and their grants/generations fenced. Restored active work stays active with `recovery_required`, retaining reservations until explicit stopped-writer recovery or ordinary authorized takeover. Unacknowledged deliveries, including uncertain/previously delivered copies, become `quarantined`; existing acknowledgments/addressed receipts stay historical facts. No credentials, connection registry or runtime endpoints are copied. New actual host sessions must bootstrap again; restore never launches/reconnects them or resends historical messages. Replaying a completed original restore returns its receipt even if the source backup has since moved.

Managed import and snapshot source/destination root opens have a five-second deadline per no-follow root walk. Root requests reuse one native helper, retired on deadline failure. Descendants and files then use descriptor-relative no-follow operations without a child per file; subsequent I/O has no hard cancellation deadline. `FOLDER_ACCESS_TIMED_OUT` / `FOLDER_ACCESS_UNAVAILABLE` names the folder, possible macOS privacy/cloud-sync access, and original-command reconciliation. A terminated opener cannot commit metadata or publish an attachment. Existing receipts replay; pending import retries retain their principal/UUID and attachment ID. A client timeout alone establishes neither commit nor rejection. See [bounded folder access](database-storage.md).

## Frozen implementation scope sharing and preparation discard

Only one frozen **Implementation** batch may share its members' canonical writable paths, and only between its original selected top-level attempts held by the exact same authenticated principal, session, authorization generation, execution domain and store incarnation. Preparation normalizes/freezes all scopes before its rollback-only claim rehearsal; dispatch installs the internal cohort before reservation validation. There is no public overlap flag. Each ticket keeps its complete scopes, distinct attempt, token, contributor history and evidence target. Same-path, ancestor/descendant, symlink and volume-case aliases use the ordinary canonical comparison.

All other live attempts see the cohort's canonical write union. A different session/generation or frozen batch (even held by the same session) still conflicts. Partial release or individual submission keeps every remaining active member's reservation; only the last owner frees the shared path. Review reservations, lane capacity, readiness, prerequisites, policy, owner assignment and review independence remain unchanged. Scope adjustment can retain/narrow frozen shared writes but cannot expand sharing beyond the frozen member envelope. Child acceptance, handoff and takeover never inherit the original attempt's sharing permission: overlapping transfers refuse atomically until narrowed or other writers release. Reconnection cannot revive an old generation's exemption. Orchestration ownership grants no member reservation authority. Scoped conflicts identify the canonical candidate/reserved paths and both ticket IDs/keys, with batch ID/digest when present; foreign-project ticket metadata stays private.

A batch has computed lifecycle `prepared`, `claimed` or `discarded`, exposed consistently by `batch_get`, `batch_list` and Triage summaries. Preparing is planning, never started/claimed work. `batch_discard(project_id,batch_id,expected_revision,reason,command_id)` lets an eligible scoped project worker or the trusted owner discard an unused preparation of either phase. A nonblank reason and exact frozen batch revision are required. The immutable project-owned `batch_disposition` retains batch ID/digest, Triage, actor/session, reason and timestamp without changing the frozen batch, ticket status, membership, attempts or orchestration. Discarded rows remain visibly labeled with their reason and history; there is no timed expiry or hidden default filter.

Claim and discard serialize in the command transaction. Any dispatch receipt **or historical associated attempt** proves claimed-ever and refuses discard with `BATCH_ALREADY_CLAIMED`, including after full release/completion. `batch_claim` and undispatched completion/retriage continuation refuse discarded preparations with `BATCH_DISCARDED` and direction to prepare afresh, acquiring no authority. Same-command replay returns the original outcome; a fresh repeat returns the existing disposition without a duplicate event/marker. Export and verified backup retain this recognized canonical family so restart cannot resurrect a discarded preparation.

Changed checkpoint text is substantive progress; a health reply is a separate handling response. `project_settings_save`/`project_edit` accept complete `work_health_settings={enabled,inactivity_minutes,response_grace_minutes}` (20-minute defaults, 1–10080 whole minutes), with ordinary project revision and rule-change authority. System health notes are not owner directions. [Work health](work-health.md) defines pause, restart, known waits, native pickup limits and recovery; claims/status/Triage membership remain unchanged.

### Delete a mistaken unused Epic (CL-245)

`epic_delete {project_id, epic_id, expected_revision, command_id}` permanently removes an active or archived Epic only when it has never held a ticket and has no incoming structural references. Enrolled workers require `agent_rule_changes=allowed`; assistants cannot use it. Read `epic_list` for the stable ID and current revision. Delete a mistaken empty Epic rather than archive it.

The service refuses current membership (`EPIC_HAS_TICKETS`), past membership (`EPIC_HELD_TICKETS`), references from any retained record or external event to the Epic or its own events (`EPIC_REFERENCED`), and legacy history that cannot prove non-membership (`EPIC_HISTORY_UNPROVEN`). Revision, project/workspace scope and policy guards still apply. Exact ID values and dictionary keys are references; prose mentions and durable command-result audit snapshots are not. No cascade removes another record. Past membership has a permanent Epic marker, retained after ticket removal/purge and command-result expiry. Legacy membership events also block deletion; unexplained revisions, missing creation history or other unproved history fail closed.

The deletion guard never scans the retained record/event corpus. Current membership uses a `(project,epic)` index, own history uses `events_scope(project_id,entity_id,seq)` with a 10,001-row refusal sentinel, and incoming structural IDs use a reverse-reference index. The same index protects references from other projects and global records. Transactional TEMP triggers maintain exact text values, dictionary keys and event entity IDs on the sole writer, including direct SQL/import/purge and rollback paths. No command-receipt snapshot enters this domain index.

On a reopened store, the first deletion can return `EPIC_HISTORY_UNPROVEN` with `reason=reference_index_pending` and start finite background reconstruction over rowid/seq ranges fixed at connection startup. The utility worker reads one bounded source payload at a time and parses its JSON on a separate in-memory SQLite connection, outside the writer and service coordinator. It commits at most 64 references/rows per continuation and yields after a 50 ms slice, preserving the next reference offset. An expired slice always allows one finite unit to commit, then resumes later; descheduling or a valid large payload cannot permanently disable proof. Each payload is limited to 2 MB. Live transactional triggers fence prepared slices for any changed/replaced/deleted source, including same-revision SQL writes. Requests never perform this backfill, and partial proof never authorizes deletion.

Only malformed, non-text or over-2-MB source payloads make reference proof unavailable (`reference_index_unavailable`); the refusal names the record/event in its message and `source_kind`, `source_id`, `payload_reason` details. An infrastructure failure retains progress and permits a later deletion request to restart the worker. Correcting/removing an invalid source through an authorized command updates proof transactionally. Deletion itself retains its 250 ms SQLite execution budget (`reference_budget_exceeded`), runs off the service coordinator queue and rolls back on refusal. Neither the background slice deadline nor the deletion budget guarantees wall latency during OS scheduling or disk stalls; one bounded payload parse or insertion can cross a slice deadline. The real-size regression measures complete background proof for 8,600 records plus 20,000 events and two large valid payloads, with forced slice exhaustion and overlapping ordinary reads. The indexed-store regression still requires deletion under one second at 30,000 records plus 30,000 events, and a concurrent read under 500 ms while deletion is in flight.

One transaction removes the Epic and events whose entity is that Epic, then adds one `epic_deleted` project-level history event (`entity_id=project_id`). Its data names `epic_id`, `key`, `name`, `expected_revision`, `origin`, `actor` and `actor_display`; the event envelope records actor and time. The response returns those fields plus `deleted=true`. Every other domain row retains its bytes and revision, including project counters/settings/policy/pinned decisions/tags and prior command receipts. Ordinary post-command maintenance/pruning is deferred for this command (including retry), so unrelated eligible rows stay unchanged until another maintenance boundary. Normal command idempotency adds the deletion receipt; event sequence bookkeeping advances once. Retrying the same command UUID/input returns that receipt without another deletion event. There is no schema migration, key reuse or installed deletion implied by source tests.

### Ticket lifecycle cleanup (CL-193)

Workers and the owner can read `ticket_cleanup_receipts(project_id, receipt_id?, section?, cursor?, limit?)`. With no `receipt_id`, this pure read returns a bounded newest-first summary page (default/max 50, `limit` 1–50), never full items or file descriptors. Each summary includes ID, time, cause, selected logical bytes, `item_count`, `action_counts`, `reason_counts`, `source_build_cache_count`, current aggregated byte `summary` and `bytes_state`, plus receipt metadata/settings. Existing byte-job summaries supply current outcomes without decoding their descriptor arrays. The durable `first_pass_receipt_id` remains addressable even outside the newest page. Settings reads these summaries and displays the same time, removed bytes, kept file count and byte state.

Supply `receipt_id` to page one retained pass: `section=items` (default) returns original ticket items with a small current `byte_deletion` ID/state/summary projection; `section=objects` returns exact linked byte descriptors as `{byte_deletion_receipt_id,item_index,object_index,object}` in ticket-item/object order; `section=source_build_cache` returns original retained-cache entries. All sections include the pass summary. Continue the same query using `has_more` and opaque `next_cursor` (null at the end). Each page selects at most `limit` entries and stops before its entry array exceeds 220 KiB; an individual oversize entry refuses with `RESULT_TOO_LARGE` rather than silently dropping audit detail. Default summary responses stay below 256 KiB on the qualified real-store copy. No durable receipt or byte outcome is rewritten. Cursors expire after 24 hours, bind project, principal, grant/session generation, store incarnation, receipt/section and limit, and refuse with `CURSOR_RESET` when changed. New passes reset list cursors; receipt or linked byte-job revision changes reset detail cursors. Restart that query without its cursor. Reads never create cursor rows or cleanup passes. `ticket_cleanup_preview` is removed; no cleanup activation command exists or is needed.

`project_settings_save` accepts `ticket_cleanup={done_evidence_enabled:Boolean, closed_purge_enabled:Boolean, closed_days:integer 1…36500}` with no preview digest. Defaults are true/true/15 and automatically apply to every project on startup. Existing expected project revision and `agent_rule_changes` enforcement apply. Saves restart the bounded scan; no activation or grace step is needed. Maintenance prepares at most one ticket action per pass on a separate read/utility lane with a bounded ticket-specific inventory. Its short writer commit fences relevant changed records and newly appearing references/holds; constant unrelated writes and project counter/revision/timestamp changes do not discard preparation. Cleanup settings, workspace roots and new references remain fenced. The transient change/reference journal refuses safely at 32,768 combined rows or 8 MiB of payload. Refusals back off for at least 60 seconds, durably across restart, and a fenced selected ticket is kept while its scan advances. Lifecycle passes and admitted byte continuations take fair turns, and the service rests at least four times each preparation’s wall duration (minimum 50 ms) between units. Ordinary requests keep serving during preparation. See [exact lifecycle, safety and accounting](archive-cleanup.md#done-evidence-and-aged-closed-tickets-cl-193). These commands launch no model and grant no manual purge authority to workers.

`ticket_cleanup_receipts` also returns a current `maintenance` observation on both list and single-pass reads, including before any pass exists: `state=disabled|due|scheduled|deferred|paused`, `next_check_at` (ISO 8601), and a deferred/paused `reason`. Scheduled CPU rest reports `reason=maintenance_yield` and its one-shot `next_check_at`; the durable preparation state remains its last outcome. Snapshot retention reports `reason=snapshot_retention`, `resume_condition=snapshot_retention_released` and `resume_at=null`: its completion time is unknown; the next 60-second check is explicitly dated. `maintenance.preparation` is durable and project-scoped, including before any pass commits: `state=preparing|idle|committed|deferred`, `attempt_count`, `attempted_at`, optional `committed_at`, `last_failed_at`, `last_failure_reason`, and `next_attempt_at`. Timestamps use ISO 8601; `next_attempt_at` is null after success. Unobserved fields are absent (empty object before the first attempt). A failure reason identifies a scoped record or the refused authority/budget, for example `fenced by concurrent write to record <id>`. Last-failure fields survive later success. Fenced semantic attempts admit no deletion; their kept pass item has `reason=fenced_by_concurrent_write`. Reading does not activate cleanup, create a pass or change its deadline. Deferred preparation and deadline failures retry automatically; archive/import failure suspension cannot suppress lifecycle scheduling.

Passes include `source_build_cache` retained-entry observations. `shared_source_build_cache` means recorded executions from multiple tickets use the retired producer's same capture/toolchain cache key; `unowned_source_build_cache` means no matching canonical execution/capture owner exists. Both stay; directory sizes are unmeasured (`null`), and no foreign ticket/session IDs are disclosed in this report. Exclusively owned regular cache files use the existing linked byte-job descriptors, fingerprints, holds and removed/absent/kept accounting. A directory byte descriptor marks `size_unknown=true`; its zero accounting placeholder is not a measured size. Current `source_review_execute` stays unavailable and cleanup launches no process. See [the exact ownership rule](archive-cleanup.md#done-evidence-and-aged-closed-tickets-cl-193).

The service preserves an already armed earlier maintenance wake when commands refresh its deadline. Frequent read traffic cannot repeatedly cancel and postpone the minimum-delay startup continuation; genuinely earlier work replaces it, and no pending work cancels it.

### One-way project transfer (CL-21)

Enrolled workers under `agent_rule_changes=allowed`, and the trusted owner, can call `import_preview`, `import_commit`, `import_receipt_get` and `import_rollback`. Assistants cannot. Preview returns a long-command operation; its preparation and receipt reads authorize and query through the read-only pool during backup capture, retaining current `write_admission` observations. Preview rechecks authority after source preparation in the same snapshot as its destination digest. File roots for workers must be inside their actual enrolled workspace; no-follow descriptor reads reject symlinks, traversal and non-regular files. No hook, command, HTML or embedded instruction executes. Only explicitly selected `checklist-project/1`, `synthetic-board/1`, `synthetic-client/1` and `synthetic-media/5` readers exist. Fictional fixture schemas establish no compatibility with an unselected real board.

Preview takes `project_id,path,source_format,source_namespace` and optional destination `epic_id`. The root contains `project.json` for canonical export, `bundle.json` otherwise. Legacy tasks require an explicit current destination Epic; canonical tasks map their exported Epics. Preview returns `checklist-intermediate/1` records with source-local IDs/raw payloads, actual source hash/time, counts, aliases/tags/status proposals, missing files, unresolved references, unverified note hints and duplicate blockers. `verdict_exports` selects one of `single-verdict`, `verdict-list`, `keyed-verdicts`, `round-envelope`, `direction-verdicts` with `version:1,payload`; filenames never select a layout. Limits are 16 MiB per JSON/file, 64 MiB aggregate, 1,000 file references, 30,000 intermediate records and 64 nesting levels. Oversized/unsupported inputs require a separately documented reader, never guessed mappings.

After reading the preview operation's final result, commit adds a fresh `command_id`, current project `expected_revision` and preview's `preview_digest`, keeping identical source/mapping inputs. Commit and rollback return operations whose final results preserve their former synchronous receipt replies. It rereads the source, validates its pinned file identities and hashes, the complete destination record/event boundary and namespace uniqueness, then atomically publishes mapped rows, inert history, receipt and command journal entry. Preparation pins the SHA-256 of every source file read; after acquiring the object gate, commit reads each available file once, refuses `IMPORT_PREVIEW_CHANGED` on a hash mismatch before writing imported objects or records, and parses only those verified bytes. Inode/size/mtime checks are additional fences, never substitutes for content verification. Source/destination changes require a fresh preview; duplicate IDs/aliases require source reconciliation. Same-command replay uses the durable receipt even after the source moves. A new command with the same namespace/hash returns `source_replayed`; changed/rolled-back namespaces refuse. Equal-text events with distinct source identities remain distinct. Generated local keys retain source keys as scoped aliases. Historical active/review task data has no live session or claim; legacy active work maps to Queued/Draft for reconciliation.

`import_receipt_get(project_id,receipt_id)` returns the archive and mapping receipt. History includes every source family/envelope, policy, setting, decision, finding, membership and unknown field as `historical_unverified`. Only ordinary tasks/taxonomy/groups/relations/available attachments and the icon are projected into current records. The source policy, owner decisions, review gates, endpoints, assistant names and claims never grant current authority. Destination root/settings/permission switch stay local; source settings remain auditable history. `import_rollback(project_id,command_id,receipt_id,expected_revision)` removes that receipt's created records only while the entire destination is untouched, restores its prior project metadata with a new revision and retains the receipt/audit and immutable bytes. Any later work requires compensating reconciliation. This is no native import wizard, cutover, dual write or in-place backup restore.

While a complete live interval waits for its page/context reads, a temporary window-local status read-ahead lane can consume newer complete coverage using its own observation cursor. It patches only newer known ticket statuses and retires older in-flight content epochs, including empty pages, before publishing. It never advances the applied cursor or certifies full context; the primary subscription still replays from its last applied cursor after failed/retired reads. The lane ends with its pending interval, query/window retirement, cancellation, reset or an error. This prevents a status commit made midway through slow reads from waiting for the entire page batch (CL-254 L254c).

Import-preview operation snapshots use source IDs before import assigns ticket UUIDs. Any later ticket purge conservatively expires those preview replies and errors, including small snapshots, as well as oversized operation results; the original command UUID stays reserved.

Any ticket purge conservatively expires all canonical operation error snapshots, including historical errors retained after a successful retry: private diagnostic text need not carry a matching ticket UUID. Operation identities and intent digests remain reserved.

UUIDs already accepted by the pre-existing backup FIFO keep that journal’s original intent, authorization generation and direct execution/replay route; they are not reaccepted as generic operations. A per-principal/UUID admission lock serializes the routing decision and durable acceptance across both journals, then releases before semantic/file execution. Different command IDs and ordinary reads do not share that lock.

Whole-project policy_preview/policy_propose/policy_apply, status_retire and relation_import also return operations. Uncapped media_publication_preview, media_type_adopt/media_type_retire, media_context_approve and media_round_finish/media_round_successor do likewise. project_edit/project_settings_save become operations when brief or pinned_decisions can trigger project-wide context propagation; settings saves with policy/policy_proposal_id are also operations. Cosmetic project edits and short no-copy media leases remain synchronous. Media publication-preview results retain the original read envelope without an added command_id; their canonical journal stores one semantic payload, not a nested envelope.
