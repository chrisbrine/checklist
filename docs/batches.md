# Fixed Triage batches

Each Triage has an immutable `PREFIX-Tn` key beside its name. Batch snapshots and receipts include `triage_key` and `triage_name`; members, claims, results and blockers include ticket `key` and `title` beside `task_id`. Older frozen batches receive display fields in projections without rewriting their stored snapshot or digest. Membership history names the Triage by key and name. Reports, notes and checkpoints cite `KEY "Title"`, with project name where needed, while commands keep stable IDs.

A prepared batch is an immutable selection from one Triage in one project. It records one phase, exact task and acceptance revisions, exact review-request and manifest revisions/digests when reviewing, normalized file and lane scopes, checks, the applicable policy snapshots, and the originating Triage revision. Preparing evaluates the whole selection without acquiring claims. Claiming validates the whole snapshot and reserves every member in one transaction. A stale task, changed request, conflicting scope, unavailable verification slot or denied reviewer rejects the entire claim.

Later Triage adds/removes affect future batches. They do not rewrite prepared membership, cancel work or move a ticket's Epic. A ticket may be in several Triages but still has one exclusive current task claim. Membership intervals and separate departure records retain entering/leaving history. Legacy memberships retain their observed join time and explicitly unknown originating revision rather than inventing an old revision.

Each Triage has one explicit phase, `implementation` or `review`. An implementation Triage may be planned in advance with Queued tickets (Draft or Ready, with or without open prerequisites), ordered with prerequisites first; claim its Ready members through a frozen batch so membership stays. For individual work, claim the ticket first, then add the In Progress ticket to an implementation Triage. Submission changes it to Review and removes it from that implementation group, including legacy manual milestones. Create a separate review Triage for the submitted exact targets; claim review before adding, or use an actual atomic review batch claim. A review verdict leaves the review Triage. Complete passing tickets once all their own gates pass; only failed or remaining tickets enter another implementation pass. Review members cannot be added to implementation groups and queued implementation tickets cannot be added to review groups. A nonempty established Triage cannot switch phase. Legacy homogeneous handling metadata supplies a derived phase; unresolved legacy groups require an explicit phase choice without silently deleting memberships.

Individual status actions, including explicit same-status marking, remove all current Triage memberships. Notes, attachments and metadata edits retain them. Actual batch claims retain their selected phase membership; atomic batch submission/verdict still departs members when that phase finishes. Same-phase ordinary group status actions retain membership. Returning a review group to implementation/parking, canceling a phase, or reaching Done departs the affected handling groups. A rejected departure is never labeled accepted. Zero-gate Done is labeled **No review required**; owner-waived findings stay explicitly waived. A batch ID never provides a public retention bypass.

## Discovered service commands

Workers must discover the installed server's catalog before using these commands. Source implementation alone is not evidence that an older installed build exposes them. All writes use a UUID `command_id`; all commands use `project_id`. Batch records remain revision 1; later dispatches and results are separate records/projections.

| Command | Inputs beyond project/command | Result and guards |
| --- | --- | --- |
| `batch_prepare` | `triage_id, expected_revision` of Triage, `phase, tasks, checks?` | 1–200 unique current members. Implementation member: `{task_id,expected_revision,file_scopes?,lane_scopes?}`. Review also requires `{review_request_id,target_manifest_id,gate}`; implementation cannot include review selectors. Returns immutable batch/digest. |
| `batch_claim` | `batch_id,expected_revision,policy_revision` | All members or none; returns each actual attempt/claim token. Lost-response replay rotates tokens for still-live original claims. Tokens are excluded from durable command outcomes. A dispatched batch cannot be dispatched again. |
| `batch_get`, `batch_list` | `batch_id` for get; optional `triage_id` for list | Frozen records, dispatch reference and current per-member outcomes, with the exact target behind each outcome. |
| `batch_submit` | `batch_id,expected_revision,members` | Every actual active implementation claim of that batch exactly once. Each member contains its ordinary `attempt_id,claim_token,acceptance_revision,evidence_manifest,direction_cursor?`. All submissions validate and commit together. |
| `batch_review_record` | `batch_id,expected_revision,members` | Every actual active review claim of that batch exactly once. Each member contains its exact request/manifest/gate, claim, verdict, checks, findings and observed direction cursor. Pass/reject outcomes can differ; all are recorded atomically. |
| `batch_complete_passing` | `batch_id,expected_revision,expected_direction_cursors` | Completes accepted current exact targets independently through ordinary completion guards; returns successful IDs and per-ticket blockers. Cursor map contains exactly the accepted, not-yet-completed candidates and comes from caller-observed task context. It never refreshes directions on the caller's behalf at commit. |
| `batch_retriage_remaining` | `batch_id,expected_revision,name?,purpose?` | Creates separate implementation/review handling sets for failed, stale, unclaimed or otherwise remaining tickets according to their current phase. Passing/completed tickets are excluded. Active work must finish or safely release first. An empty remainder is a no-op. |

The shared `review_batch_policy` default is `complete_passing_independently`: accepted tickets can become Done while failed/remaining tickets continue. An explicit project override, `hold_passing_for_batch`, holds automatic batch completion until all batch members are accepted. The override never creates work on an already accepted ticket or weakens an individual ticket's gates. The batch pins the policy that applies to its handling pass. A member whose gate waits for more evidence after an `evidence_missing` verdict has the outcome `evidence_requested`; it is neither failed nor accepted. Open advice findings do not make a member failed, and a member held for a release set (`release_set_holds`) reports its `release_hold`; `batch_complete_passing` leaves it to `release_set_complete`.

Carry input-valid passing acceptance/check-case results through rework and report them separately from newly executed checks. Select only failed, inconclusive or materially affected cases, including after fixture-only repairs; see [shared review handling](policies.md#review-handling-shared-by-every-project). Membership or a sibling failure alone does not justify reruns. A batch-completion hold alone does not invalidate passing case evidence or weaken fresh target-bound gates.

## Actual orchestration and Active

A Triage can be coordinated by an actual connected Codex or Claude session. `triage_orchestrate` takes `triage_id,expected_revision,action:start|checkpoint|finish` and optional `progress,reason`. Start derives the actual caller session, provider, execution domain and authorization generation and checks coordinator eligibility. It never accepts an arbitrary session identity, launches a model, assigns a member ticket or manufactures a member claim. The recorded session checkpoints/finishes its coordination; the owner can explicitly finish a stale recorded coordination with a reason. A disconnected/ended session produces a recovery indication, never automatic abandonment.

A ticket appears under **Active** when its own work is in progress or it belongs to a Triage with actual in-progress member work or recorded active orchestration. `active_attention` exposes that derived handling state while each ticket retains its truthful status and claim. The group still has no independent editable lifecycle status: phase, member-derived status and actual orchestration receipts are separate facts. In Progress tickets remain addable to a compatible implementation group.

## Navigation and retention

Empty and archived Triages leave the active ticket list. The existing **New triage** flow remains; **Past triages** opens empty/archived handling records so an empty Triage can be reused and an archived Triage restored. Archiving does not archive/delete member tickets, change Epics, release claims or modify a fixed batch. The Triage overlay shows fixed batch summaries alongside the current editable handling set.
