# Provider and assistant integration plan

**Development integration status, 16 October 2026.** The app, shared service and official-SDK MCP executable exist. The primary connection contract is automatic actual-host/session/workspace bootstrap when a provider thread uses bundled CLI/MCP, with actual worker status/history/recovery on each ticket and no active assistant settings/sidebar/grant UI. Installed-version observations and source support do not qualify every native route. Personal-assistant/Dot integration was cancelled on 22 October 2026 (CL-3 and CL-22). Its historical identity contracts and separate future provider adapters are defined in [assistant identity](agent-profiles.md); current limitations are in [implementation status](implementation-status.md).

The CL-128 source refactor now resolves existing behavior through the [versioned bundled provider-plugin interface](provider-plugins.md), with separate declared and host-qualified capability metadata. Existing observations below retain their original producer/version/target limitations; component checks and a disabled synthetic plugin are not new installed/native receipts. No provider/model was installed or launched. Later adapters use that document’s controlled packaging, explicit authorization, identity/route qualification and disabled recovery procedure.

## Claude relay reply listener

The service listens at `/tmp/cc-socks/<service pid>.sock`, a folder that Claude Code also uses for its own session sockets, with the same name pattern. The service therefore owns one file there. At start it replaces a file at its own PID name only if the file is a same-user socket that refuses a connection; each other existing path refuses (CL-415). A process names its socket with its own PID, and no other live process can have the service's PID, so a socket at that name has a dead creator. Darwin also refuses a connection to a live listener with a full queue, so the connection test alone does not prove that a socket is stale; the name rule does. `bind` never replaces a file, so a process that creates the path after the removal makes the start fail and keeps its file.

A SIGTERM or SIGINT stop removes the socket and then ends the process with the signal's default action. A crash or SIGKILL leaves the socket, and only a later service with that PID replaces it. The service never sweeps the folder, because it cannot tell its own older sockets from Claude's by name. A failure appears in [`service_info.native_reply_listener`](mcp-contract.md#native-reply-listener-state) and on the Claude provider card.

## Installs and running MCP shims

An install replaces the bundled CLI. A running MCP shim can still use the earlier executable from the previous bundle or the Trash. Its cdhash no longer matches the service. Before CL-171, XPC could reject its messages before delivery and the client reported `OUTCOME_UNKNOWN`.

CL-171 keeps command admission exact for the installed GUI and CLI cdhashes on each message. An earlier Checklist identity gets only a fixed `CLIENT_OUTDATED` reply: no command ran. Other identities are refused. No earlier hash gets command access.

A shim with this fix saves its launch path, its own cdhash, its instance (slot, bundle identifier and Mach service name), and the resolved bundle root at startup. Before each tool or resource request it checks that file, with a signature cache keyed by device, inode, size and modification time. A changed build or `CLIENT_OUTDATED` reply switches the bridge to the signed CLI at that same path. Before each delegated child starts, the shim follows launch-path symlinks and checks the resolved bundle root and instance again. Both must match the startup values. The parent then uses `posix_spawn` with `POSIX_SPAWN_START_SUSPENDED`. Before `SIGCONT`, it gets the suspended child's dynamic `SecCode` by PID and calls `SecCodeCheckValidity` with the exact pinned `cdhash H"<hash>"` requirement. Only a successful dynamic check admits the loaded code. It also checks that the kernel executable path resolves inside the captured bundle root. Unchecked static signing information is used only for refusal diagnostics. On a mismatch or check error, it kills and reaps the suspended child before that child can execute an instruction. The delegate alone adds an instance expectation to the child environment. The CLI checks its own resolved slot, bundle identifier, Mach service name and bundle root against that expectation immediately after instance resolution, before Checklist IPC, a credential read or bootstrap. This check also refuses an Info.plist swap after the parent check. A mismatch returns `DELEGATE_INSTANCE_MISMATCH`, says no command ran, and keeps the original command ID. These two checks keep a test-slot delegate from using the live instance or another slot, and keep a live delegate from using a slot. Static cross-bundle replacements are still refused before spawn. The bridge keeps the SDK transport and queued requests and sends one `notifications/tools/list_changed`. Each request starts a child CLI with the same working directory, environment and connection arguments. Tools use `tools` or `call NAME -`; resources use `call service_info -` or `call project_list -`. JSON arguments go through a fresh child stdin pipe, with a 1 MiB limit; the child never reads MCP stdin. No timer or background worker is added. A missing or invalid CLI gives a clear error that says to reconnect; the MCP server stays up.

A delegated result is valid only after a normal exit with status zero and JSON stdout, or status one with a final `Checklist: CODE: message` stderr line. Recovery diagnostics are not command errors. Other results return `OUTCOME_UNKNOWN` with the original `command_id` and reason `delegate_ended`. A spawn error returns `DELEGATE_LAUNCH_FAILED` and says no command ran; reconnecting does not fix an argument-size or executable launch error.

On `CLIENT_OUTDATED`, retry the call once. If it repeats, use the Codex or Claude host's MCP controls to restart or reconnect this conversation's checklist MCP server. The error carries `details.recovery_action: "restart_mcp_server"` and explicitly says no command ran. Reopening the Checklist GUI alone does not restart that host process. Shims started on a build before this fix still need a manual reconnect after the next install. Until then, for `OUTCOME_UNKNOWN` just after an install, reconnect or use the fresh installed CLI from the project folder. Retry the same method and input with the same `command_id`; do not create a second mutation. A real connection loss after delivery still has an unknown outcome.

## Honest delivery

Saving a note commits content and exact-recipient outbox atomically. Show **Saved / queued**, **held/refused**, **provider accepted**, **recipient acknowledged** and **addressed** separately. An acknowledgment names the actual recipient generation; a parent receipt is not its child's. A model report is not owner-read. Target the current attempt/explicit resolved host-assistant identity and enrolled route, not the most recently seen label.

The sender's actual permission class belongs in the provider's required parsed envelope. Missing metadata may hold; a diagnosed omission can be corrected truthfully. Never impersonate another mode/own-child sender or borrow another session's token. A genuine provider hold uses only its actual approval path. Some hosts cannot display a live approval dialog; show held/expired and that limitation rather than promise a nonexistent button.

A design target is to begin transport within one second on an awake connected Mac; model consumption can occur later. This is not a measured latency promise. For uncertain provider acceptance, reconcile with supported stable message IDs or retain uncertainty without automatic duplication. After two identical route failures, suspend and show a repair action. Ended targets retain context for eligible pickup; no hidden model launch or old-session wakeup.

Check current grant and route generation immediately before an external send. Revoke unsent work and cancel in-flight I/O where possible. Bytes already submitted cannot be recalled; retain truthful timing/outcomes, reject subsequent reads/replay and never claim remote retraction. ## Native conversation closure qualification (CL-38 / CL-83)

The [closure contract](work-authority.md#confirmed-native-conversation-closure) requires the exact native process and its applicable registry to be gone or verifiably replaced. Current route capabilities are:

| Route | Process evidence | Conversation registry evidence | Qualification still needed |
| --- | --- | --- | --- |
| Claude automatic worker | Kernel PID and start identity; exit event observation | Secure bounded native PID/session registry; directory change observation | Installed service ends the exact generation and returns work; real second conversation reuses the PID or socket path without receiving the old delivery |
| Codex native worker | Signed host PID and kernel start identity | No qualified per-conversation registry/process boundary in the shared host | Closure remains unknown; a supported per-conversation observer is missing. MCP disconnect, idle/completed turn and thread unload cannot replace it |

This table records source capabilities and missing evidence, not a native pass. Core fixtures prove transactional release and generation fencing. Bridge tests use owned non-host processes, private registry fixtures and test sockets; even a real kernel exit or socket write in those fixtures does not prove a native conversation closed or a new conversation reused its address.

A bounded installed qualification must retain the following receipts against the exact build and provider version, using synthetic tickets and explicitly selected native conversations:

1. Record the first conversation's actual scoped session, enrollment/authorization generation, PID/kernel start identity and verified registry/socket identity. Claim synthetic implementation work (and separately review work), then queue a uniquely identified comment for that exact recipient. Preserve its message/delivery IDs and unacknowledged state.
2. Close that native conversation through its host. Observe the original process absent or verifiably replaced **and** its original registry absent or verifiably replaced. Record both observations; an unreadable or malformed registry remains unknown. Do not substitute closing Checklist, its MCP shim or a turn.
3. Read the resulting session, attempts, ticket/review request and history through the service. Use `message_delivery_list(project_id,task_id,message_id)` for the pending note: retain its exact delivery ID, recipient authorization generation, `state=fenced`, `fenced_at` and matching `native_closure_ref`; new closures also record `message_delivery_fenced` in ticket history. The read requires project read scope and returns no inbox contents or credentials. Verify the generation ended, tokens are fenced and eligible work returned for pickup. A running source execution or writable descendant must keep release pending. No ticket becomes Done, no verdict appears and no delivery becomes acknowledged because of closure.
4. With a real second native conversation, observe reuse of the old PID or socket path, recording its different start/session/generation identity. Exercise ordinary dispatch and recipient inbox pickup, retaining results that show the old message is absent. Send a fresh uniquely identified control to the new conversation and verify its actual pickup to establish that the route was exercised. A test process, forged registry or synthetic socket is only a component control. If reuse cannot be observed, record that case as unqualified.
5. Verify a host-resumed conversation with the same native session ID receives a new authorization generation only after old work returned; its old token and queued message remain fenced. An owner-disconnected conversation must stay refused until the owner selects Allow again in its ticket’s session view. CL-234 adds those owner controls in source; Core refusal/component tests do not replace its non-contributor installed Codex test-slot disconnect/resume observation. Then verify Allow again permits a fresh native connection without reviving old claims or queued deliveries. Record that observation under [CL-234](implementation-status.md#cl-234-owner-disconnect).

Keep these receipts private installation evidence. Perform no new enrollment, model launch, permission-mode change or schedule without its own authorization. Independent review of the exact composed target remains separate from this qualification.

## Capability qualification and revocation

Qualify each installed adapter version/capability separately: native identity, workspace or assistant binding, message push, busy/idle, exact child route, event callback and host report. Show **verified**, **checkpoint/manual only**, **unavailable** or **unqualified** with source/time/version. Provider updates make affected qualification stale; they do not silently switch runtimes. A host display name/personality, manifest or stored desired model is not a qualification record.

Use synthetic sessions/tickets and deliberate enrollment. Prove both native provider directions, real parent/child receipts, lost replies, holds/expiry, quota/permission prompts, sleep/wake, closed clients, revocation during send and reconnect. No transcript scraping, unrelated process discovery, schedule or new runtime is a qualification substitute. Simulations exercise deterministic state only.

The assistant plugin is generic; initial Dot is one adapter, not the product's universal definition of a named agent. Public packaging and its tested surface/version remain explicit. [Plugin packaging](https://developers.openai.com/plugins/build/plugins) and [desktop-only packages](https://developers.openai.com/plugins/deploy/desktop-only) describe candidate distribution, not proof of the installed binary or a public-directory approval. Personal installation, source publication and public marketplace distribution are separate steps.

## Work health pickup boundary

System [work health](work-health.md) requests go through the Claude relay when the exact session has a verified native endpoint (CL-386), and they stay on exact-session MCP pickup. A Codex app thread has no such endpoint, and the Codex queue route skips every `origin=system` delivery, because a service timer starts no turn in a Codex thread. Such a request stays in `session_inbox`, unchanged, with the push state that shows "Queued for agent pickup". It also gets no hook context (CL-389/412). It relays at most once per progress state, never during a known wait, at most 3 times per attempt and once per session in 20 minutes, to its handler only. A durable queue entry or relay write is neither a resumed host turn nor a response. Health checks do not install adapters, enroll sessions, enable assistants or launch/poll models. Current/native provider route qualifications remain unchanged; installed health visibility and actual host pickup need their own synthetic observation.

Settings → General shows project-scoped Claude and Codex cards after explicit Refresh. The current ticket's observed handler is named when available. Local candidate paths, values, observation time and missing live inputs are shown separately from delivery receipts. Refresh and guidance are read-only; no SDK is downloaded, provider process/model launched, permission/grant changed or provider file written. Project/recipient/generation/store changes and service events (including a later host hold) invalidate observations and fence late reads. Guidance names the user-scope top-level key, all-local-senders effect, terminal /config option when supported and project/admin remedies. Automatic durable settings writes remain deferred. These readiness cards retain **Pickup only** until their app-route disclosure is qualified; the CL-413 relay, on since build 273, and its checks are recorded above. Queue/resume/notify/hooks alone are not qualification or acknowledgment. Installed exact-build display/fixture checks remain a separate requirement; source tests do not qualify a native delivery route. See [setup](project-setup.md#messages-to-claude-conversations).
