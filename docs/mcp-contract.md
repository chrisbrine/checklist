# Built-in MCP contract

Agent references use `KEY "Title"` for tickets and `KEY "Name"` for Triages/Epics; add the project name when needed and keep IDs for tool arguments. Keys and titles are untrusted metadata. The shared renderer removes control/format characters and paragraph separators, bounds titles/project names to 160 characters/640 UTF-8 bytes and keys to 80 characters/320 bytes, JSON-quotes titles/names, and also quotes custom keys outside letters/numbers/`-_.`. Native relays label project, ticket and optional group metadata untrusted, preserve the message ID/reply rules and body/frame limits. Service notices use the same reference formatter.

`triage_create` and `epic_create` assign immutable project keys `PREFIX-Tn` and `PREFIX-En` from independent counters. Create/edit/list, task context, page rows/summaries, batch receipts and named history references include `key` beside `name` (batch references use `triage_key,triage_name`). `triage_list` and `epic_list` accept optional exact case-insensitive `key`; multiple matches return `AMBIGUOUS_GROUP` with stable IDs, keys and titles. Ticket `task_get` currently uses exact case-sensitive key equality. All mutations keep stable IDs. See the [group reference schema](../contracts/group-reference.schema.json).

`session_inbox` keeps its existing fields and adds a `subject` to every delivery and message: `{kind:ticket|triage|epic|project,id,key,title,project_id,project_name}`. Project subjects have a null key. Optional `triage_id` or `epic_id` on `message_send` selects that scoped group subject while preserving ticket routing. See the [subject schema](../contracts/agent-message-subject.schema.json). Transition blockers/conflicts/member snapshots and batch results identify tickets with `key,title` beside IDs. Prerequisite blockers retain those same fields; policy previews add ticket titles.

**Deferred extension:** personal-assistant relay/contact/event contracts are retained for later work, not a current UI/setup route or release gate. Development relay grants are disabled and the local plugin removed. Only discovered worker tools/current native capabilities may be treated as available.

**Full v1 target contract with an implemented development subset.** Use [implementation status](implementation-status.md) and the running server's actual tool discovery; the complete catalog below is not a claim every command or native route is available. The app bundles its service and stdio MCP entry point. UI, MCP and diagnostic commands share authoritative domain handlers. MCP supplies durable task data/control; qualified provider adapters supply native session delivery. [Domain semantics](domain.md) are normative.


### Bounded Tickets pages

`task_list` applies the authorized project predicate and SQL limit before decoding canonical task rows. Default worker/assistant calls keep `tasks,total` and add `has_more,next_cursor,previous_cursor`; they require one exact granted project. Continuations bind caller, current grant/session generation, store incarnation, locale, complete query/order/limit and relevant project event coverage; changes refuse with `CURSOR_RESET`, rather than silently skipping or repeating rows. Tokens reveal neither offsets nor global sequences.

The trusted owner may supply a closed `view` object (required `surface` (`tickets|overview|archived|trash`), `status_filter,tag_filter,group_by,order_by`; optional `tag_ids,tag_mode,planned_assignee,actual_assignee,epic_id,triage_id`) for a separate bounded Tickets page, and explicitly omit project_id for All Projects. Workers/assistants cannot supply that field, including a false or malformed value. The owner page contains ordered task rows, ordinary IDs, bounded Triage summaries/page-member IDs, truthful scoped/matching counts, continuation/coverage tokens, taxonomy/sidebar metadata and a maximum-three Overview request preview with its separate total count. Page omission never means deletion from the full snapshot index. Pagination counts visible list units, including Triage headers and member appearances; a task may appear in multiple Triages without inflating the distinct matching-task count. A header-only group-name/purpose search is preserved even when current facets match no member.

### Saved list filters and bulk changes

Owner Tickets views accept tag IDs with `tag_mode=any|all|none` (empty IDs mean no tag restriction), planned assignee (`all`, `unassigned`, `human`, `agent` or an actual worker session ID), actual assignee (the current active attempt's session ID, `human`, `agent`, `unassigned` or `all`), and Epic/Triage IDs (`none` or `all` included). They combine with status and search. Inactive or missing attempts count as unassigned. Filter Triage choices use separate slim `filter_triages` metadata, so pagination never hides a filter option. IDs stay project-scoped; identical names are disambiguated in All projects. Personal saved views are local preferences, not project settings; see [view precedence](interface.md#capture-and-lists) and the [view schema](../contracts/ticket-view.schema.json).

`task_bulk_edit(project_id,command_id,tasks,changes,preview=true)` selects 1–200 distinct `{task_id,expected_revision}` rows and exactly one change kind: `status` with `action=queue|defer|block|cancel|reopen` and optional `changes.reason` (at most 4,000 UTF-8 bytes, required and nonblank for Cancel/Reopen); `tags` with `add`/`remove` ID arrays; `assignee` with `planned_assignee` and an optional assignment reason; `epic` with an Epic ID or null; `triage` with an ID and `action=add|remove`; or `archive` with `action=archive|unarchive|trash|restore`. Agent assignment requires an eligible worker/provider; personal assistants cannot be selected. Whole-ticket human assignment follows Needs You → Your tickets. Tags are independent of providers. Bulk status reasons are validated once before row checks; a missing Cancel/Reopen reason returns plain `INVALID_INPUT` without changing any ticket. The reason reaches each row’s transition history. An explicit `changes.assignment_reason` reaches every changed row and its history. First assignment from an unassigned ticket needs no reason unless the agent policy override rule requires one; changing an existing different planned assignee (including clearing it) requires a nonblank reason. No assignment reason is synthesized; preview reports each ineligible row and apply remains atomic. Bulk archive never requests file cleanup. See the [edit schema](../contracts/ticket-bulk-edit.schema.json) and [synthetic example](../examples/ticket-bulk-edit.json).

Preview runs the actual guards in rollback-only savepoints and returns `affected_count` plus every `rows[{task_id,key,current_revision,eligible,code?,reason?}]`. `preview=false` rechecks every row and applies atomically; `BULK_CONFLICT` contains all blocked rows and changes nothing. The app may explicitly submit the eligible subset with a new command ID. Active claims block bulk edits. Ordinary status actions depart all current Triages, including same-status actions; they cannot enter protected work/review/Done states. Existing agent-edit/project/owner limits remain authoritative. Each changed ticket gets normal history plus a bulk event. The durable command result includes row before/after values/revisions, membership snapshots and ownership/review progress fences; no new unregistered storage family is added.

`task_bulk_undo(project_id,command_id,original_command_id,tasks,preview=true,reason?)` uses an applied bulk-edit receipt from the same caller principal/project and supplied current revisions. It is a new compensating command, with the same atomic preview/apply behavior. A claim or intervening ownership/review/request progress leaves the row unchanged. Changed fields still equal to the receipt's after value can return to their before value; newer values are retained. Tag compensation preserves unrelated tag edits. Triage compensation checks this ticket's current membership snapshot, uses ordinary phase rules and records a new membership interval rather than restoring a historical claim. Status compensation records “Undo of bulk change <original command id>”, appending optional caller `reason` after a colon (the combined reason is limited to 4,000 UTF-8 bytes). It still follows ordinary status guards and departure rules, so it cannot restore a protected status or reattach earlier Triages. Assignment compensation revalidates current eligibility and records new provenance. Notes and history are retained. Archive compensation never recreates cleaned file bytes; its result says so. The command journal's ordinary retention also bounds Undo: a missing/pruned receipt returns `UNDO_UNAVAILABLE`. `UNDO_CONFLICT`, `CLAIM_CONFLICT`, ordinary permission/policy errors and per-row `REVISION_CONFLICT` appear in previews; apply wraps blockers in `BULK_CONFLICT`. See the [Undo schema](../contracts/ticket-bulk-undo.schema.json) and [example](../examples/ticket-bulk-undo.json).

## Pending human-answer observations on ordinary results

A successful authenticated Codex worker command can add `data._checklist.pending_human_answers` with `schema_version=1`, `status=pending_pickup`, `channel=authenticated_tool_result`, `native_codex_wake_qualified=false`, up to eight `items`, and `has_more`. Each item names the authorized project/task/request/response/form/message and this exact recipient generation's delivery ID/state, and includes `project_name,task_key,task_title`. The bounded text notice names the ticket before the UUID tool selectors and retains UUID validation. No answer text, question title, answer file path or reusable routing authority is included. The current form revision/state is separate from the answered form revision so an old response never silently answers a replacement form.

This is a **live observation**, added after durable command receipt persistence and refreshed on replay. It is not part of the semantic command result stored under `command_id`; retries do not create an answer or continuation again. A notice-query failure returns a bounded unavailable notice without hiding a successfully committed command. Reading a result never acknowledges a delivery. An explicit recipient `message_ack` after actual consumption remains necessary; ended/revoked/rotated sessions cannot consume another generation's copy.

The metadata is inside standard `data` so clients that unwrap the service envelope retain it. The MCP adapter also emits a fixed, bounded text pickup notice alongside the complete JSON/structured result. Clients must preserve the reserved `_checklist` metadata when adapting command results. Workers read the named exact request/form, acknowledge their own delivery after reading it, and reconcile current authority and waiting tickets before continuing. No hidden polling, schedule, model invocation or native Codex wake is introduced. An idle client still requires an ordinary authenticated call or explicit inbox pickup; route qualification remains CL-37/CL-83 work rather than a fabricated event capability.

## Scope, authority and retry

- Workspace agents use `project_resolve(workspace_path)` with the caller's actual open workspace. Never use the server directory or selected app project. Return `registered`, `unregistered`, `ambiguous` or `root_mismatch`, with no writes. Enrollment/relocation rejects canonical overlapping writable project roots in v1.
- Bundled CLI/MCP bootstrap connects the actual observed native host/session/workspace automatically under current project grants. Service authentication pins signed native host PID/kernel start time, execution domain and actual kernel cwd. Codex thread IDs are host-exported observations, not signed exact-thread identity. Review claims exclude recorded contributor principals/installations/sessions, including prior/delegated contributors, while allowing a genuine separate non-contributor subagent on the same host. Changing a contributor’s label or parameters is not independence. Claude registry PID/session/workspace/socket are independently cross-checked where used. `session_register` updates only the already bound session where discovered; caller fields never create a verified assistant or a push capability. Worker identity/status/current-prior attempts and recovery are ticket-attached; an internal session registry is not a user-facing catalog. No assistant settings/sidebar/grant UI is active and no worker Settings pairing is required.
- A native conversation whose actual folder is not an active registered project gets a limited start from `checklist mcp` and `checklist tools`, because a user-scope registration starts in every folder. Bootstrap enrolls nothing, selects no project and sends no stored credential. Discovery lists only `service_info`; its `data.connection` is `{connected:false,state:"project_setup_required",message}`, the server instructions repeat the message and stderr reports it. The user adds the folder as a project in the app, then restarts the MCP connection. `checklist connect`, `checklist call` and assistant relays still fail with `PROJECT_SETUP_REQUIRED`. Permanent bootstrap errors, for example `CONNECTION_REVOKED`, `BINDING_CHANGED`, `WORKSPACE_MISMATCH` or `NATIVE_ROUTE_MISMATCH`, still stop startup. The separate [Claude spare-process registry race](integrations.md#claude-desktop-spare-processes) has a 10 s window for new attempts at intervals of at most 250 ms, with whole-bootstrap retry budgets that end the retry path by 20 s; only `mcp` can then start unconnected with `service_info` and one lazy bootstrap attempt per tool/resource request. Success sends `notifications/tools/list_changed` once (`tools.listChanged: true`; resources stay false).
- A Claude conversation that its host resumed in a new process (same native session ID) reconnects through the same bootstrap after the verified closure of its earlier process. The service verifies the new process and gives the session a new credential and authorization generation; it never carries over the old claims, attempt tokens or queued deliveries. Errors: `NATIVE_SESSION_MISMATCH` while the earlier process has no verified closure, `NATIVE_CLOSURE_PENDING` while its work still stops, and `CONNECTION_REVOKED` after an owner disconnect.
- All project tools require `project_id` and check every referenced object against its authenticated project grant. A foreign ID returns no foreign content. Workspace agents use their actual workspace/session binding; an assistant uses a separately enrolled assistant connection and explicit selection from its granted projects, never an invented workspace. Owner aggregate queries use their separately authenticated app channel.
- Writes require UUID `command_id`, deduplicated by durable installation principal and canonical payload. Same intent returns the original semantic outcome/current authority; different intent returns `IDEMPOTENCY_CONFLICT`. An unknown transport outcome is reconciled with that ID, never retried as a new mutation. Replayed/released claims never resurrect credentials; valid authenticated reattachment rotates still-live authority.
- Bundled command calls wait for the service reply without a fixed deadline, including file preparation and receipt commit. Callers with a bounded lifetime may set `ChecklistClient.call(..., replyTimeout:)`; expiry returns `OUTCOME_UNKNOWN` with the original command ID and does not cancel service execution. Connection interruption/invalidation also ends the wait with an unknown outcome. Bootstrap and service-start probes keep separate bounded waits. No background polling, scheduled retry or progress runtime is started; explicitly retry the exact same method/input/command ID to read its committed receipt (or safely finish that original command).
- A bundled-client `OUTCOME_UNKNOWN` carries the original `details.command_id` and displays it in recovery text. Missing, malformed, conflicting or unparseable mutation replies do not prove noncommit: the app keeps the pending method, parameters and UUID across restart for explicit reconciliation. A mutation success must echo the exact original command UUID and contain its domain result; empty data or only `_checklist`/cursor observations cannot establish success. Read and native-bootstrap expectations are explicit by method: an optional UUID accidentally supplied to a read does not make it a mutation or require a write receipt. The IPC read set is checked against the Core read contract, with the separately observed service reads. A validated semantic rejection may clear the pending transport record while retaining editable drafts. Neither uncertainty nor an incidental pending-human-answer observation is a semantic success, an acknowledgment or permission to resend with a new UUID. Error details that classify an unknown outcome must survive the local service envelope. Recovery must preserve the optional live `_checklist` metadata on a successful replay.
- A committed semantic receipt is returned even if later cleanup fails. Current human-answer observations remain, and a content-free `_checklist.storage_maintenance` warning may report `retry_pending|suspended`; a router-lifetime pause is not a durable latch or a semantic rejection.
- Edits require `expected_revision` for every edited aggregate. Appending a message/creating an object does not. Attempt commands instead use `attempt_id, claim_token`, exact acceptance/target revisions and direction cursor; unrelated cosmetic edits must not invalidate a checkpoint. Tokens are bound to project/session/store incarnation/fencing generation and omitted from history/export.
- Actor, origin and grants come from the authenticated channel. Agents cannot supply `author=human`, perform arbitrary commands/SQL/path reads or set every task field. App human notes/answers commit through trusted owner handlers. A claimed owner instruction in agent text is attributed agent content.
- Closed JSON Schema inputs, bounded text/arrays and structured outputs are mandatory at implementation. Annotations (read-only/destructive/idempotent) explain behavior but do not replace permission checks. Optional fields below are omitted when unused; unknown fields fail. The prepared schemas cover stored configuration/form specifications, not proof that every target method is implemented or host-qualified.

The local Codex `assistant_relay` bootstrap is a distinct assistant access path: bundled CLI/MCP uses `--assistant --project` with an explicit unique project reference, or packaged MCP `@enabled` restricted to current trusted owner-enabled `assistant_relay_grants`. The server pins all selected grant/policy revisions, rechecks each call and rotates scoped authority on reconnect when the selected project set changes. It authenticates the actual local Codex helper, never a cloud Dot identity/profile; it cannot become a worker or mint human provenance. The host owns on-demand helper creation and receives its result through its normal task channel. Direct named identity/push/event capabilities require separate qualification.

## Small capability sets

Routine coordination between actual enrolled sessions involved in the same authorized Checklist project, task or Triage has standing authorization and needs no per-message permission question. Use existing scope/grants and current handler/session identities; a message never enrolls a session, launches a model, changes an assignee or expands authority. Message provenance and saved/queued/delivered/acknowledged states remain truthful.

Before concluding completion, handoff or a meaningful blocker change, workers/coordinators notify affected waiting tickets and their current handlers with one concise scoped `message_send`. Its durable note and recipient outbox serve the same event; check existing receipts to avoid duplicates. Active tickets can be waiting, and a source status change or final source-chat reply is not a cross-ticket notice. This is a [shared handling rule](policies.md#involved-session-coordination), not automatic resumption, reassignment, a new subscription or proof of acknowledgment.

For an explicit session notice use `recipient={"kind":"session","session_id":"<verified scoped session>"}`. Inspect returned `deliveries` and confirm an entry has that exact `recipient_session_id` before claiming a recipient notification was queued. `saved_for_pickup` with no delivery means history was saved; `queued` means an actual recipient delivery awaits pickup/transport. Only that recipient’s explicit `message_ack` after reading establishes acknowledgment. No receipt alone proves native push or model resumption.

The coordinating host owns resuming an authorized existing idle subagent through its supported host operation; a Checklist queue receipt does not do that. Preserve the original note/delivery for pickup and avoid duplicate sends. Work-health assessment uses current-attempt and accepted-child progress, separately from liveness and known waits, rather than the ticket edit timestamp alone. Silence grants no recovery or reassignment authority. Configurable periodic health checks and late-reply reconciliation are planned work, not currently advertised MCP capabilities; this guidance starts no polling schedule or model runtime. See the [coordination procedure](../skills/checklist/references/coordinate.md).

The shared workflow composes compatible Implementation Triage changes into one application target and qualifies selected cases together using the normal build graph, followed by independent per-ticket Review targets. Existing active claims can remain in the handling group without release/reclaim; they are not retroactively frozen batch claims. Shared evidence does not transfer verdicts or bypass exact-target gates. Routine harness corrections within the authorized scope need no renewed coordinator approval, and compiler release is not work release. See the [implementation and qualification path](../skills/checklist/references/coordinate.md#implementation-and-qualification); this guidance does not introduce a shared-target MCP command.

Discovery exposes tools appropriate to the caller's role and project feature use; a caller cannot gain permission by manually guessing a hidden tool name. `service_info` returns its supported tool names/limits and unsupported native-delivery capabilities. Refresh discovery on grant changes where supported; otherwise denied calls explain how to reconnect.

| Surface | Tools supplied |
|---|---|
| Connected reader/capture | Service/project resolution, policy/taxonomy reads, own registration/inbox, task create/get/list/context, permitted attachment reads and history |
| Active worker | Reader plus task edits within grants, messages, own work claim/checkpoint/delegate/handoff/release/submit, takeover of another holder's claim, human-request and permitted attachment commands |
| Reviewer | Reader/messages plus exact review claim/verdict and evidence reads; no hidden implementation write authority |
| Coordinator | Explicitly delegated assignment, transitions, review requests, recovery, groups/batches and policy proposals in addition to applicable work grants |
| Assistant connection / observer messenger | Granted project reads/settings/context/history, requested Draft capture and note messages, assistant inbox/receipt and qualified event subscription; no worker registration, assignment/claim/review/complete, trusted answers or rule edits |
| Owner app | Trusted answers/human attempts, project setup/context, policy application, status/tag editor, bulk changes/Undo, export/transfer/restore/purge and storage/development controls |

The assistant row is an assistant capability mode, not an assignable work role; it cannot be upgraded by task routing or an Assignee payload. A role is a permission set, not a model/profile catalog. An enrolled session can hold several explicit roles. Most worker turns need task context, checkpoint, messages and submission; project administration does not crowd that set. Do not replace this with one unbounded “manage everything” tool.

## Result and common types

Success has `data`, opaque `event_cursor`, `command_id` for writes, `revision` for an aggregate, `pending_message_ids`, `policy_changes`, and `next_cursor` for paginated reads. Lists default to 50, max 200. All external event/history/inbox/page cursors are opaque handles bound to the authenticated principal, project set/filter, grant generation and store incarnation; never expose or merely base64-encode the internal global sequence. A changed/revoked scope, restore or expired cursor returns `CURSOR_RESET` with a fresh authorized snapshot/catch-up plan before replay. Current cursors are sealed tokens that need no stored row; they stay valid for 24 hours and across a service restart, and a change of store key also returns `CURSOR_RESET`. Direction cursors are opaque task/work-round tokens, not global event numbers. Context names source revisions/truncation and older-history cursors. Large stored text is never silently discarded.

Failure is MCP `isError=true` plus `{code,message,retryable,details,correlation_id}`. Protocol errors use JSON-RPC. Validation/authorization failure makes no changes. `details` includes relevant safe IDs/current revisions/changed fields and the blocking reason, never another project's contents or tokens. Error text never contains SQL: a storage-engine failure returns `STORAGE_ERROR` with only `details.sqlite_code` (or `OUTCOME_UNKNOWN` for a write with its command ID), and the service log keeps the full description. A replay of a command ID whose stored result passed its 30-day retention returns `COMMAND_RESULT_EXPIRED`; the command does not run again.

The service admits commands only from the exact bundled `ChecklistApp` and `checklist` cdhashes. XPC checks their code-signing requirement against each message's audit token. An earlier Checklist signing identity can connect only to a fixed `CLIENT_OUTDATED` reply object, which has no command capability. Other identities are refused. A process-ID race on the error-only path cannot run a command. Running fixed MCP shims switch to the signed CLI at their saved launch path and keep the SDK transport. Parent preflight checks the resolved bundle root and instance against startup. A delegate starts suspended; the parent obtains its dynamic `SecCode` by PID and requires `SecCodeCheckValidity` to pass the exact pinned CLI cdhash requirement before resume. It also checks the kernel executable path against the captured bundle root. Static signing information is diagnostic only and cannot admit the child. A failed check kills and reaps that child before it executes an instruction. After resume, the CLI checks its resolved instance and bundle root against the delegate's environment expectation before Checklist IPC, Keychain or bootstrap. An instance mismatch is not sent and retains the original command ID. CLI `call METHOD -` reads at most 1 MiB of JSON from a separate child stdin pipe; MCP stdin is never passed to the child. A delegated result needs exit zero with JSON stdout, or exit one with a final CLI error line. Other child results retain the original command ID in `OUTCOME_UNKNOWN` with reason `delegate_ended`; see [install recovery](integrations.md#installs-and-running-mcp-shims). A non-owner call that names a session with no registered record in the project fails with `FORBIDDEN`. Agent reads of reference files open the final component with `O_NOFOLLOW` and check the descriptor's own path against the workspace again after the open.

Reusable shapes:

- `TaskRef`: exactly one of `task_id` (UUID) or `key` (project-local string). Mutations use task UUID after resolution.
- `Assignee`: `{kind:"human"}` or `{kind:"agent",provider?:string,session_id?:UUID}`. Provider/session selections must be eligible under the project's role/kind rule; planned assignment never starts work.
- `Scope`: `{root_id,path,access:"read"|"write"}`, normalized relative to an enrolled grant; lane entries are `{lane_key,units}`. Empty scope permits no filesystem writes.
- `TaskPatch`: only `title,brief,acceptance,kind,readiness,priority,order,planned_assignee,assignment_reason,epic_id,tag_ids,starter_fields`. `starter_fields` (also accepted by `task_create`) is an optional object of text fields for the ticket kind: Bug `reproduction` (16,000 bytes), `expected`, `actual` (4,000 each); Playtest `build` (500), `platform` (200), `clip` (2,000; a link or file name, the file itself is an attachment). Other kinds take none; an unknown field is `INVALID_INPUT`; empty fields are not stored; a patch replaces the whole set and an empty object clears it. A kind change keeps only the fields the new kind uses, and the edit's history event keeps the removed text. Kind is `work|bug|asset|playtest|question`; acceptance is a bounded list `{id,text}` with stable IDs. Readiness is `draft|ready`. Null epic clears it; ID lists replace the set. Priority is `none|low|normal|high|urgent`; order is an integer with stable ID tie-break, brief is Markdown (max 64 KiB), and acceptance has at most 100 entries of 2,000 characters. First assignment from an unassigned ticket and selecting the same planned assignee need no `assignment_reason`, except that the existing agent policy override rule still requires one. Changing an existing different planned assignee (including clearing it) requires a nonblank `assignment_reason` (at most 4,000 UTF-8 bytes; agent policy overrides at most 2,000); the reason and previous/new assignees enter history. Active work must be released before an assignment edit. Actor/time/effective policy are derived. An ordinary owner action can supply a clear action reason without extra form fields. No state/claim/history fields.
- `Relation`: `depends_on|related_to|parent_child|duplicate_of`; parent_child records source as parent, target as child. Link removal preserves its history and cannot undo an already superseded task disposition.
- `TaskFilter`: optional `text,status_ids,categories,readiness,tag_any,tag_all,tag_none,assignee_kind,provider,session_id,epic_id,triage_id,attention,archived,trashed`; `attention` is `human|review|blocked|recovery`. `sort` is `manual|updated|priority`, plus opaque `cursor,limit`. Archive/trash default false; an app global view still issues separate authorized project scopes.
- `message_send` recipient: omit the entire `recipient` field for current handlers, relevant writable descendants/reviewer and configured coordinator; without a handler the note is saved for next pickup. An explicit route is exactly `{kind:"session",session_id:"<verified scoped session>"}` with both fields required and no additional keys. Missing/unsupported kind, blank or invalid session ID, null/non-object values and unknown fields return `INVALID_INPUT` atomically; they never select current handlers as a fallback. A valid explicit session is revalidated against current project/grants and can receive a completion notice after Done. Unknown, out-of-scope or ended targets fail without enrollment or fallback. A new trusted owner `requires_action=true` message must omit recipient for mandatory handler direction fanout. Combining it with an explicit session returns `INVALID_INPUT` before writes or reply allowance changes. Previously committed valid-shape command receipts still replay their original result without being rerouted or rewritten. A reply to an owner note retains its original human route and must omit recipient; an explicit route is rejected before consuming that reply allowance. Ordinary agent-to-agent ticket replies retain their valid explicit route. Valid original-command UUID retries preserve the committed message, delivery IDs and actual recipient if the handler later changes, without new writes. Tightened explicit-shape validation runs before cached receipt replay: retrying a malformed intent committed by an older version can now return `INVALID_INPUT` while leaving its existing note, deliveries and durable receipt intact. That error does not prove the original intent never committed; retain its IDs and inspect existing receipt/history before treating it as unsent. Current authorization still applies.
- `EvidenceManifest`: `{acceptance_revision,implementation_attempt_id,source_capture?,artifact_refs,checks,limitations}`. Source capture names root/relative paths/hashes, commit/base/diff or dirty-capture reference. Git captures also record resolved `git_path` and `git_version` from the fixed trusted executable list described in [storage](database-storage.md); `SOURCE_GIT_UNAVAILABLE` explains missing/unsafe candidates, `SOURCE_GIT_UNTRUSTED` refuses a selected executable that becomes unsafe, and `SOURCE_GIT_LICENSE_REQUIRED` names the Xcode license step. Artifact refs are immutable `{artifact_id,sha256}`. Each check names `{label,command_text?,target_ref,execution_mode,result,started_at,ended_at,before_hashes?,after_hashes?,not_run_reason?}`. Mode is `immutable_artifact|captured_source|serialized_checkout`; result is `passed|failed|not_run`. Source modes require reservation/capture receipts and before/after validation, not self-declared empty hashes. Service returns manifest ID/digest; relevant limits must be policy-acceptable.

## Human requests, groups and attachments

Any individual ticket status action removes that ticket from every current Triage, including an explicit same-status mark. Notes, attachments and metadata-only edits do not detach it. Use the discovered `triage_transition` group command to apply a status to all current members atomically: ordinary group transitions retain membership, while Done removes completed tickets from all current Triages. Historical/future exit-milestone data is secondary and does not override this rule. Ordinary human answers and metadata/notes/attachments do not detach membership. Only the Triage group command has internal group context; selecting a group does not claim implementation or review authority.

## Trusted native actions

These handlers share domain validation but are not agent tools:

- `diagnostics_summary` is an owner-only read with no input fields. It returns schema version, observation time, service version/responsiveness and aggregate counts under fixed record-type labels; it never returns record contents, dynamic labels, paths, session identifiers or secrets. Settings combines it with strictly validated version/build metadata and bounded owner-app error codes for a native Save-panel JSON export. It is absent from every worker/assistant catalog; unavailable service counts stay omitted. This is separate from project export and full backup.

- Project create/update/relocate/enroll/archive, expected-revision project settings save/icon import and project context save; root changes use fresh Finder/verified workspace grants and overlap validation. Project brief/decision edits require expected revision/provenance.
- Policy apply from unchanged proposal ID/digest plus expected revision and `future_attempts|checkpoint_active` mode. Status/tag edits use the simple Name/behaves-like/color editor; the service generates protected transitions/defaults and supplies impact mappings for structural changes.
- Human request forms use flat fields. `title` defaults to “Needs your input”; `blocking` defaults true. `questions` and `file_requests` default empty, with at least one entry across both and at most 30 each. Each has a unique nonblank `id` (100 bytes) and required `prompt` (4,000 bytes). Question `type=text|choice|approval|check` defaults to `text`; `required` defaults true; `multiple` and `allow_custom` default false. A choice requires `options=[{id,label}]` (unique IDs, at most 100; labels 4,000 bytes), with at least one option unless custom answers are allowed. File `kind=file|directory|either` defaults to `either`; `selection` is an alias, with `kind` taking precedence when both are supplied. File `multiple` and `optional_explanation` default false. Extra nested entry fields are currently ignored; they cannot replace required fields or change accepted enums. `label` cannot replace `prompt`, and `single_choice|multiple_choice|short_text|long_text|file_or_directory` are unsupported types/selections. Unknown top-level fields, including `request_spec,purpose,blocking_scope,target`, are rejected on agent calls.
- Form `command` (also allowed on a question) is instructions only: `{text,working_directory,expected_result,reason?}`; text is at most 16,000 bytes, other fields 4,000. The service never executes it. Title is at most 4,000 UTF-8 bytes; agent create `explanation` is at most 4,000 bytes (revision patches allow 16,000). Optional booleans must be actual booleans. Service-derived authorship, revision, state, continuation and target hash are not form inputs. A `check` alone does not bind a review gate; human gate binding requires exactly one `approval` question and the exact managed target. Explicit `review_request_id` selects the queued gate; without it, exactly one matching queued human gate can be selected automatically when an approval question and attachment are present. Merely naming `target_manifest_id` does not create a gate.
- `human_request_answer` takes request ID/revision, target ID/hash where applicable, complete typed answers/file grants and optional explanation. `clarify|cannot_do` appends response but keeps pending/blocking; personal snooze changes only presentation. Clarify/cannot-do/Not checked retain a gate-bearing request’s verification slot; cancellation frees it with gate unsatisfied, and eligible replacement transfers it atomically. `send` validates all required fields, commits answer and deduplicated outbox deliveries to original requester/current handlers/configured coordinator atomically and applies only the eligible continuation. Ended requesters remain historical recipients; next pickup gets the answer through context. Gate approval records its exact trusted pass/reject verdict and releases verification slot; Not checked keeps pending. A complete gate-bearing answer additionally requires the caller-observed `expected_task_revision` and `direction_cursor`; the service revalidates current owner directions and approved project context before file import, answer/verdict writes or releasing the verification slot. Missing/stale context or unresolved directions reject the transaction with the draft and slot retained. Ordinary answers, clarification/cannot-do and Not checked remain available without recording a gate verdict. Forms start unanswered; no implicit selected default.
- Answer items are closed variants: `{question_id,type:"choice",option_ids,custom_text?}`, `{question_id,type:"text",text}`, or `{question_id,type:"approval",result:"approved"|"changes_requested"|"not_checked"}`. File answers are `{file_request_id,selection_refs:[{grant_id,kind:"file"|"directory",explanation?}]}`. The server validates IDs/cardinality/custom permission, required text and actual grant type. `send` with Not checked records the response but leaves the check request pending; clarify/cannot-do require an explanation and never masquerade as complete answers. Response output names request state, gate outcome, continuation and delivery IDs.
- Human work start/checkpoint/submit/complete uses a trusted human attempt and normal applicable gates. `direction_waive`, finding waiver and completion waiver name specific targets/reasons and stay visibly waived.
- Multi-select typed changes (tags, planned assignment, epic/triage, guarded status, archive) take all expected revisions and a preview. Default atomic application rejects all on conflict; owner can explicitly retry the displayed eligible subset as a new command. Undo is a revision-checked compensating command, never history deletion or resurrection of released claims/cleaned bytes.
- File/Finder grants, integration registration/bootstrap diagnostics, export, later authorized transfer/restore and trash purge. No migration now. Runtime/endpoint enrollment is explicit; proposed task text cannot authorize it.
- Checklist-only `development_build`/`development_status` use its fixed approved helper and source fingerprint, never arbitrary command execution. Required installed-build verification must pass before ordinary Checklist enhancement completion. See [self-hosting](self-hosting.md).

## Human note and child delivery

A trusted UI note creates authoritative message/delivery records. Native notification envelope includes only `schema_version,message_id,delivery_id,project_id,task_key,origin,author_display,recipient_session_generation,preview,context_action`. It is a hint, not proof of authorship: the recipient fetches through authenticated MCP. Parent relay logs each hop with original IDs, and the child acknowledges its own delivery. Delivery states are `queued|held_for_approval|refused|provider_accepted|acknowledged|addressed|unavailable|delivery_uncertain`. Provider queue acceptance is not model acknowledgment. A hold/refusal persists provider reason, hold/correlation ID, exact route/recipient generation and any real approval receipt; it is never acknowledged automatically. The qualified adapter supplies the sender’s verified current permission class in the required provider envelope; unknown/missing provenance can remain held. Correcting omitted transport metadata uses the actual unchanged sender class. No tool accepts a false/more-permissive class or approval token copied from another session to bypass a hold. Resume uses only the provider’s actual authorized approval path for the original correlated attempt, and held/refused routes do not enter an unchanged retry loop. Replies carry `reply_to` and original causal ID; another agent's request does not itself authorize sending to arbitrary tasks.

Claude reports a hold or refusal with a `peer_message_status` control frame sent to the relay’s `from` socket on a new connection. The service correlates it only when the kernel-reported notifier is the recipient process and the notice’s `orig_msg_id` equals the write’s exact `msg_id` (observed on engine 2.1.299; the notice’s own `msg_id` names the notice). There is no fallback: an absent or different ID stays uncorrelated. The bridge-only `delivery_host_status` records `held` as `held_for_approval`, `refused` as `refused`, and `expired` as `unavailable`. It keeps the write receipt separately; a later write outcome, retry or late notice cannot replace an exact acknowledgment. Each trusted app note stores one reply allowance for its explicit recipient, or else for the current handler, never for a child or coordinator that merely sorts first. Only that recipient’s native relay offers a reply; either native `CHECKLIST_REPLY` or MCP `reply_to` consumes it. A native reply's recipient is chosen among all of that note's deliveries by kernel peer PID only, never by delivery order.

Owner and agent ticket notes both use the Claude native relay. The relay states the real author and always asserts its own `prompting` class; it never claims an agent's class. A recipient whose permission class differs, such as a bypass-mode session, holds the message for its user (`mode-mismatch` on engine 2.1.299) unless that user sets Claude Code's own `crossSessionInbound` setting to `accept`. Checklist never changes that setting or the recipient's permission mode.

A recipient may include `reaction=thumbs_up|thumbs_down|done|looking|question` in `message_ack`. The service stores the fixed marker and time on that exact recipient’s delivery. A reaction is acknowledgment only: it never addresses a direction, completes a ticket, grants authority or carries human provenance.

## Ordinary comment mention preparation

`message_mentions_prepare(command_id, project_id, task_id, body, reply_to?, selections?)` is an idempotent preparation command that sends nothing. Assistant-only connections cannot discover or invoke it. `body` is the exact intended comment. Each optional selection has exactly `{start, end, target}`: nonnegative integer UTF-8 byte offsets naming a complete parsed token, and a returned exact target. Target is exactly `{kind:"ticket", task_id}` or `{kind:"session", session_id, authorization_generation}`. IDs/generations use exact bytes; labels confer no authority.

Recognized syntax: bare `@CL-12`, `@worker`, or `@<actual-session-id>` (the angle brackets here denote a placeholder, not literal syntax). Exact labels with spaces/punctuation use `@{Target worker}`. Bare tokens contain Unicode letters/digits/combining marks, `_`, and `-`; markers start at the beginning of a comment or after whitespace or `([{"'`. Email/interior-word markers are literal. Odd preceding backslashes escape a marker. Inline backtick code and line-start backtick/tilde fences are literal; unfinished code remains literal through the end of the comment. This small rule is not a complete Markdown renderer. Preserve the original body bytes; parsing does not remove escapes, rewrite code or normalize Unicode. Empty/unclosed brace tags and more than fifty tags are refused.

Each raw query collects all currently eligible same-project ticket-key, worker-label and exact-session-ID matches. Do not prefer a ticket based on its spelling or choose the first duplicate label. A duplicate key/worker label/cross-namespace match returns all exact candidate descriptors. A supplied selection must still be one of that token's current scoped matches. Otherwise refuse `RECIPIENT_CHANGED`; it cannot grant enrollment or route outside scope.

Responses include `body_sha256`, parser version, tokens with exact `{start,end,query,state,candidates,target?}`, and truthful pickup-only capability. State is `untagged`, `needs_selection`, or `prepared`. `needs_selection` can contain resolved, ambiguous and not_found tokens, but has no route token and creates no partial plan. Choose exact candidates for ambiguous tokens and prepare the entire unchanged body again. Unknown tokens must be corrected/escaped; they do not silently become untagged notes. `prepared` includes the opaque `mention_target`, expiry and references from the existing atomic preparation path. It binds the caller/project/task/reply/store, exact body hash, references and current recipient generations.

For ordinary `message_send`, pass that `mention_target` with the **same body** and normal project/task/reply/destination fields. A recognized tag without preparation refuses `MENTION_PREPARATION_REQUIRED`; changed public-token body refuses `RECIPIENT_CHANGED`. Current recipients/generations are revalidated atomically before delivery. A failed preparation/send preserves the draft and has no partial message/delivery. Use the original command ID to reconcile an unknown outcome; do not make a replacement intent. Prepared/saved/queued/acknowledged remain different receipts.
