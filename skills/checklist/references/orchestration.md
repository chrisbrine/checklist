# Run implementation and review orchestrators

Choose a setup for the authorized cohort, name who owns each next action, and keep actual ticket claims separate from coordination. This is a working procedure for existing Codex/Claude conversations. Project orchestrator registration, shared participant inboxes and the optional Orchestrators tab remain [planned work](../../../docs/project-orchestrators.md), tracked by CL-125 "Add project orchestrator registration and scoped MCP conversations" and CL-126 "Add an optional project Orchestrators tab with messaging and replies". Discover the running catalog before using any command below.

## Choose the setup

| Setup | Choose it when | Responsibility and current support |
| --- | --- | --- |
| One combined orchestrator | One conversation can keep implementation, evidence and review routing in context. Useful for a small cohort or tightly coupled changes. | The same actual conversation can coordinate separate Implementation and Review Triages. It integrates or names an integrator and starts independent reviewers. It cannot review a target it contributed to. Supported through current Triage/batch commands; no project registration is required. |
| Split IMPLEMENTATION and REVIEWS conversations | Implementation and review can advance separately, or their context and resource needs justify distinct threads. | IMPLEMENTATION owns division of source work, integration, installation, check runners, commit/push and implementation submission. REVIEWS owns the Review Triage, independent reviewer dispatch, review holds and verdict routing. Each records its own phase's orchestration. Supported today through separate Triages and scoped messages; no automatic cross-thread dispatch or shared inbox is supplied. |
| Several implementation orchestrators for disjoint Triages | Cohorts have separate writable source/resource scopes and each has a clear coordinator. | One actual coordinator per Triage; name one integration lead for any shared application round. Each coordinator retains its own claims, helpers and hand-ins. Separate groups do not make overlapping paths safe. Supported with separate batches, reservations and explicit communication; project-wide responsibility discovery and aggregation await CL-125. |

A Triage has one handling phase and one current recorded coordinator. It is not a permanent implementation-to-review container or a group of interchangeable claimants. Use two or more tickets to form a Triage; handle a lone ticket directly, and finish an established group's last member without creating another singleton. Epics remain stable containers. Follow the effective project cohort limit across threads; splitting conversations does not create more pickup capacity.

Independent review requires a genuinely separate non-contributor conversation, including an eligible fresh subagent on the same host/provider. Exclude every recorded implementation contributor, including helpers that never connected to Checklist, prior rework sessions and integrators that changed the target. A new label, role or model setting does not remove contribution history. A combined coordinator can route review but cannot supply its own independent verdict. Reviewers inspect the exact submitted target under [review](review.md).

## Select the agent tool

The 22 October 2026 Checklist rounds used Claude IMPLEMENTATION and REVIEWS conversations, with Codex `gpt-6.1-sol` sessions for implementation, check running and review. These are observed choices, not universal provider defaults or permission to start new runtimes in another project.

| Tool | Recommended work | Limits to put in the brief |
| --- | --- | --- |
| `codex exec` | One bounded implementer per ticket in a fixed private workspace; fresh non-contributor check runners for installed observations; fresh non-contributor reviewers per compatible review batch. | Follow [driven sessions](driven-sessions.md#codex-cli-codex-exec). File-only helpers can work without Checklist while the parent holds the claim. For service work, run the installed CLI from the enrolled project folder and verify actual caller/project with `service_info`; do not assume a copied source folder inherits its binding. The observed route required `danger-full-access` and a narrow brief. MCP bootstrap in this host was unavailable; do not forge identity environment variables. Finish service work in the original run; `codex exec resume` is not a supported continuation of its Checklist authority. |
| Claude subagents | Bounded analysis, planning, source inspection or disjoint file work that benefits from the current Claude context. | A helper has no ticket authority merely because its parent launched it. Record its actual identity and contribution; use discovered delegation/acceptance only with a verified enrolled child and bounded scopes. A fresh non-contributor can review only when native identity, eligibility and the review route are supported. Do not substitute an unverified child for an actual claimant or native test subject. |
| Claude Desktop `start_session` | A deliberately selected native test subject when acceptance needs a real Claude Desktop session. | In the observed host, `start_session` works only in owner turns. Do not use it as an implementation/review worker pool or assume an agent turn can launch it. A session-start receipt, native delivery, acknowledgment and completed observation are separate evidence. If unavailable, report the missing native observation; do not substitute another runtime. |
| Codex app threads | Owner-visible longer-lived coordination or interactive work through an actual supported native thread. | Use in Codex prepares a composer; owner Send and actual thread connect/attach are separate receipts. Explicit native creation requires the supported host result and its actual returned identity. Neither a composer draft nor context attachment claims work or proves a turn ran. Never replace an unavailable native creation check with `codex exec`. |

Use only launches already authorized for this task. Existing scoped coordination does not authorize enrollment, a provider adapter, a schedule or a hidden model runtime.

## Divide work and run the round

1. **Record the plan.** Read current tickets, memberships, prerequisites, project pins, policy and contributor history. Name the actual implementation/review coordinators, integrator, ticket owners, private slots, shared paths, GUI slots, compiler allocation, waiters and hand-in destination. Write prerequisite order and division of responsibility in each Triage purpose/checkpoint. Separate implementation helpers, check runners and reviewers in the plan.
2. **Start phase coordination and claims separately.** Create the phase Triage and add members with revision-checked `group_membership`, one call at a time per group. Its actual coordinator uses `triage_orchestrate action=start`. Prepare and atomically claim Ready, prerequisite-satisfied members with `batch_prepare` / `batch_claim`. Preparation is planning, never a claim. A batch's claims belong to its authenticated caller; it cannot assign different tokens to several implementers. A parent can keep claims while file-only helpers deliver patches; record all contributors. Independently claiming workers need separate disjoint batches/scopes or supported delegation, not copied parent credentials.
3. **Keep status truthful.** A ticket is Active only while its own status category is In progress. Orchestration does not promote Queued or Review members into Active. Release or move genuinely blocked work through the guarded workflow with a visible current reason and next permitted step; a reason buried in chat/history is insufficient (CL-242 "Show why a ticket is Blocked on the ticket and in lists"). A reviewer verdict `blocked` ends its claim and returns the request for eligible pickup; it does not itself set the ticket's status to Blocked. Never change status solely to make an orchestration look busy.
4. **Use fixed workspaces and bounded resources.** Give each concurrent writer its own assigned persistent slot outside Documents, with `src/` and sibling `.build/`. Sync the named base and verify its clean revision or captured bytes/fingerprint before editing; an explicitly supplied dirty combined tree must be compared with its captured base, not reset. Reuse the warm build cache with `--scratch-path <slot>/.build`. At most four concurrent Swift build/test commands were allowed globally in the observed rounds, shared by IMPLEMENTATION and REVIEWS; the implementation wrapper allocated three slots, leaving one to reviews. Use the round's actual wrapper and any stricter allocation, including for reviewer builds. Four test-app slots do not imply four simultaneous GUI operators; assign the GUI separately. Use the [cache and cleanup procedure](driven-sessions.md#scratch-cleanup-and-cache-settings) at runner, review, rework and round boundaries.
5. **Compose one combined round.** IMPLEMENTATION integrates or names one integrator. Collect `tree/`, `base/`, `files.json`, `base.txt`, `notes.md`, hashes, modes, contributor identities and case results per ticket. Compose against base bytes in a persistent slot, resolve conflicts deliberately and check the combined target. Before shared checkout writes, send a pre-merge note naming tickets, file/hash inventory, base/target, test results versus baseline, intended write window and installed checks still needed. Obtain "agreed, I do not build" from every other participant that could build. Follow [combined build rounds](coordinate.md#combined-build-rounds) for affected/full checks, storage qualification, the single install, commit/push slot and receipts. Only the integrator writes the shared checkout in its announced window.
6. **Collect installed evidence and submit.** IMPLEMENTATION assigns fresh non-contributor runners the exact build, bounded acceptance cases and prepared isolated slots. Runners observe and attach reports; they do not claim, submit or decide review verdicts. Preserve hashes, actual producer and build ID. Close clearly marked test GUIs, restore the real app window and destroy owned synthetic slots after evidence capture under the applicable authorization. Then the actual implementation holder calls `batch_submit` for every remaining live claim in that batch exactly once, with its own manifest, direction cursor and per-item evidence; omit released members. Submission ends implementation membership and moves targets to Review. Announce exact manifest/build/report IDs to REVIEWS.
7. **Hold the review target and route verdicts.** REVIEWS forms a separate Review Triage, records its actual coordination and starts fresh non-contributor Codex `gpt-6.1-sol` reviewers. It tells IMPLEMENTATION which target/files are held, who is reading them and when the hold ends. Protect the immutable capture and the checkout freshness scopes specified by the combined-round procedure; absent scoped freshness, hold the whole inventory including Git. The integrator acknowledges the hold before review begins; after all affected readers finish, REVIEWS sends the release and the integrator acknowledges it before resuming checkout writes. Reviewers use `review_batch_inputs`, prepare/claim the exact review batch, inspect and record their own evidence/assessments, then call `batch_review_record` for every remaining live claim. REVIEWS relays each verdict, findings, exact target, report/hash, retained passes and next action to IMPLEMENTATION. Release the hold explicitly after all affected readers finish; a missing reply or ended tool call does not release it.
8. **Continue failed or remaining work only.** Passing tickets complete through their own fresh gates and stay Done while siblings fail, unless effective project policy explicitly holds batch completion. IMPLEMENTATION reworks rejected tickets itself or through a session it starts for that Triage. Carry valid passing cases with original producer, target and hash; rerun failed, inconclusive or materially affected cases, naming invalidated inputs before any broader run. Missing installed evidence can require another runner and same-target review rather than a source rebuild. Return only the repaired targets or supplemental evidence to REVIEWS. Neither a batch nor an old verdict substitutes for fresh target-bound gates.

Inspect memberships before every status-changing operation. Individual claim, release, submit and verdict commands can detach memberships. Use the discovered batch/group operation when retention is intended; never simulate retention with repeated re-adds. `triage_transition` changes every current member atomically but does not claim work. `batch_release` can release a selected live subset with a reason while preserving memberships; subsequent submission/verdict includes exactly the remaining live claims. A frozen batch does not grow when urgent work joins its Triage.

For the Checklist project, the 22 October pinned decision titled "New Drafts: refine, mark Ready and add to an unstarted planned pass" allows urgent owner tickets into the active Implementation Triage: record why on the ticket and in the purpose, then prepare/claim a new batch immediately so membership stays. CL-237 "Custom project icon draws at its pixel size in the toolbar project picker" demonstrated urgent admission. CL-242 was handled directly when no active Implementation Triage existed. Read the current pin before applying this project policy elsewhere; it is not a product invariant.

## Communicate and hand over

Use one ticket-scoped Checklist note for durable history and recipient delivery, adding the relevant Triage as its subject. Include the ticket/Triage key and title, source and destination roles, event, exact target/build, evidence IDs/hashes, blocker or hold, next responsible session/action and any waiting tickets. For cross-thread coordination select a verified scoped session with `recipient={"kind":"session","session_id":"<verified scoped session>"}`; omit the whole recipient for current handlers/pickup. Use the same ticket/conversation for `reply_to`; start a new scoped note to notify another waiting ticket. Direct host messages may point an existing authorized participant to that note, but do not replace its history or prove delivery through Checklist. The inspected public `message_send` implementation requires a ticket even when `triage_id` is supplied; it has no ticket-free Triage/project note route. Use a relevant existing waiting ticket today. If none exists, report the gap rather than creating a dummy ticket or assuming a Triage subject is a conversation endpoint.

For example, a pre-merge note says which tickets and files will land, which checks passed or failed, who may write/build and when. A submission note gives target/build/report identities and asks REVIEWS to take the review phase. A rework note gives verdict/finding IDs, failed cases, carried evidence and the next implementation step. A hold-release note names the finished readers and released paths. These are distinct events; do not send the same event repeatedly while awaiting acknowledgment.

Inspect returned deliveries for the exact intended `recipient_session_id`. `saved_for_pickup` without a delivery is history only; `queued` means that recipient has a delivery waiting; only its explicit acknowledgment proves consumption. Notify affected waiting tickets and their handlers before concluding a completion, handoff or meaningful blocker change. CL-193 "Delete a Done ticket's evidence files and remove closed tickets after a set number of days" illustrates prerequisite-result notes saved for pickup without starting the dependent work. CL-129 "Watch active work health and reconcile unanswered or late handler replies" illustrates verdict routing, contributor corrections and carried evidence; its trusted owner answer changed the permitted check, without turning component tests into physical sleep/wake evidence.

Before a thread stops, checkpoint the remaining tickets, claims/attempt IDs (never tokens), helper identities and writer state, exact source/build, held paths, evidence, message/ack receipts, pending owner requests, waiters and next actions. The successor must explicitly accept coordination: finish/start when the original can finish, or use reasoned `triage_orchestrate action=takeover` from another eligible conversation. That transfers coordination only. Transfer/release ticket authority separately through the supported handoff, `batch_release` or reasoned `work_takeover`, and inspect resulting claims and batch membership before continuing. Takeover does not stop an external writer; reconcile its actual process/file state before another writer starts.

A queued note does not resume an idle host subagent. The orchestrator uses the supported host resume operation for an already authorized idle child (in Codex, `collaboration.followup_task`) and points it to the original note. A finished `codex exec` run instead needs a fresh authorized session and ordinary authority reconciliation. Silence, a timeout or a finished turn proves neither abandonment nor native closure. If a host cannot supply required closure evidence, retain the unknown state and report the capability limit. See [bounded work authority](../../../docs/work-authority.md).

## Running-server support checked 22 October 2026

The installed CLI catalog was read from the registered Checklist project folder, and these schemas were compared with `Catalog.swift`, `Groups.swift`, `Batches.swift`, `WorkAuthority.swift`, `TriageTransitions.swift` and `Communication.swift`. This was read-only inspection, not a new mutation or native-route qualification. Re-discover on the installation used for a pass; some schemas leave nested member constraints to server validation.

| Discovered command | Supported use and boundary |
| --- | --- |
| `triage_create` | Creates one phase's handling group; does not launch/assign workers or register a project orchestrator. |
| `triage_orchestrate` | `start`, `checkpoint`, `finish`, reasoned `takeover`; identity comes from the caller. One current coordinator per Triage; no participant group or cross-Triage responsibility registry. |
| `triage_transition` | Exact group revision and per-member revisions; one status for every current member, all or none. Cannot enter Active or Review without their work workflows. Ordinary same-phase transitions retain memberships; completion still needs exact gates. No worker dispatch. |
| `group_membership` | Revision-checked phase-compatible adds/removes; already In-progress members may join Implementation. Later edits do not rewrite frozen batches or transfer claims. |
| `batch_prepare` | Freezes selected current members, phase, scopes, revisions/policy and review targets; rehearses claim guards without acquiring claims. |
| `batch_claim` | Claims the complete frozen selection for the actual caller; requires the preparation's positive `policy_revision`. Retains membership. No multi-recipient dispatch or token sharing. |
| `batch_submit` | Actual holder submits every remaining live implementation claim with its own evidence; atomic validation. Submission departs the implementation phase. |
| `batch_release` | Holder releases a selected live subset with a reason, retaining all current memberships. Implementation returns to Queued; review returns its request to eligible pickup. |
| `batch_review_record` | Actual independent reviewer records every remaining live claim with per-ticket outcomes/gates. Only reviewer-side `blocked` keeps memberships; `evidence_missing`, `not_run` and `blocked` with `blocked_on:"implementation"` leave every Triage and return the ticket to its implementing holder as Active; reject/pass retain phase departure effects. Every verdict ends its claim. |
| `work_takeover` | Eligible caller replaces a live ticket holder with reason/history/notices and ordinary reservation/independence checks. Does not transfer Triage coordination, stop external writers or confer frozen shared-write permission. Reconcile the new attempt before using any prior batch continuation. |
| `message_send` | Ticket-scoped notes, optional Triage/Epic subject and exact eligible session recipient, with truthful deliveries. Although `task_id` is optional in the schema, the inspected handler requires it for ordinary `message_send`; a subject alone is insufficient. No role-based orchestrator directory, shared-inbox ownership or guaranteed native wake. |

All three setups above are supported as explicit human-authorized session workflows using these tools. The missing project-level registry, focused responsibility discovery and coordinated request aggregation belong to CL-125; the optional owner-facing conversation surface belongs to CL-126. Ticket-free Triage/project coordination notes also need the planned conversation route; current ordinary `message_send` needs an existing ticket. Checkout/build holds currently rely on scoped notes and explicit agreement, not a service-enforced round lease. Multi-holder dispatch is not provided by one batch; choose separate disjoint batches or parent-held helpers. Unsupported host launch/wake routes remain unavailable, rather than becoming implied requirements to introduce automation.
