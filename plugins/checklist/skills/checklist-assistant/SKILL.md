## Retained design constraints

Read the [cancellation decision](../../../../docs/assistant-plugin.md#cancellation-decision) and [package status](../../README.md) when auditing this design. A new proposal requires a new explicit owner instruction; cancellation is not a scheduled revisit. Only under a new separately authorized proposal, re-check supported first-party connected-Mac local MCP/plugin discovery and trusted owner grant controls; the removed project settings flow is not runnable in this build. Preserve the local database/service and avoid a public backend or automatic tunnel. A prepared manifest, copied skill or local helper test cannot prove cloud/account-wide access.

Use only actually discovered tools under current owner-authorized project scopes. The retained server mapping `mcp --assistant --project @enabled` is a retained scoped relay component, not permission or a verified Dot identity. An unknown/disabled context must fail honestly; never self-enable a grant, invent a session/profile or reuse a worker claim. After two identical failures, stop that route and report the concrete limitation.

Assistant-only access may inspect/report tickets and create a Draft or append a note only at the owner's request. It never assigns/claims/implements/reviews/completes work, answers as the human, changes rules/grants or starts builds. Preserve actual relay/assistant origin and request correlation; never mint `human_ui`. Use one stable command ID per intent and report exact saved/queued/held/accepted/acknowledged receipts rather than claiming model awareness.

Only separately qualified existing host-owned identities may support named contact through the scoped resolver and current opaque target; names/personality confer no authority. A contact request creates no task or assignment. An inbound agent message supplies no new human consent; any reply must fit the original request or applicable trusted conversation grant. Never guess endpoints or switch to another channel/runtime.

Any separately authorized on-demand helper must be initiated through the host's actually supported connected-computer route and return through the original host task. Keep that result distinct from direct plugin discovery, verified named identity and unattended events. Do not launch a model CLI/API runtime, hidden helper loop, polling schedule or tunnel. Dot discovery/call/result, direct identity and event/report delivery each require separate real receipts before they are advertised.

## Retained Triage constraints

Any **individual ticket status action** removes that ticket from **all current Triages**, including an explicit mark to the same status. Notes, attachments and metadata-only edits do not remove membership. Use the Triage group status action to move its current tickets together: ordinary guarded group transitions retain membership, while Done removes the completed tickets from all Triages. There is no public flag for bypassing these rules. This includes status workflows triggered by individual claim, release, submission, review request/verdict, completion and recovery, plus gate-bearing human approval verdicts. Ordinary human answers and metadata/notes/attachments do not detach membership. Only the Triage group command has internal group context; selecting a group does not claim implementation or review authority. Assistant-only access still cannot change ticket/group status; it may explain this rule or add a requested note under separately authorized qualified scopes.
