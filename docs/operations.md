# Task and project operations

This is the full operation target, including behavior beyond the local development build. Check [implementation status](implementation-status.md) and actual MCP discovery before using a command; the [MCP contract](mcp-contract.md) includes future methods. The worker skill is under [skills/checklist](../skills/checklist/SKILL.md).

## Create and organize

Capture a task with **project and title only**. Notes, a pasted screenshot or files are optional; the task starts in the project's Draft status and cannot be claimed. The service allocates a key if omitted; a user-supplied key must be unique after case folding within that project. Same keys in another project are valid. Do not make the owner fill in acceptance criteria while playing a game or testing an app.

Before agent pickup, the owner or an authorized coordinator fills in enough brief, intended outcome and evidence/check requirements for the work, then moves it to Ready. Optional **Work, Bug, Asset, Playtest and Question** templates suggest useful fields without making a new capture form compulsory. A Bug can suggest reproduction/build/screenshot; an Asset can suggest a candidate/output; a Playtest can suggest a build/platform and what to check. An ordinary note or human decision needs only the detail its outcome requires.

Add dependencies, a primary Epic, ticket tags and Triage membership independently. Start with one project list. An Epic is a stable subproject containing related tickets by task type; moving a ticket reconciles its old/new Epic container. A Triage is a temporary handling set that can span several Epics; adding/removing a member never changes its Epic or lifecycle. They are distinct containers rather than shared tag-like groups. Creating either is optional. The project tabs are Tickets and Epics; temporary Triages are expandable handling-group rows inside Tickets, with purpose/membership editing from the group menu in the right overlay. They have no separate workspace. A group shows its members' shared status, Mixed or Empty. Choosing a group status applies that transition to all current member tickets atomically, through their normal rules and completion gates. Preview blockers/revision changes; one blocked or stale member leaves every member unchanged. Ordinary group status changes retain membership. Any individual ticket status action, including an explicit same-status mark, removes it from every current Triage. Notes/attachments/metadata retain membership. Individual claim/release/submission, review request/verdict, completion/recovery and gate-bearing human approval status workflows detach too; ordinary human answers do not. Group Done removes all completed tickets from all current Triages; Epics and historical batches stay intact. Linked follow-up tasks preserve the original context; atomic task merge/split and automatic parent completion are deferred.

Choose from the project's working status preset. Multiple Parked types are configured through **Project settings → Statuses & tags**: name, behaves like Parked, color. Internal categories and transition guards are supplied by the preset. Selecting a custom name cannot bypass claim/review completion. Tags are freely reusable project-local metadata, separate from the actual provider/session. Status/tag edits and task changes update other open windows live. See [statuses/tags/live behavior](statuses-tags-live.md).

Creating a task does not start a model session. Choose a role/provider preference, a specific eligible actual Codex/Claude session, or the human. Existing personal assistants are communication partners, never assignees. Planned assignment is visible on queued work; actual handling appears only after a successful claim. Deferred work remains deferred until an authorized queue action.

## Edit and note

Edits use the latest revision. Preserve unrelated concurrent changes and show a conflict when the same intent is stale. Changing title/ordering does not automatically invalidate code review; changing acceptance or relevant work does. A human direction note marked requires-action must be addressed with a response/checkpoint/evidence before submit/complete, or explicitly waived by the human with reason. Acknowledgment records receipt only. An ordinary human note still enters the delivery outbox immediately; the owner need not choose recipients to tell the current handler something.

Notes are append-only messages. Corrections append an edit/retraction event and retain the earlier version in history. Do not replace prior authorship or quietly rewrite an agent's findings. A granular message-redaction workflow is deferred; do not advertise normal correction as removal of earlier content from backups or exports.

The current service returns a compact, versioned `task_context` at pickup and checkpoint: the project brief and applicable approved pins, their source revisions, unresolved directions/findings, current and prior handlers, and the next action. Recent messages and compatibility sections are bounded and show counts/truncation. `task_context(detail_level=full)` pages complete task records with `history_cursor`; `history_list` separately pages append-only events and only the message bodies belonging to that event page. The project context's `previous_context_revision_id` can be supplied as `context_revision_id` to retrieve the earlier brief and decisions, including its predecessor link.

Approved project brief/pin changes retain the prior version and create a requires-action direction for each affected visible ticket. Kind/tag applicability limits pin propagation. Current handling attempts, accepted registered children and an optional policy-selected coordinator receive separate delivery receipts; a context-only session attachment is not a work handler. Notes without a handler remain saved and enter the next actual handler's pickup context/outbox. Native push remains unavailable unless separately qualified.

To address a direction, the current worker records a later response explicitly replying to it, a checkpoint naming its `direction_ids`, or manifest evidence explicitly naming it. `message_ack(stage=addressed)` then names that actual record as `response_ref={kind,id}`. The service verifies ticket, author, current attempt and the explicit direction link. Arbitrary text, invented IDs, unrelated evidence and acknowledgment alone do not dispose of a direction. The owner can use an explicit, reasoned waiver. A correction appends a new message linked by `correction_of` and does not silently clear the original direction. An author can retract an own note with the same link and `kind=retraction`; the reason stays in the new body. Owner notes require the trusted owner channel. Retraction withdraws future action through a linked disposition, while acknowledgment, addressed work and delivery receipts remain. Current handlers receive the linked note. The owner’s ordinary notes offer Correct and Retract in the conversation. Refresh the direction cursor after a disposition; submission, verdict and completion atomically compare the current task/round context before committing.

The composer identifies **Project / task · to current handler**, or **Saved for next pickup** when none exists. It includes an attachment button. The agent decides how to respond and may show a reaction; this marker never completes the ticket. Send to the task's current handlers through the durable outbox; show Queued, Delivered and Acknowledged truthfully, with per-recipient detail on demand. Mentioning an agent's name in prose does not register that session or grant access. Historical participants remain in context but do not receive new work automatically.

Both owners and agents can add images/files to tickets through the Attachments section or scoped MCP attachment tools. Previews, attribution and retention are described in [attachments](attachments.md). Archiving queues large-managed-copy cleanup, with shared/active/Keep original/backup holds shown; it never removes external originals, and unarchive cannot invent bytes already cleaned.

Use native multi-select for tags, planned assignment, epic/triage membership, permitted status changes and archive. Show affected count and conflicts; do not silently skip conflicting tasks or create an automation editor. Reversible edits have a guarded Undo command bound to their receipt and affected revisions. If work was claimed or a dependency changed, explain why the old state cannot be restored. Offline work is limited to saved capture/note/form drafts; the app cannot claim or complete work without the service.

## Deferred named-assistant contact

Routine coordination between actual enrolled sessions involved in the same authorized Checklist project, task or Triage has standing authorization and needs no per-message permission question. Use existing scope/grants and current handler/session identities; a message never enrolls a session, launches a model, changes an assignee or expands authority.

When another ticket or session is waiting, completion, handoff or a meaningful blocker change includes a concise note on that waiting ticket routed to its current handler. An active status does not mean it is free of dependencies. Include the source ticket, outcome/evidence and next permitted step; use the same note for durable history and outbox delivery, and deduplicate existing notices. Do not rely on the source ticket's status or final chat reply to notify others, send repeated unchanged updates, or mistake queued delivery for acknowledgment. Follow the [shared coordination rule](policies.md#involved-session-coordination).

This future flow is unavailable while personal-assistant integration is deferred; the current UI provides no assistant directory/setup controls. If explicitly reactivated and qualified later, once the human establishes an existing host-owned personal assistant in Checklist, **“contact Rowan”** or **“ask agent Rowan”** prefers Checklist automatically. First-use wording can name the app/MCP route; repeated technical wording is unnecessary. Treat the human's current explicit request as the message authorization within existing grants. Otherwise use an applicable project communication grant; an inbound agent message cannot create new consent.

Resolve the friendly name through the caller's scoped `agent_resolve` directory and send through `agent_message_send` to the permitted opaque target. Current project/task context can disambiguate; if more than one valid match remains, show the relevant verified host/connection/project labels and ask which one. Do not guess a native endpoint or choose the first name match. The directory cannot reveal or contact assistants outside the caller's grants; app-created, manual or unverified identity records and ordinary worker sessions are not named-assistant matches.

Keep ticket-related contact in that task's history. Contact without a ticket can use an explicitly scoped project conversation; it does not automatically create a ticket, set an assignee, claim work or convert assistant access into a worker role. Replies and receipts keep their actual agent origin. A submitted message is not proof that the recipient model read it. If a target or route is unavailable, report that state without quietly switching to other chats, email/Slack, a model runtime or scheduled retries.

## Open work in Codex or Claude

**Use in Codex** opens the prepared native composer with a scoped ticket prompt; the user presses Send without copying instructions. A prepared composer is not a started turn, connected worker or claim. After Send, the actual thread bootstraps and attaches itself to this ticket. A separate explicit native Codex creation test returned a real new thread and automatically attached its ticket context; that observation does not claim assignment or work. Claude keeps its open/copy fallback where no native route is qualified. Actual current/prior worker status/checkpoints/recovery/actions stay on the ticket, never a global Settings catalog. There is no active assistant Settings catalog. Current project grants and a successful claim still determine authority to work.

## Triage phases and orchestration

A Triage directs one Implementation or Review pass, led by an actual Codex or Claude conversation. An In Progress ticket can join an Implementation Triage. For Ready/Queued tickets, claim first and then group the attempts, or use an atomic batch claim. A ticket receives Active attention while its own work or its Triage's actual orchestration is in progress. Orchestration does not replace per-ticket claims.

Each submitted implementation moves to Review and leaves its implementation handling set. Form a separate Review Triage for submitted targets. Passing tickets proceed to Done as soon as their fresh gates permit; rejected tickets return to Active or Ready/Queued and only those tickets receive another implementation pass. This is the shared default; an explicit effective project completion override can hold passing tickets without repeating their work. Current group commands, observed direction cursors and truthful phase departures are detailed in [batches](batches.md).

## Assign, hand off, review, complete

An unclaimed task can change planned assignment through a revision-checked edit. Active assignment changes use the current attempt's checkpoint/release, a handoff, a verified recovery, or a `work_takeover` by any eligible agent with a reason; the takeover notifies the earlier holder. The new handler receives the old brief, context cursor, human directions, findings and limitations.

Agents submit work with evidence and enter ready review. Reviewers claim an exact `review_request_id`, gate and immutable target; allow one active verification attempt per task initially, including native human approval. The app shows implementation and review sessions separately and does not treat “the original session has ended” as “review can close”. Review acceptance is target-specific; required gates and authority determine when completion can be recorded. Findings retain stable IDs and the states open/resolved/rejected/waived. A later review resolves a verified fix or rejects a finding with a reason; the owner can explicitly waive one. New submission alone cannot erase findings, and superseding a verdict/request is not a finding disposition.

For an image or build approval, show the actual candidate/build and **Approve / Needs changes**, with an optional note. Bind the human request to the exact `review_request_id`, manifest and attachment checksum or build/artifact ID, short version/platform label and request revision. A later candidate does not inherit approval. Human approval shares the single active verification slot; an agent reviewer must block/release its attempt before the human can claim it. **Not checked** leaves the gate/request pending. Use an immutable build for a playtest or review; checking a changing checkout requires reservations and before/after fingerprints. Do not add an asset library or build farm to support this simple approval.

The normal Triage flow is the group status action versus an individual ticket action, rather than configuring exit milestones. Stored milestone metadata is retained for history/future policy; an implementation-submission milestone uses that task's real submission receipt. Exit at review accepted means **all required gates for the current round/target have fresh passes**, rather than whichever gate finished first. The required installed-build gate for Checklist improvements is included. For zero review gates, a retained review-milestone record requires normal authorized completion and the label **No review required**; it does not prevent ordinary individual status-action departure. A waived completion remains labeled waived, never a passing review. Whenever a ticket actually reaches Done, remove it from every current Triage regardless of the selected exit milestone; preserve the departure history and frozen batch records. Exit changes grouping; it never alters dispatched batch history or silently closes the task.

For example, a “Playtest fixes” Triage contains BUG-12 and BUG-18 from different Epics. Changing the group to a custom Parked status moves both together and retains the group. Marking BUG-12 individually to Ready—or marking it to its current Parked status—removes BUG-12 from every active Triage. Adding a note to BUG-18 leaves it grouped. Group Done succeeds only when every current ticket satisfies normal completion gates; one blocker leaves all tickets and memberships unchanged.

Reopen creates a new round with a reason; old evidence and verdicts remain. A failed row in a successful batch can be retriaged without reopening the accepted rows. A fixed batch manifest does not prevent individual task completion.

## Human work and answers

**Needs You** has two views: **Requests** and **Your tasks**. Assigning the whole task to the owner places it in Your tasks. Trusted native Start/Progress/Submit/Complete actions record a human attempt and its evidence without a provider session. Decision-only work can complete with a recorded answer if project policy permits; technical human work retains its configured review gates. Asking a question creates a linked request without transferring the whole task. Agents cannot answer as the human via MCP.

Allow **one active blocking request per task**, containing several questions, choices/custom answers, Finder file/directory needs and optional explanations. A mixed question/file/playtest form appears once with type filters, its requesting task, why it blocks work and required/remaining answers. Drafts autosave with a clear saved/error state. Command requests describe what the owner should run and accept reported results/output; the app does not execute arbitrary ticket commands.

Send answer validates all required fields, the request revision and any exact approval target atomically. Record the trusted human response and notify the requester/current handler through the durable outbox. A valid submitted answer clears that request's dependency; actual resumption still needs an eligible current attempt or pickup. **Need clarification** and **Cannot do this** notify the requester and keep the dependency unresolved until it is revised, withdrawn or explicitly waived; **Snooze** only hides it from the owner's current view until the chosen time. None completes or abandons the task. No provider polling or model launch follows Snooze.

A confirmed saved **Send answer** returns from that exact request overlay through its existing Back path, or closes the overlay when no prior item exists, restoring the corresponding focus. The saved response remains in request history. A valid saved **Not checked** answer also dismisses while its request and gate remain pending. Failed, stale or rejected incomplete submissions and an unknown command outcome retain the form and its draft. A delayed reply or reconciliation cannot dismiss another request or clear its draft; leaving the original request ends that presentation’s automatic dismissal. Answer persistence, requester delivery and acknowledgment remain separate receipts.

If a request or target changed, show old/new target or changed questions and require an answer against the new revision. Keep the previous draft/explanation separately linked to the old target, available for reference. Clear selected **Approve**, **I ran it** and other check outcomes for a replacement target; stable question IDs cannot carry those answers onto new bytes/builds. Never silently default an unanswered choice. If a requester ended, show pickup required while retaining the answer in task context. Report answer saved separately from delivery/acknowledgment.

## Cancel, split, archive, trash, purge

| Operation | Meaning / effect |
|---|---|
| Cancel | Scope is deliberately abandoned; reason and authority recorded; not done |
| Linked follow-up | New task links to the original; dependencies are explicit; full atomic merge/split is deferred |
| Mark duplicate | Preserve original as redirected/superseded; never discard its notes or unresolved findings |
| Archive and clean large managed files | Reject active implementation/review/verification claims; then hide without a lifecycle rewrite; task/history restore is reversible, deletion of managed bytes may not be |
| Trash | Reversible removal from ordinary use; record reason and prior state; reject unresolved implementation/review/verification claims; UI drafts are not claims |
| Purge | Owner-only permanent deletion after preview and dependency/history/export impact; no automatic timed purge initially |

Do not cancel active work only by changing a row. Queue a stop request; confirm session checkpoint/termination and file state; then release/recover and apply the disposition. Cancellation/reassignment while disconnected stays visibly pending if the process may still write.

Purging a task may remove its body, messages, request answers and managed attachments; shared attachment references survive while still referenced. Keep a minimal non-content tombstone for referential integrity, ID reuse prevention, and purge receipt. Explain that old backups and user-created exports still contain earlier content until separately removed. Never silently delete files referenced in a project directory. The app manages only its own copied attachments and store records.

Routine archive uses the project's storage preset and a short retained/cleaned summary, with Keep original available; no confirmation ceremony for every ticket. Undo can cancel cleanup before bytes are deleted. After deletion, task restore cannot restore the original. Exceptional irreversible purge/hold removal needs a clear impact preview and deliberate owner action.

Project archive pauses new claims and retains all tasks/history. Project purge requires no active attempts, an explicit owner action, impact preview and a backup/export choice. Disconnecting the project does not delete its repository. Deleting an epic/triage defaults to archive; removing a triage only removes grouping, never its member tasks.

## Backups, troubleshooting and export

Show last successful backup, restore rehearsal status, service/schema versions and per-client qualification. Export one project or an owner-selected set; include canonical IDs, aliases, history, policies, evidence manifests and file-reference metadata. Secrets/claim tokens/native socket endpoints are excluded. Warn when external references will not travel with the bundle; offer explicit attachment copies.

Diagnostics distinguish service offline, unauthorized workspace, unsupported client, stale claim, unavailable native endpoint, pending acknowledgment, broken file bookmark and version mismatch. Include a copyable redacted report. After two identical failures, suspend the route and report a concrete next step instead of repeating unchanged requests.

The deferred personal-assistant design would permit inspection/reporting, requested Drafts and notes after a separately requested and qualified integration. No assistant UI/setup or active plugin is currently provided. Assistant-only access never receives the task assignment or work/review claim. Notes retain stable host-assistant/source identity, the display label at send time and request provenance; native owner answers/approvals remain distinct. A host rename does not rename past authors or change delivery authority. Notification subscriptions can let the assistant report selected changes without polling; actual capability/receipts are explicit. See [assistant plugin](assistant-plugin.md). Database/backup controls and project identity/settings follow the [storage](database-storage.md) and [customization](project-customization.md) guides.


### Current correction and retirement limits

Cancel, reopen and changing an existing different planned assignee (including clearing it) require a nonblank reason. First assignment from an unassigned ticket and selecting the same assignee need no reason unless the existing agent policy override rule requires one. Single and bulk edits use the same rule and record supplied assignment reasons in history. Active parent or accepted child attempts, verification and unresolved source execution prevent a row edit from ending work. Release/takeover or recovery after a verified stop must happen first. Reopen returns Done/canceled tickets to Queued, retaining prior evidence and relations while clearing current completion authority. Individual status changes remove Triage memberships.

Trash is reachable beside Done / Archived, with Restore. It is a separate bounded list; ordinary search, Overview and pickup exclude trashed tickets. Restore keeps the earlier status and archive visibility. Single-ticket Undo uses the action result’s revision and the normal inverse command; edits, claims or cleanup invalidate it. Unarchive restores visibility and reports cleaned originals as unavailable. Reopening Done cannot offer a status-edit Undo that bypasses completion gates.

Permanent removal is available only through **Trash → Delete permanently** in the trusted owner app. Read the preview of exclusive records, shared/incoming references, history content and retained files/backups, then confirm the destructive action. The service requires a current revision and preview digest and refuses active work, review, verification, source execution and pending owner requests. A new note/reference after preview requires a new preview even if the ticket revision stayed unchanged.

Purge replaces the ticket with an immutable **Purged ticket** reference retaining its id, project and key, purge time and actor. It removes exclusive notes, work/review/request/file records and indirect delivery records, removes grouping entries, clears affected history-event content without deleting sequence rows, and expires earlier cached command results containing removed content. Incoming relations and records shared with other tickets remain. It cannot be undone. Other tickets' quoted content is not granularly redacted.

This version retains all managed-file and captured-source bytes; original-size totals are not reclaimed disk space. External originals and workspace files are never deleted. Known backup counts and recorded times come from existing metadata; unrecorded backups/exports may also contain the ticket. **Checklist does not change existing backups or exports; delete those copies yourself if needed.** No backup indexing, timed purge, secure erasure or conversation-redaction system is added.

## CLI JSON results

Every successful `checklist call` result is one RFC 8259 JSON value followed by a newline. Literal U+0000–U+001F inside string keys or values are escaped at the CLI output boundary; existing escapes and formatting whitespace outside strings are preserved. Standard strict JSON parsers can consume the output. MCP tool/resource JSON and SDK protocol frames have separate control-character regression coverage.
