# Versioned provider plugins (CL-128)

The local source has a Foundation-only `ChecklistProviders` target with a small version-1 contract, reviewed bundled Codex and Claude implementations, and an immutable validated registry. It is compiled into the existing macOS products. It is not a runtime loader, marketplace, model runtime, new enrollment route or future server. Windows/Linux clients remain deferred. The separate [project orchestrator](project-orchestrators.md) and [optional content](conversation-content.md) contracts are planned; this refactor does not expose them as commands or UI.

## Ownership and interface

`ChecklistProviderPlugin` owns a validated `ProviderPluginManifest`, observed-session parsing, host signing/application/registry metadata, registry field interpretation, composer creation/validation and provider host-status explanations. Default methods return unavailable. A plugin's `ProviderModel` catalog can describe exact model IDs and display names; only an explicitly qualified `model_selection` capability and a selectable catalog entry allow `registry.model`. Neither bundled plugin advertises model selection or a model catalog: existing `preferred_models` values remain opaque preferences, not applied settings or proof a host ran that model. Unknown model/provider IDs never fall back to another selection. Model catalog IDs compare exact UTF-8 bytes; Unicode canonical equivalence does not select another ID.

`ProviderPluginRegistry` validates interface/schema versions, bounded IDs/version/display/model metadata, duplicate provider/plugin/model identities, and capability dependencies before registration. `ProviderPluginManifest.decode` additionally bounds JSON to 64 KiB and rejects unknown top-level/model keys, repeated capabilities and unknown capability words. The [manifest schema](../contracts/provider-plugin.schema.json) and [synthetic example](../examples/provider-plugin.json) share its wire spelling. Registration has separate host-owned `enabled` and `qualifiedCapabilities` values; those are deliberately absent from the manifest. Merely declaring a capability cannot enable it. Registry construction rejects incompatible/invalid entries without publishing a partially changed registry. Disabled and unqualified entries may be inspected as metadata but cannot resolve an operational plugin.

| Layer | Owns after this refactor |
|---|---|
| `ChecklistProviders/ProviderPlugin.swift` | Portable versioned manifest/model/capability contracts, registration validation and unavailable lookup |
| `ChecklistProviders/BundledProviderPlugins.swift` | Codex/Claude observed session/model metadata, signed host/application IDs, registry interpretation, composer/hold explanations, compatibility policy defaults |
| `ChecklistBridges` | Provider adapters for native process discovery, bounded secure registry observations and existing Claude peer framing/status/reply I/O; `NativeProviderTransport` gates reviewed dispatch by capability |
| Core | Project policy intersection, claims, review independence, Triage phases, immutable history/outbox, exact reply allowance and trusted owner answers; no native provider transport |
| Service | Kernel/signature/workspace/credential/grant validation, committed registration, durable pre-I/O fence, callback attribution and transaction coordination using validated plugin contracts |
| App | Generic provider presentation, eligible menus/settings, installed-app lookup, explicit composer/open/copy actions; no authority or model launching |

The plugin interface does not take claim tokens, project grants or credentials. These remain with the existing service/Keychain and domain handlers. An observed session or manifest is not authentication. Verified principal/session, project grant, work role, model preference and optional orchestrator registration remain separate identities.

## Audit and preserved behavior

The build-106 provider/model audit covered every `codex`, `claude`, `provider`, `model` and adapter branch under `Sources`. Cosmetic source-format words such as `CLAUDE.md` and the MCP SDK's model types are unrelated to provider execution.

| Existing coupling | Boundary now used / retained limitation |
|---|---|
| `Work`, `WorkAuthority`, `TaskSessions`, policy provider whitelist and review preparation | Router-owned validated registry `work_session`; project role/kind rules, grants, contributor exclusions and individual/batch semantics still apply |
| `Policy` default participants and named routing presets | Plugin-owned compatibility defaults. Persisted `shared`, `claude_coordinates`, `codex_led` choices keep their meanings; no provider-name switch in ticket/review/Triage transitions |
| `HumanAnswerNotices` Codex-only decoration | Qualified `answer_notice`; legacy `native_codex_wake_qualified=false` wire field retained for compatibility, never used to select a route |
| `NativeDeliveryStatus` Claude-specific permission help | Provider-owned status explanation; Core still owns allowed state transitions, late-ack precedence and immutable receipts |
| `NativeSessionContext`, native ancestry and service signing branches | Registry-provided executable/signing metadata plus plugin observed-session/registry interpretation; actual OS ancestry, signing and kernel cwd checks remain mandatory |
| Claude spare-process registry startup recovery | Existing bounded `ClaudeRegistryStart` provider adapter and exact retry diagnostic retained; other providers do not inherit its retry policy |
| Lifecycle process/registry closure and resumption | Qualified `registry_closure`, exact process start and secure registry identity. Codex lacks a per-thread closure registry and cannot inherit Claude resumption |
| `dispatchNative`, endpoint naming, Claude framing/status and reply translation | Qualified reviewed `NativeProviderTransport` adapter; actual kernel peer, socket identity, message correlation and native host identity checks stay in place |
| `prepareHandoff`, `prepareAgentReview`, `CodexComposeLink`, app menus/settings | Selected plugin's composer/validator/application metadata; Claude/unknown providers cannot acquire a Codex link by fallback |
| Deferred `codex.dot` verified-assistant identity and `native_codex_helper_not_dot_identity` provenance | Retained historical/future identity contracts, not generic provider selection; no assistant UI or grants are enabled |
| CLI/MCP connection text, documentation and existing diagnostics | Informational labels and stable protocol fields, not runtime model/provider selectors; bounded existing CLI/MCP upgrade delegation remains unchanged |

Provider adapters may implement provider-specific wire types inside Bridges. Those types do not become domain state or a second integration engine. Unknown native frames/status words, ambiguous kernel recipients, mismatched message IDs or changed generations are left uncorrelated; they never mint acknowledgment or consume a reply allowance.

## Capabilities and evidence limits

| Bundled plugin | Advertised implementation contract | Explicitly unavailable |
|---|---|---|
| `org.checklist.codex` 1.0.0 | Actual host-exported thread context, authenticated MCP pickup/ack/reply, human-answer pickup notice, prepared draft composer; retained deferred helper source | Native idle/child wake, per-thread process/registry closure, automatic app Send/create, model selection, schedules |
| `org.checklist.claude` 1.0.0 | Actual process/session registry bootstrap, authenticated MCP pickup/ack/reply, bounded same-user native peer transport/host hold notices, exact registry closure | Native composer/automatic creation, model selection, schedules; permission-mode holds remain holds |

`service_info.provider_plugins` reports versioned manifests and distinct declared/qualified capability lists. An enabled capability means that the reviewed bundled implementation is eligible for its existing bounded operation, subject to all current identity/route/grant checks. It does not assert a live endpoint, universal host-version compatibility, a newly observed installed pass, or a model response. `native_push=false` and the existing unsupported list remain unchanged. The retained assistant-helper capability describes dormant source support, not qualified Dot access or permission to enable it.

Existing native evidence is recorded in [integrations](integrations.md): the bounded Claude 2.1.299 attributed socket/model reply and permission-mode hold observations, Codex 0.159.0 authenticated native thread use and prepared-composer/explicit host-native creation distinction. Those receipts support only their original versions, targets and configurations; this refactor reuses no receipt as a fresh installed qualification. Deterministic plugin/bridge/domain/app tests prove parsing, dispatch gating, provenance preservation and refusal behavior only. The composed installed bundle still needs the same Codex/Claude bootstrap, pickup/ack/reply, composer and held-delivery checks on explicitly selected existing synthetic routes. No provider was installed, configured, launched or contacted by these component tests.

## Packaging, updates and recovery

1. Add reviewed Swift plugin code through the root package/build capture. Keep protocol-specific I/O in Bridges and signing/kernel checks in the service; no arbitrary manifest command, dylib, repository path, URL or downloaded code is executed. Stable provider ID and namespaced plugin ID identify the adapter, independently of version and model IDs.
2. Validate a manifest against the schema and Swift semantic checks. Add a registration **disabled and unqualified** first. The bounded synthetic additional-plugin tests exercise this exact boundary without editing Core's ticket logic or the app's provider names. A later provider requires its own explicit install/configuration/connection authorization and actual supported host authentication.
3. Qualify each supported capability against the real host/version with redacted receipts for session/workspace isolation, wrong peer/generation, busy/idle/held/refused/ended routes, durable original-command retries, acknowledgment/reply correlation, independent-review contributor preservation, and unsupported creation/model settings. Simulated endpoints are component evidence only. Enable only qualified capabilities in the reviewed bundled registry; never infer them from metadata.
4. Ship plugins as part of the normal exact signed Checklist bundle. Interface/schema major 1 is the only accepted version. Patch/minor plugin versions keep wire/identity semantics; changed host identity, serialization or capability behavior needs its affected native cases requalified. An incompatible manifest refuses registration; it does not select a different plugin/provider. No mutable external plugin directory exists.
5. At startup and on actual connection/use, the service still verifies the exact bundled CLI, signed host, process start, native session/workspace/registry, current saved credential, enrollment generation, committed registration and project grants. Current policy/work eligibility and delivery dispatch also recheck registry capabilities. Native incoming status/reply decoding requires the current kernel peer’s qualified adapter, and Core rechecks native reply qualification before consuming its exact allowance. Disabling native I/O leaves permitted MCP bootstrap/pickup available; current registry identity inspection remains separate from permission for automatic closure monitoring. Updating metadata alone rotates no principal, grant, contributor, pending message ID, reply correlation or claim. There is no store migration for this boundary.
6. Disable an unavailable capability/provider in the reviewed registry and rebuild through the ordinary controlled release path. Existing connection records, claims, messages/outbox, reply IDs and contributor provenance remain durable; disabled operational lookups return unavailable and work/receipt routes cannot silently transfer. A disabled adapter does not stop an external process or release its reservations. Restore a compatible qualified adapter and revalidate the original identity/generation before recovery. A genuinely resumed native process still uses the existing verified-closure/new-generation flow; pending deliveries stay with their original generation. Keep uncertain writes fenced and reconcile original IDs rather than replaying to another provider.

The version-1 macOS bootstrap retains the existing UUID-shaped Codex/Claude session context and process-domain layout. A host with a different native identity representation needs an explicit compatible mapping or a versioned contract extension plus qualification; registering its metadata cannot bypass those checks.

Optional provider-specific settings belong to a future versioned plugin-owned schema and explicit qualified operation. Neither bundled plugin currently adds writable settings. A model catalog, settings label or new orchestrator registration cannot grant access, choose a different provider, change host permission modes, launch a model or enable a schedule.
