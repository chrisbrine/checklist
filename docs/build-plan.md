# Build plan

This is the delivery plan for the local development implementation; [implementation status](implementation-status.md) records what exists and what remains unverified. The baseline is independent game and app production: quick capture, reliable continuation, practical artifacts/review and easy human answers. No source-board migration has been performed. The app, shared service and official-SDK MCP runtime exist; the broader release gates below remain the completion criteria. Work on main when a repository exists; no branch/worktree is needed for preparation.

CL-124 defines the bounded future sequence for optional [project orchestrators](project-orchestrators.md#bounded-implementation-sequence) and [conversation content](conversation-content.md). These contracts add no server build, native launch, enrollment, schedule or current Orchestrators UI. CL-128 implements the [versioned bundled provider boundary](provider-plugins.md), preserving the existing macOS routes and qualification limits; new providers and other-platform clients remain deferred.

Qualify native session routes early, before a broad UI or tool catalog. A limited local existing-Claude-session round trip was observed; see the sanitized integration report. It is not broad release qualification. Missing/incorrect sender permission metadata remains a required serializer negative test. Do not treat socket reachability as push support. Prove idle/busy Codex and Claude, exact parent/child routes both ways, lost replies, native holds/refusals and ended targets. An unavailable route stays visibly checkpoint/manual only; an app can be useful at that reduced level, but must not claim the full communication promise.

Personal-assistant/Dot integration was cancelled by the owner on 22 October 2026 (CL-3 and CL-22). Preserve generic source/contracts and prior component evidence as historical reference without installing the package or exposing assistant controls. There is no planned reactivation or qualification milestone. See the [cancellation decision](assistant-plugin.md#cancellation-decision).

Exit: measured packaging/startup results and provider capability matrix with actual versions and receipts. A pure simulated adapter is insufficient for native qualification. Keep any failed capability narrow and explicit while developing the rest.

## 1. One complete production task

Build the smallest trustworthy vertical slice using one synthetic Bug task in a fake game project in a disposable [test slot](test-instances.md). Create the project with `project_create` through the slot CLI from its actual authorized workspace. Never create synthetic projects in the live installation; destroy the owned slot after evidence capture instead of retaining its projects. Do not implement all proposed tools first.

1. Native title/project capture, Draft/Ready, brief/outcome and one simple status preset; project-scoped store and caller workspace binding.
2. Enrolled worker claims atomically, gets brief/pinned decisions, checkpoints and shows actual session/last checkpoint.
3. Owner adds a note and screenshot in the right overlay; durable outbox, held/failed/accepted/acknowledged display and real qualified transport.
4. Agent asks a multi-question blocking request with a file reference. Owner answers via Needs You; trusted answer, Finder access, draft/revision preservation, requester continuation.
5. Submit an immutable dirty/untracked-inclusive artifact manifest; independent reviewer claims **review_request_id**, executes on captured work, returns one identified finding; worker fixes, reviewer accepts the new target, task completes only through configured gates.
6. Archive, preview eligible large-copy cleanup and holds, unarchive with honest file availability. Export and restore the whole task and context without reviving old claims.

Build store transactions/events/idempotency and UI/live subscriptions as each step needs them. Follow the storage plan for composite keys/indexes/FTS, one-writer SQLite, immutable files, backup capture/GC barriers, full restore and disk-full recovery; use actual crash-boundary tests, not just happy-path CRUD. Use an append-only history with revisions, durable receipts and post-commit external delivery; only the service writes SQLite. Role-scoped MCP tools expose only the needed operations in each step. Keep the tool catalog a contract, not a stage-one backlog quota.

Exit: this full loop works in the installed test app, across UI/service restarts, with one lost-reply retry and one simultaneous-claim conflict. Capture observed receipts and UI evidence. Do not seed or migrate production work.

## 2. Game and app work variations

Add optional Work/Bug/Asset/Playtest/Question starters and cheap capture without mandatory metadata. Project brief/pinned decisions automatically enter context. Add exact image/build approval (immutable target, revision-safe answer), manual run/check result and whole human task assignment. Add local file/image paste/drop/import for owner and agents, previews, references and storage holds; remote/chunk streaming remains deferred.

Implement customizable project statuses including several Parked types, tags, basic search/filter/saved views, linked follow-ups/duplicates, guarded Undo and per-task-revision bulk edits. Provide project tabs **Tickets** and **Epics**. Epics contains stable subprojects by task type; Tickets contains expandable temporary Triage rows spanning Epics, with member tickets and fixed dispatched batches. Triage purpose/membership editing stays in the right overlay, without a separate Triage workspace. Moving a ticket reconciles its primary Epic; Triage add/remove never changes that container. Any individual ticket status action, including explicit same-status marking, removes it from all current Triages; notes/attachments/metadata do not. Ordinary group status changes retain membership, while group Done removes completed tickets from all Triages. Historical/future milestone policy stays secondary to that simple flow. Derive each Triage's shared/Mixed/Empty status from its members; a group status change atomically transitions all current tickets using the expected group/member revisions and ordinary guards. Any blocker leaves the entire group unchanged; Done still requires actual completion gates. Keep actual worker sessions/current-prior attempts attached to their ticket; no global worker Connections catalog. Rules/Activity remain secondary to Tasks and Needs You. Navigation, composer destination and offline/draft states follow interface.md.

Add owner-applied project identity/icons/accent/future-key prefix, optional starter/default-view/quiet-alert settings, with independent icon retention and portable export. Ordinary Codex/Claude work uses actual provider session identities. Personal-assistant identity, named contact, Draft/note access and notifications were cancelled; the [assistant design](assistant-plugin.md) is historical reference excluded from delivery. Keep its retained contracts generic and separate from worker authority; no named-worker/personality catalog or second database.

Exit: asset candidate replacement cannot inherit approval; Playtest refers to the exact build; partial/clarification/refusal answers do not silently unblock; Questions use suitable completion checks; a triage changes during a batch without rewriting it.

## 3. Concurrency, policy and recovery hardening

Expand project preset rules and limited task-kind overrides, assignment explanations, versioned preview, future-attempt/checkpoint-active modes and policy acknowledgment. Avoid a routing programming language. Prove separate projects with the same keys and reject physically overlapping writable roots after canonical symlink/case/path checks. Shared read-only references are allowed. Atomic scope expansion reserves additions before release/change; conflict preserves old claims.

Prove delegated contributor independence, one active review per task, stable finding resolution/supersession, relevant-writer exclusion or immutable execution, evidence invalidation and all-gate completion. Add handoff/stale recovery, parent ending before child, source changes during review, fencing after restore and native reconnect. Ending a session never proves abandonment or completion. History and context summaries preserve owner direction and old provenance.

Exit: deterministic race/failure tests plus real qualified-provider checks pass with no fabricated delivery, identity or evidence. A test checkout containing a different revision cannot satisfy review. No route retries forever after two identical failures. Verify opaque scoped cursors/CURSOR_RESET, grant revision/keyed-duplicate rejection, last pre-send revocation race and honest in-flight outcome, notification self-failure suppression and bounded catch-up coalescing. Historical actor snapshots remain intact. Assistant-only identity/contact/notification qualification is cancelled and is not an exit criterion.

## 5. Checklist develops itself

Once working, register a **Checklist** project in the app. Seed only its own approved enhancement/verification tasks. Self-build/install is an explicit per-installation opt-in. An applicable existing local grant remains valid; repository contents or another user's grant do not authorize a public installation. First prove staging, compatible rollback and state retention with disposable data.

Each relevant implementation submission captures source including dirty/untracked inputs, builds/checks/signs once per source+toolchain fingerprint, stages and safely installs `/Applications/Checklist.app`, reopens that actual build and verifies live MCP/UI behavior. The required **installed_build_verified** gate binds running bundle identity and critique to the snapshot built; compile success alone cannot complete the task. Failed builds preserve the working app; Retry is explicit for the failed job. Notes/status/build events cannot trigger their own rebuild loop. Follow [self-hosting](self-hosting.md).

Exit: an improvement travels through Checklist, is compiled/installed, critiqued on the actual running build and verified with retained drafts/claims. No broad migration is bundled into that milestone.

## Triage handling direction

Each Triage handles one phase, Implementation or Review, and can bind an actual Codex or Claude coordinating conversation. An Implementation Triage can be planned in advance with Queued tickets, ordered by prerequisites; claim its Ready members with the atomic batch workflow. Already In Progress tickets may join the same implementation pass. Active attention also includes membership in an actively orchestrated Triage. Submission finishes that phase and leaves the Implementation Triage; form a separate Review Triage for exact submitted targets. A review outcome departs that pass: complete fresh passing targets independently, and return only failures to Active or Ready/Queued for another implementation pass. The explicit project completion override can hold passes without reworking them. Epics stay stable. See [the current batch contract](batches.md).

## Scope and verification discipline

Current game/app features are sequenced; personal-assistant integration is cancelled and is not planned release work. Defer enterprise management, streamed uploads, full split/merge/redaction, optional board view and a model runtime. Keep delivery units compilable and reviewable. Separate review is useful for claims/restore, trusted human authority and real adapters; repeated tests should prove a changed behavior or unresolved risk. Simulations prove deterministic state handling; installed native behavior needs actual receipts and observed results.
