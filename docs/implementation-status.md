# Development implementation status

16 October 2026. Checklist is a local macOS development app, shared SQLite service and official-SDK stdio MCP executable. This page describes current source support and its limits; it does not claim every release acceptance scenario or native host route has passed. No existing checklist has been migrated.

## Build and connection flow

`script/build_and_run.sh --verify` captures immutable source/dependency/toolchain inputs, builds/signs a bundle, installs `/Applications/Checklist.app`, launches it and checks the shared service. `CHECKLIST_BUILD_CONFIGURATION=debug` selects the development configuration; the default is release. The displayed build ID comes from the captured input fingerprint. Compatible binary rollback retains the prior app without replacing the database or copying an open SQLite main file as a purported backup.

The app bundle contains `ChecklistApp`, `ChecklistService` and `checklist`; distinct GUI/CLI names are required on case-insensitive volumes. In a supported existing or new Codex/Claude conversation, `/Applications/Checklist.app/Contents/MacOS/checklist mcp` or its CLI call path bootstraps the actual host/session/workspace automatically. Explicit installation selection is a legacy/advanced configured route, not the primary per-thread setup. Worker status, current/prior attempts, checkpoints and recovery/actions belong on the ticket, not a global Connections catalog. The current UI has no personal-assistant settings/sidebar/grant controls and no manual worker pairing prerequisite. Credentials stay in Keychain and project files contain no token. Bootstrap uses observed local host/process provenance and host-exported thread/session context where available; this is not cryptographic attestation of a conversation ID. An unknown or unsupported native context returns a specific limitation; caller-supplied names cannot manufacture a verified personal-assistant identity. A user-scope MCP registration also starts in conversations outside Checklist projects. There verified native Codex/Claude conversations start `checklist mcp` and `checklist tools` without project enrollment or a stored credential, discover `service_info` and `project_create`, and can create only their actual workspace. Creation atomically grants/enrolls the calling worker; the same MCP connection completes bootstrap with one tools-list change notice. `checklist call project_create` uses the same flow; other calls and `connect` still require a registered project. The [Claude spare-process path](integrations.md#claude-desktop-spare-processes) can start MCP unconnected and recover on a later tool/resource request with one tools-list change notice. Build 113 has two natural initial-start recoveries. Under the owner-delegated CL-168 decision of 22 October 2026, the named real-server and bridge tests satisfy revised acceptance item 3 as component coverage, as recorded in that section. Native persistent limited start, next-call bootstrap and Claude Code receiving `notifications/tools/list_changed` remain unobserved and unqualified. Assistant relays and permanent bootstrap failures stay strict; see the [MCP contract](mcp-contract.md#scope-authority-and-retry).

Current source supports **Use in Codex → Open prepared chat**: a native composer contains the scoped prompt and the user presses Send. A separate native Codex `create_thread` exercise returned a real new thread, which automatically ran `connect --task CL-4`; the running UI showed its context-only association. Preparing/opening a draft, starting a turn, attaching, assignment and claim are separate outcomes. This evidence qualifies that explicit native creation/attachment path, not automatic sending from the GUI composer. Claude automatic native creation remains unqualified with an honest open/copy fallback.

The bundled launch agent uses SMAppService and a per-user Mach XPC service. Exact bundled GUI identity/CDHash checks guard owner actions, while automatic agent bootstrap and project grants constrain agent calls. macOS may require approval of the background item before UI-closed cold start. Distribution signing/notarization remain separate release work. No HTTP listener, model runtime, polling schedule or automatic source import is created.

CL-171 adds an error-only XPC peer for earlier Checklist builds and a `CLIENT_OUTDATED` reply with `command_executed: false`. Current GUI/CLI command admission stays exact by cdhash. Fixed MCP shims detect a replaced launch file or that reply and delegate requests to the signed CLI at the saved launch path, with one catalog-change notice and the same SDK transport. Parent preflight checks the bundle root and instance. The child starts suspended; the parent dynamically validates its loaded code by PID with `SecCodeCheckValidity` against the exact pinned CLI cdhash requirement. Its kernel executable path must also resolve inside the captured bundle root before resume. Static signing information is used only for refusal diagnostics. A failed check kills and reaps it before any instruction. The resumed CLI checks its own instance and bundle root against the delegate expectation before Checklist IPC, Keychain or bootstrap; a mismatch returns `DELEGATE_INSTANCE_MISMATCH` as not sent with the original command ID. Tool arguments use a bounded, separate child stdin pipe. Unverified child results return `OUTCOME_UNKNOWN` with the original command ID and reason `delegate_ended`; spawn errors report that no command ran. Shims started before this fix need a manual reconnect after the next install. Source checks do not qualify live install recovery; the existing Claude and Codex read/mutation checks remain with the orchestrator. See [install recovery](integrations.md#installs-and-running-mcp-shims).

### Service file safety, writer lock and agent boundary (20 October 2026)

Triage c7612d4c (CL-81, CL-70, CL-71, CL-72, CL-80) changes the service and storage core; [database and storage](database-storage.md) and the [MCP contract](mcp-contract.md) state the rules.

- **Agent boundary (CL-81).** Agent reads of reference files open the final component with `O_NOFOLLOW` and check the descriptor's own path against the workspace again; a preview read without a separate preview checks the original's hash. A non-owner call that names an unregistered session fails closed. Every XPC connection carries a code-signing requirement on the CDHashes of the installed `ChecklistApp` and `checklist`, checked by XPC against each message's audit token. Client error text contains no SQL (`STORAGE_ERROR` with the SQLite code only).
- **Failed-command files (CL-70).** Source captures use pending markers; a failed command removes its own uncommitted capture, and startup removes captures that a crash left. Startup settles managed import jobs that stayed 7 days without a receipt and removes only their own unreferenced files. Exports appear at their destination only complete, carry their command's owner marker until the receipt commits, and are removed when the receipt rolls back; a same-command retry replaces only its own uncommitted export, and a pending record in the store lets startup remove an export that a crash left without a receipt. The record stays until its cleanup is complete or while the owner marker cannot be read, so a later startup retries a removal that failed.
- **Writer lock (CL-71).** Source capture copying, hashing and git inventory, managed and reference-mode import file work, source-target inventories, captured-target validation and the hashing of managed objects that a command checks (submission artifacts, review targets and evidence, human-request targets) run before the object gate and the SQL writer; inside it, an unchanged content identity (device, inode, size, modification time), or for a capture the same content observation of every captured entry, stands for the bytes, and the transaction commits metadata only. A changed prepared file, or one whose preparation failed for any reason (including a read error or a failed live inventory), fails inside the writer without a read, and a permission-only change keeps the identity. Git calls have a 60-second limit and read both pipes at once. The service runs these commands and pure reads off its serial queue. Measured in the core harness on this Mac with a 256 MiB source: before the change, the one write issued during a 3.11-second submission waited 3.08 seconds; after it, 87 writes and reads ran during a 2.94-second submission, with the longest write wait 48 ms and the longest read wait 6 ms. After the review rework, a 256 MiB reference import took 0.14 seconds with the longest concurrent write wait 6 ms (the reviewer measured 0.276 seconds of 0.282 before), and a review claim on a 128 MiB captured target took 0.32 seconds with the longest write wait 40 ms.
- **Pruning and reads (CL-72).** Cursors are sealed tokens with a per-store key, so no method adds a `cursors` row. Maintenance prunes cursor rows after 24 hours (20,000 per pass), tombstones command results after 30 days (500 per pass; a late retry returns `COMMAND_RESULT_EXPIRED`) and deletes stale cleanup previews; a repeated preview reuses its record. Every read method, including attachment metadata and preview reads and `changes_wait`, starts on read-only connections without the gate or the writer; a read that writes runs again on the writer path.
- **Native outcomes (CL-80).** Native write results, host statuses and native replies go through a recorder that retries storage failures with the same command ID, logs every failed attempt with its delivery ID (also one that a retry recovers) and marks the delivery `delivery_uncertain` when the write is lost.

Source checks: the full Swift suite has the same 105 failing cases as the unchanged baseline (pre-existing failures, mostly fixtures that open a store under a missing parent folder) and no new failure. The 30 new tests pass; of the 11 first-pass tests that also compile against the unchanged baseline, 10 fail there and the snapshot test passes, because its behavior already existed. An independent Codex review passed CL-81 and found one gap each in CL-70, CL-71, CL-72 and CL-80 (three of them also present before the change); the rework covers them with five more tests. A failed-case recheck passed CL-72 and CL-80 and found one more gap each in CL-70 (a crash-left export) and CL-71 (a capture changed after prevalidation); the second rework covers them with two more tests. A second recheck found that a failed export cleanup lost its pending record (CL-70) and that a permission-only change of a capture made the writer hash it again (CL-71); the third rework covers them with two more tests and more cases. With it, a review claim on a 256 MiB capture after a permission-only change took 0.023 seconds inside the writer. A third recheck found that an unreadable export marker dropped the pending record (CL-70) and that a failed prefetch read was forgotten, so the writer hashed the object (CL-71); the fourth rework covers them with one more test and more cases. A fourth recheck (Codex thread 01a1585c, installed build 570a316d4aa4d663) passed CL-70 and CL-71 with no new finding; all five tickets are Done. Plan and schema validation passed. ### Review outcomes and attempt records (20 October 2026)

Triage 3fd2303d (CL-41, CL-42, CL-43, CL-44, CL-46, CL-47, CL-45) adds review outcomes and attempt records; the [MCP contract](mcp-contract.md), [domain](domain.md) and [project customization](project-customization.md) state the rules.

- **Evidence missing and check not run (CL-41).** `review_record` accepts `evidence_missing` (with a reason) and `not_run` (with the check and a reason). Missing evidence keeps the same target and waits as `evidence_requested` until `review_request` returns it with `supplemental_evidence_refs`; no new implementation round. A check that did not run returns the request to any eligible reviewer and is not a fail. Neither satisfies a gate.
- **Advice findings (CL-42).** Findings are `blocking` (default) or `advice`. Advice stays visible on the ticket and in later rounds and never blocks completion; a pass may add advice only. `finding_severity_set` lets the finding's reviewer, the current reviewer of its gate or the owner change a severity with a reason, kept in `severity_history`.
- **Repeated causes (CL-43).** `same_cause_as` links a finding to an earlier finding of the ticket. `task_context.review_summary` shows failed rounds per gate and a warning when a cause returns for the second time; `triage_list` shows it to the coordinator. The warning changes no status, claim or verdict.
- **Draft verdict handoff (CL-44).** `review_draft_save` validates a reviewer's verdict as a dry run and keeps it on the active claim. `review_draft_submit` lets the owner or the Triage's actual orchestrator submit it; the verdict names the reviewer as its author and the submitter in `submitted_by`, and independence is checked for the reviewer.
- **Final reports (CL-46).** `work_submit`, `work_release` and `review_record` accept `final_report` (at most 64,000 bytes), stored on the attempt as agent text and shown on the ticket for current and prior attempts.
- **Shared resources (CL-47).** `work_checkpoint` accepts `waiting_for_resource`; an active attempt's `checkpoint_health` is `waiting_for_resource`, `current` or `quiet` (30 minutes), and waiting time is never quiet. A failed check can name `failure_cause` `defect`, `environment` or `other_ticket`. No retry, schedule or model launch is added.
- **Release-set holds (CL-45).** With the policy key `release_set_holds: true`, a pass can name a release set and a reason; the ticket waits, accepted and held, and `release_set_complete` completes the whole set through each ticket's fresh gates, all or nothing. Without the policy, passing tickets complete independently.

The app shows the new verdict states, failed rounds, repeated-cause warnings, advice findings, draft verdicts, release holds, final reports and resource waits on the ticket.

An independent review (Codex thread 01a15887) passed CL-42, CL-43, CL-46 and CL-47 and found one gap each in CL-41 (supplemental evidence could not be cited by the next reviewer), CL-44 (a draft submission skipped the live-claim generation fences) and CL-45 (a later owner approval completed a held ticket). The rework covers them with two more tests and more cases. A failed-case recheck (Codex thread 01a1589f, installed build fd4a5cb07cbf2eb8) passed CL-41, CL-44 and CL-45 with no new finding; all seven tickets are Done.
