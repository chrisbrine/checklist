# Sessions that another agent starts (optional)

Read this only when an orchestrator starts a provider session outside that provider's own desktop or terminal host, for example `codex exec` started from a Claude conversation or a script. A native Codex or Claude conversation, including a Triage that Codex itself orchestrates, uses its MCP connection; skip this reference.

Each host has its own section. A host without a section here is not supported for this route until someone observes and records it.

## Codex CLI (`codex exec`)

Observed on 19 October 2026 with codex-cli 0.159.0 and installed Checklist build 47:

- `codex exec` starts stdio MCP servers with a filtered environment that has no `CODEX_THREAD_ID`. The bundled `checklist mcp` server cannot find the native thread, so no Checklist tools appear in the thread and no error is shown. A `-c mcp_servers.checklist=...` override does not change this.
- Shell commands that Codex runs have `CODEX_THREAD_ID` and a `codex` ancestor process. From such a shell, `/Applications/Checklist.app/Contents/MacOS/checklist call` bootstraps the actual Codex thread as its own session. Its caller `session_id` is the thread ID, and its installation differs from the orchestrator's.
- The `read-only` and `workspace-write` sandboxes block the call. `workspace-write` cannot write the Checklist folder in `~/Library/Application Support`. With that folder added as a writable root, the call returns `OUTCOME_UNKNOWN` because the sandbox blocks the service connection. Only `danger-full-access` reached the service.

### Procedure

1. Decide which threads need Checklist. A helper that only edits files and reports back does not need it: the orchestrator keeps the claim, and the helper can stay in `workspace-write`. A thread that claims, reviews or sends notes needs the route below.
2. Start that thread in the registered project folder (`codex exec -C <project root> -s danger-full-access ...`). `danger-full-access` removes the sandbox for every shell command of the thread. Give such a thread a narrow task (for example, review only, no file edits), and do not use it for unrelated work.
3. Make the first command `checklist call service_info '{}'`. Continue only if `caller.session_id` equals the thread ID and `project_ids` contains the project.
4. Call tools as `checklist call <tool> '<json arguments>'`. The names and arguments are the same as the MCP tools; `checklist tools` lists the catalog. Each write needs a new random UUID `command_id`; reuse it only to retry the same command with the same input.
5. Keep claim tokens out of prompts, notes, logs and reports that another agent reads. The thread obtains and uses its own tokens.
6. Finish all Checklist work in the same `codex exec` run that made the first call: connect, read context, claim, check, add evidence and record the verdict, submission or release before the run ends. Write the prompt so that the thread does not stop early to ask a question.
7. Do not use `codex exec resume` for more Checklist work. A resumed run is a new Codex process. Checklist binds a Codex thread to the process that first connected it (provider, PID and kernel start identity), and it lets only a verified Claude session resume after its process closes. On 19 October 2026 (build 47) a resumed reviewer thread got `NATIVE_SESSION_MISMATCH` on its first call. For later Checklist work, start a fresh thread. A resumed thread can still edit files or report without Checklist.

### Run lifetime

- A run that ends does not release its claim, prove native closure, complete work or acknowledge a message. A claim that a finished run still holds stays until an eligible session takes it over with `work_takeover` and a reason, or the owner recovers it.
- A queued Checklist note does not wake a finished `codex exec` thread, and a resumed thread cannot read that thread's inbox. Send the next step to a fresh thread in its prompt.

### Identity and review independence

- Each `codex exec` thread is a session separate from its orchestrator. Its Checklist authority belongs to the process of the run that connected it, not only to the thread ID.
- A fresh thread is a new session. It gets no claim, message or authority of an earlier thread, and it follows the ordinary claim and takeover rules.
- A thread that edited files for a ticket is an implementation contributor, even when the orchestrator held the claim and the thread never connected to Checklist. Record its thread ID in a note on the ticket. It never reviews that ticket.
- A fresh thread that did not contribute can review, under the ordinary review rules in [review](review.md).

### Scratch cleanup and cache settings

CL-202 applies at the end of each check-runner and rework step, and at each combined-round boundary. Reviewer steps run no scratch cleanup preview or apply; the orchestrator covers review scratch at the next round boundary. Check-runner and rework steps clean only their own session's disposable scratch. Mark every persistent implementation, integration, build or review workspace **when it is created, before syncing sources or building**: `python3 <project folder>/script/clean_scratch.py --mark <scratch folder> --purpose "persistent review/build slot" --session-id <own session ID>`. Keep the marker at the workspace root beside `src/` and `.build/`, outside source-sync deletion. Names such as `rv1`, `rv2`, `rv3`, `rw-current` or any other name have the same protection. The owning session marks existing assigned slots before reuse too. Do not release a workspace between tasks while it remains assigned for reuse. Only its owning session releases it when retiring the assignment: `python3 <project folder>/script/clean_scratch.py --release <scratch folder> --session-id <own session ID>`. Re-mark a released slot before reusing it. Release changes eligibility; it does not remove bytes or bypass the quiet/process/qualified-copy checks.

The root `.checklist-workspace.json` is versioned JSON: `{"version":1,"session_id":"<own session ID>","purpose":"persistent review/build slot","released":false}`. `--mark` writes it and `--release` sets the boolean `released` to true, preserving owner and purpose; neither command invokes Git or cleanup. Another session cannot change an existing marker through these commands. An unreleased marker anywhere within or above a candidate retains the whole item, including source and warm build output. Invalid, unreadable or linked markers fail closed. Released marker files remain as ownership/release records, except when a whole disposable qualification run retires as described below. Unmarked legacy `ws[a-z]*\d+` folders are conservatively kept and reported for migration, including nested slots: their owner marks them, then explicitly releases them only when retired. The old name check is a migration safeguard, never a way to establish ownership or release.

The cleanup owner runs `python3 <project folder>/script/clean_scratch.py --preview --repo <project folder> --session-id <own session ID> --keep-qualified <qualified round> --keep-qualified <scratch folder>` and saves its JSON-lines report with the step evidence. Fill `<qualified round>` with the exact retained copy for the latest installed build; repeat `--keep-qualified` for other required copies. Review each item's `build_bytes`, `git_redundant_source_bytes`, `qualification_bytes`, `kept_bytes` and reasons. Then use the same command with `--apply` in place of `--preview` within the authorized cleanup scope. Apply freshly inspects the folders and moves eligible paths to the macOS Trash. Wholly eligible trees (including empty subfolders) move as one folder; for session scratch and legacy markers, unique files, links, Git metadata and ownership markers prevent coalescing across them. With `/usr/bin/trash`, remaining paths share bounded Trash calls across up to 32 items (at most 256 paths and 64 KiB of path arguments per call). Systems without that tool retain the existing single-path compatibility route. Process inspection resolves distinct observed paths once and matches their ancestors to candidate roots. Each batch refreshes process use, inventories, workspace protections and the installed identity before moving, then verifies remaining bytes. Reports retain per-item byte/reason totals and one `trash_move` receipt per confirmed path. A partial failure keeps confirmed receipts, reports the affected items as `kept_error` and stops without retrying uncertain paths. Do not run apply when the task forbids it. A private worker restricted to its assigned folder hands its cleanup evidence and limitations to the orchestrator.

Default scope is the caller's own session, using `CODEX_THREAD_ID` or `CLAUDE_SESSION_ID`, then `CHECKLIST_SESSION_ID`; if none is exported, supply `--session-id` with the caller's actual session ID. An exported host identity cannot be overridden with `--session-id`. Never name another session to widen cleanup. The tool inspects only that session's scratchpad entries below Checklist hosts or spare-process hosts (spare items also need a retained Checklist package). Another session's unmarked or unreleased items are never candidates, even if idle. An authorized orchestrator may add `--include-released` to inspect foreign items whose **root** marker records their owning scratch session's release; a nested release cannot release its enclosing folder. Qualification runs in `~/Library/Caches/ChecklistQualification/*` need a root marker establishing the caller as owner, or an explicit owning-session release with `--include-released`; unknown unmarked runs are report-only after seven days. Mark qualification runs when created as described below. A delegated worker's assigned slot can live under its orchestrator's scratch session. In that layout the owning orchestrator marks it before assignment and releases it when retired; the worker verifies the unreleased marker and never overrides its native identity to act as that owner. The worker hands cleanup outside its own session to the orchestrator. This marker is local filesystem coordination, not service authentication or a work claim.

Qualification runs need the exact round identity before any store copy, project creation or measurement. For a manual run, create `~/Library/Caches/ChecklistQualification/<run>` and immediately run `python3 <project folder>/script/clean_scratch.py --mark <run> --purpose "disposable qualification run" --source-fingerprint <64-character source_fingerprint> --session-id <own session ID>`. Use the captured build's `source_fingerprint`, never a round label, short commit or build ordinal. This adds `source_fingerprint` to the root marker. Mark the enclosing run, not only a nested project or report folder. Keep required evidence outside the disposable run before its owning session releases it. The latest installed fingerprint, nested unreleased workspaces, explicit keeps, process use and the quiet period still retain the run. A released obsolete fingerprinted run can move as one whole folder to the Trash, including copied databases and managed files; `qualification_bytes` reports those bytes separately. Legacy markers without a fingerprint retain the existing build/Git-byte-only behavior. Unmarked runs whose entries have not changed for seven days appear as `unmarked_qualification` with `total_bytes` and age; preview and apply both retain them. Do not infer their owner, mark/release them on another session's behalf or delete them by age.

`test_instances.py create` writes the owning-session/fingerprint marker at the slot root before seeding or copying the app; slots still retire only through the slot harness or `clean_builds.py`, not qualification scratch cleanup. `measure_build_times.py` marks its output root before saving originals or running builds and requires `--source-fingerprint`; a separate enclosing qualification run or warmed checkout still needs its own creation-time marker. Both scripts require the actual exported native session, `CHECKLIST_SESSION_ID`, or `--session-id` when none is exported; missing or invalid identity refuses before creation/replacement, locks or copies. They keep failed/incomplete runs protected for inspection. Headless `test_instances.py start --slot N --headless` takes no `--session-id` and retains the creation marker. Creating synthetic project workspaces manually still requires the enclosing-run marker before the slot CLI's `project_create`.

Process-used or recently changed items stay (45 minutes, including preserved-mtime copies with new ctimes), as do links, protected workspaces and matching installed-round captures. For session scratch and legacy qualification markers, files whose exact bytes are absent from the retained repository's reachable Git history remain, except rebuildable `.build`, `CompilationCache[.noindex]` and `module-cache` contents. Git metadata stays; preserve qualification reports externally before releasing a disposable run. Missing installed identity or failed process inspection refuses uncertain cleanup. Keep explicitly named qualified copies when their layout has no build fingerprint. Checkout folders `.local/build`, `.local/evidence` and test slots are cleaned by CL-194's command, not by `clean_scratch.py`. Record skips once and revisit at the next ordinary boundary; do not wait or start a cleanup polling loop. Keep every assigned persistent `.build` warm across tasks.

Before any SwiftPM build/test in these briefs, set `export CHECKLIST_SWIFTPM_CACHE_PATH="$HOME/Library/Caches/ChecklistSwiftPM"` and pass `--cache-path "$CHECKLIST_SWIFTPM_CACHE_PATH" --enable-dependency-cache` alongside the fixed `--scratch-path <scratch folder>/.build`. This shares downloaded dependency repositories, not writable build slots. `swift package --help` on the current toolchain advertises both options. Keep this shared dependency cache outside scratch retirement.

Set `export CHECKLIST_COMPILATION_CACHE_MAX_BYTES=10737418240` (10 GiB allocated) as the round's CompilationCache budget. At each step boundary, record `du -sk "$HOME/Library/Developer/Xcode/DerivedData/CompilationCache.noindex"` when present and compare KiB × 1024 to `$CHECKLIST_COMPILATION_CACHE_MAX_BYTES`; include any per-run CompilationCache folders in that budget. If over budget, pause further cache-producing qualification work until the orchestrator reconciles idle disposable runs. The variable is a workflow budget, not a claimed compiler environment switch or automatic eviction mechanism. Do not alter global Xcode settings or remove a shared active compiler cache through this script. Any separately authorized global cache pruning uses the toolchain's supported cache operation while users are idle. Record before/after allocated bytes, build time and dependency-fetch reuse in a later measured round; this setting alone proves no speed or disk-saving result.

### Limitation

The MCP route for `codex exec` stays unavailable while Codex does not pass the thread identity to MCP servers. Do not set `CODEX_THREAD_ID` or another identity variable by hand: Checklist must observe the actual host, and a supplied value is not evidence.

## Other hosts

Before a host (for example T3 Code) gets a section here, observe and record:

- How the host gives its session identity to MCP servers and to shell commands, and whether the Checklist bootstrap finds the host process.
- Which sandbox or permission mode lets `checklist call` or `checklist mcp` reach the service, and what else that mode allows.
- That `service_info` returns the host's own session, separate from the orchestrator, in the expected project.
- How a finished session continues: whether a continued session keeps its Checklist binding or is refused as a new process, and whether a queued note can wake it.

Until then, report the host as unsupported for this route. Do not fake identity variables or reuse another session's identity.
