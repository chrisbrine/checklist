# Ticket attachments and archive cleanup

Owner requirements added **16 October 2026**: both agents and the owner can attach images/files to tickets; archiving cleans up large material.

## Attachment behavior

A task has an Attachments section with Add Files, drag-and-drop, paste image, and Finder selection. Images have inline thumbnails and a larger preview; other files show type/name/size and native preview/open/reveal actions where supported. Attachments can be referenced in a note, acceptance evidence, or a human request response without duplicating the bytes. Agents can attach generated images, build logs, reports and other outputs through MCP.

Distinguish **managed copy** (Checklist owns its stored bytes) from **external reference** (approved original path/bookmark). Default ordinary ticket uploads/pasted images to managed copies. Finder references requested as references stay references. Show the distinction clearly. Neither removing an attachment nor archive cleanup deletes an external original.

An owner answering a file request can explicitly choose managed copies. The trusted `human_request_answer` prepares each selected file through the existing managed importer before the answer's writer transaction, with a deterministic child command identity per selection and a reservation of the enclosing answer's original intent. Reads, hashes, previews and staging stay outside the writer; the transaction checks prepared identities and atomically commits all attachments, SHA-256 artifact references in the response, exact import receipts, any gate verdict and the continuation message. A missing, changed or refused selection rejects the whole answer and removes only its own recorded stages; finalized uncommitted bytes remain attributed to their existing recovery jobs. A same-command retry reuses those verified bytes or the committed answer receipt, including after the original disappears. Incomplete answers import nothing, and reference selections retain their existing reference behavior. Owner provenance and current gate-direction checks still precede import.

Each attachment records UUID, project/task links, uploader origin, file name, content type, byte length, checksum, source reference if any, preview metadata, created time, retention mode, and availability. Managed originals have immutable checksums and distinct attachment/task attribution. Current local imports use command-bound object identities; separate links never grant authority to remove another original. Inline rendering never executes scripts/macros/HTML; uncertain formats use a download/open action rather than active content.

For this single-Mac release, agents attach **authorized local sources**: project-root files, explicitly approved output roots, owner-granted files, or verified local session artifact handles. Enrollment can authorize the provider's generated-artifact directory for this purpose, rather than requiring a Finder prompt for each generated image. It does not grant general arbitrary filesystem reads. Remote/streaming/chunk upload and resumable upload handles are deferred until a real client requires them.

The service opens the authorized source safely, imports to app-managed staging, checks byte limit/type and hashes the copied bytes, then atomically creates the immutable attachment and task link. Reject sources that escape the enrolled root through aliases/symlinks, change during capture or fail validation; preserve the original and return a useful error. Failed import staging is reclaimed separately. Do not put large base64 content in notes/tool arguments. Availability is recorded only after commit; a cancelled import does not leave a falsely available attachment.

## Attached test results

Review details can read an explicitly selected managed `.xml`, `.trx`, `.txt`, `.log` or `.out` result attachment. It supports NUnit test-case XML, dotnet TRX and complete plain Swift XCTest output from `swift test`; it requires the enclosing All tests or Selected tests suite start/completion and its final Executed summary, so an inner-suite summary cannot qualify a truncated log. It does not open or execute an xcresult bundle. The service authorizes the exact original and supplies a reader hold; the app rechecks identity and SHA-256 before parsing. Cleaned, missing, changed, external-reference or oversized originals stay unavailable here. Report-contained file paths, links and commands are never followed or executed.

Counts describe parsed leaf test cases: total, passed, failed, skipped and other outcomes, with failing names. Suite aggregates are not counted again. Declared-counter disagreements and unclassified outcomes are visible; counts never create a Checklist verdict or prove that a check ran. Test names render as plain text. Read also compares the unambiguous same-name result from the immediately previous target when formats match, showing signed changes and both reports' warnings. Missing or ambiguous previous results remain explicit. Unsubmitted attachments are labeled separately from target-bound evidence; reviewer evidence retains its service-recorded uploader, target and review attempt before a verdict references it. It stays with that target and compares only to that target’s preceding round, never to a later current target. Incomplete or conflicting reviewer bindings are not treated as new unsubmitted uploads.

Reading is off the main thread and canceled when the result view leaves or identity changes. Limits are 4 MiB of UTF-8 bytes, 20,000 cases, 64 XML levels, 100,000 XML elements and a 250 ms cooperative parsing budget. Names are bounded to 512 characters and 2,048 UTF-8 bytes; XML DTD/entity declarations are rejected. The view shows at most 20 result attachments and the first 100 failing names with an explicit remainder. Larger results can be split into complete files and inspected as their own evidence; a preview never substitutes for the original. No parser or display action changes a gate, status, claim or approval.

### Measured budgets and playtest bundles

Submission evidence and reviewer-authored reports can carry `measures:[{name,unit,limit,before,after}]`. Names are unique within the bounded list and units are explicit; values are finite numbers, with unsafe integer rounding rejected. Submission digests and reviewer report bytes/hash cover the measurements. The ticket warns when an after value exceeds its upper limit; equality is within budget. This is advisory and does not create a finding or verdict. The review detail compares exact name/unit series from the previous loaded submission or same-gate review attempt, also matching reviewer report title, and labels missing/ambiguous history or changed limits. Previous source, target, author and hash remain inspectable.

A Playtest's optional immutable bundle references a managed exact build artifact (`artifact_id`, `sha256`, `build_id`, `version`, `platform`) plus hashed scenario, state files, screenshots and log. These are ordinary managed attachments in the submission's existing `artifact_refs`; the service mints the bundle identity/digest. New build identities need newly attached run files; earlier state/screenshot/log IDs cannot be relabeled onto the new build. Bundle presence is an attributed run report, not proof that Checklist executed a game. Agent pass/reject verdicts use the existing `review_assessment` with one pass/fail per captured acceptance item. The bundle view shows role files and their availability/hashes, the exact build, and recorded item results using the verdict's historical acceptance wording.

With `review_record.retain_cited_files:true`, only bundle files cited by the validated assessment/checks receive the ordinary Keep original flag; the verdict records `retained_artifact_refs`. Existing holds are never cleared. Normal cleanup preview/settings/jobs govern uncited files, so small files can remain under the project budget. Cleanup retains metadata, hashes and verdicts while marking removed originals unavailable for reinspection. No alternate storage or cleanup system is introduced.


## Image and build approval

The task overlay can preview an image and show its short candidate label with **Approve / Needs changes** and an optional note. A human approval request binds to the exact `review_request_id`, manifest and immutable attachment ID/checksum, or build/artifact ID with fingerprint/version/platform. Human approval shares the task's single verification slot: an agent reviewer must block/release before the native human attempt can claim it. **Not checked** leaves approval pending. Approval references those exact bytes/build, never a path named `latest` or whichever attachment was added most recently. A new candidate uses a revised request/target; keep the previous candidate and answer in history. A preserved preview is sufficient to understand what was discussed, but cannot stand in for a missing original when verification requires it.

Build references can point to an authorized local artifact/build receipt; duplicating a large build into the ticket is optional. Show whether it is a managed copy, external reference or cleaned original, and whether the exact build is still available. This is a small task-review feature, not an asset/version-management product.

## Archive policy

The default **Clean large managed files on archive** storage preset makes an original at **20 MiB or larger** eligible for pruning and gives an archived ticket's retained unpinned originals a **50 MiB total budget**. These are design defaults, not owner-specified thresholds. A simple Keep originals preset is also available. The owner’s **Archive storage** project settings change the threshold and total budget with exact whole-byte values and guarded project/settings revisions; the owner need not configure them at setup. Individual attachments can be marked **Keep original**.

The triggers are independent: aggregate overflow makes smaller unpinned originals eligible, pruned largest-first until under budget or only protected content remains. Six 10 MiB files therefore permit pruning one or more, even though none reaches the individual threshold. Holds can make the budget temporarily unattainable, which is reported with retained bytes/reasons.

**Archive and clean large managed files** atomically records the cleanup plan and queues one durable local storage job. Show a compact summary of retained/eligible files with Keep original; do not require a new confirmation form for every routine archive. A 30-second cancellation window precedes deletion. Cancel remaining cleanup or Undo archive preserves originals not already removed; it cannot undo an earlier unlink. It does not run a model. Preserve metadata, checksums, original attribution, small image previews where practical, and a cleanup event. Mark removed originals **Original cleaned on archive**, never as a mysteriously broken upload. Removing full bytes does not remove evidence records or their fingerprints, but the app must state that the original is no longer available for reinspection.

Reject archive/trash while an active implementation, review or verification claim remains; resolve the attempt through release/checkpoint or verified recovery first. Saved UI drafts do not count as claims. Active-reader/download holds, Keep original, shared attachments on other live tickets, and backup retention remain additional protection against physical deletion. Show selected logical bytes, active-store original bytes actually removed, originals already absent, and why an original remains. Do not call those lengths physical disk savings. Do not silently break another task's evidence to meet this task's storage budget.

The cleanup worker deletes only unreferenced app-managed blobs or staging files, never source project files/Finder targets. Reference removal and garbage collection are crash-safe: tombstone/mark in a transaction, delete content through a guarded app-storage helper, then record outcome; retries are idempotent. Suspend after two identical failures and expose explicit project-authorized retry with a new cancellation window. One bounded service pump checks at most eight items and unlinks at most one managed original, with a durable cursor and intent; restart reconciles an already absent original without inventing a fresh removal. User-created exports and prior backups are separate copies; cleanup never edits them. Verified backup receipts report known-at-backup logical retained originals, with current external presence and physical allocation explicitly unverified. Automatic-backup retention/purge remains separate future work.

Unarchiving restores the ticket/history, not pruned bytes. Offer reattach/recover from an existing source/backup after verifying the checksum, or keep the preview/metadata. A missing original is explicit in export and review context. New reviews that need the original are blocked until it is available or a permitted limitation is recorded. Export distinguishes available copies, references, cleaned originals and retained previews.

## MCP additions

The installed catalog is authoritative for caller-visible tools. Implemented local methods include `attachment_add`, which imports a permitted local source/artifact, records agent attribution, hash and task link. `attachment_list` returns metadata/availability and bounded previews. `attachment_update` changes description, removes/restores a task link, or changes retention within the caller's authority; bytes are immutable and an enrolled worker may release the Keep original flag while `agent_rule_changes=allowed`, with agent provenance; this never releases other reader, backup or reference holds. `attachment_read` returns a bounded authorized preview or local access handle for the exact attachment, with size limits and no general path read. `attachment_cleanup_preview` explains archive policy, holds and expected reclaimed space. Native owner actions grant external sources or adjust retention. Project-authorized `archive_storage_settings` saves canonical thresholds/budget; `cleanup_job_list` and `cleanup_job_get` read durable observations, and `cleanup_job_cancel`/`cleanup_job_retry` guard current job revisions. See [the implemented cleanup lifecycle](archive-cleanup.md) for final hold/reference revalidation, descriptor-safe deletion, restart receipts and honest physical accounting.

Release checks include both human/agent local image and file imports, changing/interrupted source capture, hash/type mismatch, exact image/build target approval, changed target with saved answer draft, shared blob references, active-reader hold, large-file and aggregate-budget cleanup, Undo before/after deletion, failed cleanup retry, cleaned-original task restore, and proof that no external original is changed.

Project icons use separate project-settings asset references, not ticket links. Their bounded normalized thumbnail remains held while selected by project settings; archiving a ticket cannot clean the current icon. The [customization](project-customization.md) and [storage](database-storage.md) contracts define replacement, Undo/backup holds and export.

## Internal media ownership foundation (20 October 2026)

CL-110 extends the existing importer and hold graph with internal typed owners for media intake, Draft items and immutable targets. These methods are absent from public dispatch/catalogs; ordinary `attachment_add/list/read/update` remain task-compatible and expose no taskless creation or publication route. A taskless attachment ID alone is refused by the task read/update handlers. See [pure intake/list values](media-intake.md) for CL-109.

A canonical project-owned `storage_job` with `kind=media_attachment_owner`, stable ID, owner kind, revision and active/Draft/published state anchors each owner. Canonical project-scoped `storage_hold` records with `kind=media_reference` bind that exact owner ID/kind to an immutable attachment ID, SHA-256 and size. They have no expiry. A type label, path, digest or foreign/released/stale anchor is insufficient. Internal reads resolve both current anchor and active reference in the caller's project and validate the current worker session/workspace; original access acquires a separate bounded reader lease. Reader holds retain their own lifetime even after an owning reference is released. Only the lease's actual caller can release it; new leases carry store incarnation and session generation.

Task adoption hashes originals before entering the object gate/writer and rechecks their exact file observation inside it. The independent media references are committed before matching source reader holds are released. Intake capture reuses the existing command-owned staging/finalization pipeline, with an owner field instead of a synthetic task. Publication/Draft handover creates destination references, invokes the canonical manifest write, releases source references and changes a target anchor to published in one transaction under the same `ArchiveStorageGate` as final deletion. A published target's reference set is immutable through this API. Manifest or later receipt failure rolls back the entire handover. Cleanup winning first refuses absent/changed originals; publication winning first retains them despite source-task archive or unlink. The cleanup graph treats an active media reference as an independent shared-live hold.

Cancellation first commits a durable fence under the object gate, then removes only that command's recorded staging entries and UUID partial files in its private staging directory using no-follow helpers. Partial creation, stage rename and final link recheck the current job under that same gate; progress writes also reject the fence. An in-flight copy can finish writing its already-open, unlinked inode outside the writer, but cannot recreate staging, publish final bytes or record finalization. Cleanup failure leaves the fence and pending cleanup durable; retry or startup completes only that job's staging cleanup. Copies published before cancellation remain retained for recovery. The saved cancellation receipt separates observed reclaimed staging logical bytes (including partials), retained final logical bytes, unavailable recorded staging entries and unavailable final entries; a successful retry returns that same receipt. Absent entries are unavailable rather than newly reclaimed, and physical reclamation is unmeasured. No selected external source is removed. CL-111 now registers media history and ownership in export/backup; owner context validation and public media writers remain later work. This internal foundation does not activate them.


## Media history export and backup (CL-111)

Taskless managed originals now use the same protected capture as task attachments. Export preserves media owner anchors and active/released exact references, all registered Draft/Open/Closed media history and referenced type/context/target revisions. It creates scoped reader holds before byte capture, copies outside the writer transaction and releases those holds after completion or failure. Backup derives the inventory from its consistent copied database while the root deletion gate remains held. Missing available bytes or unknown required records refuse capture; cleaned originals remain explicit metadata, and external references do not become managed copies.

A partial intake exports only committed attachments/ownership, together with its exact row plan, committed receipts and unresolved remainder. Its summary explicitly excludes staging. Backup can retain finalized uncommitted bytes solely as labeled recovery objects, without claiming they are captured Drafts. No media read/write command or UI is enabled. See [the capture registry and dependency contract](database-storage.md#media-history-capture-registry-cl-111) for registered families, version preservation and limits. Restore and installed compatibility qualification remain separate work.

## Shared native file previews (CL-121)

`FilePreviews.swift` separates portable format detection (`FilePreviewKind`), capability limits, declarative `FilePreviewPresentation` and Markdown resource policy from macOS adapters in `ChecklistApp/Previews`. Attachment rows, submitted artifacts and exact-target request attachments use the same `FilePreviewSheet`. New formats add a detection/capability case and a native adapter; ticket and verdict logic do not select decoders or follow paths. Optional `preview_presentation` values (`scale: fit|actual_pixels`, `nearest_neighbor`, `accessible_label`) choose presentation only. They cannot choose a file, override its type or grant access. The existing `MediaReviewSchema.filePreviewPresentation` slot adapter maps image/video/audio/text slots onto the same presentation values and accessible slot labels. Existing media type primary/reference layout and material signatures remain unchanged; activation of internal taskless media commands is separate work.

Markdown renders headings, paragraphs, ordered/unordered lists, quotes, bounded tables, fenced code and inline emphasis/code/links. Markdown images in prose resolve only by an unambiguous, exact attached filename on the same project and ticket. The preview reads ticket attachment metadata independently of the current submission’s artifact refs, with a 1,000-attachment client limit. Failed, incomplete or over-limit metadata reads leave resources unavailable; a partial set cannot hide a duplicate name. They use the attachment service and bounded native image renderer. Inline/unsupported constructs remain readable source; Supported-size documents retain a Source switch; oversized documents retain Open in…. HTML stays literal; no browser, script, macro or executable renderer is used. Remote images, data/file/custom URL schemes, absolute paths and parent traversal are refused. A relative path is not a directory grant: only explicitly supplied attachments can resolve. A web link opens only after a click, through macOS, and never as an implicit document fetch. Missing/ambiguous resources show a reason. UTF-8 text/source is selectable monospaced text; invalid UTF-8 and binary content have an external-open fallback. Text is limited to 2 MiB; Markdown to 4,096 blocks, 200 table rows and 20 columns. Native inline parsing is bounded per block. Images in the first 100 document blocks can load inline when at most 25 MiB; larger/later attached images offer an explicit preview action.

Raster images use Image I/O with a 2,048-pixel fit preview and an explicit original decode for Actual pixels (80 million pixels maximum), optional nearest-neighbor interpolation and checkerboard transparency. Native video/audio share default AVURLAsset loading and a concrete AVPlayerView adapter with explicit Play, pause, seeking and volume; codec availability is checked rather than inferred from an extension. Forced approximate timing is avoided because it rejects otherwise playable PCM WAV assets. PDFKit provides scrolling and zoom for PDFs up to 50 MiB and 2,000 pages; annotation actions (URL, JavaScript, launch) are disabled. Encrypted/unreadable PDFs and unsupported codecs say so and offer Open in…. SVG/HTML/XML are source text. Unknown types keep their name, size, availability and external-open action. Unavailable previews use static content inside a concrete accessibility container: the title, reason and descendant control labels remain readable without rewriting the conditional content’s accessibility preferences. Other-platform renderers remain future capability work.

Every original is authorized again through `attachment_read`. Known cleaned/unavailable metadata refuses preparation immediately; a fresh service refusal preserves its reason text. The app matches an available attachment's project/ticket/hash/size/mode and managed reader hold, then copies and streams SHA-256 verification off the main thread through a no-follow regular-file descriptor. It releases the bounded service hold after copying stops, including cancellation or failure. Decoders use only the completed verified copy. Cleaned/missing/changed originals show a static unavailable title and reason inside an explicit accessibility container, even when a thumbnail remains. Neither Preview nor Open in… enters a decoder, application chooser or inspection action for them.

Preparation shows copied/total bytes and an accessible exact byte count during the verified copy. **Cancel preview** or Escape while preparing stops cooperative copying and keeps the sheet open with **Preview canceled** and the final copied/total counts; this outcome appears after the copy has stopped and its temporary file has been discarded. Canceling before copying starts says so. A completed copy is not evidence of cancellation during active work. Close still dismisses and cancels preparation; after preparation or cancellation, Escape closes the sheet. Leaving the preview discards late results and removes the preview copy. Image I/O/PDF native decode itself may finish an in-flight bounded call after cancellation; its result is discarded. No preview limit is relaxed or artificial work delay added.

**Open in…** discovers actual compatible installed applications with `NSWorkspace` for the authorized copy's type; the default is labeled and included when present. The owner explicitly chooses an application and presses Open working copy. No handler is an honest empty result; closing/canceling launches nothing. The service reauthorizes the original before export. External apps receive a separate writable cache copy with a source-attribution sidecar (attachment, project, ticket, origin, author and source SHA-256). That copy persists for the external editor and is never imported back automatically. It is not new target evidence: edits cannot replace managed bytes, mark an image inspected or grant any approval. macOS accepting the open request is reported separately from any application outcome. Installed chooser, cancellation and codec/UI responsiveness checks remain required; component tests do not establish those native observations.

Large image inspection and exact inspected-image verdict references are described in [image review](image-review.md).
