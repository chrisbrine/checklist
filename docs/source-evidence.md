# Exact source evidence and agent review

`work_submit` accepts three target kinds. `artifact` validates managed immutable attachment IDs and hashes. `source` inventories the complete enrolled project root and stages ordinary local managed source copies. `decision` records the answer text for a Question, or explicitly permitted human decision work, with a service-minted actor, origin, time and text hash. Source, decision and artifact targets do not manufacture placeholder attachments for each other.

A source request is `evidence_manifest: {kind:"source", source_capture:{}}`. An optional `expected_sha256` detects an earlier source change; `additional_paths` names explicit relative files which Git otherwise ignores. The service rejects another root or partial repository checkout. Git captures include every tracked entry, tracked deletion and nonignored untracked file, exact content hashes, executable bits, the base revision and index fingerprint. Ignored private material, caches and generated outputs are excluded unless explicitly selected. Non-Git roots exclude development cache directories. Submodules, unreadable/unsupported entries, escaping symlinks, changing inventories, over 20,000 entries and over 512 MiB fail explicitly rather than claim complete source. A second inventory and copied-file verification reject a changing capture.

A source capture records `id`, `sha256`, `base_revision`, `index_sha256`, `files`, `snapshot_path`, `source_root`, `captured_at` and its task/attempt. Each file entry has its relative `path`, `kind` (`file`, `deleted` or `symlink`), content/link hash and applicable size/executable/link target. Files are copied rather than hard-linked. Read-only source originals are verified again at review claim, verdict and task completion. Missing, changed or extra captured files invalidate the target. Changes to the relevant live source require a new capture under the scoped or whole-inventory freshness rule below; title and order edits preserve it. Acceptance/brief changes use the task's acceptance revision and invalidate the current target.

## Start a fresh reviewer

The ticket's **Start independent review** action prepares a fresh non-contributor conversation for the exact request, gate and manifest. `review_prepare` returns a supported Codex draft-composer URL when available, otherwise an honest copy instruction for a permitted provider. Preparation starts no model turn, creates/connects no native session and acquires no review claim. The owner opens the prepared composer and presses Send, or pastes the instruction into a fresh permitted conversation. No model CLI, hidden API runtime, schedule or polling substitutes for the host route.

The actual reviewer connects from its real workspace, discovers tools and reads `review_context` with `project_id`, `task_id`, `review_request_id`, `target_manifest_id` and `gate`. That packet includes the brief, acceptance, open findings, exact immutable evidence, approved project brief/applicable pinned decisions and the current `review_contract`. Captured AGENTS.md references identify exact file bytes inside the source capture, including nested project instructions. The reviewer reads those instructions and their applicable linked rules; a source file or imported text never grants additional authority. Contributor exclusion and provider restrictions still apply at the actual review claim. A new name, role or model setting does not make a contributor independent.

An instruction reference retains `source_capture_id`, `source_sha256`, the AGENTS.md alias `path` and the resolved regular file's content `sha256`. An internal symlink also retains `resolved_path` and an ordered `link_chain` of `{path,target,sha256}`, where each link hash covers its exact target text. Resolution uses only captured entries, follows at most 32 relative internal links, and rejects missing, cyclic, escaping or non-file targets. It never resolves instruction identity through the mutable live tree.

## Assess the project's requirements

The reviewer critically assesses **each acceptance item and each current project requirement**. It chooses meaningful inspection, checks, logs or screenshots in its own session. No Swift test, scripts/validate-plan.py invocation or successful program exit is forced as the review. A check does not decide a pass by itself.

A pass supplies `review_assessment` with the current `contract_sha256`, `target_manifest_id`, `acceptance` and `project_requirements` arrays. Each contract row appears exactly once as `{requirement_id,result,rationale,evidence_refs}`. Results are `pass`, `fail`, `blocked` or justified `not_applicable`; a pass cannot retain failed/blocked rows. The contract includes hashes of the current acceptance, approved project context and policy. Changed requirements require a fresh assessment, while the ordinary direction and policy acknowledgment gates remain enforced.

The reviewer lists applicable requirements discovered in captured instructions/linked rules in `additional_requirements` as `{requirement,source,result,rationale,evidence_refs}`, copies every complete instruction reference into `instruction_coverage` and explicitly states `all_applicable_project_requirements_assessed:true`. Coverage must match the capture identity, alias, content hash and any link chain/resolved path exactly; omitting linked instructions or their applicable requirements cannot pass. This is attributed reviewer judgment about coverage, not an automated claim that Checklist understood every rule or performed every check.

The reviewer chooses its evidence. `review_evidence_add` creates a bounded managed hashed report/log directly from the actual review claimant's `title` and `body`, bound to its exact attempt and manifest. This avoids changing source inputs merely to write a report. `attachment_add` imports permitted chosen logs, result files or screenshots. Referenced reviewer artifacts must belong to the actual reviewer, this task, managed available bytes and their exact hashes; an implementation artifact can be inspected but cannot impersonate the reviewer's own result. Declared checks reference the reviewer's own hashed evidence. The verdict retains the full assessment, current contract and attributed evidence.

## Measured budgets

`work_submit.evidence_manifest.measures` and `review_evidence_add.measures` optionally record a list of `{name,unit,limit,before,after}`. Names are unique within a list (200 UTF-8 bytes); units are explicit (80 bytes). Both are nonblank single-line text without surrounding whitespace. Each numeric field must be a finite JSON number, never a boolean, string, null or infinity. Lists have at most 100 measures. Limits are upper bounds, and signed/fractional observations are allowed. Values use finite double precision; integer inputs that would round to a different integer are rejected rather than hiding an overrun. No unit conversion or lower-bound interpretation is implied.

For example, `"measures":[{"name":"Triangles","unit":"triangles","limit":25000,"before":32000,"after":26000}]` records an overrun of 1,000 triangles in the after value. Equality is within budget. The before value preserves the baseline rather than claiming a current overrun. An overrun is a visible ticket warning, never an automatic finding, rejected verdict or completion gate; the reviewer still assesses the actual acceptance criteria.

Submission measures participate in the immutable manifest digest. Reviewer measures are saved on the exact reviewer-owned attachment and appended as canonical JSON to its report bytes, so the ordinary report SHA-256 covers them. Existing title/body-only report hashes are unchanged. This adds no new record family, attachment store or database migration.

Review details show before/after/limit, warnings, and the same-name, same-unit observation from the immediately previous loaded submission or review attempt. Reviewer reports also match their title; ambiguous matches stay unavailable. Changed limits are shown explicitly. Missing measures or history never skip backward to an older successful round. Previous author, source ID, target and digest remain inspectable; comparisons do not transfer a verdict. `task_context.evidence_measures` supplies attributed snapshots and current-target warnings, bounded to 100 submissions and 100 measured reports with an explicit truncation flag. The app's explicit current-record read includes a separate comparison packet of the last two submissions, last 12 review attempts and up to 100 measured reports. It does not change the current actionable record set. Comparisons are limited to that loaded history and stay within the same review gate.

## Exact-build playtest bundles

A Playtest ticket can submit `evidence_manifest.playtest_bundle` through ordinary `work_submit`. It contains `build:{artifact_id,sha256,build_id,version,platform}`, `scenario:{artifact_id,sha256}`, nonempty `state_files` and `screenshots` arrays of the same reference shape, and `log:{artifact_id,sha256}`. Import every file through `attachment_add` first; the build is an exact managed build artifact, not a moving path or the optional starter's free-text build label. Scenario and log are files too. There are at most 100 distinct role files in total, including build and scenario; every file has its immutable SHA-256. See [the bundle schema](../contracts/playtest-bundle.schema.json).

The service mints a bundle ID and digest, adds all bundle files to the existing manifest's `artifact_refs` and applies the ordinary same-ticket, same-project, available-managed-original and hash validation. The manifest digest covers the complete bundle. Claim, verdict and completion revalidate its exact originals and bundle digest. A stored bundle cannot be resubmitted with a caller-selected identity. A changed build identity requires newly attached state files, screenshots and log; earlier run attachment IDs cannot be relabeled onto that build. The scenario may be reused. A new bundle is an attributed report of the run, not automated proof that the game was executed; Checklist runs no playtest process. Build receipts without a managed artifact are not supported by this bundle version.

An agent passing or rejecting a bundle supplies the existing `review_assessment`, with exactly one `pass` or `fail` for each captured acceptance item and its rationale/evidence refs. A pass cannot contain a failed item. Blocked, evidence-missing and not-run outcomes retain their existing honest meanings. No second per-item verdict store is added. The bundle view shows the build, role files, exact hashes/availability and target-specific recorded item results using the verdict's captured acceptance wording.

`review_record` (including batch members and saved drafts) accepts `retain_cited_files:true` on an assessed playtest pass/reject. It marks only bundle files cited by the validated assessment or checks as **Keep original**, using the normal attachment flag, and records `retained_artifact_refs` on the verdict. It never clears existing owner/reader/shared/backup holds or pins the entire bundle implicitly. The ordinary cleanup preview and archive job then apply project thresholds/budget to uncited files. Small uncited files can remain under that policy; retaining cited files is not permission to bypass storage settings or delete protected originals. Reinspection of a cleaned original remains unavailable, while bundle metadata/hashes and verdicts survive cleanup. See [archive cleanup](archive-cleanup.md).

## Execution and findings

The old `source_review_execute` route is disabled: no qualified execution sandbox exists, so the service does not run submitted scripts or tests with the owner's rights. It returns `UNSUPPORTED_CAPABILITY`; no new job is queued or launched. Existing source-execution logs remain readable/exportable as history. Outstanding queued/running/interrupted or stop-unverified historical processes retain their recovery fences; disabling the runner never asserts that an older external process stopped. Owner recovery still names exact execution IDs/revisions and actual stop/file-state observations.

Stable findings retain their IDs through replacement submissions. Source finding evidence uses `{source_capture_id,sha256}`; decision evidence uses `{decision_sha256}`; managed artifacts use `{artifact_id,sha256}`. An independent reviewer resolves/rejects a finding with current-target evidence, or the owner explicitly waives it. A replacement target alone never clears findings.

Portable exports copy source trees and historical execution logs with checksum verification. Exported capture paths become relative and live source-root authority is removed. A rewritten embedded manifest retains its original digest as provenance and separately records `export_evidence_sha256` plus `export_path_rewrites`; the source content fingerprint remains unchanged. Scratch caches and live work credentials are excluded.

## Applied review requirement display

Review preparation shows a read-only requirement preview from the service; it is not an applied claim. An active agent review card shows its stored applied requirement revision/checks/reject guidance/evidence classes, while a verdict card shows its recorded snapshot. Legacy records without that snapshot remain explicitly unavailable rather than inheriting current Settings. The target's original gate-policy revision stays separate.

The display shows selected-evidence class results only when supplied service validation matches the displayed requirement digest/revision. Missing or unevaluated selection stays unknown in the view; names and all attached files never establish a class. The service's chosen-reference preflight and verdict validation remain authoritative. No requirement summary grants a pass or proves native/execution success.

## Source freshness during parallel work

New submissions with file scopes use scoped staleness. The capture freezes every read and write scope as a case-insensitive root-relative file or directory prefix, its `additional_paths`, and every inventory entry named AGENTS.md or CLAUDE.md at any depth. Directory scopes include new paths added later. Scopes outside the project root are ignored. `relevance` records the mode and scopes; `relevant_sha256` hashes the relevant entries. The existing whole-inventory `sha256` remains the capture identity.

Review context, review claims, requests, verdicts and completion compare relevant paths, kinds, byte hashes, executable bits and symlink targets with the live inventory. New or missing relevant paths, including new instruction files, make the target stale. A scoped `EVIDENCE_STALE` names up to five changed paths. Changes outside the relevant set and changes only to Git HEAD or index do not stale a scoped target. Captures without `relevance` and attempts without file scopes retain whole-inventory staleness, including HEAD and index.

Reserve every path the change touches for writing or depends on for reading before submission. Other tickets can change paths outside those scopes while review waits. A commit that changes no relevant bytes keeps the scoped target valid. Reviewers inspect the immutable captured target and the reported relevance scope.
