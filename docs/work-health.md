# Active work health

Work health is advisory state alongside workflow status. It never releases or steals a claim, changes status, removes Triage membership, declares a writer stopped, completes a ticket, accepts review, or acknowledges delivery. Existing takeover, handoff, release, verified-stop recovery and qualified native closure retain their ordinary authority checks.

Project Settings exposes **Check active work**, inactivity and response grace. Both intervals default to 20 minutes and accept whole minutes from 1 through 10080, including 15 minutes. `project_settings_save` and `project_edit` accept the complete `work_health_settings={enabled,inactivity_minutes,response_grace_minutes}` object with the normal project revision and agent rule-change permission. Pause suppresses checks and keeps historical requests. Resuming or changing intervals grants a fresh inactivity window or response grace on the next observation; saving unchanged settings does not postpone a deadline.

The installed local service checks bounded pages of at most ten candidate tickets, at 30-second observation intervals (consecutive full pages continue promptly). All Active-attention tickets qualify: a current implementation/review attempt, an Active status, or an active Triage. A missing ticket worker routes to its one actual active phase orchestrator; ambiguous/missing orchestrators remain visible and do not invent a worker claim. No session is enrolled, model started, assistant enabled or future server runtime introduced. Two consecutive maintenance failures stop the service health wake until service restart; the service logs the failure and retains durable requests/claims.

The progress clock uses the current attempt and its accepted child tree, including completed accepted child work. An unaccepted delegation offer is not progress. A changed nonempty checkpoint advances that clock; repeated identical checkpoints, ticket edits, reads, message acknowledgments and session heartbeat traffic do not. Orchestration progress likewise requires changed text. Liveness (`session_state`, `last_seen`) is shown separately. Resource waits, blocking owner requests, prerequisites and finite source jobs are reported as known waits/jobs; a wait or a running process cannot prove useful progress indefinitely. Existing legacy `checkpoint_health` remains a separate 30-minute checkpoint indicator; `work_health` is the configured supervision result.

After inactivity, one durable correlated request message captures exact target kind/identity, attempt or orchestration, phase, session authorization generation, task/acceptance/material revisions, last progress, request time and deadline. Queueing uses the existing exact-generation pickup delivery. `queued`, `acknowledged`, `saved_for_pickup` and a qualifying response are separate observations. Health messages have system provenance, never human direction provenance. Native wake for these system health requests is unavailable: the exact session must pick up through authenticated MCP, or its actual orchestrator must use a supported host operation. No queue receipt claims a new native turn. Existing native routes remain separately qualified; no hidden CLI/API runtime or model polling is added.

After grace, one no-response ticket note and attention flag appear. Repeated ticks/restarts preserve the request/deadline and do not repeat the note. Sleep runs the overdue transition once on wake. Backward wall-clock movement rebases the remaining window rather than generating a negative age or immediate timeout. One check remains outstanding until substantive current/accepted-child progress is observed or its exact recipient responds. A changed target gets its own independent health cycle; old requests stay in history for explicit reconciliation.

Use discovered `work_health_get(project_id,task_id)` to inspect state, target, next check, deadline, progress, liveness, waits, jobs and actual delivery receipts. Use `work_health_respond(project_id,task_id,request_id,expected_revision,progress,command_id)` to answer with current progress or an honest known wait; a normal `message_send` reply to the request also reconciles. Acknowledging the request alone does not answer it. The response rechecks the current task in the same transaction, exact recipient generation, owner/attempt/phase, acceptance and submission basis, store incarnation, ancestry and policy authority. A valid late response resumes supervision with the existing claim/assignment. A response confirms handling and grants one new inactivity window, but never advances the substantive progress clock; continued lack of progress remains an attention flag. If ownership, phase, material basis or authority changed, the result is `fresh_claim_or_handoff_required`; newer work is preserved and the responder must use normal fresh authority. No old claim/token is resurrected.

An outcome note records reconciliation once and queues the same note to relevant current Triage orchestrators other than the replying handler. Actual recipient delivery remains distinct from acknowledgment. Revoked/ended session generations cannot answer as their former authority. History and the native ticket work section show the same service state, including missing handlers; Overview quiet attention includes outstanding health attention for current workers. Assistant integration is cancelled; these worker checks do not reactivate it.

Storage uses existing canonical task, attempt, group, message and delivery families; no schema migration or new managed files are introduced. Candidate pages filter project/task scope in SQL; progress aggregates only the selected accepted tree, and reads never decode the project message/event corpus. These are local service component contracts. Installed MCP visibility, native UI and actual supported host pickup still require bounded synthetic-task observation on the staged installed target. By owner decision (22 October 2026, CL-129), sleep/wake overdue recovery and backward wall-clock recovery are qualified by the deterministic WorkHealth component tests `testWorkHealthInactivityGraceAckIsNotResponseAndNoAuthorityChange` and `testWorkHealthPauseResumeAndBackwardClockRebaseWithoutDuplicatePing`, respectively: installed observations would require Mac sleep or a system clock change that the owner declines and agents may not make. Component tests do not qualify a provider route.

Eligibility inspection shares the selected reader's exact attention predicate, including byte-exact Triage membership and current sibling/orchestrator attention. It does not construct attachment, tag or prerequisite display fields while holding the writer. The same bounded page, transaction, persisted deadlines and recipient-generation checks still control health mutations.

Health responses without an already selected projection compute only exact prerequisite blockers and attention, retaining the duplicate-reference guard. They do not count cleaned attachments or render tags/status-reason fields inside claim and verdict response transactions. The ten-ticket maintenance page yields between existing prompt continuations; each ticket's check, request and outcome still commit together under the same writer, scope and generation fences.

Candidate discovery materializes current, unarchived Triage member identities once within each page query. The same project/task visibility filters and attention checks still decide inspection; the ten-result rowid continuation, transactional health effects and recipient-generation fences are unchanged. This avoids repeating membership JSON expansion for each inactive task examined before the page is full.
