# Local attachment cleanup

Capture and note composers accept selected files, dropped local files/images and pasted clipboard images. The selection records a managed-copy or external-reference choice. Clipboard images use a bounded private PNG staging file and a managed copy. Selection drafts are specific to the window, project, task and store generation. A successful, matching attachment receipt clears only that selection; unknown outcomes retain its original command ID for reconciliation. A managed import keeps the source file. Directory recursion and remote/chunk uploads are not supported.

Project **Archive storage** settings contain the complete preset, large-original threshold and retained-ticket budget. Defaults are 20 MiB and 50 MiB; Keep originals disables selection. Threshold and aggregate budget are independent: smaller originals can be selected largest first until the budget is met. Settings edits check both the project and settings revisions and preserve unrelated workflow settings.

The archive preview records the exact task/settings revisions and selected immutable attachment IDs, hashes and logical lengths. It validates every retained envelope in the current SQL observation, preserving the original identity/revision tokens and ownership fields while SQLite checks the complete JSON and the adapter checks its complete UTF-8. One byte-exact pass collects references to stored record IDs and the ticket’s original paths, including foreign projects. It then decodes full payloads only for reachable records; task liveness and current review heads remain available for hold decisions. Unrelated captured-file lists, notes and evidence are not decoded or indexed in Swift. The resulting reverse index belongs only to this observation and is never reused across commands or deletion checks. Captured-file metadata still participates in the same reference checks, and preview sizes come from recorded immutable logical lengths without reading captured file bytes. Archiving and the durable cleanup job commit together. A 30-second cancellation window precedes execution. Cancel remaining cleanup and Undo archive preserve all originals not already removed. Unarchiving restores ticket/history state; it cannot recreate deleted bytes.

**Archive…** presents a sheet immediately and starts a retention preview only for that open sheet. Selecting a ticket makes no speculative retention read. While the preview is in flight or has failed, the sheet shows loading or retry information and disables archive actions; it never substitutes zero totals. A matching result fills the readable totals, holds and cleanup choice. The result is bound to the store, project, ticket and settings revisions. Any observed service change invalidates it, including cross-ticket or cross-project holds; an open sheet refreshes against the new observation. Closing and reopening starts a fresh read, and leaving the detail discards late replies. Confirmation retains the service's revision, preview and current-hold checks. This UI presentation changes no preview results and establishes no native latency guarantee under load.

The service runs a bounded synchronous maintenance pump after import reconciliation. Archive work admits at most eight job items and removes at most one original per pump. A separate utility maintenance continuation processes at most one purge or Done-evidence object per call. A durable cursor and exact deletion intent survive restart. The service arms a one-shot continuation for unfinished bounded work or a real grace/reader deadline. Permanent holds do not create an indefinite polling timer. Two matching failures suspend the item; an explicit owner retry starts a new cancellation window.

Execution obtains the store object gate before the SQL writer, rereads the complete persisted reference graph and current retention settings, commits a deletion intent, then checks current references again in the final writer transaction. Current work/verification, human inspection, review/build references, reader/backup leases, shared references, pending imports, Keep original and unknown or invalid metadata retain the original. The gate stays held through descriptor-relative no-follow hash/identity checks, unlink, directory flush and the recorded outcome. Archive jobs admit only exact managed originals below `objects/`; archive cleanup retains previews. Permanent ticket purge shares this permit and unlink through durable `ticket_object_delete` intents. It also admits exact previews, captured-source files, manifest sidecars and verified captured link text. Purge uses stricter remaining-record ownership checks and retains backup-referenced, reader-held and media-owned bytes. External originals and workspace files are never cleanup targets.

A failure after unlink but before its SQL outcome leaves the durable intent. Restart observes absence and records **already missing**, rather than claiming the missing file was just removed. Attachment metadata, provenance and checksum remain. Missing/cleaned originals are unavailable to exact-original reads and verification gates even when a retained preview exists.

Accounting separates selected logical original bytes, managed pathname bytes actually removed, and originals already absent. Those lengths are not measured disk savings: hardlinks, APFS clones and backups can retain the same blocks. Completed verified backup receipts also report known-at-backup retained logical originals. Current external backup presence is unverified; physical reclamation and backup-retained physical allocation remain explicitly unmeasured. Existing exports and backup copies are never purged by this job.

The implemented project operations (owner, or enrolled worker while `agent_rule_changes=allowed`) are `archive_storage_settings`, `attachment_cleanup_preview`, `cleanup_job_list`, `cleanup_job_get`, `cleanup_job_cancel` and `cleanup_job_retry`, alongside existing attachment and archive commands. Jobs are project scoped; cancellation remains available for an archived project. Retry requires a current job revision and a suspended job. These operations do not launch a model or change work authority.

Playtest reviewers can set `retain_cited_files:true` with their assessed pass/reject. Only exact bundle attachments cited in that verdict's validated assessment/checks receive the ordinary Keep original flag. A verdict records those exact retained references. Other bundle files remain eligible under the current project storage preset, threshold and budget; existing pins and all ordinary protections remain. The bundle offers the same `attachment_cleanup_preview`, without deleting files or introducing a second cleanup job. For a disposable check that should select every uncited original, the owner can choose a one-byte threshold and zero retained budget; production defaults still retain small files when within budget. Cleanup preserves the bundle's role metadata, build/file hashes and per-acceptance verdicts, and labels pruned originals unavailable for reinspection.

## Done evidence and aged closed tickets (CL-193)

Project settings → **Closed ticket cleanup** controls two independent rules in `ticket_cleanup`: `done_evidence_enabled` and `closed_purge_enabled` (both default true), and `closed_days` (default 15, whole days 1–36500). These are ordinary project settings, subject to project revisions and `agent_rule_changes`. Open statuses are never selected, including archived or trashed open tickets. Closed means the status category is Done or Canceled; a label alone grants no authority.

Cleanup starts automatically for every project after service startup, including existing projects with no cleanup settings. No preview, digest, activation or observation window is required. The owner saves the two switches and day count in Project settings; agents use `project_settings_save` with the current project revision. Saving settings restarts that project’s bounded scan. The lifecycle-specific `ticket_cleanup_preview` command is removed; manual Archive and permanent-removal previews retain their existing contracts.

A transition to Done commits a recovery wake in the same transaction. The existing maintenance pump admits the deletion job after commit or on startup. It retains ticket/history/evidence records and immutable file lists, names, sizes and SHA-256. It queues only the ticket's exclusively owned managed originals, previews, captured files, captured link text and sidecars admitted by the existing CL-154 plan. At final unlink it rechecks current Done status, ticket revision, settings, owner fingerprints, foreign references and every existing hold. Reopening or disabling the rule retains remaining bytes; removed bytes cannot be recreated. New references and changed owner metadata retain their files. Files protected by readers, Keep original, media ownership, backups or shared/unknown authority stay. Workspace and external originals are never removed.

A closed ticket unchanged for `closed_days` is purged by the existing CL-24 record-removal path, with its owned-byte intents committed atomically. Age uses the latest valid ticket update or ordinary ticket event (including notes), excluding cleanup accounting. Missing change time retains the ticket. Active work, unresolved execution and pending owner requests block both rules. Purge retains a minimal reference and shared records and scrubs private history/command results as in manual purge. Its byte jobs survive a crash and recheck holds; turning a rule off cannot undo a committed purge.

A pass scans at most 32 tickets and admits at most one ticket action. Expensive purge planning, command-history inspection and reference traversal run in a read snapshot on a utility maintenance lane, outside the request queue, object gate and SQL writer. A bounded in-memory cache reuses canonically decoded unchanged records and exact UTF-8 reference edges (100,000 records and 2,000,000 visited JSON values maximum). The writer’s total-change counter and connection data version must still match the preparation; any intervening write, including a new hold or settings change, discards it. The short commit saves the semantic action, byte intent and receipt together. Byte continuations drain admitted jobs before planning another ticket and remove at most one verified object per wake. Regular-file hashing pins an open descriptor outside the writer and object gate. Final unlink checks the same root, relative path, digest, length, device, inode, modification time and change time against both that descriptor and the current pathname; changed or newly appearing files stay. Captured links keep their bounded no-follow identity and target-chain checks. The service command queue is free during preparation and between commits. If a separate read lane is unavailable, automatic cleanup retains data rather than scanning on the writer. No schema migration is added. A durable cursor continues an unfinished scan through the existing one-shot maintenance deadline. A completed sweep is due again in one day; a new Done transition wakes it sooner. Aging is therefore enforced on the next daily pass after the threshold. Permanent file holds do not receive a per-file polling timer. Existing cleanup's root gate, descriptor-relative verified unlink and two-failure limit remain the only deletion engine.

`ticket_cleanup_receipts` returns the newest 50 project-scoped pass receipts. Supply `receipt_id` for one retained pass. The list also returns a durable `first_pass_receipt_id`, so a large backlog cannot hide the first pass by pushing it out of the newest-50 window. Every receipt records considered ticket actions, kept reasons, settings and `selected_bytes`; linked byte receipts retain exact file descriptors. Its current projection includes each exact byte-job outcome, file names/hashes/lengths, removed/absent/kept totals and reasons. `bytes_state=pending` is not completion; `already_missing` is never counted as removed bytes. Record the first receipt’s `selected_bytes`, receipt ID and final `summary.removed_bytes` during installed qualification, without changing settings to activate it. These are managed pathname bytes, not physical disk savings. Previous backups and exports remain unchanged.

Intentional evidence absence is retained in the durable receipt. Snapshot inventory uses its exact path/kind/hash/length outcome to report `evidence_cleaned`, preserving immutable source manifests and allowing later backups to retain metadata without demanding removed previews/captures. This is not restore support. No schema/protocol migration or new canonical family is introduced. Installed compatibility still requires exact staged startup and protected backup against an owned consistent real-store copy before replacement.
