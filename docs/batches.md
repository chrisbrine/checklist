# Fixed Triage batches

For the working procedure, tool choices and division between implementation and review conversations, see [run implementation and review orchestrators](../skills/checklist/references/orchestration.md). The project-level registry remains separate planned work.

Each Triage has an immutable `PREFIX-Tn` key beside its name. Batch snapshots and receipts include `triage_key` and `triage_name`; members, claims, results and blockers include ticket `key` and `title` beside `task_id`. Older frozen batches receive display fields in projections without rewriting their stored snapshot or digest. Membership history names the Triage by key and name. Reports, notes and checkpoints cite `KEY "Title"`, with project name where needed, while commands keep stable IDs.

A prepared batch is an immutable selection from one Triage in one project. It records one phase, exact task and acceptance revisions, exact review-request and manifest revisions/digests when reviewing, normalized file and lane scopes, checks, the applicable policy snapshots, and the originating Triage revision. Preparing evaluates the whole selection without acquiring claims. Claiming validates the whole snapshot and reserves every member in one transaction. A stale task, changed request, conflicting scope, unavailable verification slot or denied reviewer rejects the entire claim.

Later Triage adds/removes affect future batches. They do not rewrite prepared membership, cancel work or move a ticket's Epic. A ticket may be in several Triages but still has one exclusive current task claim. Membership intervals and separate departure records retain entering/leaving history. Legacy memberships retain their observed join time and explicitly unknown originating revision rather than inventing an old revision.

Each Triage has one explicit phase, `implementation` or `review`. An implementation Triage may be planned in advance with Queued tickets (Draft or Ready, with or without open prerequisites), ordered with prerequisites first; claim its Ready members through a frozen batch so membership stays. For individual work, claim the ticket first, then add the In Progress ticket to an implementation Triage. Submission changes it to Review and removes it from that implementation group, including legacy manual milestones. Create a separate review Triage for the submitted exact targets; claim review before adding, or use an actual atomic review batch claim. A batch review verdict keeps every current Triage membership for `blocked`, `not_run` and `evidence_missing`; reject and pass keep their departure effects. Complete passing tickets once all their own gates pass; only failed or remaining tickets enter another implementation pass. Review members cannot be added to implementation groups and queued implementation tickets cannot be added to review groups. A nonempty established Triage cannot switch phase. Legacy homogeneous handling metadata supplies a derived phase; unresolved legacy groups require an explicit phase choice without silently deleting memberships.

Individual status actions, including explicit same-status marking, remove all current Triage memberships. A `review_request` that returns or replaces an existing request for the same target and gate while the ticket is already in Review continues that phase and keeps its Review Triage memberships, including supplemental evidence after `evidence_missing` and pickup after `not_run`. `review_batch_inputs` immediately selects the available request; no membership re-add is needed. A new target or actual phase change still removes all current memberships. Notes, attachments and metadata edits retain them. Actual batch claims retain their selected phase membership; atomic batch submission, reject and pass still depart members when that phase finishes. `batch_release` keeps every current membership while releasing selected live claims; non-final batch verdicts also retain membership. Same-phase ordinary group status actions retain membership. Returning a review group to implementation/parking, canceling a phase, or reaching Done departs the affected handling groups. A rejected departure is never labeled accepted. Zero-gate Done is labeled **No review required**; owner-waived findings stay explicitly waived. A batch ID never provides a public retention bypass.

## Discovered service commands

Workers must discover the installed server's catalog before using these commands. Source implementation alone is not evidence that an older installed build exposes them. All writes use a UUID `command_id`; all commands use `project_id`. Batch records remain revision 1; later dispatches and results are separate records/projections.

| Command | Inputs beyond project/command | Result and guards |
| --- | --- | --- |
| `batch_prepare` | `triage_id, expected_revision` of Triage, `phase, tasks, checks?` | 1–200 unique current members. Implementation member: `{task_id,expected_revision,file_scopes?,lane_scopes?}`. Review also requires `{review_request_id,target_manifest_id,gate}`; implementation cannot include review selectors. Returns immutable batch/digest. |
| `batch_claim` | `batch_id,expected_revision,policy_revision` | All members or none; returns each actual attempt/claim token. Lost-response replay rotates tokens for still-live original claims. Tokens are excluded from durable command outcomes. A dispatched batch cannot be dispatched again. |
| `batch_discard` | `batch_id,expected_revision,reason` | Audited disposition of a never-claimed preparation. Requires a nonblank reason; keeps frozen bytes and ticket/work state. Claimed-ever refuses, including after release/completion. |
| `batch_release` | `batch_id,members:[{attempt_id,claim_token}],reason,final_report?` | Release selected live claims of this exact batch/digest/phase atomically, including all live members. Require a non-empty reason, record it on each ticket and the Triage, retain every current membership and leave unselected claims unchanged. Review stays in Review with its request available again; implementation returns to Queued. |
| `batch_get`, `batch_list` | `batch_id` for get; optional `triage_id` for list | Frozen records, dispatch reference and current per-member outcomes, with the exact target behind each outcome. |
| `batch_submit` | `batch_id,expected_revision,members` | Every remaining live implementation claim of that batch exactly once; omit released members. Each member contains its ordinary `attempt_id,claim_token,acceptance_revision,evidence_manifest,direction_cursor?`. All submissions validate and commit together. |
| `batch_review_record` | `batch_id,expected_revision,members` | Every remaining live review claim of that batch exactly once; omit released members. Each member contains its exact request/manifest/gate, claim, verdict, checks, findings and observed direction cursor. Pass/reject outcomes can differ; all are recorded atomically. |
| `batch_complete_passing` | `batch_id,expected_revision,expected_direction_cursors` | Completes accepted current exact targets independently through ordinary completion guards; returns successful IDs and per-ticket blockers. Cursor map contains exactly the accepted, not-yet-completed candidates and comes from caller-observed task context. It never refreshes directions on the caller's behalf at commit. |
| `batch_retriage_remaining` | `batch_id,expected_revision,name?,purpose?` | Creates separate implementation/review handling sets for failed, stale, unclaimed or otherwise remaining tickets according to their current phase. Passing/completed tickets are excluded. Active work must finish or safely release first. An empty remainder is a no-op. |

`batch_claim` requires the positive integer `policy_revision` returned by `batch_prepare`. Missing, null, string, Boolean, fractional, zero, negative or out-of-range values return `INVALID_INPUT` naming the field, without claims or a need to prepare again. Correct the input with a new `command_id` and reuse the same still-valid preparation. A supplied revision inconsistent with the frozen batch returns `POLICY_CHANGED`; read that batch and current policy before retrying. A project policy change after preparation also returns `POLICY_CHANGED` and requires a fresh preparation; supplying the new project revision cannot bypass the older frozen snapshot. For an unknown-outcome retry, preserve the original `command_id` and identical input.

The shared `review_batch_policy` default is `complete_passing_independently`: accepted tickets can become Done while failed/remaining tickets continue. An explicit project override, `hold_passing_for_batch`, holds automatic batch completion until all batch members are accepted. The override never creates work on an already accepted ticket or weakens an individual ticket's gates. The batch pins the policy that applies to its handling pass. A member whose gate waits for more evidence after an `evidence_missing` verdict has the outcome `evidence_requested`; it is neither failed nor accepted. Open advice findings do not make a member failed, and a member held for a release set (`release_set_holds`) reports its `release_hold`; `batch_complete_passing` leaves it to `release_set_complete`.

Carry input-valid passing acceptance/check-case results through rework and report them separately from newly executed checks. Select only failed, inconclusive or materially affected cases, including after fixture-only repairs; see [shared review handling](policies.md#review-handling-shared-by-every-project). Membership or a sibling failure alone does not justify reruns. A batch-completion hold alone does not invalidate passing case evidence or weaken fresh target-bound gates.

## Actual orchestration and Active

A Triage can be coordinated by an actual connected Codex or Claude session. `triage_orchestrate` takes `triage_id,expected_revision,action:start|checkpoint|finish|takeover` and optional `progress,reason`. Start and takeover derive the actual caller session, provider, execution domain and authorization generation and check current coordinator eligibility. They never accept an arbitrary session identity, launch a model, assign a member ticket or manufacture a member claim. The recorded current session checkpoints/finishes its coordination; the owner can explicitly finish a stale recorded coordination with a reason. A disconnected/ended session produces a recovery indication, never automatic abandonment.

`takeover` requires a nonempty reason and a different eligible coordinating conversation. It atomically ends the earlier active record as `taken_over`, links the new active record to it, retains progress as takeover context and records both in Triage history. A Triage-scoped note names the new coordinator and reason; `takeover_notice` returns its message ID and exact recipient deliveries. A receivable earlier session gets a `queued` receipt for its current generation; an ended/unavailable session retains the note in Triage history with `saved_for_pickup` and no claimed delivery. Queued is not native receipt or acknowledgment. No member ticket, claim, fixed batch or membership changes. No permission from the previous coordinator or inactivity timeout is required.

A service-verified native resumption of the **same conversation** can `finish` its earlier active record with a nonempty reason, then `start` a new one. Recovery matches that record's session, original principal, provider, execution domain and authorization generation to a released native closure retained by the resumed session. The finish event keeps `native_closure_ref`, the recovery reason and finishing principal/generation; the new start links `previous_orchestration_id`. Recovery never checkpoints the old generation or revives ticket claims/deliveries. An ordinary end/reconnect or an unrelated closure does not qualify. Other conversations cannot use this recovery finish; they use the separate explicit eligible takeover route.

A ticket appears under **Active** only when its own status category is `active` (In progress). Queued and Review members keep their own sections during orchestration; a Triage has active work only when its members themselves are In progress. The backward-compatible `active_attention` field is advisory handling state for work health, not the Active section predicate. Orchestration and its actual coordinator remain visible as Triage information. The group still has no independent editable lifecycle status: phase, member-derived status and actual orchestration receipts are separate facts. In Progress tickets remain addable to a compatible implementation group.

## Navigation and retention

Empty and archived Triages leave the active ticket list. The existing **New triage** flow remains; **Past triages** opens empty/archived handling records so an empty Triage can be reused and an archived Triage restored. Archiving does not archive/delete member tickets, change Epics, release claims or modify a fixed batch. The Triage overlay shows fixed batch summaries alongside the current editable handling set.

## Shared implementation reservations

Only one frozen **Implementation** batch may share its members' canonical writable paths, and only between its original selected top-level attempts held by the exact same authenticated principal, session, authorization generation, execution domain and store incarnation. Preparation normalizes/freezes all scopes before its rollback-only claim rehearsal; dispatch installs the internal cohort before reservation validation. There is no public overlap flag. Each ticket keeps its complete scopes, distinct attempt, token, contributor history and evidence target. Same-path, ancestor/descendant, symlink and volume-case aliases use the ordinary canonical comparison.

All other live attempts see the cohort's canonical write union. A different session/generation or frozen batch (even held by the same session) still conflicts. Partial release or individual submission keeps every remaining active member's reservation; only the last owner frees the shared path. Review reservations, lane capacity, readiness, prerequisites, policy, owner assignment and review independence remain unchanged. Scope adjustment can retain/narrow frozen shared writes but cannot expand sharing beyond the frozen member envelope. Child acceptance, handoff and takeover never inherit the original attempt's sharing permission: overlapping transfers refuse atomically until narrowed or other writers release. Reconnection cannot revive an old generation's exemption. Orchestration ownership grants no member reservation authority. Scoped conflicts identify the canonical candidate/reserved paths and both ticket IDs/keys, with batch ID/digest when present; foreign-project ticket metadata stays private.

## Prepared batch disposition

A batch has computed lifecycle `prepared`, `claimed` or `discarded`, exposed consistently by `batch_get`, `batch_list` and Triage summaries. Preparing is planning, never started/claimed work. `batch_discard(project_id,batch_id,expected_revision,reason,command_id)` lets an eligible scoped project worker or the trusted owner discard an unused preparation of either phase. A nonblank reason and exact frozen batch revision are required. The immutable project-owned `batch_disposition` retains batch ID/digest, Triage, actor/session, reason and timestamp without changing the frozen batch, ticket status, membership, attempts or orchestration. Discarded rows remain visibly labeled with their reason and history; there is no timed expiry or hidden default filter.

Claim and discard serialize in the command transaction. Any dispatch receipt **or historical associated attempt** proves claimed-ever and refuses discard with `BATCH_ALREADY_CLAIMED`, including after full release/completion. `batch_claim` and undispatched completion/retriage continuation refuse discarded preparations with `BATCH_DISCARDED` and direction to prepare afresh, acquiring no authority. Same-command replay returns the original outcome; a fresh repeat returns the existing disposition without a duplicate event/marker. Export and verified backup retain this recognized canonical family so restart cannot resurrect a discarded preparation.
