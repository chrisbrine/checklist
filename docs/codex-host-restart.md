## Strict restart scan and first installed result (4 November 2026)

The first installed build-291 restart check refused. The owner approved one restart at 4:44 PM PDT (request `128e594c-ea3c-467c-ae61-57997e8c60b2`, response `70880019-5344-4deb-a64b-7ea088248d46`). The selected app thread connected at 16:42, the old host quit at 16:45:56 and was gone at 16:46:01, and a new host started at 16:46:10. A relayed note started its turn, but its 16:46:57 MCP call returned `NATIVE_SESSION_MISMATCH`: the process/holder observation was unreadable or incomplete. Authorization did not rotate. Supplied read-only diagnostics found 257 other-account processes denying BSD info, two same-account executables replaced on disk, and seven non-Codex Apple agents with one unreadable vnode each. Part 2's strict scan conflated those with possible Codex holders. This is a real refusal, not reconnect qualification.

Part 3 separates strict restart classification from the unchanged transport scan:

1. Read BSD process account metadata, falling back to `sysctl KERN_PROC_PID`. Skip a process only when both real and effective accounts exclude the caller. Unknown account refuses unless the kernel positively reports the PID gone.
2. Read complete arguments for every same-account process. When the executable path is unavailable, require readable kernel `p_comm` as well. A process is a Codex candidate if its executable/argv[0] basename or kernel command is `codex`, or its arguments name the thread or `--last`. Unreadable/truncated arguments refuse. Known Codex processes never get a non-Codex exemption.
3. Read kernel descriptor/vnode paths without opening any files. Preserve readable paths even if another vnode fails. A complete or partial table that shows any other holder of the exact rollout filename still obstructs reconnect. Strict matching includes matching rollout filenames outside the conventional root, adding conservative refusals without filesystem path resolution.
4. Incomplete descriptors in an identified non-Codex process (readable non-Codex identity and arguments, no thread/`--last` claim) do not make the scan unreadable. Count each such process in `incompleteNonCodex`. Incomplete Codex-candidate descriptors remain unreadable. Process disappearance requires positive kernel absence; permission failure never means absence.
5. Compare sorted hosts, holders, exec claims, unreadability and the incomplete count across both scans. Count-bearing refusal messages distinguish the exempted observations. Successful `native_session_resumed` history records `incomplete_non_codex` from the final successful verification immediately before Core commit, not the earlier pre-closure scan.

This is sound within the owner's Codex-specific, first-connection trust rule: it excludes identified non-Codex incompleteness from the requirement to exclude another Codex holder, while retaining every readable competing holder and every unknown candidate. It does not prove absence of a malicious disguised non-Codex holder behind an unreadable descriptor, create a general registry observer or promise an exclusive lease. The opt-in kernel-only scan test checks scan usability on this Mac; it does not reconnect a thread, open a store, sign a host, release work or qualify an installed restart. On 4 November at 17:03 PDT, the authorized opt-in kernel-only scan passed once on this Mac: `hosts=1 holders=0 unreadable=false execClaim=false incompleteNonCodex=7`. The test used a random UUID, read kernel metadata only, and opened no rollout/store or native thread. This establishes scan usability for that observation, not a successful reconnect.
