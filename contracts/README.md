# Prepared v1 data contracts

These closed JSON Schemas describe project binding/settings, workflow policy, taxonomy, human requests, host-owned assistant identity snapshots and assistant grants. They are prepared target contracts, not proof that every integration is implemented or qualified. Validate the same-name synthetic examples in `../examples` against them; no source tasks were imported. Checklist has no app-created named-worker/persona catalog: worker identity is the actual Codex/Claude session, while an existing personal assistant's name/personality stays with its host.

The [MCP contract](../docs/mcp-contract.md) specifies the bounded role-based tool surface, concrete shared input/result shapes and semantic commands. Exact per-tool JSON Schemas and generated structured types are implementation deliverables before either client uses the server. The [domain](../docs/domain.md) is normative for authority, atomicity and lifecycle behavior.

- `project-binding.json` represents `.checklist/project.json`; resolve `root_relative_to_binding` from that file's parent. An ID in a file grants no access. Automatic CLI/MCP bootstrap for created/existing provider threads validates the actual caller workspace/native host, available host-exported session ID, file grants and canonical non-overlapping writable project roots. A signed executable establishes observed host provenance, not a cryptographically signed thread identity. Do not invent attestation or accept a worker's assistant/profile binding. When native thread creation is unsupported, the app opens the provider or offers a scoped instruction to copy; it does not fabricate a created/enrolled session or require manual Settings pairing.
- `project-policy.json` is a **resolved preset** with participating providers, three role rules and bounded per-task-kind exceptions. The owner starts with three simple presets, not this JSON form. Kind exceptions replace listed role/gate settings and cannot introduce a provider outside `allowed_providers`; a planned task exception can only choose within effective eligibility. Model names are preferences, not claimed native selections. The example Asset rule allows either provider for implementation and human approval; a real technical asset-pipeline task can also require technical review.
- `taxonomy.json` is a **resolved service snapshot** with generated defaults/protected edges. Ten internal destinations are not ten owner setup decisions. The editor asks Name → behaves like → color. The example preserves several Parked types and independent tags. Draft/Ready is task readiness over queued semantics, not a new user-maintained category.
- `human-request.json` is a synthetic mixed input form with flat `human_request_create` fields; supply real `project_id`, `task_id` and `command_id` alongside them. The same fields can be revised through `human_request_revise patch` (a non-empty subset; see the schema’s `$defs/patch`). Questions use `prompt` and `text|choice|approval|check`; files use `prompt` and `kind=file|directory|either` (`selection` is an alias). There is no `request_spec` wrapper or `human_request_edit` tool. Exact gate binding uses `review_request_id`, `target_manifest_id` and an available managed `target_attachment_id`; the service derives its hash. The example is input collection, not an outstanding gate or a human answer. Only the trusted app channel can create human answers.

JSON Schema verifies shape, not the following domain conditions, which must be checked transactionally:

- Project scope and unique IDs/names/keys/question-option IDs, policy kind uniqueness, lane uniqueness and provider-registry validity.
- Preferred provider belongs to effective eligibility; base/override providers belong to project participants; enrolled session grants and independent-contributor review still apply.
- Gate registry/eligibility, Checklist-only installed-build gate, permitted empty-gate decision tasks, completion-contract revisions and source/artifact check provenance.
- Status/default/edge references point to live same-project definitions with correct behavior; fixed guards cannot be bypassed through a rename or transition route.
- Human required-answer/file completeness, exact approval bytes/manifest, one active blocking request and single active verification slot, request revision/draft reconciliation and eligible continuation. Not checked/clarification/cannot-do never passes a gate or clears blocking.
- File access, symlink containment, immutable attachment capture, scope reservations/expansion rollback, claim/recovery fencing, delivery receipts and revision-checked Undo.

No remote/chunk upload protocol, arbitrary routing language, provider marketplace, atomic task split/merge or generic SQL/state mutation is promised for v1.

Additional prepared contracts: [project-settings schema](project-settings.schema.json) and [example](../examples/project-settings.json) keep identity/icon/starter/view/alert values separate from canonical policy/taxonomy/context. [Assistant-identity schema](assistant-identity.schema.json) and [example](../examples/assistant-identity.json) describe a read-only snapshot of an existing host-owned personal assistant. They contain no editable personality, provider switch or worker profile; the synthetic Rowan snapshot is **host-reported**, not a qualified Dot route. `host_verified` requires an actual identity-proof receipt, and shape validation cannot verify that receipt. An internal legacy profile ID in implementation storage is a mapping detail, not a public profile-creation contract.

[Assistant-grant schema](assistant-grant.schema.json) and [example](../examples/assistant-grant.json) specify owner-approved read, requested Draft capture, requested notes/messages, incoming direct messages/replies and optional ticket updates for the existing assistant. Direct receipt and ticket-update subscription are independent; no grant supplies a work role or trusted human authority. These records do not contain credentials, subscribe events or enroll a live connection. Runtime validation rejects repeated project IDs, checks actual bootstrap/host identity assurance, current grants and source-request provenance, and validates icon/assistant references and canonical revisions. Public source must not advertise qualified Dot access until real discovery/authentication/delivery checks succeed.

[Review-assessment schema](review-assessment.schema.json) and [synthetic example](../examples/review-assessment.json) describe attributed per-acceptance/project-requirement judgments and reviewer-chosen hashed artifacts. Runtime checks additionally bind the current contract/manifest, exact review claim, contributor independence, complete requirement IDs and actual managed bytes/author. A schema-valid report is not a created reviewer, a verified check or a passing gate. The service execution runner is disabled without a qualified sandbox; review preparation uses the supported composer/copy flow.

[Evidence-measures schema](evidence-measures.schema.json) and [example](../examples/evidence-measures.json) describe optional `evidence_manifest.measures` / `review_evidence_add.measures`, with runtime finite-number, unique-name and bounded single-line text checks. [Playtest-bundle schema](playtest-bundle.schema.json) and [example](../examples/playtest-bundle.json) describe the optional Playtest submission input, not a new command or record family. The service adds immutable bundle identity/digest and validates the exact managed files/build. Pass/reject uses the existing review assessment with per-acceptance pass/fail results. Optional `review_record.retain_cited_files` reuses attachment Keep original and normal archive cleanup, without weakening other holds. See [source evidence](../docs/source-evidence.md).


`media-record-reference.schema.json` describes one internal `record_references` entry used by the CL-111 media capture registry. Same-project resolution, registered family membership and exact revision presence are runtime capture checks. Immutable version families require a revision; mutable identities can omit it, so releasing an ownership reference does not invalidate its historical identity. The schema is not a media command or a restore format; see [media history capture](../docs/database-storage.md#media-history-capture-registry-cl-111).

[Ticket-view schema](ticket-view.schema.json) and [example](../examples/ticket-view.json) describe the owner Tickets `view` object (surfaces `tickets|overview|archived|trash`, status and tag filters with `tag_mode`, planned and current assignee, Epic and Triage). [Bulk-edit](ticket-bulk-edit.schema.json) and [bulk-Undo](ticket-bulk-undo.schema.json) schemas with their [edit](../examples/ticket-bulk-edit.json) and [Undo](../examples/ticket-bulk-undo.json) examples describe CL-16's `task_bulk_edit` and `task_bulk_undo` inputs. Shape validation does not check row revisions, active claims, Triage phase rules or Undo preconditions; the service checks them in the command transaction.

[Ticket-operations schema](ticket-operations.schema.json) and [examples](../examples/ticket-operations.json) contain synthetic command shapes for CL-24: own-note correction and retraction, reasoned cancel, reopen and reassignment, archive, trash and restore, guarded single-ticket Undo and the owner-only previewed permanent record purge. The purge example's zero digest is a shape placeholder; a runtime call uses the current preview digest and ticket revision. Shape validation does not check provenance, active-work refusal, shared-reference preservation, transactional scrubbing or the native confirmation. The current purge keeps managed bytes and existing backups and exports (follow-up CL-154).
[group-reference.schema.json](group-reference.schema.json) and [agent-message-subject.schema.json](agent-message-subject.schema.json) define group display labels and inbox subjects. They preserve stable tool IDs separately from untrusted display text.

- `acceptance-evidence.json` shows the per-item submission map. Installed/native reports also require a matching `evidence_manifest.installed_build_id`, same-ticket managed bytes and non-contributor authorship, enforced by the service.
