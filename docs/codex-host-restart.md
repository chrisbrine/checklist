# Codex app host restart: design boundary (CL-417)

The 4 November 2026 build-289 observation proves a note can open an unloaded `source=vscode` app thread after a host restart. In that thread, CLI bootstrap then returned `NATIVE_SESSION_MISMATCH`. This is an authority gap separate from the queue transport pass and from MCP startup.

No sound small automatic-reconnect change is available with the current provider contract. `CodexProviderPlugin` declares no `registryClosure`, has `registryDirectory=nil`, and authenticates a signed host process with a host-observed thread UUID. `observeNativeConversationLifecycles` therefore cannot create a Codex closure proof. `reconnectNativeSession` deliberately requires that capability and a fenced enrollment before Core accepts a resumption. A queue source row, rollout descriptor absence, old host exit or a loaded-thread event is not the applicable native conversation registry proof required by [work authority](work-authority.md#confirmed-native-conversation-closure). The shared host's restart affects many conversations, and thread unload does not close a conversation.

A separate implementation ticket needs a supported native registry/host binding and an independently reviewed observer. Its rule must be:

1. Persist the old verified provider, native thread, PID and kernel start identity, workspace, installation/enrollment generation, Core authorization generation and applicable registry identity at bootstrap. Never infer these from service cwd, a queue result or a caller's supplied ID.
2. Observe independently that the exact old process is gone or its PID was reused, and that its applicable registry binding is absent or verifiably replaced. An unreadable, incomplete, missing registry directory, permission failure or unsupported observer stays unknown. A persistent conversation catalog row is not evidence that an old process-to-thread binding has ended. A valid new host binding needs explicit semantics establishing replacement of that old binding; new PID alone is insufficient.
3. Fence the exact old generation through the existing service-owned native closure path. Reconcile all its work through Core, retaining source-execution and writable-descendant stop fences. Do not reconnect until closure has returned eligible claims for pickup; otherwise retain `NATIVE_CLOSURE_PENDING`. Preserve owner disconnect/Allow again controls.
4. Verify the new signed host PID/start identity, native registry binding of the same thread, actual workspace and unchanged project/mode constraints as for a first connection. Recheck the old closure and current enrollment atomically against races. Rotate the credential, installation generation and Core authorization generation using the existing rollback-safe connection commit and `resumeVerifiedNativeSession` path.
5. Keep released attempts/tokens ended, reservations reconciled and old-generation deliveries fenced. Preserve the same session/principal identity for contributor independence. Use existing generation-specific recovery summaries and eligible notice-resumption receipts; never transfer old claim authority, infer acknowledgment or blindly replay the backlog. A resumed thread takes ordinary claims again.

Open questions and acceptance inputs for that ticket:

- Which supported host API/registry exposes an authenticated thread-to-host-process binding, its replacement semantics, and an exhaustive old-binding absence result? The current `state_5` queue observer is transport classification, not a qualified closure adapter. Do not enable `registryClosure` merely because `source=vscode` is observed.
- Can a same thread remain in more than one host/exec process, and how are old bindings and registry-address/PID reuse distinguished from incomplete reads? How does the observer stay valid across host upgrades, crashes and service restarts?
- What receipt proves the new host's thread identity independently of its inherited environment UUID? What races remain between registry observation, process observation and enrollment commit?
- Use fake process/registry effects for unit coverage of every gone/replaced/running/unknown combination, owner revocation, changed workspace/source/generation, interrupted credential commits, pending descendants/source work, old token/delivery fences and repeated resumption. Qualify native restart and current-generation pickup separately on the exact staged build through the orchestrator. No test may substitute an idle timeout, MCP EOF, rollout unload or queue marker for closure.

CL-417 leaves the provider capability and reconnect implementation unchanged. The owner Allow again path is an explicit authority decision, not an automatic restart workaround, and is not exercised or recommended as a substitute for the missing proof.
