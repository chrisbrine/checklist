# Provider and assistant integration plan

**Development integration status, 16 October 2026.** The app, shared service and official-SDK MCP executable exist. The primary connection contract is automatic actual-host/session/workspace bootstrap when a provider thread uses bundled CLI/MCP, with actual worker status/history/recovery on each ticket and no active assistant settings/sidebar/grant UI. Installed-version observations and source support do not qualify every native route. Existing personal-assistant identities and future adapters are defined in [assistant identity](agent-profiles.md); current limitations are in [implementation status](implementation-status.md).

Local development observed Codex CLI 0.159.0 and a Claude Desktop Code engine 2.1.299. This proves that particular socket/model round trip only. It does not prove idle Codex chat delivery, children, restart recovery, the implemented MCP service or assistant event notifications. Raw session/process identifiers and runnable historical probes are private local evidence and are excluded from public source. Release qualification must use repeatable synthetic test sessions with publishable redacted receipts.

On 19 October 2026, with codex-cli 0.159.0 and installed build 47, a thread that a Claude orchestrator started with `codex exec` did not get the Checklist MCP tools: Codex starts stdio MCP servers without `CODEX_THREAD_ID`, so bootstrap finds no native thread and no error is shown. A shell command in that thread (`checklist call service_info '{}'`) bootstrapped the thread as its own session, but only under `danger-full-access`; `read-only` and `workspace-write` blocked the support folder or the service connection. A later `codex exec resume` of a connected thread runs in a new process and was refused with `NATIVE_SESSION_MISMATCH`, because only a verified Claude session can resume after its process closes; each Codex thread can use Checklist only inside the run that connected it. The optional [driven sessions](../skills/checklist/references/driven-sessions.md) reference records this route. It does not qualify the MCP route for `codex exec`, native wake or other hosts.

On 17 October 2026, a local observation with engine 2.1.299 in Claude Desktop found that the Checklist relay truthfully sent `from-mode="prompting"`. Claude held delivery to a bypass-mode recipient for permission-mode parity; the desktop showed no approval control while busy or idle. Native delivery in that observed configuration stays held, and the note remains available at the agent’s next Checklist check. The relay never claims a more permissive class to pass parity. Claude records this hold as `mode-mismatch`; its recipient-side `crossSessionInbound` setting (`hold` by default here, or `accept`) is the user's own control for releasing such messages, and a repository or managed setting can only tighten it. This observation does not qualify other recipient configurations or versions.

## Deferred assistant access through the connected Mac

**Not active setup instructions.** The owner deferred assistant integration, disabled all development-installation relay grants and removed the local plugin. Assistant controls are absent from the current UI; do not install or enable it as part of ordinary setup. The remaining section records the future candidate design.

If reactivated later, prefer the first-party connected-computer **local MCP/plugin** with owner-authorized project scopes, while Checklist's database/service remain on the Mac. The bundled local marketplace installs through the official Codex plugin commands; [prepared package](../plugins/checklist/README.md) records its status; no current installation steps are provided. Its server uses `mcp --assistant --project @enabled` and only current owner-enabled relay grants, with per-call/reconnect revision checks. Local installation/discovery, an authenticated local relay and an actual cloud-Dot call/result are separate capabilities; none should be inferred from another.

The on-demand local Codex helper remains preserved source and prior component evidence only. Through the host's supported local task route it can call the scoped assistant CLI/MCP and return results through that task. It authenticates the local helper only, not cloud Dot identity/consent, and does not create a named profile or unattended report route. Read/requested Draft/Note access is never work assignment, human provenance or rule authority. A real Dot must initiate/discover the path and receive/report its actual result before the full integration is qualified.

If the native first-party host cannot forward/use this local MCP, document the concrete limitation. A separately selected private authenticated outbound transport may then be evaluated; it is not a public Checklist backend or automatic tunnel fallback. No remote listener/network exposure is created by these instructions. Direct named-Dot identity and event push remain unqualified.

## Provider handoff and automatic bootstrap

Use an existing or newly opened provider conversation; its first bundled Checklist CLI/MCP use connects actual host/session/workspace to allowed project context. First-run integration registration and real host/background-item permissions may be necessary, but manual Settings pairing is not the primary thread workflow. Bootstrap checks observed local host/process provenance, available host-exported thread context and current grants/revocations; it must not describe that as cryptographic thread attestation. In particular, the MCP cwd, app selection, display label or self-reported Dot name cannot supply that proof.

Task **Use in Codex** prepares a native chat composer with the scoped ticket prompt, so the user can press Send without copying instructions. That draft is not a started turn, connection or claim; only the actual resulting thread can attach through bootstrap. An explicit native Codex `create_thread` test returned a real new thread that ran `connect --task CL-4` automatically, with context-only attachment observed in the app. This does not assign work or claim the ticket; it also does not make the GUI composer send automatically. Claude retains an open/copy fallback where no native route is supported. No generic app-server/CLI/API model runtime substitutes for a missing native route.

Named discovery recognizes existing verified host-owned personal assistants only. Ordinary Codex/Claude workers remain native sessions, and app-created/manual/unverified profiles are excluded. No assistant connection controls are active. Future assistant diagnostics/scopes/revoke controls cannot manufacture a qualified identity or catalog ordinary worker sessions. Actual Dot identity bootstrap remains unqualified until a supported real-host exercise succeeds. Connection/inbox tools can exist before native push, Dot host integration or event reporting is qualified.

## Local connection failure boundaries

### Claude Desktop spare processes

Claude Desktop can start a spare `claude` process before it assigns a conversation. It starts that conversation's MCP servers before it writes the process registry. Evidence from 21 October 2026 found 10 failures in 62 logged starts, all from spare processes. For host PID 16909, MCP started at 03:10:36.261Z and failed at 03:10:36.379Z. The registry `startedAt` was 03:10:37.057Z, about 0.7 s after the failure. A manual reconnect at 03:54:02Z succeeded in 3.4 s with the same registry.

Automatic `mcp`, `tools`, `call` and `connect` commands repeat native discovery and bootstrap for this short-lived class only: a Claude host and valid exported Claude session ID with an absent registry, a different registry session or a registry cwd outside the workspace; or the exact service error `NATIVE_SESSION_MISMATCH: Claude's current session registry does not match this native process and workspace.` New attempts start only within 10 s of the first attempt, at intervals of at most 250 ms; a check after each sleep prevents a start at or after that window. After the first registry failure, each retry has one bootstrap budget of min(15 s, 20 s minus elapsed time), across its request, service-start path and second request, so the retry path ends by 20 s. The first attempt and lazy attempts keep the unchanged default of 15 s per request. Claude has a 30 s MCP connect timeout. All identity checks stay exact. No background timer or schedule is added. Claude Code records server stderr in its MCP log; a single recovery line gives the attempt count, elapsed time and first race reason (plus the last reason if it changed), and an exhausted startup notice gives the count, time and last reason without IDs, tokens or paths.

If that class persists, only `mcp` starts unconnected. It advertises only `service_info`, with the last error in its description, result `connection` object and server instructions. Each later `tools/list`, `tools/call`, `resources/list` or `resources/read` request makes one new bootstrap attempt without a wait loop. Success completes that request with the full connection and sends `notifications/tools/list_changed` once; the server declares `tools.listChanged: true` and keeps `resources.listChanged: false`. Until then, only `service_info` can reach the service, without a stored credential. A permanent lazy error ends further attempts and remains visible without a process exit.

`tools`, `call` and `connect` still report the final error to stderr and exit 1. Codex and assistant relays have no retry. Permanent startup errors keep their text and exit behavior: revoked connections, workspace/host/client/route failures and every other `NATIVE_SESSION_MISMATCH` message remain permanent. The unregistered-folder `PROJECT_SETUP_REQUIRED` path keeps its separate behavior and text. Source and deterministic tests do not qualify live Claude Desktop recovery; the installed native check remains separate.

Credential and enrollment writes complete before session registration. A staged enrollment without its exact registered session installation/generation, project membership, provider and role cannot authenticate; ended/revoked registrations remain unavailable. A failed write restores the prior local connection where possible; failed restoration requires visible repair rather than assuming either pairing succeeded. Disposable write/process interruption tests do not qualify actual Keychain failure or real provider pairing. Primary actual native bootstrap remains the supported worker route; this adds no manual Settings pairing workflow.

The existing local native receipt listener backs off after non-timeout errors with a capped delay, resets after a valid frame and keeps its blocking idle timeout. It neither retries a model send nor converts a listener error into message acknowledgment. Manual pairing's original method/payload/UUID is checked under the actual owner principal before random generation or credential preparation. Its internal session registration and whitelisted outer receipt share one Core transaction. A matching replay returns the original semantic receipt, skips preparation and reports current registration authority separately; it cannot resume a revoked generation. Prepared manual enrollments retain the original command/digest/principal and cannot authenticate without that exact committed registration/receipt. Existing automatic bootstrap also verifies credential digest and exact current registration before reporting connected.

Credential/enrollment files and SQLite are not one transaction. A preparation or commit failure attempts both prior-state restorations; failed cleanup retains the original failure with an explicit repair requirement. Prepared artifacts after a process interruption remain fenced. Once a receipt committed, failure to refresh current state reports a recovery warning instead of rolling back or fabricating failure. The initial synchronous preparation callback is a bounded exception and does not solve long I/O under the writer. These are internal failure contracts; no new Settings pairing UI, grant, runtime or provider qualification is introduced.

## Honest delivery

Saving a note commits content and exact-recipient outbox atomically. Show **Saved / queued**, **held/refused**, **provider accepted**, **recipient acknowledged** and **addressed** separately. An acknowledgment names the actual recipient generation; a parent receipt is not its child's. A model report is not owner-read. Target the current attempt/explicit resolved host-assistant identity and enrolled route, not the most recently seen label.

The sender's actual permission class belongs in the provider's required parsed envelope. Missing metadata may hold; a diagnosed omission can be corrected truthfully. Never impersonate another mode/own-child sender or borrow another session's token. A genuine provider hold uses only its actual approval path. Some hosts cannot display a live approval dialog; show held/expired and that limitation rather than promise a nonexistent button.

A design target is to begin transport within one second on an awake connected Mac; model consumption can occur later. This is not a measured latency promise. For uncertain provider acceptance, reconcile with supported stable message IDs or retain uncertainty without automatic duplication. After two identical route failures, suspend and show a repair action. Ended targets retain context for eligible pickup; no hidden model launch or old-session wakeup.

Check current grant and route generation immediately before an external send. Revoke unsent work and cancel in-flight I/O where possible. Bytes already submitted cannot be recalled; retain truthful timing/outcomes, reject subsequent reads/replay and never claim remote retraction. A new host name/provider connection cannot inherit old authority.

## Deferred named contact through Checklist

This future flow is unavailable while assistant integration is deferred. After the user establishes a qualified assistant app context in a later release, requests such as “contact Rowan” use `agent_resolve` and `agent_message_send`. Resolve within the actual project grant, show provider/access mode to disambiguate friendly names and bind the resulting opaque target to current verified host-assistant/principal/route generations. Never guess a native address or switch to email/another channel. A task conversation is preferred; a project-scoped contact conversation can exist without creating a ticket or assigning work. See [assistant contact](assistant-plugin.md).

The user's current send instruction or an applicable explicit communication grant authorizes the message. Receiving another agent's text is not itself new human consent. An unavailable adapter/closed host remains explicit; stored-for-pickup is not delivery.

## Capability qualification and revocation

Qualify each installed adapter version/capability separately: native identity, workspace or assistant binding, message push, busy/idle, exact child route, event callback and host report. Show **verified**, **checkpoint/manual only**, **unavailable** or **unqualified** with source/time/version. Provider updates make affected qualification stale; they do not silently switch runtimes. A host display name/personality, manifest or stored desired model is not a qualification record.

Use synthetic sessions/tickets and deliberate enrollment. Prove both native provider directions, real parent/child receipts, lost replies, holds/expiry, quota/permission prompts, sleep/wake, closed clients, revocation during send and reconnect. No transcript scraping, unrelated process discovery, schedule or new runtime is a qualification substitute. Simulations exercise deterministic state only.

The assistant plugin is generic; initial Dot is one adapter, not the product's universal definition of a named agent. Public packaging and its tested surface/version remain explicit. [Plugin packaging](https://developers.openai.com/plugins/build/plugins) and [desktop-only packages](https://developers.openai.com/plugins/deploy/desktop-only) describe candidate distribution, not proof of the installed binary or a public-directory approval. Personal installation, source publication and public marketplace distribution are separate steps.
