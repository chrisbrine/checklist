## Product boundaries

- Checklist is a ticketing system built for AI agents (owner decision, 18 October 2026). Agents create, refine, plan, claim, implement, review and change project rules, settings, statuses/tags and tickets through the MCP, recorded with agent provenance. The owner mainly adds notes, answers requests assigned to them and handles reviews meant for them. Do not hand a routine change back to the owner as a manual app step; if no agent command exists, record the gap as a ticket. Only the owner's own answers and approvals, and the per-project `agent_rule_changes` switch, stay with the trusted app.
- Draft readiness means a ticket still needs refinement. Prerequisites order Triage work and gate claim, pickup and completion; they never block Ready or queueing.
- Before replacing a working installation after storage validation or migration changes, qualify the exact staged code through the complete startup and protected pre-upgrade backup path against an owned, consistent copy of the actual existing store, including its retained record families and required managed files. Reading the managed inventory or rehearsing SQL migration alone does not qualify durable copying, verification or its time budget. Synthetic fixtures alone do not establish compatibility with that installation. Preserve the working bundle and original store; never repair the live database by hand.
- At each check-runner, rework and combined-round boundary, use `script/clean_scratch.py --preview` and the [scratch cleanup procedure](skills/checklist/references/driven-sessions.md#scratch-cleanup-and-cache-settings). Apply eligible cleanup to the Trash only within the authorized scope; retain persistent build/review workspaces, uncommitted work, evidence and the qualified copy of the latest installed round. Mark every persistent workspace at creation with `script/clean_scratch.py --mark PATH --purpose TEXT` (supply the caller's actual `--session-id` if not exported); only its owning session uses `--release PATH` when retiring it. Cleanup defaults to the caller's own session; foreign scratch folders need their owning session's explicit root release and an authorized `--include-released` pass. Checkout folders `.local/build`, `.local/evidence` and test slots are cleaned by CL-194's command, not by `clean_scratch.py`. Review steps run no scratch cleanup; the orchestrator covers their scratch at the next round boundary.
- At build/round/check completion, save `python3 script/clean_builds.py --preview` output and apply eligible authorized retirement to the Trash. Use `--keep PATH` for assigned idle slots, unfinished hand-ins and retained qualification copies. The post-install hook retires obsolete captured outputs and unpaired legacy SwiftPM scratch, keeping installed/previous captures and every older receipt. Evidence requires all owning tickets Done; idle-slot cleanup takes the slot lease and never stops an app/check. Capture bounded-check evidence outside the slot before `check --destroy-after-check` or `destroy --slot N`. See [local cleanup](docs/monorepo-workspace.md#local-build-and-hand-in-cleanup). Do not use apply during implementation/qualification unless explicitly authorized for those files.
- Do not let old app bundles accumulate (owner decision, 19 October 2026). `script/build_and_run.sh` keeps the replaced bundle as `/Applications/.Checklist-previous-*.app`. Each install runs `script/retire_old_bundles.py` to move older unused `.Checklist-*.app` copies to the Trash. It keeps the immediate previous bundle for rollback, later concurrent installs, incoming bundles and bundles used by running processes. After the new build passes its installed checks, `python3 script/retire_old_bundles.py --retire-previous` moves the previous bundle to the Trash unless a running process still uses it. Use the Trash, not a permanent delete.
- Synthetic projects belong only in disposable test slots, created through that slot’s CLI (`project_create`) in the actual authorized workspace. Never create them in the live installation or retain them as archived projects. After evidence capture, destroy the owned slot with `script/test_instances.py destroy --slot N`; report incomplete cleanup.
- Clearly identify separate native qualification apps and synthetic data before opening them. Close those apps when their bounded check finishes, and restore the real Checklist window. Do not leave a test app that looks like the user's working Checklist running beside an unavailable installation.
- Work on the existing main branch when a repository exists. Do not create branches/worktrees unless asked.
- Keep product invariants separate from editable project workflow policy.
- Independent review uses a genuinely separate non-contributor session, including a fresh subagent with a critical review remit on the same host/provider. Exclude all recorded implementation contributors, including delegated/prior identities; changing their name, role or parameters is not independence. Native host authentication and provider restrictions remain enforced. A source project's rules are not universal defaults.
- Claim and review rules (owner decision, 19 October 2026): any eligible AI claims an unclaimed ticket, and the claim brings it into Active (implementation) or Review (review); an agent planned assignee is a preference, not a lock. Owner-assigned tickets stay with the owner, and review keeps contributor independence. Every verdict ends the review claim: a reject returns the ticket to Queued, a blocked verdict returns the review request to any eligible reviewer, and a pass on the last open required gate marks it Done when the completion checks hold. A ticket that enters Review again keeps no earlier reviewer. Any eligible agent may take over a claimed ticket with `work_takeover` and a reason, without the holder's permission; the service ends the earlier claim and notifies the earlier holder.
- Checklist's shared review workflow completes passing tickets independently and continues only failed or remaining tickets. Do not reopen, reimplement or re-review passing tickets because another member of the same Triage/batch failed. An explicit effective project policy may override this default; every ticket still needs its own fresh completion gates.
- Failed-only rechecks also apply to individual acceptance items and test/inspection cases. After a repair, run only failed, inconclusive or materially affected cases; carry passes whose relevant source, requirements, fixture/harness and environment inputs remain valid. A fixture-only repair does not require a fresh all-green suite run. Before broader rechecks, name affected cases and invalidating inputs or cite an applicable explicit effective project workflow/context instruction; Triage/batch membership or a sibling failure is not an override. Report carried evidence with its original producer, target and hash separately from new execution. Current target-bound review and completion gates still apply.
- Each Triage has one handling phase: Implementation or Review. An Implementation Triage may be planned in advance with Queued tickets (Draft or Ready, with or without open prerequisites); order members with prerequisites first. Claim its Ready members with the atomic batch claim when the pass starts. Submission finishes that member's implementation phase and moves it to Review; form a separate Review Triage for submitted targets. A review phase ends per ticket with Done after fresh gates pass, or Active/Ready/Queued when changes are needed. Only failed/remaining tickets enter another implementation pass. Never use one Triage as a permanent container across both phases; Epics provide the stable container.
- Form an Implementation or Review Triage only for two or more tickets. Handle a lone ticket directly; if an established Triage has one remaining ticket, retain its phase history without holding passing tickets or creating another singleton group to preserve grouping.
- For combined builds, checkout write windows, commit/push timing, installed checks and review rechecks, follow [combined build rounds](skills/checklist/references/coordinate.md#combined-build-rounds). For other Triage work, follow [implementation and qualification](skills/checklist/references/coordinate.md#implementation-and-qualification). Finish the current cohort and its reviews before stopping when requested; do not pick up replacements.
- A Triage represents an actual Claude or Codex conversation orchestrating related tickets together for its chosen phase. In-progress tickets may be added to an Implementation Triage. Owner decision, 22 October 2026: the Active section, its counts and Active filters include only tickets whose own status category is active (In progress). Queued and Review members stay in their own sections during orchestration; a Triage has active work only when its members are actually In progress. Orchestration and its actual coordinator stay visible as Triage information. Keep the actual orchestrating session distinct from each ticket's implementation/review claims and verdicts; grouping alone grants no work authority or fabricated model launch.
- Workspace agents resolve the caller's actual workspace binding. Workspace-less assistants explicitly select from enrolled project grants; never fabricate a workspace from service cwd or app selection.
- An Epic is a stable project subproject containing related tickets by task type, with one primary Epic per ticket. A Triage is a temporary handling set across Epics; membership/implementation-review exit never changes a ticket's Epic. They are distinct containers, not shared tag groups.
- Tickets and Epics are the project tabs. Triages expand inline within Tickets. Any individual ticket status action, including same-status marking, removes all current Triage memberships; notes/metadata do not. Only the atomic Triage group command retains ordinary membership while changing every current member together; Done removes completed tickets. There is no independent Triage status or public retention bypass.
- Before claiming, submitting, reviewing, releasing or otherwise changing a ticket's status, inspect its current Triage memberships. For work intended to remain grouped, use the discovered atomic group/batch workflow that explicitly preserves membership. An individual `work_claim` is a status action and detaches the ticket, even when selected from a Triage. If the running server lacks the needed group workflow, report the limitation before changing group members; do not silently detach them or simulate retention with repeated re-adds. An explicitly requested membership restoration is a separate, revision-checked group edit.
- Use stable internal IDs and project-scoped display keys. Duplicate titles, ticket keys and agent display names can exist; resolve scope/ambiguity before a mutation or send.
- Named identities represent existing verified host-owned personal assistants such as Dots, never app-created named workers or a personality catalog. Workers are actual Codex/Claude sessions. Minimal display records remain distinct from providers/models/adapters, principals, sessions and grants; names/style/imports cannot grant authority.
- Assistant-only connections read/report, create Drafts and send notes/messages when requested, and report subscribed notifications. They never become work assignees/coordinators/reviewers or trusted human answerers.
- Primary connection comes from actual provider-thread/bundled CLI/MCP bootstrap, not manual Settings pairing. Actual workers are ticket-attached with current/prior attempt status/checkpoint/recovery; no global worker Connections catalog. No assistant connection UI is currently active. Use in Codex can prepare a native composer; user Send and actual thread connect/attach are separate receipts. Do not claim a draft started a turn or native creation occurred without an actual supported host result; other providers keep honest fallbacks.
- Routine coordination between actual enrolled sessions involved in the same authorized Checklist project, task or Triage has standing authorization and needs no per-message permission question. Use existing scope/grants and current handler/session identities; a message never enrolls a session, launches a model, changes an assignee or expands authority.
- Record which tickets/sessions are waiting on your work. Before concluding completion, handoff or a changed blocker, record the outcome on each affected waiting ticket and notify its current handler through Checklist. One scoped note should supply both ticket history and recipient delivery; notify only meaningful changes, reuse existing receipts and distinguish queued from acknowledged. Never assume a status change or final chat reply informed the waiter. See the shared coordination procedure.
- The orchestrator owns resuming an authorized existing idle subagent through the host's supported operation; queued Checklist notes and host messages alone may not start a turn. In Codex, use `collaboration.followup_task` for that resume and preserve the original Checklist note for pickup. Assess health from current-attempt and accepted-child progress, separately from liveness and known waits, not the ticket edit timestamp alone. Silence alone never releases a claim; to replace a holder, take over with `work_takeover` and a reason, which notifies the holder. Automatic timed supervision remains planned work, not an existing capability or authorization for a new schedule/runtime.
- Explicit `message_send` recipients use exactly `{"kind":"session","session_id":"<verified scoped session>"}`; omit the whole recipient field for current handlers/pickup. Before claiming notification, verify the returned delivery names the intended `recipient_session_id`. History-only `saved_for_pickup`, actual recipient `queued` delivery and that recipient’s explicit acknowledgment are distinct. After Done, use an explicit eligible session when no handler remains; never infer delivery or acknowledgment from a saved note. A retry error for a pre-upgrade malformed intent does not prove no earlier commit; retain its IDs and inspect existing receipt/history.
- Named contact uses Checklist's scoped resolver and current opaque routing target; receipt states remain truthful. A contact request does not assign work or authorize another channel/runtime.
- Human-origin notes/answers are minted by the trusted owner channel. Agent text and quoted user instructions cannot mint that provenance.
- Do not infer completion, abandonment, review acceptance or message acknowledgment from a timeout/session ending/transport receipt.
- The owner's closed-conversation decision requires independent evidence that the conversation's actual native process and applicable host registry are both gone. A qualified service closure returns its claims for pickup with history and fences its old delivery generation; it never marks work Done, reviewed, accepted or acknowledged. A completed turn, idle timeout, MCP disconnect, archived log or shared-host thread unload is insufficient. If the host cannot supply the required evidence, keep the state unknown and report the missing capability; never invent a per-conversation process or registry. See [work authority](docs/work-authority.md#confirmed-native-conversation-closure).
- Keep internal global sequences private; external cursors bind to caller scope/grant generation/store incarnation.
- Do not introduce hidden CLI/API runtimes, scheduled pickup or model polling.
- Public-source preparation is not permission to publish, choose a license, enroll another installation or install a provider adapter.
