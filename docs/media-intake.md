# Declarative media intake and list values

CL-109 adds internal Foundation-only helpers over the portable `MediaReviewSchema` values. They do not read files, query storage, authorize examples, capture bytes or publish media. Native owner composition and the later worker routes are documented below. The [prepared configuration schema](../contracts/media-intake.schema.json) and [animation example](../examples/media-intake.json) describe optional values beside a separately validated M1 type; they do not install a project taxonomy. The referenced type declares `character` and `animation_label` as material short text and `direction` as a material choice in the desired direction order.

`MediaIntakePlan` accepts selected-file **metadata**, literal TSV, or explicit typed scalar columns. Its assignments copy a column, supplied filename stem, zero-based source index, or literal-delimited stem token. The selected-file adapter supplies the stem; this helper never derives a grant or traverses a path. For `hero__walk__NE__take02`, token indexes 0, 1 and 2 give `hero`, `walk`, `NE`. Unknown operations and configuration keys are rejected. Missing/empty values, duplicate matching column IDs and invalid field values produce row diagnostics. Duplicate target assignments are rejected as an ambiguous plan. Formula-like text stays literal text. Numeric and Boolean fields accept finite numeric literals and exact `true`/`false`, then use M1 field validation.

There are at most 20 assignments and 64 columns per row (no row-count ceiling, CL-307), a 4 MiB TSV input, 4,096 UTF-8 bytes per stem, and 65,536 bytes per cell. A delimiter has 1–32 UTF-8 bytes with no controls; token indexes are 0–63. TSV uses a literal tab header and newline records, preserves empty cells and duplicate headers, allows CRLF and one final newline, and rejects excess cells. It has no CSV quoting convention. Stable row IDs come from the caller and must be unique by exact UTF-8 bytes. The transport must reject duplicate JSON keys before these parsed-object helpers.

`FrozenMediaIntake` is a value-only resume plan, not a durable capture receipt. A mapping revision remaps only failed/uncaptured rows. Captured targets, IDs and their mapping revision stay unchanged. Equal content or filenames never merge rows, discard duplicates or create best-of-N groups. A 296-row fixture preserves its 200 captured rows and offers exactly 96 remaining IDs after revision.

`MediaListConfiguration` allows eight visible field columns, two field grouping levels and three distinct sort keys. Each supplied metadata value must have the canonical tag for its declared field: text for short/long text, number, Boolean or choice. A scalar that validates but carries another tag (such as `.text("E")` for a direction choice) is rejected with an explicit field diagnostic before projection. Groups are ordered by their declared field values, with finite choices in declaration order; the animation example groups character then animation label and orders directions together. Sorts select a declared field or the built-in title/order. Text grouping and sorting use the same exact UTF-8 comparison, as do final stable-ID ties, without locale or Unicode normalization. Missing values have a separate final bucket, including descending sorts. The helper emits flat headers with counts and lightweight item rows from at most 1,000 supplied items. SQL paging, filters and native virtualization belong to later adapters.

`MediaHistoricalExamples` supplies an optional collapsed-by-default request descriptor. No request is produced until explicitly expanded. Match fields are capped at three; explicit immutable target IDs are an alternative capped at eight, with a page size of 1–8. Every request names project/type and requires later current authorization and historical-context labeling. The helper does not decide whether any target was accepted, reversed or still available. Show/Hide, columns, grouping and sorting never enter material definition bytes. Explicit adoption instead creates a `MediaMaterialReference` for a compatible material slot and exact project/type/target/hash; its length-prefixed bytes must join the future item's material basis. This value alone grants no publication authority or approval.

The dedicated helper tests exercise the actual animation example, exact-byte identities, limits, missing/ambiguous mappings, deterministic groups and partial-plan revision. They establish portable helper behavior only; they do not qualify native rendering, media decoding, filesystem grants or historical-example access.


## Registered durable capture boundary (CL-111)

The pure `FrozenMediaIntake` value remains distinct from durable records. The canonical capture registry now recognizes `media_intake`, immutable `media_intake_plan`, per-row `media_intake_row`, immutable committed `media_intake_chunk`, `media_bulk_operation` and immutable committed `media_bulk_chunk`, alongside media history/context/type families. Each future durable writer must record its same-project dependencies and exact immutable versions in `record_references` using the [reference schema](../contracts/media-record-reference.schema.json), and preserve explicit committed/failed/uncommitted row IDs in its receipt. Captured rows keep their original plan revision; later plan versions get distinct immutable IDs.

Project export and backup retain those complete records without interpreting an unfinished row as captured ownership. Only committed canonical attachments and media references count as captured media. Export lists uncommitted import job IDs and explicitly excludes staging bytes. Backup excludes media staging/partials too; any finalized uncommitted files retained for recovery carry `uncommitted_recovery` authority and explicit unresolved metadata. Those files cannot silently become a captured row, a resumed import or publication. Originals marked available must be captured successfully, while cleaned/unavailable states remain honest. Missing or foreign referenced revisions fail the capture. These internal registration and owned-fixture checks enable no intake/publication commands and claim no restore or old authority reactivation.

## Gated round writers and context reconciliation (CL-112)

`CommandRouter.executeMediaCommand` began as an internal seam; CL-116's native owner channel and the worker subset below now compose it. Its title-only type, round and item commands save Drafts without fields, a media folder or mandatory schema editing. A type name is a label. Workers can propose immutable type revisions through the internal seam, capture Draft targets and make attributed suggestions; only the authenticated owner channel adopts a type, publishes a manifest, approves applicable context, reconciles attention or records an owner decision. Adoption appends a separate owner receipt and retains the worker-authored revision/suggestion unchanged. Agent-supplied origin/author fields are refused.

Type revisions, candidates, item targets, round manifests, context snapshots, suggestions and decisions use the CL-111 registered canonical families and exact same-project `record_references`. Each immutable version has its own ID. Items retain a Draft target independently of the published manifest, so a worker's new take cannot replace the owner's active review. Publication previews exact Draft target IDs, item revisions and prospective bases; publication validates the whole selected set before appending any targets/manifest. Decisions name the manifest ID/digest, current item revision, exact published target, basis and explicit winning candidate. Missing answers remain Pending. Replacements and reconciliations append new history. A decision remains applicable when its complete per-item basis is identical; a changed sibling never resets it.

The internal text slice stores exact UTF-8, including Unicode spelling and newlines. Supplied candidate text must be a string; numbers, Booleans, nulls, arrays and objects refuse with zero canonical/event/receipt writes, while an empty string remains valid captured text. `MediaCanonical` v1 uses length-prefixed atoms, byte-ordered object keys, tagged scalar/array/object values and finite IEEE-754 numbers in POSIX `%.17g` form (negative zero is zero). Canonical content/basis/manifest bytes are retained as base64 with SHA-256; display JSON is not reserialized to reconstruct signatures. A basis includes candidate IDs/content, material metadata, M1's effective used/required material definitions, applicable approved context, rubric, completeness and the single-explicit-winner selection rule. Whole type revision IDs are provenance, rather than unconditional per-item invalidation inputs.

The narrow media applicability resolver uses explicit project/type/round/item scope. It does not infer media scope from task kinds or tags. Approved global project pins and an explicitly owner-adopted project brief enter immutable project-context snapshots. Owner project-context edits also create scoped media attention in the same transaction; worker edits and ordinary task notes do not become approved media instructions. A pre-existing meaningful brief/global pin set without media approval blocks first publication with `MEDIA_PROJECT_CONTEXT_REQUIRED`: the owner explicitly approves the observed project revision through the internal context command. An unrelated owner edit of pins does not adopt an unchanged agent-proposed brief. Rubric and requires-action direction revisions retain their source records. Scope removal affects both the former and new round scopes even before a Draft has items; later publication remains fenced until trusted reconciliation.

Every round read returns an opaque observation MAC bound to round/context/manifest/attention, adopted type, caller/project grant scope, workspace, session authorization generation and store incarnation. Publication, suggestions, owner decisions, suggestion adoption and closure validate it before writing. Relevant approved changes leave attention pending: an old observation is refused with `MEDIA_CONTEXT_CHANGED`; a refreshed observation still refuses with `MEDIA_CONTEXT_ATTENTION` until the owner reconciles the exact attention set. Both failures change zero records/events/receipts. Keep records a reasoned exception for this round; migrate appends a context and manifest and stales only changed effective item bases. Previously kept directions do not silently return during an unrelated migration. Cosmetic labels and unused optional definitions cause no attention or decision invalidation. Newly required/used material changes preserve the captured historical values, mark incompatible targets incomplete and stale affected bases.

An adoption that supersedes pending type attention appends its own attention even when it returns to the pinned effective basis. Type migration resolves the current owner-adopted head, retaining every intermediate revision and reconciliation dependency; an obsolete intermediate adoption cannot win. Returning to an identical effective basis preserves applicable decisions. A previously reconciled Keep remains pinned during unrelated context migrations.

Media mutations prepare their canonical rows, exact hashes, complete dependency validation and encoded result before the object gate and SQL writer, using a read-only snapshot and a copy-on-write overlay on that snapshot's connection (CL-307). The overlay reads only the records the command touches through the store's indexes, and validates every row it writes against that row's declared dependencies, resolved on the same snapshot; it never copies the whole project. There is no project-size, record-count or payload ceiling: preparation time and memory follow the touched records, not the project size. The transaction rechecks current access and command intent/receipt, then checks SQLite's `data_version` on the same observing connection after acquiring the writer. An intervening commit, including a same-revision edit, refuses with `MEDIA_CONTEXT_CHANGED`; retries prepare afresh. Only prepared media rows and their atomic event/receipt are written. Retained text history is never decoded or hashed under the writer. This conservative fence can also require a retry after an unrelated concurrent commit.

Direct item input accepts inline text candidates only. A path, digest, external reference or arbitrary attachment ID refuses with `MEDIA_CAPTURE_REQUIRED`; it cannot stand in for captured media. CL-113 now composes prepared managed capture, ownership handover, frozen intake and publication through the internal seam described below. No large original read/copy/hash occurs inside these writers. Reads are bounded to 1,000 items per round for this internal fixture seam; production paging, bounded native renderers and public activation remain later composition work. These tests do not qualify app UI, native owner authentication, restore, installation compatibility or playback.


## Frozen selected-file and paste capture (CL-113, internal only)

The internal router adds `media_intake_preview/get/revise/confirm/capture`. CL-116 subsequently activates the native owner route, and CL-331 activates the same frozen intake for workers preparing Draft rounds. This foundation's storage checks remain distinct from native navigation/rendering and installed evidence.

Preview accepts exactly one explicit `sources` list (one or more selected regular local files; no file-count ceiling, CL-307), `text` (nonblank literal lines, at most 1 MiB), or `tsv` (the CL-109 literal grammar, with distinct headers and a required `text` column). TSV may explicitly supply `title`, `slot` and `group`; other scalar columns can use the finite CL-109 field mappings. One file/line defaults to one item/candidate. File order uses numeric filename comparison in a fixed POSIX locale, exact UTF-8 filename ties and selected-source index; pasted input keeps its order and exact line text, including a CR before LF. No formulas execute. The original filename/source index remains attributed. Preview inspects at most 1 GiB of originals, each within the existing 500 MiB importer cap; text is at most 256 KiB per row. Every readable source's observed size is charged before reading or decoding, including unsupported, undecodable or subsequently changed sources. Reads cannot exceed that reserved size. Exactly 1 GiB is permitted; a source exceeding the remaining allowance refuses the whole preview with `CAPACITY_EXCEEDED` before that source is read, with no intake/row/event/receipt writes. Supported byte-only validation is ImageIO-decodable images up to 16 megapixels, exact UTF-8 `.txt`/`.md`, and local PCM RIFF/WAV (one/two channels, 8/16/24/32 bits, at most 192 kHz and 30 minutes). Self-contained MP4/QuickTime movies are recorded as video (CL-117): byte inspection refuses external data references, reference movies, fragmented movies and tracks other than video/audio, and applies the shared playback budget below. Other codecs remain explicit unsupported rows. No playlist, remote reference, watcher, recursive scan or source deletion is used.

Every row reports `valid`, `duplicate`, `missing` or `unsupported`, the source hash/size when valid, proposed title/order, `slot_id`, `group_id`, a resulting `groups` preview, mapped metadata/diagnostics, and `disposition=include|skip|unresolved`. A single compatible slot is supplied; ambiguity requires an explicit slot. Equal hashes flag later rows without dropping or grouping them. `media_intake_revise` takes the intake revision and explicit row resolutions (`row_id`, include/skip, optional title/slot/group) and/or a finite mapping. Only uncommitted rows change. A new immutable plan ID, monotonically increasing plan revision and canonical digest capture the full mapping; committed rows and their original mapping revisions stay unchanged. An explicit shared group creates bounded candidates of one item, with compatible metadata. Rows of one group that fill different slots join one candidate: the n-th row of each slot in frozen plan order joins candidate n (for example a Take row and a Reference row make one candidate with both slots), whatever the capture order; rows with the same slot stay separate candidates, and the candidate limit applies to the largest per-slot row count. Group IDs compare exact UTF-8 bytes; the first included row in frozen order supplies the initial item title/order regardless of capture/chunk order; later plan revisions preserve an already captured item label/order. `media_intake_confirm` names the current plan ID/digest and expected intake revision; every row must have an included/skipped resolution and a compatible slot before capture.

Durable paste preview counts LF and CRLF records with the same literal parser, including a final CRLF; it never uses Swift character-suffix matching to infer the row count. TSV requires nonempty text in every row. Missing mapped columns/values, invalid mapped choices (including direction), extra cells and malformed mappings refuse the whole paste with `INVALID_INPUT` and a row/field or grammar reason, before any intake, plan, row, event or command receipt is written. Portable schema errors from paste or selected-file explicit metadata are translated to definite command errors at the media command boundary. Selected-file mapping diagnostics remain editable preview rows; the pure CL-109 helpers still return row diagnostics, and direct captured candidate text retains its separate empty-string contract.

Required IDs are nonblank bounded strings: preview/publication require `round_id`; get/revise/confirm/capture require `intake_id`; confirm/capture also require `plan_id`. Capture takes one internal chunk of 1–200 distinct included `row_ids`; callers repeat capture until no included row remains (the app does this automatically), so an intake of any size is captured without a visible limit (CL-307), and each supplied revision resolution requires its own `row_id`. Missing or malformed IDs return `INVALID_INPUT`; unknown scoped records return the ordinary lookup error. Preview resolves its round before source reads, and capture validates the intake, exact confirmed plan and row selection before reserving any intent or preparing files. Candidate sets are ordered by stable candidate ID in every intake target, independently of source/capture/chunk order. Retaining the same IDs, content and material context in a different input order keeps the canonical content/review basis and any applicable owner decision.

`media_intake_capture` names the intake revision, confirmed plan ID and at most 200 original row IDs. Reads/decoding/hashing and command-bound staging/finalization run before canonical preparation and the writer. Selected sources are revalidated against frozen SHA-256; changed/missing rows receive a bounded error and create no item. Managed final bytes are checked again against the frozen media kind/hash, then the writer checks prepared file identities/presence only. The command reserves its principal/UUID intent before file work; each row retains its own original import UUID, and a finalized uncommitted copy can be verified/recovered under that same identity after the chooser file disappears. Canonical attachment, intake-to-Draft holds, candidate/target/item, row, immutable chunk and both row-import and enclosing command receipts commit together. Failures leave only attributed pending recovery bytes. Cancellation fences remain CL-110's existing per-import protocol; stopping between chunks preserves committed Drafts. A 200-of-296 stop returns 200 committed and 96 remaining row IDs; resume or a plan revision cannot import the 200 again. External originals are never removed.

Publication requires all included rows of every intake in the round to be committed and selected; skipped rows stay explicit. It validates the current owner/context token, all exact item/target/basis selections and every active owner/reference plus managed original before the writer. Prepared target owners and independent exact references replace Draft holds in the same transaction as new targets, one immutable manifest, event and command receipt. Previously published owners retain history holds. The writer rechecks the original observations under the shared deletion gate and the same snapshot-change fence as CL-112; failure at owner/reference creation, source release, target, manifest, round head, event or receipt preserves the prior state. No large reads, copies, decoding, retained-history hashing or dependency walk runs under the writer.

These are owned-store router tests, not native UI, playback, installation compatibility, restore or power-loss qualification. Intake plans/rows/chunks use only CL-111's registered canonical families and dependency graph; there is no migration or second persistent store.

## Exact decisions and failed-only bulk receipts (CL-114, internal only)

Only the authenticated owner channel appends `media_owner_decision`; an actual enrolled worker can append only `media_suggestion`. Supplied author/origin fields and quoted owner text confer no authority. `media_adopt_suggestion` validates the exact current published target/basis, copies the suggestion's disposition/selection/note, and appends a separate owner action with `adopted_suggestion_id`; the original suggestion never changes. Each decision retains the observed item revision, exact target/candidate set, manifest/digest, canonical basis bytes, material/context/type provenance and an explicit predecessor when reversing a prior action. The item's `last_decision_id` is the current head; immutable history is not ordered by timestamps.

No answer, comment, suggestion, hidden row or bulk preview accepts an item: its disposition remains Pending. Acceptance requires one actual current `winner_id`, including with one take. The receipt labels other candidates `not_selected_candidate_ids`; no ticket is created for them. For multiple takes, Changes requested requires explicit Boolean `none_fit=true`, with no winner. Needs look remains an explicit deferral without a selection. Exclusion requires a note. A suggestion follows the same selection grammar; adoption cannot override its choice. Missing or stale revision, target, basis, manifest or observed context refuses the whole 1–200-item direct decision selection with zero decisions/events/receipts. A sibling failure or successor target with an identical complete per-item basis preserves the existing passing decision; changed material derives Stale. No code-review or task-completion authority is produced.

`media_bulk_prepare` freezes one or more ordered exact selections (no count ceiling, CL-307) plus the observed round/context/manifest and intended action. It validates all entries before writing one immutable `media_bulk_operation`. `chunks` partition the original order into at most 200 entries each and contain stable chunk IDs and original command UUIDs. Preparing accepts nothing. `media_bulk_apply` names only `operation_id`, `chunk_id` and that chunk's original `command_id`; it never consults a filter or refreshes the original observation. All selected item revisions are checked before any decision is appended. A committed chunk atomically saves its immutable `media_bulk_chunk`, decision IDs and operation/chunk/command links, item heads, event and ordinary command result. A stale chunk records `state=failed`, its error code and all selected IDs, with zero decisions; a failure of the enclosing transaction leaves it uncommitted. All canonical preparation, hashing and dependency validation remain outside the object gate/writer.

After a lost reply, read `media_bulk_get(operation_id)` and reconcile the original chunk/command receipt; an identical retry returns the original semantic result even after a later owner reversal. A fresh UUID cannot reapply a chunk. The view preserves the immutable original `selection`, `action`, `intent`, digest, prepare command and chunk command IDs, and returns each receipt plus separate committed/failed/uncommitted/superseded IDs and counts. A failed receipt also replays unchanged. To retry failed or uncommitted chunks whose observation changed, the owner inspects current targets and submits a new `media_bulk_prepare` with `supersedes_operation_id`, the same round/action, and exactly complete unresolved original chunks. Committed or already refreshed selections are refused. The new operation retains the parent and its receipts as exact dependencies; the old remainder is fenced. This explicit refresh may update failed item revisions/bases/winners without changing any earlier passing decision. Item revision checks also fence a never-committed original chunk after any later owner action.

For example, a 450-item operation freezes chunks of 200, 200 and 50. If the first reply is lost, the middle chunk conflicts, and the last commits, reconciliation reports 250 committed and 200 failed. The refreshed operation selects only those original middle 200 IDs and links the earlier operation; it never selects the 250 passes again. A reversal of one of those passes stays current even if the first command is replayed. Original operations, failed/committed chunk receipts, suggestions and owner decisions are immutable, with exact same-project dependencies captured through CL-111 export/backup. No new record family, table, migration, public dispatch or app call site is added. Cross-round successor inclusion/rework and native UI remain later composition work.

## Bounded grouped queries and approved examples (CL-115, internal only)

`media_item_page` and `media_item_counts` read canonical records through the internal seam. A page returns at most 100 lightweight rows: exact item ID/revision, immutable target ID, title/order, selected visible metadata, disposition/decision observation and a flat `group_path` with prefix counts. Visible metadata and group values preserve declared JSON scalar types: Boolean false/true remain distinct from numeric 0/1, and missing values are null. Published items display the published target; unpublished items display their Draft target. The CL-109 list configuration controls up to two grouping levels, three sort keys and eight visible columns. Choice groups and `declared_choice_order` follow the declared order; missing values stay last, text compares exact UTF-8, and exact item-ID bytes break ties. Filters allow explicit dispositions, up to three typed metadata equalities and at most 1,000 hidden item IDs. Filters and display configuration write nothing and never change material meaning.

The first read selects the round's lightweight item/target references in SQLite, with no item ceiling (CL-307); candidates, originals and canonical content/basis payloads are not decoded. Counts decode only this bounded reference index and return no rows. Only the selected at-most-100 targets' display fields leave SQLite. A sealed, authenticated 24-hour cursor retains the ordered reference index and decision observations, so live inserts and successor edits cannot skip, duplicate or reorder that window. When the index is too large to seal (more than 900,000 encoded bytes), the cursor keeps its digest instead: each later page recomputes the index and asks for `CURSOR_RESET` if it changed. Rows/counts are explicitly `snapshot=true` and require a fresh current observation for any decision. A new first page reflects later changes. Tokens bind the exact request, principal, project grants, workspace, session authorization generation and store incarnation; changes of authority/query, expiry or tampering require `CURSOR_RESET`. There is no persistent cursor row or retained SQL snapshot.

`media_approved_examples` defaults to collapsed and performs no historical selection until both configuration `enabled=true` and `expanded=true` (Show) are supplied. Matching uses at most three declared metadata fields, or at most eight explicit target IDs. Only other rounds of the same project/type are searched; a digest is never an access key. The deterministic reference window is capped at 64 candidates, paged at 1–8 per Show. `capped` reports further candidates outside that window; invalid/reversed entries can leave a short or empty page, and the cursor still advances. Each page rechecks the exact owner-accepted decision head, winner, historical manifest/target basis, current published basis/context and all target originals' active typed references and availability. A pending context reconciliation, reversal, changed basis or missing original excludes the example. Only the winning candidate's slots are returned with historical context/type/decision IDs, the label “Historical owner-accepted example — no current approval”, `display_only=true` and `grants_current_approval=false`. Show creates no file lease and reads no managed original bytes.

`media_example_read_lease` separately names an exact shown target, decision and winning original reference in the current round's project/type. Basis validation and hashing precede the writer. Under the shared deletion gate, a short transaction rechecks current authority, the accepted head/round token, typed reference and original presence, then creates the existing caller/generation/incarnation-bound 1–300-second reader hold. Raw attachment IDs, digests, foreign references and reversed decisions confer no lease. `media_example_read_release` releases only the current caller's lease. Native consumers must use the existing managed-original read/integrity contract; a lease is neither an owner decision nor proof of decoded playback.

Only the owner can explicitly `media_material_reference_adopt` an exact accepted target/decision/winner slot into a compatible material slot of an observed published item. The command fences both item and round revisions/context/manifest, refuses an unpublished successor, appends an immutable target and manifest, and retains exact source target/decision dependencies. The ordered `material_references` array joins that item's canonical content basis; ordinary subsequent item edits and context shaping preserve it. A changed material basis derives Stale while retaining the earlier decision and unaffected siblings. Hiding, grouping, sorting and showing a reference never perform that adoption. All six query/lease/adoption commands remain absent from public dispatch, catalog, CLI and app; the full app snapshot is unchanged. No table, record family or storage migration is added. Owned query/lease fixtures do not qualify native UI, playback or an installed upgrade.

An internal target's `material_references` entry contains `project_id`, `type_id`, exact source `target_id`/`decision_id`/`candidate_id`, `source_slot_id`, destination `slot_id`, declared native `kind` and the exact slot `sha256`. Entries are ordered by destination slot-ID bytes. Adopted slots enter the effective used material definition; removal or an incompatible kind in a later type revision makes the shaped target incomplete rather than silently dropping the reference. The target also declares exact immutable source-target and owner-decision dependencies in `record_references`. No reference array is accepted through direct item input or ordinary list configuration.

Example and lease eligibility also follows adopted material references through at most 64 distinct same-project/type historical targets (at most 64 typed original references each). This bounded metadata/presence walk reads no blob bytes. A missing/released original or an over-budget dependency graph excludes the example and refuses its lease. A later source decision reversal does not rewrite an explicitly adopted immutable material reference; the offered target still needs its own exact current accepted head.

## Rework links, closure and successor rounds (CL-118)

CL-300 routes these owner-only commands through the native owner channel: `media_rework_create`, `media_round_finish` and `media_round_successor` are in the native owner allowlist, and `media_rework_preview` is a native owner read. They stay out of public dispatch, tool schemas, catalogs and the CLI; a worker or assistant caller is refused.

- `media_rework_preview(round_id,epic_id,items[{item_id}])` reads an Open round. Every selected item must have a current applicable Changes requested owner decision; Accepted, Pending, Needs look, Excluded and Stale items refuse the whole selection (`MEDIA_REWORK_INELIGIBLE`). The preview shows `create` or `reuse` per decision, Draft readiness, no assignment and a `preview_digest`.
- `media_rework_create` repeats the observation fence (`expected_revision`, `observed_context_token`, `manifest_id/digest`), the chosen same-project Epic, each item's `expected_revision` and exact `decision_id`, and the `preview_digest`. A changed preview refuses with `MEDIA_REWORK_PREVIEW_CHANGED`. One `media_rework_link` exists per decision: a retry or a later selection of the same decision reuses that link. A new decision on the same item gets its own link. Tickets use ordinary ticket capture in the round's project and the chosen primary Epic, with Draft readiness, Queued status and no assignee, Triage, session, attempt or model launch. No media decision, round or sibling item changes. This command writes in one direct writer transaction because ordinary ticket capture cannot run in the media-only preparation workspace.
- `media_round_finish` requires a current explicit Accepted, Excluded or Changes requested disposition for every published item. Pending, Needs look and Stale refuse with `MEDIA_UNRESOLVED`. Changes requested also needs a link to its current decision or an owner `no_follow_up_reason`. The closed record stores `closure` counts (`accepted`, `excluded`, `changes_requested`, `rework_linked`, `no_follow_up`) and `rework_link_ids`.
- The round view and owner header add a live `rework` projection (link rows with ticket key/title/status category and `open/closed/unavailable` counts). A Closed record can show open rework. Rework creation on a Closed round refuses with `MEDIA_ROUND_CLOSED`. A rework ticket's status never writes a media decision, round or review gate, and a media decision never satisfies that ticket's own completion guards.
- `media_round_successor(source_round_id,…,title,items[{item_id,carry_decision_id?}])` creates a Draft round with only the owner-included items. A carry must name the item's current applicable decision (`MEDIA_BASIS_CHANGED` otherwise). It writes a new decision with `carried_from_decision_id` only when the new target has an identical complete review basis. With a changed basis the item records `stale_predecessor_decision_id` and shows Stale after publication. Items with no carry start Pending. The source record is not changed.

The media review workspace (CL-300) offers these commands on the selected round:

- Create rework Drafts (Open round): toggles list only the loaded Changes requested rows. The owner chooses a current Epic and previews; each preview row says "Creates a Draft ticket" or "Reuses its existing rework ticket". Create repeats the exact preview (observation fence, Epic, item revisions, decision IDs and `preview_digest`). A changed selection or Epic drops the preview. The preview record stays under Technical details.
- Close this round (Open round): Pending, Needs look and Stale counts each show their own blocking text and disable Close round. The service still refuses a Changes requested item without a current link or no-follow-up reason (`MEDIA_UNRESOLVED`). Close round asks for confirmation first.
- Rework status: Open and Closed records list each linked ticket with its live state (Open, Closed or Unavailable) and the closure counts.
- Start successor round (Open or Closed round): the owner includes items one by one and can carry the current decision of an Accepted, Excluded, Changes requested or Needs look item. Pending and Stale items have no carry. The new Draft round opens after creation. Row, comparison headline and counts use one disposition label, so a changed item reads Stale in each view.

## Native owner composition (CL-116)

The historical “internal only” sections above describe their foundation delivery boundaries. CL-116 exposes an explicit subset through authenticated native-owner `CommandRouter.handle`; [the command contract](mcp-contract.md#cl-116-native-owner-media-channel) lists every name. The later worker subset below has separate closed schemas and safe projections; assistants have no media catalog. No agent-origin input can select human provenance. Native app reads/writes use `ChecklistStore.request` → `NativeServiceTransport` → `ChecklistClient.callAsync`; writes reuse the persisted command UUID/reconciliation path. There is no new store, table, migration, watcher or model runtime.

Navigation/header/item/publication projections avoid loading a whole round's candidates into the item list. Item pages remain 100 rows; detail resolves one exact current published target (or Draft when unpublished), up to eight candidates, original-reference availability and last decision. Round pages use a bounded 100-row offset window, explicitly refreshed after changes. Native image reads resolve a same-project target/reference, acquire a short reader hold, read/hash at most 8 MiB outside the writer and release the hold; image decoding separately limits source pixels and display dimensions. The app admits at most two outstanding read/decode jobs and retains up to eight current slot images plus one historical display buffer; switching originals or historical pages releases prior buffers. Historical-example metadata includes actual owner-decision time/origin/session and round/source attribution. Exact example image access still uses CL-115's target/decision/reference lease. UI toggles, grouping, columns and ordering never become material adoption.

Title-only setup remains Draft. Native starters supply optional bounded slots/fields; TSV metadata columns and the optional filename-token mapping use CL-109's finite grammar. ## Worker preparation, owner publication and decision reporting (CL-331–333, CL-336)

An enrolled worker can prepare a complete round through public MCP/CLI commands with its current project grant and actual workspace binding. `media_type_list` discovers the project's adopted enabled type IDs and schemas (at most eight), and `media_type_get` reads one exact type; the owner need not copy an ID. The worker calls `media_round_create(type_id,title)` to save an attributed Draft. It cannot create a round against a Draft/unadopted or retired type. The public worker subset does not include type editing/adoption, direct item mutation, publication, context approval/reconciliation or owner decisions. [The worker command contract](mcp-contract.md#worker-media-preparation-and-decisions-cl-331-cl-332-cl-333-cl-336) lists every input and bound; `ChecklistContracts.MediaWorkerContract` is shared by catalog and validation.

The worker supplies explicit workspace files to `media_intake_preview` with scalar `columns` and a finite type-defined mapping. For an animation type, it can map the columns `character`, `animation_label` and `direction` to the corresponding declared fields. Filename tokens are an explicit mapping alternative. Literal text/TSV use the same frozen grammar. Source paths must be regular selected files inside both the enrolled workspace and project; symlinks/path spelling cannot expand that grant. Preview creates no published review or decision. It retains stable row IDs, source hashes, diagnostics, explicit grouping/slot choices and an immutable plan digest.

The worker resolves its uncaptured rows with `media_intake_revise`, confirms the exact current `plan_id`/`plan_digest` at `expected_revision`, then uses `media_intake_capture` in remaining-only chunks of 1–200 original row IDs. Capture copies and hashes managed originals before canonical writing, uses the existing typed reference registry, and records actual agent provenance on intake, items, targets and receipts. `media_intake_get` resumes only the calling worker's own scoped intake; no other worker's selected source paths are disclosed. Worker intake writes require a Draft round and an enabled adopted type on every call. An Open round's published review and owner decisions cannot be changed by this route. Unknown outcomes use the original command UUID; changed bytes or plans require a fresh explicit preparation rather than substituting an original.

The owner opens the prepared Draft in Media review and presses **Publish** once. That action obtains the exact publication preview and sends the frozen item revisions/targets/bases through the existing owner-only publication guard. The owner performs no import preview, revise, confirm or capture step. Workers never publish, even when agent project-rule changes are enabled. Missing capture, incompatible material or outstanding approved-context attention still refuses; the worker repairs preparation and the owner retains the context/publication decision.

`media_round_get(round_id,limit?,cursor?)` returns at most 100 safe item rows, also named `items`, with the round revision/observation token, manifest ID/digest, schema-defined metadata, exact item/target/basis/candidate IDs and snapshot dispositions. It includes safe latest decision fields but excludes private approved-context source bodies and owner-channel principal/session fields. A suggestion uses the current round/context/manifest fence plus exact item revisions/targets/bases. `media_suggest` appends actual `media_suggestion` records with worker attribution. The owner sees those beside the selected item, separately from the last owner decision; their stale-basis label is display context. Suggestions never move the decision head or satisfy a task review gate. Only a separate trusted owner action can decide.

`media_decision_list(round_id,limit?,cursor?)` returns at most 100 append-only owner-decision `rows`, including `id`/`decision_id`, item/target IDs, disposition, optional winner/none-fit/note, `created_at` and its `decided_at` alias. Reversals append new records with `supersedes_decision_id`; old action/time values stay immutable. Its opaque `cursor`/`next_cursor` remains reusable at the end, allowing the worker to copy only later decisions into its own records. The cursor binds project, round, caller, current grant/session generation, workspace and store incarnation and exposes no global sequence. A decision history row does not assert present applicability: use a fresh round item's disposition to distinguish Pending/Stale and the latest owner action. No private owner principal/session or approved-context body appears in decision results.

Component tests use owned templates and mocks. The runner must still observe worker discovery/preparation through the composed service, a three-item attributed Draft with metadata and managed originals, a refused foreign grant and owner action, the single native Publish press, suggestion visibility and the owner's playable item review in its authorized disposable slot. These routes introduce no storage family, migration, backup/startup change, hidden runtime, enrollment or schedule.

## Bounded video and audio comparison (CL-117)

The owner comparison shows declared `video` and `audio` slots with native playback. Project Settings > Media review offers the native starters "Video takes" and "Audio takes": slots `take` and `reference` of that kind, layout `video_compare` or `audio_compare` with `primary_slot_id: take` and `reference_slot_id: reference`, and no other keys. Intake offers "Include as …" only for valid or duplicate rows whose measured `media_kind` matches a declared slot; other rows offer Skip. A take is compared only when its captured `media_kind` matches the slot's declared kind and its typed original is available. Each slot has a role label: the layout's `reference_slot_id` is "Reference" and every other slot is "Candidate N"; historical examples add "Approved example ·". Technical details show the exact slot, reference, attachment, target, decision and SHA-256 IDs and the measured facts of each loaded take.

A load requests a fresh caller-bound reader lease (`media_original_read` with `representation:"lease"`, or `media_example_read_lease` for an approved example). The app copies the leased bytes to a private temporary file, checks size and SHA-256 against the slot, and releases the lease after the copy, also on refusal or cancellation. Open original requests a new lease every time and opens a separate working copy; edits never change the reviewed original or record a decision.

Budgets (`MediaPlaybackBudget`):

- Original: at most 500 MiB.
- Video: at most 600 s, 3840×2160 pixels (8192 px per side) and 36,000 frames.
- Audio: at most 1,800 s.
- At most 2 loaded takes within a 1 GiB copy cache, 1 preparation at a time and 1 playing take. A take that starts, also from its native controls, pauses all other takes.
- Native probe: 15 s. Reader lease: 60 s.

A take outside a budget shows a plain refusal. A change of selection, project or example display, or a slot that leaves the view, stops preparation and unloads its take.

An unavailable original shows an honest outcome from the service's `unavailable_reason`: `cleaned`, `missing`, `changed` or `reference_unavailable`. No cached preview replaces the exact original. The portable schema holds typed IDs and digests only: it refuses Swift class, path, bookmark, player/playback state and renderer keys for video and audio slots.


## Mixed animation comparison and owner notes (CL-334, CL-335, CL-337)

A `video_compare` layout may declare `reference_slot_ids` (at most seven distinct declared slots), instead of the legacy singular `reference_slot_id`. References may be images or videos; the primary remains a distinct material video slot. The eight-slot type bound remains. The comparison orders the take first, then every declared reference in an adaptive grid, and labels each reference independently. Selected-file rows sharing an explicit group and filling different slots join the same candidate, so one take and several references publish as one item. Loading a reference image retains the other current images (up to eight, with two concurrent reads/decodes); images load automatically when the comparison appears. Historical examples retain their separate one-image display bound. Video references remain playable within the two-copy/one-playing-take budget.

The optional native starter “Animation takes (12 fps)” declares `take` (video), `model_sheet` and `concept_art` (images), and `reference` (earlier video), with this layout:

```json
{"kind":"video_compare","primary_slot_id":"take","reference_slot_ids":["model_sheet","concept_art","reference"],"loop":true,"frame_rate":12}
```

`loop` is a strict Boolean (default false); `frame_rate` is an optional finite number from 1 to 240 fps. They apply to the primary video take; reference videos retain their source speed. Historical examples also play at source speed, explicitly labeled because their historical playback settings are not returned by the example query. Looping uses a retained native queue looper, without replacing the displayed player or seeking at each end. Pause retains the queue; unloading releases it. Nonlooping videos/audio retain their single item and rewind after completion so native Play can replay them; a seek completion never resumes playback after Pause. A declared rate changes playback speed by declared/source nominal fps. Unmeasurable source rates or speed above 2× refuse with a request for a video rendition encoded at the stated rate. Frame sequences must be supplied as self-contained video renditions; raw image-sequence files are not a new slot kind. One Play press obtains/verifies the original, probes it and starts playback. The declared frame rate participates in material meaning; loop is presentation only. New present reference roles participate in material definition bytes; existing definitions retain their exact bytes.

The native owner actions are **Accept**, **Changes requested** (with a nonblank owner note), and **Needs look**. They map the earlier animation page's Accept, Redo/Other pose and Look at it respectively. They use the existing exact-target `media_decide` envelope and native owner authority. Typing a note makes no decision. The per-project/item note saves on every edit in the existing local window preferences, remains after a decision, and restores when the item or app reopens. Deleting the note also saves automatically. Changes requested includes that note in the owner decision; Accept and Needs look may also include it. These local notes do not create a service record before an explicit owner action.

Native qualification must observe the mixed images/videos together, repeated 8-frame/12-fps playback without a poster flash or gap, Pause, all three owner outcomes, and note restoration after restarting the app. Model and native AVFoundation tests alone do not establish those UI observations.
