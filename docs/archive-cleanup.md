# Local attachment cleanup

Capture and note composers accept selected files, dropped local files/images and pasted clipboard images. The selection records a managed-copy or external-reference choice. Clipboard images use a bounded private PNG staging file and a managed copy. Selection drafts are specific to the window, project, task and store generation. A successful, matching attachment receipt clears only that selection; unknown outcomes retain its original command ID for reconciliation. A managed import keeps the source file. Directory recursion and remote/chunk uploads are not supported.

Project **Archive storage** settings contain the complete preset, large-original threshold and retained-ticket budget. Defaults are 20 MiB and 50 MiB; Keep originals disables selection. Threshold and aggregate budget are independent: smaller originals can be selected largest first until the budget is met. Settings edits check both the project and settings revisions and preserve unrelated workflow settings.

The archive preview records the exact task/settings revisions and selected immutable attachment IDs, hashes and logical lengths. It validates every retained envelope in the current SQL observation, preserving the original identity/revision tokens and ownership fields while SQLite checks the complete JSON and the adapter checks its complete UTF-8. One byte-exact pass collects references to stored record IDs and the ticket’s original paths, including foreign projects. It then decodes full payloads only for reachable records; task liveness and current review heads remain available for hold decisions. Unrelated captured-file lists, notes and evidence are not decoded or indexed in Swift. The resulting reverse index belongs only to this observation and is never reused across commands or deletion checks. Captured-file metadata still participates in the same reference checks, and preview sizes come from recorded immutable logical lengths without reading captured file bytes. Archiving and the durable cleanup job commit together. A 30-second cancellation window precedes execution. Cancel remaining cleanup and Undo archive preserve all originals not already removed. Unarchiving restores ticket/history state; it cannot recreate deleted bytes.

**Archive…** presents a sheet immediately and starts a retention preview only for that open sheet. Selecting a ticket makes no speculative retention read. While the preview is in flight or has failed, the sheet shows loading or retry information and disables archive actions; it never substitutes zero totals. A matching result fills the readable totals, holds and cleanup choice. The result is bound to the store, project, ticket and settings revisions. Any observed service change invalidates it, including cross-ticket or cross-project holds; an open sheet refreshes against the new observation. Closing and reopening starts a fresh read, and leaving the detail discards late replies. Confirmation retains the service's revision, preview and current-hold checks. This UI presentation changes no preview results and establishes no native latency guarantee under load.

The service runs a bounded synchronous maintenance pump after import reconciliation. Archive work admits at most eight job items and removes at most one original per pump. A separate utility maintenance continuation prepares a bounded batch of purge or Done-evidence objects outside the writer, then removes a bounded subset through the existing deletion engine. A durable cursor and exact deletion intent survive restart. The service arms a one-shot continuation for unfinished bounded work or a real grace/reader deadline. Permanent item holds do not create an indefinite polling timer. Infrastructure failures defer for a 60-second one-shot retry and cannot disable the independent ticket-cleanup lane. Two matching object failures suspend the item; an explicit retry by the trusted owner or an enrolled worker while `agent_rule_changes=allowed` starts a new cancellation window, with the actual actor’s provenance.

Execution obtains the store object gate before the SQL writer, rereads the complete persisted reference graph and current retention settings, commits a deletion intent, then checks current references again in the final writer transaction. Current work/verification, human inspection, review/build references, reader/backup leases, shared references, pending imports, Keep original and unknown or invalid metadata retain the original. The gate stays held through descriptor-relative no-follow hash/identity checks, unlink, directory flush and the recorded outcome. Archive jobs admit only exact managed originals below `objects/`; archive cleanup retains previews. Permanent ticket purge shares this permit and unlink through durable `ticket_object_delete` intents. It also admits exact previews, captured-source files, manifest sidecars, verified captured link text and exactly inventoried source-build cache files. Purge uses stricter remaining-record ownership checks and retains reader-held and media-owned bytes. Ticket-byte cleanup retains live-only bytes until a completed backup independently holds the exact path, kind, digest and length. A verified completed copy or backup-owned hard link permits removal of the live pathname; it is not a live-file hold. The active backup-capture barrier still prevents unlink while capture is in progress. External originals and workspace files are never cleanup targets.

Archive with cleanup and `attachment_cleanup_preview` never run the reference scan inside the store's write transaction (CL-344). The command first scans the complete reference graph, with every envelope validation and the 250,000-row and 2,000,000-edge bounds, on a read snapshot. A connection-local journal on the writer meanwhile records each changed record and the text values of each new payload. The write transaction then checks only that fence: the ticket's attachments are unchanged, no other store connection committed, no scanned record, the ticket, its attachments or the tickets they name changed, and no write added a reference to an attachment id, object path or scanned record. On a fence miss the archive is refused with `CLEANUP_CONCURRENT_WRITE` (`details.retry: true`); nothing is archived or queued, and the agent retries. Retention rules and the archive reply are unchanged. The cleanup executor's service turn uses the same pattern (CL-345): it reads its unchanged complete reference graph (every record) for the first due job's ticket on a read snapshot before the object gate and the writer, and each item's admission and final pre-unlink transaction re-read the job, ticket, attachment and project and check the same fence; a fence miss deletes nothing, writes no intent and no failure, and the next turn rescans and retries the item, while a turn without a prepared scan (the maintenance tail of a command) leaves due items for that service turn.

A failure after unlink but before its SQL outcome leaves the durable intent. Restart observes absence and records **already missing**, rather than claiming the missing file was just removed. Attachment metadata, provenance and checksum remain. Missing/cleaned originals are unavailable to exact-original reads and verification gates even when a retained preview exists.

Accounting separates selected logical original bytes, managed pathname bytes actually removed, and originals already absent. Those lengths are not measured disk savings: hardlinks, APFS clones and backups can retain the same blocks. Completed verified backup receipts also report known-at-backup retained logical originals. Current external backup presence is unverified; physical reclamation and backup-retained physical allocation remain explicitly unmeasured. Existing exports and backup copies are never purged by this job.

Known-at-backup accounting comes from one process-wide index per store root (CL-343). Its background build runs at default QoS and uses the same per-receipt SQLite extraction (CL-355). A cleanup-job read never decodes or validates backup receipts: it reads a fingerprint of the receipt rows (rowid, key and byte length) and uses the index only when that fingerprint matches and a returned job has items. While the index is cold or rebuilding, the read answers at once with `backup_retention_observation` `unavailable` and a null byte total. One background build at a time parses only added receipts, each in its own short read, and drops removed receipts without a full rebuild. An unreadable or non-complete receipt keeps the total unavailable. The storage status fallback for stores without `storage-last-verified-backup` checks receipts newest first, one row at a time.

The implemented project operations (owner, or enrolled worker while `agent_rule_changes=allowed`) are `archive_storage_settings`, `attachment_cleanup_preview`, `cleanup_job_list`, `cleanup_job_get`, `cleanup_job_cancel` and `cleanup_job_retry`, alongside existing attachment and archive commands. Jobs are project scoped; cancellation remains available for an archived project. Retry requires a current job revision and a suspended job. These operations do not launch a model or change work authority.

Playtest reviewers can set `retain_cited_files:true` with their assessed pass/reject. Only exact bundle attachments cited in that verdict's validated assessment/checks receive the ordinary Keep original flag. A verdict records those exact retained references. Other bundle files remain eligible under the current project storage preset, threshold and budget; existing pins and all ordinary protections remain. The bundle offers the same `attachment_cleanup_preview`, without deleting files or introducing a second cleanup job. For a disposable check that should select every uncited original, the owner can choose a one-byte threshold and zero retained budget; production defaults still retain small files when within budget. Cleanup preserves the bundle's role metadata, build/file hashes and per-acceptance verdicts, and labels pruned originals unavailable for reinspection.

## Done evidence and aged closed tickets (CL-193)

Project settings → **Closed ticket cleanup** controls two independent rules in `ticket_cleanup`: `done_evidence_enabled` and `closed_purge_enabled` (both default true), and `closed_days` (default 15, whole days 1–36500). These are ordinary project settings, subject to project revisions and `agent_rule_changes`. Open statuses are never selected, including archived or trashed open tickets. Closed means the status category is Done or Canceled; a label alone grants no authority.

Cleanup starts automatically for every project after service startup, including existing projects with no cleanup settings. No preview, digest, activation or observation window is required. The owner saves the two switches and day count in Project settings; agents use `project_settings_save` with the current project revision. Saving settings restarts that project’s bounded scan. The lifecycle-specific `ticket_cleanup_preview` command is removed; manual Archive and permanent-removal previews retain their existing contracts.

A transition to Done commits an exact-ticket recovery wake in the same transaction. It queues that ticket as due now with a fresh private token, preserves the current sweep cursor and brings forward the next maintenance deadline. The existing maintenance pump admits the deletion job after commit or on startup. It retains ticket/history/evidence records and immutable file lists, names, sizes and SHA-256. It queues only the ticket's exclusively owned managed originals, previews, captured files, captured link text and sidecars admitted by the existing CL-154 plan. At final unlink it rechecks current Done status, ticket revision, settings, owner fingerprints, foreign references and every existing hold. Reopening or disabling the rule retains remaining bytes; removed bytes cannot be recreated. New references and changed owner metadata retain their files. Files protected by readers, Keep original, media ownership or shared/unknown authority stay. The remaining-record check excludes the unchanged historical owners whose bytes this same cleanup retires. Historical batch, group and delivery ID pointers preserve that metadata without retaining its files; their direct file references and actual transitive use by another live record still retain the bytes. An owner outside the cleanup scope, a new reference or a changed owner also retains the file. A completed backup must independently hold the exact bytes before the live copy can be removed. Missing, changed or unverified backup bytes retain the live copy with an explicit reason; historical backup metadata alone is not proof. Preparation pins and hashes the recorded completed manifest once per generation in a batch, then verifies each candidate payload outside the writer. Final unlink rechecks the named manifest and payload identities; a replaced or missing backup entry cannot release the live copy. Removing a live pathname leaves the completed backup and its exact restore unchanged, including when that backup deduplicates its own payload with hard links. Workspace and external originals are never removed.

New Done-evidence byte receipts record `cleanup_policy_version=2`. A pending older receipt retains its original fingerprints and records its actual outcomes, then queues an exact-ticket tokenized retry while preserving the durable scan cursor, so a fresh plan can apply the corrected ownership rule. Existing receipts are not rewritten to claim bytes were removed. Completed purge jobs retained solely for backup or remaining-record reasons are eligible for one recheck under the corrected policy, then only after a newer completed backup generation exists. Rechecking rebuilds current references and holds and verifies no-follow identities and digests; Keep original, reader/media holds and other permanent reasons are not blindly cleared. This is generation-triggered work through the ordinary one-shot maintenance deadline, with no retained-file polling timer.

A closed ticket unchanged for `closed_days` is purged by the existing CL-24 record-removal path, with its owned-byte intents committed atomically. Age uses the latest valid ticket update or ordinary ticket event (including notes), excluding cleanup accounting. Missing change time retains the ticket. Active work, unresolved execution and pending owner requests block both rules. Purge retains a minimal reference and shared records and scrubs private history/command results as in manual purge. Its byte jobs survive a crash and recheck holds; turning a rule off cannot undo a committed purge.

A logical sweep covers the eligible tickets through durable cursor chunks of at most 32 tickets; a retained ticket or a ticket with no new eligible bytes does not end the chunk. While a sweep is due or in progress, at most 16 slots serve due exact-ticket wakes or retries, leaving at least 16 slots for the ordinary scan. When no sweep is due, an exact-ticket-only chunk can use all 32 slots. Continuous Done transitions therefore cannot restart or consume the entire ordinary scan. Expensive purge planning, command-history inspection and reference traversal run in a read snapshot on a utility maintenance lane, outside the request queue, object gate and SQL writer. The selected tickets share a validated corpus stream while retaining separate ownership closures, references and fences. Preparation keeps the 4 MiB per-record and 16 MiB/4,096-record per-ticket inventory bounds, with a 64 MiB aggregate selected-inventory bound per chunk. It does not cache the corpus across preparations. Known `storage_job(kind=ticket_object_delete)` rows are accounting, so they do not enter byte-reference ownership or selected-inventory budgets and skip expensive SQLite reference matching; their complete canonical and Unicode validation still runs. Unknown or missing storage-job kinds remain conservative references. Rows above 4 MiB are checked through a canonical header projection, complete SQLite JSON reference traversal and chunked UTF-8 validation, without decoding their full payload; bounded smaller rows reuse their required Foundation validation payload. Ownership depth is capped at 64; history and command scans stream their unrelated rows too. Limit exhaustion retains bytes and reports the refusal. A sweep is a sequence of bounded preparations and short commits, not one long writer transaction.

Done-job accounting uses one project-scoped `records_scope` stream per selection. Every bounded storage-job envelope receives canonical JSON/UTF-8 validation once; only the selected tickets' pending flags and distinct retained `(stored_path, sha256, ordered reasons)` signatures survive. Ticket and project matching uses exact UTF-8 identity; descriptor comparisons preserve the existing optional-String and ordered-reason semantics. The observation admits at most 32 tickets, 100,000 streamed jobs, 4 MiB per job, 4,096 matching jobs and 100,000 distinct signatures/16 MiB per ticket, and 200,000 signatures/64 MiB in aggregate. Duplicate signatures share admission within a ticket. A ticket exceeding a retained-state bound is kept for retry and releases its observation budget; an unassignable oversized row or exhausted stream bound defers the affected scope. An incomplete observation never means that prior jobs are absent. The observation is discarded after this snapshot; action fences and final deletion proofs are unchanged.

Selected lifecycle plans share one snapshot-local backup-descriptor observation, one project event observation and one command-result stream for aged purges. Complete backup entry shapes are validated even when unrelated; the observation is the wanted keys intersected with the per-receipt backup index below (CL-355). The observation records exact generation manifest digests; the final deletion fence guards generation metadata, and the byte continuation pins/verifies the independent manifest and payload again before unlink. Rows are tokenized once for matching and admission; existing owned-row tokens are reused. Reference preparation reuses its already validated full payload from one bounded blob read through 4 MiB, rather than rereading/copying the SQLite value per 64 KiB slice. Larger rows retain the canonical header, exact SQL matcher and bounded UTF-8 stream. A token traversal-limit fallback uses exact SQL relevance to refuse only affected inventories; an unrelated deeply nested row cannot stop the cohort. Backup candidates/descriptors and shared history each have a 64 MiB retention bound; history keeps the existing 4 MiB row, 16 MiB per-ticket and 100,000-row scan limits. Backup observation is capped at 1,024 generations, 10,000,000 descriptors and 2 GiB of generation JSON. Exceeding a bound retains the bytes. Lifecycle observations never cross a preparation snapshot or pass. Existing pending Done-evidence jobs continue their durable byte intents without replanning them.

Ticket cleanup reads backup receipts through the same process-wide per-store index as known-at-backup accounting, with the same fingerprint rule (CL-355). The index keeps, for each receipt, its sorted presence keys (duplicates kept), entry count and independent-copy path and manifest; each receipt is validated once when it is added. A cleanup step reads only the receipt fingerprint and intersects its wanted keys with the index in memory. When the fingerprint shows new receipts, that step extracts only those receipts, each in its own short read on its own snapshot (SQLite `json_each` of each entry's path, sha256 and size; no full Foundation decode), and removed receipts are dropped without a reparse. An invalid or non-complete receipt stays in the index as invalid, so every step still refuses with `RECOVERY_REQUIRED`/`backup_receipt_index_invalid` and retains the bytes. The results (retained keys, copy paths, copy manifests) equal the earlier per-step scan; the generation, descriptor and memory bounds, the deletion fence on generation metadata and the final-unlink manifest/payload verification are unchanged, so the index never grants unlink authority by itself.

Byte deletion observes a bounded cohort of at most 32 receipts for one project, 16 MiB of receipt JSON and 100,000 object descriptors per maintenance call. Its receipts share one complete corpus stream, one media-authority validation and one exact backup-generation/manifest descriptor observation; their references and ticket/receipt fences stay independent. Reference inventories and reverse-index charges each cap at 64 MiB. Candidate admission still pins at most 256 payloads or one second of verification, and each writer chunk still attempts at most 128 objects or 25 ms of unlink work. Unconsumed candidates and verified manifests are reused only inside this call, which admits at most 2,048 writer chunks or 30 seconds of continuation work (cooperative; a single verification retains its 60-second ceiling). Payload pins are released before the next candidate batch; at most 1,024 generation manifests survive. The original bounded TEMP change journal stays active between chunks, and each receipt validates its original fence immediately before its next chunk. Only this executor's receipt state, attachment availability and cleanup-outcome accounting bypass that journal while it exclusively holds the writer; they add no byte authority. Every intervening command and external writer remains fenced. A stale receipt defers independently while valid siblings continue. Every later maintenance call freshly prepares its cohort; no unchecked observation or verification is cached across calls. The normal four-times-elapsed production rest includes the whole cohort call.

A transactional TEMP index observes only writes made during each preparation, including direct SQL and deletes; it retains no Swift payload graph. Changed identities and distinct exact reference tokens share a hard 32,768-row/8-MiB payload budget; exhaustion records a refusal and stops retaining new index entries without interrupting the ordinary write. The short commit uses indexed matches for changed records, events, command receipts and storage metadata against the selected IDs, paths and digests; unrelated notes and edits do not invalidate a pass. A selected-record change or newly appearing reference/hold fences the affected ticket. Changed backup/media authority, ticket_cleanup settings, any project workspace root or store identity, an external-connection write or a changed-payload validation limit still conservatively fences the applicable preparation. Project counters, revision and updated_at alone do not fence a pass; newly introduced project references still do. Unchanged project tokens are subtracted from updates, and repeated reference values across unrelated writes share one TEMP entry (with a separate typed-hold flag). Each write indexes its own valid JSON up to 1 MiB; over-budget or invalid writes conservatively fence that attempt. Final validation queries only indexed changed identities/references, never the corpus on the writer. Each ticket has its own final fence, so valid sibling plans commit when another selected ticket changes. A refused ticket receives a kept pass item (`reason=fenced_by_concurrent_write`), advances the scan and records a durable ticket retry at least 60 seconds later. That retry prepares only the due fenced ticket rather than restarting the whole project sweep. Done transitions enqueue exact-ticket wakes without resetting or fencing the whole scan. A commit consumes an observed retry only when its token still matches; a newer Done wake for that same ticket survives even if the earlier preparation saw it open and kept it. Changed project settings still reset the scan and retain the project policy fence. Refused project-wide preparation retains its durable retry, including after service restart; other projects can continue. There is no immediate preparation retry loop. The short commit saves the semantic action, byte intent and receipt together. Lifecycle planning and admitted byte continuations take alternating turns when both are due, so neither a byte backlog nor repeated passes starve the other. A byte continuation prepares at most 256 candidates or one second of verification outside the writer, then unlinks at most 128 verified objects or 25 ms of writer work per wake. These time limits are cooperative; an individual filesystem call can exceed them. It resumes the remaining durable descriptors on a later wake. The service rests for four times the preceding preparation’s elapsed wall time, with a 50 ms minimum, using the same one-shot maintenance deadline; refusals retain their longer durable retry. During this rest, maintenance reports scheduled with reason=maintenance_yield and its next_check_at. Backup descriptors use per-row autorelease scopes, and all preparation temporaries drain on their producing read queue. No descriptor or payload cache accumulates across attempts. Regular-file hashing pins an open descriptor outside the writer and object gate. Final unlink checks the same root, relative path, digest, length, device, inode, modification time and change time against both that descriptor and the current pathname; changed or newly appearing files stay. Captured links keep their bounded no-follow identity and target-chain checks. The service command queue is free during preparation and between commits. If the startup read pool is unavailable, the maintenance lane retries opening a separate read pool; failure retains data for a 60-second retry rather than scanning on the writer. Ticket deadlines remain armed independently of archive/import maintenance failures, including after two failures. Retained snapshot directories do not activate the kernel capture lease. An active capture defers cleanup to a 60-second lease recheck; backup completion also rearms the ordinary deadline. Deadline-read failures likewise schedule a retry rather than silently dropping the wake. No schema migration is added. A durable cursor continues an unfinished scan through the existing one-shot maintenance deadline. A completed sweep is due again in one day; a new Done transition wakes it sooner. Aging is therefore enforced on the next daily pass after the threshold. Permanent file holds do not receive a per-file polling timer. Existing cleanup's root gate, descriptor-relative verified unlink and two-failure limit remain the only deletion engine.

`ticket_cleanup_receipts(project_id, receipt_id?, section?, cursor?, limit?)` returns bounded newest-first summaries, default/max 50 (`limit` 1–50). Summary rows contain receipt metadata/settings, ID/time/cause, `selected_bytes`, `item_count`, counts by action and reason, `source_build_cache_count`, current aggregated byte `summary` and `bytes_state`. They omit ticket items and file descriptors; the reader aggregates the existing durable byte-job summaries. Project settings uses this summary page, preserving its displayed timestamp, removed bytes, kept file count and pending/completed state. Its window-local cache is bounded to five scoped pages and invalidated by store incarnation, observed service changes and explicit Refresh/settings save; late or canceled replies cannot install another project's rows.

Both list and single-pass reads include `maintenance.preparation`, a durable project-scoped observation: `state=preparing|idle|committed|deferred`, `attempt_count`, `attempted_at`, `committed_at` when applicable, `last_failed_at`, `last_failure_reason`, and `next_attempt_at` (ISO 8601, or null after a successful commit). Fields with no earlier observation are absent; an untouched project returns an empty object. The last failure remains visible after later success. A fence reason identifies a scoped record or the bounded authority/check that refused it; no receipt is implied by an attempted preparation. Reads never start a preparation or clear its backoff.

The list retains `first_pass_receipt_id`, so a backlog cannot hide the first pass. Supply that ID (or another retained `receipt_id`) for detail. `section=items` (default) pages original ticket items with linked byte-receipt ID/state/summary; `section=objects` pages their exact file descriptors as `{byte_deletion_receipt_id,item_index,object_index,object}`; `section=source_build_cache` pages the original retained-cache entries. Sections retain array order and include the pass summary. Continue the identical query with `next_cursor` while `has_more` is true. The entry array is bounded to 220 KiB as well as the entry count; a single oversize entry returns `RESULT_TOO_LARGE`. Cursors are sealed, expire after 24 hours, and bind caller/project/grant/session/store and the receipt/section/limit. New passes reset list cursors; changed pass or linked outcome revisions reset detail cursors (`CURSOR_RESET`: restart without a cursor). No audit records, item detail, byte outcomes or deletion authority change, and no migration is required.

`bytes_state=pending` is not completion; `already_missing` is never counted as removed bytes. Record the first receipt's `selected_bytes`, receipt ID and final `summary.removed_bytes` during installed qualification, without changing settings to activate it. These are managed pathname bytes, not physical disk savings. Previous backups and exports remain unchanged.

Intentional evidence absence is retained in the durable receipt. Snapshot inventory uses its exact path/kind/hash/length outcome to report `evidence_cleaned`, preserving immutable source manifests and allowing later backups to retain metadata without demanding removed previews/captures. This is not restore support. No schema/protocol migration or new canonical family is introduced. Installed compatibility still requires exact staged startup and protected backup against an owned consistent real-store copy before replacement.

Source-build cache ownership comes from the retired `source_review_execute` Swift test producer: `source-build-cache/SHA256(capture.sha256 + execution.toolchain_sha256)`. The execution must record `tool=swift_test`, a same-project/same-ticket source-capture ID and both valid digests; argument overrides do not establish ownership. Current service source execution remains disabled. Existing execution/capture records are the owner model; a cache directory name or output-log mention alone is not authority. An entry used by another ticket stays with `shared_source_build_cache`, even if that other ticket is also Done. No matching recorded execution means `unowned_source_build_cache`: keep and report it, never infer an owner from its hash.

For an exclusive entry, automatic read-lane preparation inventories regular files with no-follow descriptors and records each name, logical size and SHA-256 in the ordinary byte job. Existing owner fingerprints, reference/reader/media/backup holds and per-object verification apply; a newly recorded execution using the same derived entry retains remaining files. Cache aliases use verified no-follow link-text unlink and protect their recorded target chains, including directory descendants; held aliases retain those targets. Alias closure work is capped at 2,000,000 visits across an intent; exhaustion retains the affected entries. Escaping/cyclic links and unsupported entries conservatively retain the entry's files. Empty directory scaffolding is retained. A manual purge planned on the writer retains cache entries with `cache_requires_read_lane` rather than hashing the cache in its semantic transaction; automatic Done/aged cleanup prepares on the read lane. Files above the snapshot per-object bound stay with `cache_identity_limit`, and entry preparation has a cooperative 60-second budget. Shared/unowned entry sizes are `null` (unmeasured); a retained directory descriptor has `size_unknown=true` and contributes no invented byte total. Pass receipts include a `source_build_cache` retained-entry report, including entries without a ticket owner. Snapshot inventory records `rebuildable_source_build_cache` for pending/retained cache descriptors, preserving their receipt metadata while excluding the rebuildable cache payload. Such a live-only cache file therefore stays with `backup_required` unless a completed backup independently holds its exact bytes. Existing snapshots and exports are unchanged; a historical descriptor alone does not establish current backup bytes.

Receipt lists and single-receipt reads also expose current `maintenance`: `disabled`, `due`, `scheduled`, `deferred` with reason and `next_check_at`, or `paused` with `reason=snapshot_retention`, `resume_condition=snapshot_retention_released` and `next_check_at`. Capture has no promised finish time: `resume_at=null` states that honestly; the dated next check is a retry time, not a fabricated lease expiry. This observation is available before the first pass exists and creates no pass or deletion receipt merely by reading it.

The service preserves an already armed earlier maintenance wake when commands refresh its deadline. Frequent read traffic cannot repeatedly cancel and postpone the minimum-delay startup continuation; genuinely earlier work replaces it, and no pending work cancels it.
