# Local attachment cleanup

Capture and note composers accept selected files, dropped local files/images and pasted clipboard images. The selection records a managed-copy or external-reference choice. Clipboard images use a bounded private PNG staging file and a managed copy. Selection drafts are specific to the window, project, task and store generation. A successful, matching attachment receipt clears only that selection; unknown outcomes retain its original command ID for reconciliation. A managed import keeps the source file. Directory recursion and remote/chunk uploads are not supported.

Project **Archive storage** settings contain the complete preset, large-original threshold and retained-ticket budget. Defaults are 20 MiB and 50 MiB; Keep originals disables selection. Threshold and aggregate budget are independent: smaller originals can be selected largest first until the budget is met. Settings edits check both the project and settings revisions and preserve unrelated workflow settings.

The archive preview records the exact task/settings revisions and selected immutable attachment IDs, hashes and logical lengths. It validates every retained envelope in the current SQL observation, preserving the original identity/revision tokens and ownership fields while SQLite checks the complete JSON and the adapter checks its complete UTF-8. One byte-exact pass collects references to stored record IDs and the ticket’s original paths, including foreign projects. It then decodes full payloads only for reachable records; task liveness and current review heads remain available for hold decisions. Unrelated captured-file lists, notes and evidence are not decoded or indexed in Swift. The resulting reverse index belongs only to this observation and is never reused across commands or deletion checks. Captured-file metadata still participates in the same reference checks, and preview sizes come from recorded immutable logical lengths without reading captured file bytes. Archiving and the durable cleanup job commit together. A 30-second cancellation window precedes execution. Cancel remaining cleanup and Undo archive preserve all originals not already removed. Unarchiving restores ticket/history state; it cannot recreate deleted bytes.

**Archive…** presents a sheet immediately and starts a retention preview only for that open sheet. Selecting a ticket makes no speculative retention read. While the preview is in flight or has failed, the sheet shows loading or retry information and disables archive actions; it never substitutes zero totals. A matching result fills the readable totals, holds and cleanup choice. The result is bound to the store, project, ticket and settings revisions. Any observed service change invalidates it, including cross-ticket or cross-project holds; an open sheet refreshes against the new observation. Closing and reopening starts a fresh read, and leaving the detail discards late replies. Confirmation retains the service's revision, preview and current-hold checks. This UI presentation changes no preview results and establishes no native latency guarantee under load.

The service runs a bounded synchronous maintenance pump after import reconciliation. Archive work admits at most eight job items and removes at most one original per pump. A separate utility maintenance continuation processes at most one purge or Done-evidence object per call. A durable cursor and exact deletion intent survive restart. The service arms a one-shot continuation for unfinished bounded work or a real grace/reader deadline. Permanent item holds do not create an indefinite polling timer. Infrastructure failures defer for a 60-second one-shot retry and cannot disable the independent ticket-cleanup lane. Two matching object failures suspend the item; an explicit retry by the trusted owner or an enrolled worker while `agent_rule_changes=allowed` starts a new cancellation window, with the actual actor’s provenance.

Execution obtains the store object gate before the SQL writer, rereads the complete persisted reference graph and current retention settings, commits a deletion intent, then checks current references again in the final writer transaction. Current work/verification, human inspection, review/build references, reader/backup leases, shared references, pending imports, Keep original and unknown or invalid metadata retain the original. The gate stays held through descriptor-relative no-follow hash/identity checks, unlink, directory flush and the recorded outcome. Archive jobs admit only exact managed originals below `objects/`; archive cleanup retains previews. Permanent ticket purge shares this permit and unlink through durable `ticket_object_delete` intents. It also admits exact previews, captured-source files, manifest sidecars, verified captured link text and exactly inventoried source-build cache files. Purge uses stricter remaining-record ownership checks and retains backup-referenced, reader-held and media-owned bytes. External originals and workspace files are never cleanup targets.

A failure after unlink but before its SQL outcome leaves the durable intent. Restart observes absence and records **already missing**, rather than claiming the missing file was just removed. Attachment metadata, provenance and checksum remain. Missing/cleaned originals are unavailable to exact-original reads and verification gates even when a retained preview exists.

Accounting separates selected logical original bytes, managed pathname bytes actually removed, and originals already absent. Those lengths are not measured disk savings: hardlinks, APFS clones and backups can retain the same blocks. Completed verified backup receipts also report known-at-backup retained logical originals. Current external backup presence is unverified; physical reclamation and backup-retained physical allocation remain explicitly unmeasured. Existing exports and backup copies are never purged by this job.

Known-at-backup accounting comes from one process-wide index per store root (CL-343). A cleanup-job read never decodes or validates backup receipts: it reads a fingerprint of the receipt rows (rowid, key and byte length) and uses the index only when that fingerprint matches and a returned job has items. While the index is cold or rebuilding, the read answers at once with `backup_retention_observation` `unavailable` and a null byte total. One background build at a time parses only added receipts, each in its own short read, and drops removed receipts without a full rebuild. An unreadable or non-complete receipt keeps the total unavailable. The storage status fallback for stores without `storage-last-verified-backup` checks receipts newest first, one row at a time.

The implemented project operations (owner, or enrolled worker while `agent_rule_changes=allowed`) are `archive_storage_settings`, `attachment_cleanup_preview`, `cleanup_job_list`, `cleanup_job_get`, `cleanup_job_cancel` and `cleanup_job_retry`, alongside existing attachment and archive commands. Jobs are project scoped; cancellation remains available for an archived project. Retry requires a current job revision and a suspended job. These operations do not launch a model or change work authority.

Playtest reviewers can set `retain_cited_files:true` with their assessed pass/reject. Only exact bundle attachments cited in that verdict's validated assessment/checks receive the ordinary Keep original flag. A verdict records those exact retained references. Other bundle files remain eligible under the current project storage preset, threshold and budget; existing pins and all ordinary protections remain. The bundle offers the same `attachment_cleanup_preview`, without deleting files or introducing a second cleanup job. For a disposable check that should select every uncited original, the owner can choose a one-byte threshold and zero retained budget; production defaults still retain small files when within budget. Cleanup preserves the bundle's role metadata, build/file hashes and per-acceptance verdicts, and labels pruned originals unavailable for reinspection.

## Done evidence and aged closed tickets (CL-193)

Project settings → **Closed ticket cleanup** controls two independent rules in `ticket_cleanup`: `done_evidence_enabled` and `closed_purge_enabled` (both default true), and `closed_days` (default 15, whole days 1–36500). These are ordinary project settings, subject to project revisions and `agent_rule_changes`. Open statuses are never selected, including archived or trashed open tickets. Closed means the status category is Done or Canceled; a label alone grants no authority.

Cleanup starts automatically for every project after service startup, including existing projects with no cleanup settings. No preview, digest, activation or observation window is required. The owner saves the two switches and day count in Project settings; agents use `project_settings_save` with the current project revision. Saving settings restarts that project’s bounded scan. The lifecycle-specific `ticket_cleanup_preview` command is removed; manual Archive and permanent-removal previews retain their existing contracts.

A transition to Done commits a recovery wake in the same transaction. The existing maintenance pump admits the deletion job after commit or on startup. It retains ticket/history/evidence records and immutable file lists, names, sizes and SHA-256. It queues only the ticket's exclusively owned managed originals, previews, captured files, captured link text and sidecars admitted by the existing CL-154 plan. At final unlink it rechecks current Done status, ticket revision, settings, owner fingerprints, foreign references and every existing hold. Reopening or disabling the rule retains remaining bytes; removed bytes cannot be recreated. New references and changed owner metadata retain their files. Files protected by readers, Keep original, media ownership, backups or shared/unknown authority stay. Workspace and external originals are never removed.

A closed ticket unchanged for `closed_days` is purged by the existing CL-24 record-removal path, with its owned-byte intents committed atomically. Age uses the latest valid ticket update or ordinary ticket event (including notes), excluding cleanup accounting. Missing change time retains the ticket. Active work, unresolved execution and pending owner requests block both rules. Purge retains a minimal reference and shared records and scrubs private history/command results as in manual purge. Its byte jobs survive a crash and recheck holds; turning a rule off cannot undo a committed purge.

A pass scans at most 32 tickets and admits at most one ticket action. Expensive purge planning, command-history inspection and reference traversal run in a read snapshot on a utility maintenance lane, outside the request queue, object gate and SQL writer. Preparation streams and validates the corpus one record at a time; it retains only the selected ticket’s ownership closure and relevant references, with a 4 MiB per-record limit and a 16 MiB/4,096-record selected inventory limit. It does not cache the corpus between attempts. Large unrelated records are checked through a canonical header projection, complete SQLite JSON reference traversal and chunked UTF-8 validation, without decoding their full payload. Ownership depth is capped at 64; history and command scans stream their unrelated rows too. Each step plans at most one ticket, including a ticket with no eligible bytes. Limit exhaustion retains bytes and reports the refusal.

A transactional TEMP index observes only writes made during each preparation, including direct SQL and deletes; it retains no Swift payload graph. Changed identities and distinct exact reference tokens share a hard 32,768-row/8-MiB payload budget; exhaustion records a refusal and stops retaining new index entries without interrupting the ordinary write. The short commit uses indexed matches for changed records, events, command receipts and storage metadata against the selected IDs, paths and digests; unrelated notes and edits do not invalidate a pass. A selected-record change, a newly appearing reference/hold, changed backup/media authority, changed ticket_cleanup settings or any project workspace root, external-connection write or changed-payload validation limit safely fences the attempt. Project counters, revision and updated_at alone do not fence a pass; newly introduced project references still do. Unchanged project tokens are subtracted from updates, and repeated reference values across unrelated writes share one TEMP entry (with a separate typed-hold flag). Each write indexes its own valid JSON up to 1 MiB; over-budget or invalid writes conservatively fence that attempt. Final validation queries only indexed changed identities/references, never the corpus on the writer. A refused selected ticket receives a kept pass item (`reason=fenced_by_concurrent_write`) and advances the scan so the next ticket can proceed; a changed project policy preserves its own reset cursor. Every refused project preparation waits at least 60 seconds before another attempt, including after service restart; other projects can continue. There is no immediate preparation retry loop. The short commit saves the semantic action, byte intent and receipt together. Lifecycle planning and admitted byte continuations take alternating turns when both are due, so neither a byte backlog nor repeated passes starve the other. A byte continuation removes at most one verified object per wake. The service rests for four times the preceding preparation’s elapsed wall time, with a 50 ms minimum, using the same one-shot maintenance deadline; refusals retain their longer durable retry. During this rest, maintenance reports scheduled with reason=maintenance_yield and its next_check_at. Backup descriptors use per-row autorelease scopes, and all preparation temporaries drain on their producing read queue. No descriptor or payload cache accumulates across attempts. Regular-file hashing pins an open descriptor outside the writer and object gate. Final unlink checks the same root, relative path, digest, length, device, inode, modification time and change time against both that descriptor and the current pathname; changed or newly appearing files stay. Captured links keep their bounded no-follow identity and target-chain checks. The service command queue is free during preparation and between commits. If the startup read pool is unavailable, the maintenance lane retries opening a separate read pool; failure retains data for a 60-second retry rather than scanning on the writer. Ticket deadlines remain armed independently of archive/import maintenance failures, including after two failures. Retained snapshot directories do not activate the kernel capture lease. An active capture defers cleanup to a 60-second lease recheck; backup completion also rearms the ordinary deadline. Deadline-read failures likewise schedule a retry rather than silently dropping the wake. No schema migration is added. A durable cursor continues an unfinished scan through the existing one-shot maintenance deadline. A completed sweep is due again in one day; a new Done transition wakes it sooner. Aging is therefore enforced on the next daily pass after the threshold. Permanent file holds do not receive a per-file polling timer. Existing cleanup's root gate, descriptor-relative verified unlink and two-failure limit remain the only deletion engine.

`ticket_cleanup_receipts(project_id, receipt_id?, section?, cursor?, limit?)` returns bounded newest-first summaries, default/max 50 (`limit` 1–50). Summary rows contain receipt metadata/settings, ID/time/cause, `selected_bytes`, `item_count`, counts by action and reason, `source_build_cache_count`, current aggregated byte `summary` and `bytes_state`. They omit ticket items and file descriptors; the reader aggregates the existing durable byte-job summaries. Project settings uses this summary page, preserving its displayed timestamp, removed bytes, kept file count and pending/completed state. Its window-local cache is bounded to five scoped pages and invalidated by store incarnation, observed service changes and explicit Refresh/settings save; late or canceled replies cannot install another project's rows.

Both list and single-pass reads include `maintenance.preparation`, a durable project-scoped observation: `state=preparing|idle|committed|deferred`, `attempt_count`, `attempted_at`, `committed_at` when applicable, `last_failed_at`, `last_failure_reason`, and `next_attempt_at` (ISO 8601, or null after a successful commit). Fields with no earlier observation are absent; an untouched project returns an empty object. The last failure remains visible after later success. A fence reason identifies a scoped record or the bounded authority/check that refused it; no receipt is implied by an attempted preparation. Reads never start a preparation or clear its backoff.

The list retains `first_pass_receipt_id`, so a backlog cannot hide the first pass. Supply that ID (or another retained `receipt_id`) for detail. `section=items` (default) pages original ticket items with linked byte-receipt ID/state/summary; `section=objects` pages their exact file descriptors as `{byte_deletion_receipt_id,item_index,object_index,object}`; `section=source_build_cache` pages the original retained-cache entries. Sections retain array order and include the pass summary. Continue the identical query with `next_cursor` while `has_more` is true. The entry array is bounded to 220 KiB as well as the entry count; a single oversize entry returns `RESULT_TOO_LARGE`. Cursors are sealed, expire after 24 hours, and bind caller/project/grant/session/store and the receipt/section/limit. New passes reset list cursors; changed pass or linked outcome revisions reset detail cursors (`CURSOR_RESET`: restart without a cursor). No audit records, item detail, byte outcomes or deletion authority change, and no migration is required.

`bytes_state=pending` is not completion; `already_missing` is never counted as removed bytes. Record the first receipt's `selected_bytes`, receipt ID and final `summary.removed_bytes` during installed qualification, without changing settings to activate it. These are managed pathname bytes, not physical disk savings. Previous backups and exports remain unchanged.

Intentional evidence absence is retained in the durable receipt. Snapshot inventory uses its exact path/kind/hash/length outcome to report `evidence_cleaned`, preserving immutable source manifests and allowing later backups to retain metadata without demanding removed previews/captures. This is not restore support. No schema/protocol migration or new canonical family is introduced. Installed compatibility still requires exact staged startup and protected backup against an owned consistent real-store copy before replacement.

Source-build cache ownership comes from the retired `source_review_execute` Swift test producer: `source-build-cache/SHA256(capture.sha256 + execution.toolchain_sha256)`. The execution must record `tool=swift_test`, a same-project/same-ticket source-capture ID and both valid digests; argument overrides do not establish ownership. Current service source execution remains disabled. Existing execution/capture records are the owner model; a cache directory name or output-log mention alone is not authority. An entry used by another ticket stays with `shared_source_build_cache`, even if that other ticket is also Done. No matching recorded execution means `unowned_source_build_cache`: keep and report it, never infer an owner from its hash.

For an exclusive entry, automatic read-lane preparation inventories regular files with no-follow descriptors and records each name, logical size and SHA-256 in the ordinary byte job. Existing owner fingerprints, reference/reader/media/backup holds and per-object verification apply; a newly recorded execution using the same derived entry retains remaining files. Cache aliases use verified no-follow link-text unlink and protect their recorded target chains, including directory descendants; held aliases retain those targets. Alias closure work is capped at 2,000,000 visits across an intent; exhaustion retains the affected entries. Escaping/cyclic links and unsupported entries conservatively retain the entry's files. Empty directory scaffolding is retained. A manual purge planned on the writer retains cache entries with `cache_requires_read_lane` rather than hashing the cache in its semantic transaction; automatic Done/aged cleanup prepares on the read lane. Files above the snapshot per-object bound stay with `cache_identity_limit`, and entry preparation has a cooperative 60-second budget. Shared/unowned entry sizes are `null` (unmeasured); a retained directory descriptor has `size_unknown=true` and contributes no invented byte total. Pass receipts include a `source_build_cache` retained-entry report, including entries without a ticket owner. Snapshot inventory records `rebuildable_source_build_cache` for pending/retained cache descriptors, preserving their receipt metadata while excluding the rebuildable cache payload; existing snapshots/exports are unchanged, and any recorded exact backup authority still wins.

Receipt lists and single-receipt reads also expose current `maintenance`: `disabled`, `due`, `scheduled`, `deferred` with reason and `next_check_at`, or `paused` with `reason=snapshot_retention`, `resume_condition=snapshot_retention_released` and `next_check_at`. Capture has no promised finish time: `resume_at=null` states that honestly; the dated next check is a retry time, not a fabricated lease expiry. This observation is available before the first pass exists and creates no pass or deletion receipt merely by reading it.

The service preserves an already armed earlier maintenance wake when commands refresh its deadline. Frequent read traffic cannot repeatedly cancel and postpone the minimum-delay startup continuation; genuinely earlier work replaces it, and no pending work cancels it.
